# CLAUDE.md — frontend

Frontend-specific guidance. Read the root `CLAUDE.md` first — this file only covers gotchas specific to `frontend/`, found the hard way during REQ-2's implementation (2026-09-05).

> **2026-09-08 — [ADR-0042](../docs/adr/0042-adminlte-design-system.md):** the design system moved CoreUI → AdminLTE v4 + Bootstrap 5 + Font Awesome, big-bang, and every `@coreui/*` package is gone. Notes below that name a CoreUI component (`CTable`, `CTooltip`, `CPaginationItem`, `CContainer`, `CCard`, ...) are annotated in place — most describe a DOM/CSS fact that survives the rename, but **three are now actively wrong under AdminLTE and are marked as superseded**: the `--cui-is-mobile` note, the `CTooltip`+`CDropdownToggle` ref note, and the `CPaginationItem`-renders-`<span>` pagination-test note. Read each section's own marker before acting on it.

## Don't nest a `<table>` inside another `<table>`'s expanded-row cell

*(Written for `<CTable>`; the fact is about the raw `<table>` element, so it survives ADR-0042 unchanged — only the component name in the original text was CoreUI's.)*

An expand-in-place pattern (a table row that, when clicked, renders a child list inside its own cell — `ProjectDetail.tsx`'s Release→TestCycle audit view, and originally REQ-2's Requirement→TestCase section too) breaks browser/Playwright accessible-name computation if the child list is itself a table: a `<table>` nested inside another `<table>`'s `<td>` has no ARIA role boundary between them, so the *outer* row's computed accessible name aggregates the inner rows' text too. This makes `getByRole("row", {name: /some inner text/})`-style lookups ambiguous — they resolve to both the outer wrapper row and the actual target row, a Playwright strict-mode violation.

**Use a flat `<ul>`/`<li>` for the nested level instead**, same convention the pre-existing Release→TestCycle view already used and REQ-2's Requirement→TestCase→TestStep section was refactored to match. Reserve `<table>` for the outermost, non-nested list in a given screen.

## Unit tests live in `frontend/tests/`, not co-located next to their source in `src/`

Every Vitest + RTL spec in this repo is under `frontend/tests/` (mirroring `src/`'s own directory shape — e.g. `src/pages/workflows/ProjectDetail.tsx` → `tests/pages/workflows/ProjectDetail.*.test.tsx`), **never** a `*.test.tsx` file sitting next to its component in `src/`. This is the opposite of the more common industry default (co-located tests), so a `find src -iname "*.test.*"` search comes back empty and *looks* like zero coverage exists — the actual answer requires checking `frontend/tests/` specifically before concluding a gap is real (a REQ-4 verification pass wasted a round-trip on exactly this before finding `tests/pages/workflows/ProjectDetail.TestConditions.test.tsx`, 2026-09-06). A per-story test file follows the shipping story's own name (`ProjectDetail.TestConditions.test.tsx`, `ProjectDetail.TestSuites.test.tsx`, ...) rather than one giant `ProjectDetail.test.tsx` — grep for the screen name across `frontend/tests/`, don't just check one filename.

## No frontend unit-test convention existed before ADMIN-2 (2026-09-05)

`frontend/tests/` (Vitest + RTL) only started getting real coverage with ADMIN-2's generic CRUD UI — earlier bespoke screens (`Login`, `OrgHome`, `ProjectDetail`, etc.) shipped with e2e (Playwright) coverage only, no per-component unit tests. Both are legitimate per the root `CLAUDE.md`'s three-layer testing model, but don't assume a bespoke screen has Vitest coverage just because the layer exists in the repo now — check `frontend/tests/` for that specific component before assuming a gap is actually a regression.

## A "Cannot find module 'react'" diagnostic right after adding a new file can be stale, not real

The harness's own background diagnostics can fire on a just-created `.tsx` file before its module resolution/language-server view has caught up (observed on a freshly-added page component + its imports, 2026-09-06) — every import line (`react`, `react-router-dom`, `@coreui/react`, ...) flagged `Cannot find module`, which reads exactly like a broken `node_modules` or a real compile break. It wasn't: `node_modules` was present and `npx tsc --noEmit` (run directly, not through the diagnostic system) was clean. **Before acting on a wall of module-resolution errors on recently-touched files, run `npx tsc --noEmit` yourself and trust that over the background diagnostic** — it's the ground truth; the diagnostic view can lag. Confirmed again on PLAN-3 (2026-09-06) across a much larger edit (a full page section + a new e2e spec) — same stale-diagnostic shape, `tsc --noEmit` clean both times a sub-agent reported it.

## `entityConfigs/<entity>.ts` can silently drift out of sync with a backend route restriction

An entity's generic-admin `methods` array and its backend `_<ENTITY>_CONFIG.methods`/`create_schema` (`backend/app/api/routes/*.py`) are two independently-maintained lists describing the same thing — nothing in the type system links them. PLAN-3/ADR-0033 restricted the backend's generic `TestExecution` create (see `backend/CLAUDE.md`'s "removing/restricting" note) but the frontend's `entityConfigs/test-execution.ts` still declared `"create"` — the admin surface would have rendered a working-looking "New Test Execution" button that submitted to a route now answering `405`, a dead affordance no test caught until someone went looking specifically. **Whenever a backend generic-CRUD `create`/`update`/`delete` is added or removed for an entity, check that entity's own `entityConfigs/<entity>.ts` `methods` array agrees, in the same change** — and consider a paired test (this repo's fix added `tests/entityConfigs/bespokeCreateOnly.test.ts`) asserting the frontend config and the backend route shape for a given entity can't drift apart again, rather than relying on someone noticing the mismatch by hand next time either side changes.

## A hand-typed Vitest mock stays green after a backend response-shape change — mocks don't know the contract changed, only a real backend does

`vi.mock("../../src/lib/api/roleAssignments", ...)` mocks (and every other `lib/api/*` mock in this repo) are typed against whatever the mocked function's TypeScript signature says *right now* — if the signature and the mock's return value are updated together (which they were, in the same commit, for DS-2's envelope change), the test suite passes and tells you nothing is wrong, even on the exact same day a real backend caller of the un-mocked route broke (see `backend/CLAUDE.md`'s and root `CLAUDE.md`'s fuller write-up of `RoleAssignmentsPanel`'s crash, DS-2, 2026-09-08). The danger isn't the mock itself — it's trusting "Vitest is green" as evidence the frontend and backend still agree, when a mock can only ever attest that the frontend agrees with *itself*. **A green Vitest run after a backend contract change proves the frontend's own internal consistency, not integration with the real backend — that proof only comes from an integration test hitting the live route (`backend/tests/integration/`) or an e2e test loading the real page (`e2e/`), per root `CLAUDE.md`'s testing philosophy.**

## A bespoke screen's list must be `useQuery`-backed (fetched on mount), never local `useState` populated only by a create/update response

`OrgHome.tsx`'s Project list (PROJ-1, ADR-0017) shipped this way from the start and stayed broken for four stories' worth of work before a manual-test handoff caught it (2026-09-07): `useState<ProjectSummary[]>([])`, appended to only inside `createProject`'s own success handler. It looked completely correct in every check anyone actually ran — a create-then-assert automated test (the list updates immediately after create, because it's the same in-memory array) and a manual click-through that stays on one screen (same reason) both pass identically whether the list is fetched or not. The bug only exists on **any unmount** — not just a page reload, which is the framing the original code's own docstring used and the reason it went unnoticed. Navigating into a just-created row's own detail page and clicking back is a plain client-side route change, unmounts the component, and a `useState` with no fetch-on-mount comes back empty even though the row still exists server-side.

**Before shipping a bespoke (non-generic-admin) screen with a list, check it's backed by a `useQuery` (or equivalent fetch-on-mount), not a `useState` whose only writer is a create/update handler.** If a route already exists for the list (check the generic factory / API Document §3 first — `OrgHome`'s fix needed no new backend route, `GET /projects?org_id=` had shipped under ADR-0022 for over a month before anyone wired it into this screen), reuse it. The regression test for this class of bug is specifically an **unmount-then-remount** case (Vitest: unmount, remock the fetch, remount, assert the data still renders) or, at the E2E layer, a literal "navigate away, navigate back" — a create-only test structurally cannot catch it, the same way `backend/CLAUDE.md`'s resolver-completeness note explains a create-only test can't catch a resolver gap.

## `FkAutocomplete` supports a `:paramName`-shaped `listPath` via an optional `routeParams` prop

Added by PLAN-3 (2026-09-06) — before this, a ref-entity config whose `listPath` contained a path placeholder (`release`'s config is the one example today, `:projectId`) had no way to have that placeholder filled in, a latent pre-existing gap on the generic admin surface that just happened not to matter until a bespoke screen (`TestPlanDetail`'s new Test Cycles section) needed a `release_id` autocomplete scoped to the current project. If you hit a `FkAutocomplete` requesting the literal string `:someParam` instead of a real id, this prop is the fix — pass `routeParams={{ projectId: currentProjectId }}` (or whatever the placeholder names) — not a one-off inline workaround in the page component.

## ~~`CTooltip` wrapping a `CDropdownToggle` needs a plain host element in between~~ — SUPERSEDED by ADR-0042 (historical)

> **Obsolete as of 2026-09-08.** `@coreui/react` is removed; there is no `CTooltip` or `CDropdownToggle`. Tooltips are now a native `title="..."` attribute on the child element (the precedent `AppHeader.tsx` already set under ADR-0037), which has no ref plumbing and therefore none of this failure mode. Kept as history — the *general* lesson (a component that resolves its own ref via context rather than `forwardRef` cannot receive one from a parent that clones it) is still worth knowing if any future wrapper library is ever reconsidered.

`CTooltip` positions itself by cloning its child and attaching a ref to it — but `CDropdownToggle` is a plain function component (it reads its own ref from `CDropdownContext`, not via `forwardRef`), so passing it a ref logs "Function components cannot be given refs" and the tooltip's popper ends up anchored to `null` (renders, but never positions correctly, or never shows). SHELL-6 (2026-09-07, `AppHeader.tsx`'s org-switcher trigger) hit this directly. Fix: put a plain host element (a `<span className="d-inline-block">` works) between `CTooltip` and `CDropdownToggle` — it accepts the ref `CTooltip` needs, and `CDropdownToggle` still reaches its parent `CDropdown` through context, not through being `CTooltip`'s direct child, so the dropdown itself is unaffected:

```tsx
<CTooltip content="...">
  <span className="d-inline-block">
    <CDropdownToggle>...</CDropdownToggle>
  </span>
</CTooltip>
```

Same fix applies to any other CoreUI trigger component that resolves its own ref via context instead of `forwardRef` — check for the same console warning before assuming a `CTooltip` that "isn't showing" is a CSS/z-index problem.

## Bootstrap ships both `container` (centered, max-width) and `container-fluid` (100%-width, padding-only) — confirm which one a reference actually uses, don't assume

*(Still true verbatim under ADR-0042 — `container`/`container-fluid` are Bootstrap classes AdminLTE inherits unchanged, and AdminLTE's own shell markup uses `container-fluid` throughout. Only the `<CContainer>` component in the last paragraph is gone: write the `<div className="container-fluid">` directly, which removes the "which does the default prop render" question entirely.)*

Matching the CoreUI free-template demo's breadcrumb pixel-for-pixel (SHELL-2, 2026-09-07) got the wrong one twice before landing on the right one: first a raw `px-3` div, then a plain `<CContainer>` (which renders `.container` — centered, per-breakpoint max-width), when the demo's actual markup is `.container-fluid` (100% width, `px-4` only, no centering). The two look identical in a narrow viewport or a small example and diverge hard at real desktop widths — exactly the kind of mismatch a screenshot alone won't explain (see root `CLAUDE.md`'s Testing section on this). `<CContainer>` defaults to non-fluid; `<CContainer fluid>` is the `container-fluid` variant. **Before wrapping anything in `<CContainer>` to match a CoreUI-template reference, check the reference's actual rendered class (view-source, or a real browser's computed style/`className`) for whether it says `container` or `container-fluid`** — never assume the default prop shape matches what a specific template element uses.

## Dumping a component's actual rendered DOM (RTL) is the fastest, most reliable way to know what a UI library really renders — faster than reading its source

*(Unchanged and, if anything, more load-bearing under [ADR-0042](../docs/adr/0042-adminlte-design-system.md): with raw HTML now the universal rule, an RTL dump of whatever is being replaced — plus a grep of `node_modules/admin-lte/dist/css/adminlte.css` for the target class — is the only sanctioned way to derive class names. Never invent one.)*

Before removing a `@coreui/react` (or any UI library) import to hand-roll the same markup, render the current component with React Testing Library and `console.log(container.innerHTML)` (or a target element's `outerHTML`) rather than guessing from the library's prop docs or reading its source for the expected output. Used for the SHELL-2 raw-HTML migration (ADR-0037, 2026-09-07): every hand-rolled component's classes/attributes were copied from an actual dump of what `@coreui/react` was rendering moments before its import was deleted, not reconstructed from memory or docs — the resulting raw HTML needed zero test-assertion changes across 24 existing tests because the DOM shape was byte-for-byte identical. This is strictly more reliable than reading the library's source for the same purpose — see root `CLAUDE.md`'s Testing section for a case where reading `CSidebar`'s own source produced an actively wrong prediction that only a live, empirical test caught.

## ~~CoreUI signals its own responsive/breakpoint state to JS via a CSS custom property (`--cui-is-mobile`)~~ — SUPERSEDED by ADR-0042, and following it now silently breaks the mobile branch

> **Actively wrong as of 2026-09-08.** **AdminLTE defines no `--cui-is-*` (or equivalent) custom property**, so `getComputedStyle(el).getPropertyValue("--cui-is-mobile")` returns `""` — falsy, no error, no warning — and the mobile branch simply never fires. AdminLTE's own `push-menu.ts` uses a literal `globalThis.innerWidth <= 991.98`; our React reimplementation uses **`matchMedia("(max-width: 991.98px)")` with a `change` listener** (not a raw resize handler), which is the technique of record now. The breakpoint number is corroborated by `sidebar-expand-lg` publishing `content: "991.98px"` on a `::before` — so it isn't a hand-picked value, it's AdminLTE's own, just read from a different place. The paragraph below is kept as history because its *closing instruction* generalizes: grep the shipped CSS for how the library actually signals a piece of responsive state before inventing your own media query.

`coreui.min.css` sets `--cui-is-mobile: true` on `.sidebar` inside its own `@media (max-width: 991.98px)` rule; `CSidebar`'s real implementation reads it back via `getComputedStyle(element).getPropertyValue('--cui-is-mobile')` rather than duplicating the breakpoint number in JS. When hand-rolling equivalent responsive behavior (the SHELL-2 sidebar migration's mobile show/hide, ADR-0037), reading the same custom property off your own element (`getComputedStyle(ref.current).getPropertyValue("--cui-is-mobile")`, re-checked on a `resize` listener) is the correct technique — it stays in sync with CoreUI's own CSS forever, and doesn't reintroduce the "no custom breakpoint logic" hand-rolled-media-query smell ADR-0018 originally chose CoreUI specifically to avoid. Grep `coreui.min.css` for any other `--cui-is-*` custom property before assuming a piece of CoreUI's responsive behavior needs a bespoke `window.matchMedia` breakpoint of your own invention.

## ~~CoreUI's `CPaginationItem` renders the active/current page as a plain `<span>`~~ — SUPERSEDED by ADR-0042; the *conclusion inverts*, the test-writing habit doesn't

> **Changed as of 2026-09-08.** Pagination is now hand-written markup: `<li className="page-item [active|disabled]"><button type="button" className="page-link" onClick={...} aria-current={active ? "page" : undefined}>` — **a real `<button>` with a live `onClick` on every item, including the active one**, so clicking the current page now *does* fire `onPageChange` rather than being CoreUI's silent no-op. Two things carry forward unchanged: (a) the `active`/`disabled` classes must stay on the **`<li>`**, not the inner control, because existing tests do `getByText("Previous").closest("li")` and assert there; (b) **still click a *non-active* page number to prove navigation wiring** — a same-page click is now a no-op for a different reason (the handler runs but the page number doesn't change), so it remains a test that proves nothing. The CoreUI-source detail below is kept only as the historical record of why `container/Table.test.tsx` was written the way it was.

`CPaginationItem`'s own source (`node_modules/@coreui/react/dist/cjs/components/pagination/CPaginationItem.js`): `Component = rest.active ? 'span' : 'a'`, and only the `'a'`/`CLink` branch spreads `rest` (which is where `onClick` lives) — the `active` branch renders `<span className="page-link">{children}</span>` with no click handler wired at all. `EntityTable.test.tsx`'s own comment already flagged the render-as-`<span>` half of this ("CoreUI renders each `CPaginationItem` as an `<a class="page-link">` (or `<span>` for the active one)"), but the consequence — clicking it fires nothing, no error, `onClick` mock never called — bit `container/Table.test.tsx` directly (DS-2, 2026-09-08): a test that navigated to page 3 and then clicked "3" itself (rather than a different page number) to assert `onPageChange` fired got zero calls, reading like a broken click handler rather than a deliberate "you're already here" no-op this is CoreUI's own intended UX. **When writing a pagination test, click a *non-active* page number to prove navigation fires — clicking the current page is testing CoreUI's own no-op, not your `onPageChange` wiring.**

## Making a page's content "fill" `AppShell`'s content column: `h-100` only works if the target is the *sole* child of its parent — a sibling heading needs flex instead

> **Re-verify the measurements under [ADR-0042](../docs/adr/0042-adminlte-design-system.md) before reusing the numbers below.** The sizing context changed shape: `AppShell`'s CoreUI-era `div.d-flex` + nested `flex-column` column is replaced by AdminLTE's `.app-wrapper` **CSS grid** (`grid-template-rows: min-content 1fr min-content`, `min-height: 100vh`), with `.app-main` occupying the `1fr` row and `.app-content` inside it. The *rule* below still holds (an `h-100` target must be the sole child of its sizing context; a sibling heading means `flex-column` on the parent + `flex-grow-1` on the target), and so does the method — measure `getBoundingClientRect()` live against a real stack, don't infer from source, since jsdom does no layout. But the specific 795px-in-a-900px-viewport figure and the "already fills via `min-vh-100`" findings were measured against the old flex column and are not evidence about the grid. `CContainer`/`CCard` in the text below are now `div.container-fluid`/`div.card`.

`AppShell.tsx`'s content column (`div.flex-grow-1`) is a real flexed box with a definite height (confirmed live: 795px in a 900px viewport, not `auto`), so `height: 100%` (Bootstrap's `h-100`) on a page's own `CContainer`/`CCard` correctly resolves against it — *when* the element you're sizing is the only thing occupying that space. `Dashboard.tsx`/`EntityListPage.tsx`/`EntityFormPage.tsx` (2026-09-07) all have exactly that shape (`CContainer` wraps one single `CCard`, `h-100` on both is correct and sufficient). `Typography.tsx` doesn't: its `<h1>` page heading is a sibling *before* the `CCard`, not nested inside `CCardBody` — a plain `h-100` on that `CCard` computes 100% of the *container's* height, ignoring that the heading above it already consumes some of that space, so the card would render taller than what's actually left and overflow past the container's own bottom edge. The fix there was `d-flex flex-column h-100` on the `CContainer` and `flex-grow-1` (not `h-100`) on the `CCard`, so it fills only the space genuinely remaining after the heading. **Check whether the thing you're trying to stretch is the sole child of its sizing context before reaching for `h-100`** — if a heading, toolbar, or anything else shares that parent, use `flex-column` on the parent + `flex-grow-1` on the target instead, and verify the actual rendered height live (`getBoundingClientRect()`), not just that the page compiles and "looks probably fine."

**A close, easy-to-make mistake in the same family: adding `h-100` (or any height utility) to a plain, unstyled wrapper `div` achieves nothing visible if nothing inside it paints a background or border into the new space.** `Colors.tsx`/`Icons.tsx` (a `CRow` of many small independent `CCard`s, no single card wrapping the whole page) were deliberately left untouched during the same pass — their `CContainer` has no `bg-*`/border of its own, so making it taller would be a purely structural change with zero visible effect, and force-stretching each individual small swatch/icon card to match the full column height would look broken (a color swatch growing to 700px tall). Reserve the `h-100` stretch pattern for pages where a single visible box (a card, a bordered/backgrounded container) is meant to visually reach the bottom of the content area — for a grid/gallery of many small independent items, natural content height is correct, not a bug to fix.

## `fill="currentColor"` inside an `<img src="*.svg">` does NOT inherit the host page's color — the SVG loads as its own document, and `getComputedStyle` on the `<img>` is a false-pass trap for checking it

BRAND-1 (2026-09-09, ADR-0048): the brand mark SVGs (`logo-mark.svg`/`logo-full.svg`) were built with `fill="currentColor"` specifically so one asset file could serve both light and dark mode, mirroring how `currentColor` already works for every inline SVG/Font Awesome `<i>` icon elsewhere in this app. Mounted via `<img src={logoMarkUrl} />` (the sidebar/header pattern this repo already used for other raster-ish assets), the marks rendered **solid black in dark mode** — invisible against the dark sidebar. Root cause: an `<img>` element loads its `src` as an entirely separate document with its own rendering context; `currentColor` inside that document resolves against *that document's own* initial/inherited color (black, absent any other rule), never against the host page's `color` the `<img>` tag itself happens to sit inside. This is unrelated to (and a strictly different failure mode from) the already-documented `--cui-is-mobile` custom-property gap above — that one is about a CSS custom property CoreUI stopped defining; this one is about a CSS keyword (`currentColor`) that behaves completely differently depending on whether the SVG is *inlined* (as JSX/raw markup, where it does inherit) or *referenced* (`<img src>`, `background-image`, `<object>` — where it does not).

**The verification step this bug's own fix-in-progress first reached for was itself a false pass**: `getComputedStyle(imgElement).color` happily reports a real, healthy-looking inherited color (e.g. `rgb(110, 168, 254)`) — that's the `<img>` element's own CSS `color` property, which exists and inherits normally, but which the *replaced content* (the SVG's internal `fill="currentColor"`) never consults at all. Asserting on `getComputedStyle(img).color` to prove theme-tracking works would pass cleanly on a mark that is, in fact, invisible. The actual fix: drive the color swap from the host document instead, via a `data-bs-theme`-keyed CSS `filter` (`brightness(0)` / `brightness(0) invert(1)`) applied to the `<img>` itself — `filter` *does* apply to the whole rendered `<img>` regardless of what's inside its loaded document, unlike `currentColor`. The SVG source stays `currentColor`-only (still correct, still theme-agnostic *as an asset*) — the fix lives entirely in the mount's CSS, not the asset.

**Before shipping any icon/logo SVG meant to track the app's own theme via `currentColor`, decide inline-vs-referenced first, and verify by checking the actual painted pixel color (or an explicit `filter`/`fill` rule that's known to apply to the mount type), not `getComputedStyle` on whatever wrapper element happens to be convenient to query.** If a raster-style `<img src="*.svg">` mount is required for another reason (lazy-loading, browser-native caching, an existing established pattern), the mark cannot use `currentColor` for real theme-tracking — reach for a `filter` pair, an inlined `<svg>`/React component instead, or (for a case that genuinely needs multiple fixed color states) simple asset duplication.
