# CLAUDE.md — e2e

E2E-specific guidance. Read the root `CLAUDE.md` first (isolated-test-env rule, three-layer testing model). This file is the full worked recipe for standing up an isolated Compose stack and running Playwright against it — distilled from repeated real runs across AUTH-1, REQ-2's implementation, REQ-2's post-merge/manual-verification passes, and REQ-3 (2026-09-05/06).

## Full isolated-stack recipe

1. **Pick a project name and port.** `docker compose ls` first to check nothing stale is already running under a name you're about to reuse — orphans accumulate across sessions and will collide on ports. Project name: `testnexa-<purpose>-<port>` (e.g. `testnexa-verify-55495`). Port: any free 5-digit port (`lsof -i :<port>` to check), bound as `"<port>:80"` (not `"127.0.0.1:<port>:80"`) so it's reachable via both `localhost` and the host's LAN IP — Compose's plain `"<port>:80"` shorthand already binds `0.0.0.0`, no extra config needed for that half.

2. **`docker-compose.override.test.yml`** in the worktree root (already gitignored, `.gitignore:7` — don't fight that, don't try to commit it):

   ```yaml
   services:
     nginx-dev:
       ports: !override
         - "<port>:80"
     postgres:
       ports: !override        # only needed if backend/tests/integration/*.py will run
         - "<db-port>:5432"    # against this stack from the host (see backend/CLAUDE.md)
       volumes: !override
         - <project>_postgres_data:/var/lib/postgresql/data
   volumes:
     <project>_postgres_data:
   ```

   The `!override` tag is not optional — Compose's default merge behavior for a list key like `ports`/`volumes` is to **append**, not replace; omit the tag and you'll get both the original and new port bound, and the original (main's `54593`) will still be a live conflict if you're also trying to rebind that same service. This has bitten more than one session — always watch the `up` output for a "port already allocated" error and fix the tag if you see one.

3. **Bring it up:** `docker compose -p <project> -f docker-compose.yml -f docker-compose.override.test.yml --profile dev up -d --build` from the worktree root (build context must be the worktree, not the main repo root, or the isolated stack won't contain the branch's code).

4. **Clone main's DB**, don't start empty:
   ```
   docker exec testnexa-postgres-1 pg_dump -U testnexa -d testnexa --no-owner --no-privileges \
     | docker exec -i <project>-postgres-1 psql -U testnexa -d testnexa
   ```
   (equivalently, `pg_dump -F c -f /tmp/clone.dump` + `docker cp` + `pg_restore --clean --if-exists`, same result). Verify with a row-count spot-check on a couple of tables (`organization`, `project`) — main vs. clone — not just "the command exited 0." **Also confirm `alembic_version` exists and matches main's own current head** (`docker exec <project>-postgres-1 psql -U testnexa -d testnexa -c "SELECT * FROM alembic_version;"`) — a stack that never actually ran this step still shows healthy containers and a green `/api/health` (health checks don't touch the DB schema), and every integration test that seeds via `AsyncSessionLocal` then fails identically with `UndefinedTableError: relation "..." does not exist`, reading like a real regression (see `backend/CLAUDE.md`'s SHELL-6 note for the confirmed case, 2026-09-07 — an orchestrator died before reaching this step and nothing downstream flagged it). If you clone into a stack whose backend container is already running, `docker restart <project>-backend-1` afterward (stale pooled connections against the old data otherwise hang requests) and expect a brief `502` right after restart before it's ready again.

5. **Migrate:** `docker exec <project>-backend-1 alembic upgrade head` — a no-op if main was already at head (expected, since main is what any feature branch merges from), but always run it and check `alembic heads` shows exactly one head.

6. **Health-check both IPs:** `curl http://localhost:<port>/api/health` **and** `curl http://<lan-ip>:<port>/api/health` (get the LAN IP via `ipconfig getifaddr en0` on macOS) — both must return `{"status":"ok"}`. This is the actual proof the "both IP" requirement is satisfied, not just that the port bound.

**Steps 3-7 above all name the same `-f docker-compose.yml -f docker-compose.override.test.yml` pair for a reason — repeat both flags on *every* compose command against this stack for its whole lifetime, not just the initial `up`.** Confirmed DS-2 (2026-09-08): a later mid-session rebuild of just the `backend` service (`docker compose -p testnexa-ds2-test build backend` + `up -d --build backend`, no `-f` flags — an easy habit-slip once the stack's already up and you're only touching one service) recreated `postgres` too, using the base `docker-compose.yml`'s own defaults — silently dropping the override's `5432` port publish (the named volume/data itself was untouched, only the host-reachable port). `docker ps` still showed `postgres-1` as `Up (healthy)`, no visible sign anything had changed; the only tell was every subsequent `backend/tests/integration/` run refusing the connection a few minutes later. Compose recreates the whole dependency graph under whatever config it's actually given *that invocation* — a single-service rebuild with the flags dropped doesn't stay scoped to that one service if a dependency's own effective config just changed underneath it. Re-verify with `docker ps`'s port column (not just container status) after any rebuild, same postcondition-checking discipline this file's DB-clone step already teaches.

7. **Tear down when done:** `docker compose -p <project> -f docker-compose.yml -f docker-compose.override.test.yml --profile dev down -v` (removes containers, network, and the cloned DB volume), then delete the worktree-local `docker-compose.override.test.yml` and any `.env` you created for the stack (check `git status --short` after — neither should show as untracked cruft left behind; `.env` is *not* currently in `.gitignore`, unlike the override file, so don't forget it manually).

## Known, harmless failures when testing through this topology

`nginx/nginx.dev.conf` only proxies `/api/health` and `/api/*` to the backend — bare `/health` falls through to the frontend's catch-all `index.html`. If `TEST_API_BASE_URL` points at the isolated stack's **nginx** port (rather than the backend directly), `backend/tests/integration/test_health_api.py::test_health_returns_ok_over_real_http` and `test_rbac_seed.py::test_live_server_health_check_still_ok_after_rbac_seed_migration` will fail — both call bare `/health` on purpose (matching the direct-backend-port default). This is a topology artifact, not a regression; don't chase it, just note it in your report.

**Separately, don't append `/api` to `TEST_API_BASE_URL` itself** when pointing it at this stack's nginx port — `backend/CLAUDE.md` has the full write-up (a REQ-4 verification pass lost real time to this exact mistake, 2026-09-06). The `/health`-only artifact above is about which *path* two specific tests hit; this one is about the *base URL* every other integration test's path gets built on top of, and getting it wrong breaks far more than two tests.

**A third failure you'll see in a full integration run against any isolated stack, `test_mcp_e2e_client.py::test_mcp_sdk_client_handshake_and_tools_list_over_lan_ip`, is NOT the same class as the two above** — those two are topology artifacts (expected, harmless, don't chase). This one has a hardcoded LAN IP+port with no env-var override at all (`backend/CLAUDE.md` has the exact line) and will fail against every isolated stack, and eventually against `main` too once the host's IP changes. Report it as a known-broken test needing a real code fix, not as another "topology, ignore it" line — the two are easy to conflate at a glance since both show up in the same full-suite run's tail.

## Seed/cleanup script pattern (used by every `req*-ui.spec.ts` file)

Each UI-level spec seeds its own fixture via `docker exec -i <backend-container> python -` with a heredoc Python script (direct `AsyncSessionLocal` inserts — `User`/`Organization`/`OrgMembership`/`RoleAssignment`/`Project`, printing a JSON blob of the ids it created to stdout), and cleans up the same way in a `finally` block with a matching FK-safe (child-first) delete script taking those ids as `sys.argv`. FK-safe delete order matters: link tables (`app/models/trace.py`) before the rows they link, dependent rows before their parents. See `req1-requirements-ui.spec.ts` or `req3-test-condition-rigor-path.spec.ts` for the canonical shape — copy one of those rather than writing a new pattern from scratch. `E2E_BACKEND_CONTAINER` (env var, defaults to a specific prior session's container name — always override it to whatever isolated stack you're actually running against, `<project>-backend-1`) is how these scripts find the right container: `E2E_BASE_URL=http://localhost:<port> E2E_BACKEND_CONTAINER=<project>-backend-1 npx playwright test <spec>`.

**If you hand-seed an account meant for a human to actually log in with** (not just a Playwright fixture) — e.g. handing the environment to a person to try manually — seed one extra, non-cleaned-up account explicitly for that purpose, and see `backend/CLAUDE.md`'s email-domain gotcha: don't use `.local`/`.test`/`.invalid`/`.example`, use `example.com`/`example.org` instead. **Construct it as `User(name=..., email=..., password_hash=...)` directly, never `Actor()` then `User(actor_id=actor.id, ...)`** — see `backend/CLAUDE.md`'s joined-table-inheritance note, same trap either way you're hand-seeding a `User`. **Also add the matching `AuthIdentity(user_id=user.actor_id, provider=AuthProvider.local, is_primary=True)` row** — every canonical `SEED_SCRIPT` in this directory already does, but a hand-written one-off script easily skips it, and the failure mode (a real, correct password still gets a generic `invalid_credentials` 401) looks identical to a typo'd password, not a missing row — see `backend/CLAUDE.md`'s own note on this, confirmed 2026-09-07.

## Running the full suite (not one spec) against a stack needs BOTH container-name overrides, not just `E2E_BACKEND_CONTAINER`

A second env var, `E2E_POSTGRES_CONTAINER`, exists for the same reason and defaults the same broken way — `auth-refresh.spec.ts` (and any spec that revokes/mutates rows directly via `docker exec ... psql`, not just the seed-script pattern above) reads it separately, also defaulting to a specific prior session's container name. Running `npx playwright test` (no filter, every spec) against a stack without overriding **both** produces a wall of `Error response from daemon: No such container: testnexa-<other-story>-backend-1` failures — 20+ specs at once, since nearly every spec file has its own stale default. **This looks exactly like a broken environment, but it isn't one** — same "suspect harness config before the code under test" instinct `backend/CLAUDE.md`'s `/api`-prefix note already teaches, just at the container-name layer instead of the URL layer: `grep -rn "BACKEND_CONTAINER\s*=\|POSTGRES_CONTAINER\s*=" e2e/tests/*.spec.ts` to see every default in one pass, then run with both overrides set: `E2E_BASE_URL=http://localhost:<port> E2E_BACKEND_CONTAINER=<project>-backend-1 E2E_POSTGRES_CONTAINER=<project>-postgres-1 npx playwright test`. Confirmed 2026-09-06: 26 false failures with no overrides → 3 real/pre-existing ones with both set.

**Confirmed again 2026-09-07 (OrgHome project-list-fix verification), same exact miss:** set `E2E_BACKEND_CONTAINER` for a first-run single-spec check, forgot `E2E_POSTGRES_CONTAINER` for the follow-up full-suite run, got `auth-refresh.spec.ts` failing with `Error response from daemon: No such container: testnexa-auth2-postgres-1` — a fresh instance of the exact failure this section already documented, not a new discovery. **The actionable fix isn't another doc edit, it's process discipline: grep this file's own "known, harmless failures" section (or just re-read it) *before* your first full-suite run against a newly-named stack, not after seeing failures that then need diagnosing back to a note that was sitting here the whole time.** A single-spec check passing is not evidence the full-suite env vars are also set correctly — set both container overrides as a matter of course any time the run isn't scoped to one spec file.

## `auth-login.spec.ts` is permanently broken against a DB cloned from `main`, by design gap not regression

Unlike every other spec in this directory, `auth-login.spec.ts` does **not** self-seed its fixture — its own header comment says the account (`e2e-auth1@example.com` by default, `E2E_LOGIN_EMAIL`/`E2E_LOGIN_PASSWORD` overridable) is "seeded directly into the target environment's DB... see the AUTH-1 test-env handoff for credentials." That account was seeded only into AUTH-1's own now-torn-down isolated stack — it was never persisted to `main`, so a fresh isolated stack cloned from `main` (this directory's own documented recipe, above) will never have it. Confirmed by direct query 2026-09-06 (`SELECT email FROM "user" WHERE email = 'e2e-auth1@example.com'` → zero rows on a `main`-cloned DB). **Don't chase this as a regression** — either seed that exact account yourself first (same pattern as the hand-seed note above) or skip the spec. Worth fixing properly some day by converting it to the same self-seeding pattern every other spec already uses, so it doesn't require an undocumented, one-off manual precondition — flagged here, not fixed, since that's a real code change outside a docs-only pass.

## `e2e/` has no `tsconfig.json` and no `@types/node` — editor/tsc diagnostics on spec files are pre-existing noise

Confirmed on `main` itself, not just a worktree (2026-09-06): `e2e/node_modules/@types` has no `node` package, and there is no `e2e/tsconfig.json` anywhere in the repo's history. Any spec file will show editor-level errors like `Cannot find module 'node:child_process'`, `Cannot find module '@playwright/test'`, `Cannot find name 'process'` — even on a file where you only changed a string literal, not an import. Playwright's own test runner (esbuild-based) doesn't need `tsc`/a `tsconfig.json` to actually run the suite, so this doesn't block real test execution — treat it as an IDE-only false alarm, not a regression from whatever edit triggered the diagnostic, unless `npx playwright test` itself fails.

## `admin2-generic-crud.spec.ts`'s "create Requirement -> TestCondition through nginx" case is broken against current `main`, not flaky

Reproducible on rerun alone (2026-09-06), not a `--workers=1` timing issue. It still calls the generic `POST /test-conditions` route, which ADR-0028/REQ-3 (`app/api/routes/test_condition_authoring.py`) replaced with a bespoke `POST /requirements/{id}/test-conditions` route — per `backend/CLAUDE.md`'s "audit for a matching bespoke route" note, the old generic create path for this entity was deliberately restricted, so this test's request now fails against real `main` code. Pre-existing app/test drift, not something a docs-only or infra-only pass should fix — flagged here so it isn't mistaken for a new regression next time it's hit, same as the `auth-login.spec.ts` note above. Real fix is to update the spec to call the bespoke route.

## Run `--workers=1` when exercising more than one or two specs together

This repo's specs are written to run in real browsers against a single dev-mode stack (one Vite process, one uvicorn process) — `playwright.config.ts`'s `fullyParallel: true` default is fine for a single spec, but multiple specs/workers hammering that same single-process stack concurrently produces real flakiness (`page.goto` timeouts, slow `expect` timeouts) that has nothing to do with the code under test. Confirmed repeatedly: the exact same spec set that flakes under default parallelism passes reliably at `--workers=1`. If a test fails once under any multi-worker run, **rerun it alone** before concluding it's a real bug — this session hit that exact false-positive-then-clean-rerun pattern more than once.

**A concrete mechanism behind the multi-worker flakiness above, worth grepping for by name:** DASH-1 (2026-09-07) hit `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out` in the backend container's own logs (`docker logs <project>-backend-1`) during a 4-worker Playwright run — the isolated stack's Postgres connection pool (15 connections max: 5 base + 10 overflow, `app/db/session.py`'s default) was simply too small for 4 workers' worth of concurrent logins/seeds/permission-resolution queries at once, and the resulting timeout surfaced in the browser as a test stuck on a loading spinner past its `expect(...).toBeVisible()` timeout — reading exactly like a real hang in the app, not a backend resource limit. A serial rerun (`--workers=1`) of the same test passed clean. **If a multi-worker run produces a test stuck waiting on something that should resolve quickly (a spinner never clearing, a redirect never firing), check the backend container's own logs for `QueuePool`/`TimeoutError` before assuming the frontend logic is broken** — then confirm with a `--workers=1` rerun, same as this section's own standing advice, before reporting anything as a real bug.

**The same false-positive risk exists across two *separate* concurrent runs against one shared stack, not just multi-worker parallelism within one run.** If you (or a second agent/session) run a backend integration or e2e suite against an isolated stack while another test process is *also* hitting it, both share the same rows/counters — anything keyed on shared mutable state can flip. Confirmed twice in one pass (PLAN-2, 2026-09-06): (1) `test_login_failure_count_behavior_across_a_successful_login` failed in a consolidated run but passed 10/10 alone — login rate-limiting is keyed on `(client_ip, email)` (root `CLAUDE.md`'s Auth section), and a concurrently-running e2e suite hitting the same fixture email mutated the counter mid-assertion; (2) an apparent 6-row `entry_exit_criteria` table "leak" (3→9 rows after a run) turned out to be two concurrent test runs' fixtures both alive at the count-check instant, not an orphaned-row cleanup bug — the row count was back to identical before/after once the runs weren't racing. **Before reporting a flaky/leaked-state finding as real, rerun the specific failing assertion completely alone** (no other test process touching that stack) — a fixture racing a *different* fixture is a much cheaper explanation than a real regression, and this file's own multi-worker note above is the same principle one level up.

## A brand-new spec using Node built-ins (`node:child_process`, `process.env`, etc.) can trip a `Cannot find module`/`Cannot find name 'process'` diagnostic — this is cosmetic, not a real break

`e2e/package.json` has no `@types/node` devDependency and no `tsconfig.json` of its own (confirmed 2026-09-06) — every prior spec avoided Node built-ins entirely (the seed/cleanup pattern above shells out via `docker exec`, never `child_process` directly), so this gap went unnoticed until a spec imported `node:child_process`/read `process.env` for the first time. The harness's background diagnostic flags this as a TS compile error, which reads exactly like a broken import. It isn't: Playwright runs specs through esbuild's transform, which strips types without type-checking, so the file executes fine regardless — confirmed by actually running the spec (`npx playwright test <spec>`) and getting a clean pass with the diagnostic still showing red. Same instinct as `frontend/CLAUDE.md`'s stale-diagnostic note: **trust an actual run over the diagnostic for a file that imports something new**, don't assume a real break without executing it first. Fixing it properly (`npm i -D @types/node` in `e2e/`) is a cheap, low-risk follow-up if a spec is going to keep using Node builtins going forward — just don't block on it.

**A spec that creates its parent entity through a real UI action/route (not a direct ORM seed) is exposed to any new side effect that route grows, and its own cleanup script is the thing that breaks, not the test's own assertions.** Confirmed EXEC-2 (2026-09-07): `exec1-record-execution.spec.ts` and `plan3-test-cycle.spec.ts` both record a `TestExecution` through the real "Record Result" UI / `POST /test-cycles/{id}/executions` call — a new backend change (an auto-appended `TestLog` row on that same route, `RESTRICT` FK back to the `TestExecution`) broke both specs' `CLEANUP_SCRIPT`s, which deleted `TestExecution` before the now-real `TestLog` rows referencing it. The specs' own test bodies/assertions were untouched and still correct — only the `finally`-block delete order needed the new child model deleted first. A third spec creating `TestExecution` via a **direct ORM insert** in its seed script (`plan2-entry-exit-criteria.spec.ts`) was unaffected, since ORM-direct rows never pass through the route and its side effect. **When auditing the blast radius of a new route-level side effect with a `RESTRICT`-FK child, `grep -rl "delete(<Model>)\|<Model>(" e2e/tests/` is not optional just because the change is backend-only** — a spec that only *reads* the backend through a browser is still coupled to it exactly the way a `backend/tests/integration/` file is, and it's easy to check only the latter (this repo's own first regression sweep did, and missed both e2e files — only found via a later, separately-scoped sub-agent run that happened to exercise the sibling specs alongside its own new one).

## A throwaway Node script (not a real spec) is the fastest way to answer a one-off "what does this actually render/measure right now" question against the isolated stack

Distinct from writing a real `*.spec.ts` file: for a single diagnostic question with no lasting test value (e.g. "which pages actually fill their content column, and by how much" — DASH-2, 2026-09-07), write a plain `.cjs` script using `require("@playwright/test")` directly, **copy it into `e2e/` first** (its `node_modules` is what resolves the import — running from `/tmp` or elsewhere fails with `Cannot find module '@playwright/test'`), log in and navigate the real isolated stack, run `page.evaluate()` to read `getBoundingClientRect()`/`getComputedStyle()`/`className` on the exact DOM path in question, and **delete the script the moment you have your answer** — it has no assertions, isn't meant to be re-run, and shouldn't accumulate in the directory as clutter future sessions have to figure out the purpose of. This is the same "verify empirically, don't trust source-reading" instinct as this file's own recipe for the full isolated stack, just scoped down for a five-minute question instead of a real feature's test coverage — used repeatedly in one session to settle exactly which of several pages had a real CSS layout bug versus which already worked via a different mechanism, something no amount of reading `AppShell.tsx`'s source would have settled on its own (see root `CLAUDE.md`'s Testing section and `frontend/CLAUDE.md`'s `h-100` note for what it found).

## Playwright's default 30s test timeout and 5s per-assertion timeout get squeezed as a story's own spec compounds more UI round trips onto an established pattern — bump them explicitly rather than fighting the defaults

Each EXEC-* spec in this directory follows the same "one test, everything sequential" shape as the last (login → record a result → interact with a modal → assert), and each story adds one more round trip on top of the one before it (EXEC-1: record; EXEC-2: + History modal + comment; EXEC-3: + two record/raise-Defect cycles + a final cross-screen navigation). EXEC-3's own spec (2026-09-08) hit the **whole-test** default 30s timeout on nothing more than the `page.goto("/login")` → `waitForURL` step — not because that step is slow, but because the fixture's own `docker exec` seed script plus the test's later steps all count against one shared 30s budget, and this spec simply does more of them than its predecessors did when they set the precedent of never touching `test.setTimeout`. Separately, several **individual assertions** immediately after a modal-closing submit (`toBeHidden()` on `record-result-modal`/`raise-defect-modal`, `toBeVisible()` on the final `test-case-defects-list`) hit their own default 5s timeout even after the whole-test timeout was fixed — the cold-Vite-first-navigation cost this directory's other notes already document (stale-diagnostic section, `frontend/CLAUDE.md`'s dumping-the-DOM note) compounds with a real network round-trip on the very first submit of a fresh test run, and 5s isn't always enough for both at once. **Fix: `test.setTimeout(90000)` (or similar) as the first line of the test body for any spec chaining 3+ modal round trips, and pass `{ timeout: 15000 }` explicitly to any single assertion that immediately follows a form submit** — don't just keep copy-pasting the previous story's spec shape and assume its untouched defaults still have headroom; each added round trip eats into the same fixed budget the first story's spec never came close to using.

## A concurrent, entirely unrelated isolated stack from a different session can crash your Playwright browser via plain host resource contention — not the same class as this file's own same-stack-concurrent-run note above

The "concurrent-run false positive" section above is about two workstreams sharing *one* stack's Postgres. Root `CLAUDE.md`'s own "Working with agents" section now documents a related but distinct class found in the same EXEC-3 session: a *second, fully separate* isolated Compose project (different name, different ports, different DB, zero shared state) on the same host can still starve your browser process via raw CPU/RAM contention, producing widespread `page.goto` timeouts and CDP `session closed` errors that look exactly like a real regression. `docker stats --no-stream` is the diagnostic — if an unrelated stack's container is pegged, that's your answer, not the code under test. See root `CLAUDE.md` for the full write-up.

## `exec1-record-execution.spec.ts` broke the "rerun alone = clean" heuristic 4/4 times — flag this specific spec as unresolved, don't fold it into the two documented flakiness classes above without a clean pass

DS-3 (2026-09-08): every other flakiness case this file and root `CLAUDE.md` document — same-stack concurrency, cross-stack host contention — resolves cleanly on a solo rerun once the contending process is gone (`docker stats --no-stream` confirms nothing else running). This spec didn't: rerun alone, sequentially, across roughly an hour, it failed **4 times with 4 different symptoms** (a "Signing in…" hang past the login POST, a `page.goto("/login")` timeout before the request even resolved, a real assertion mismatch — `dashboard-tile-pass-count` stuck at `"—"` instead of settling to `"0"` — and a `page.getByLabel(/password/i).fill()` timeout), with the backend container's own logs showing zero errors in every window. Two of those four attempts had a confirmed sibling stack contending (`testnexa-shell7-test-backend-1` at 37% CPU) — consistent with the already-documented class. **The other two did not** — `docker stats` showed only this spec's own stack active, and it still failed, differently each time.

**Don't report this spec's own failures as "known contention, safe to ignore" without a clean pass in hand** — the honest state, until someone gets one, is "intermittently broken, cause not yet isolated, possibly a real timing bug in the record-execution flow itself, possibly a host factor this file doesn't document yet (thermal throttling, another non-Docker process, Chromium's own resource ceiling)." Next investigation step: add explicit request/response logging around the login `POST`/dashboard `fetchCounts` calls inside the spec temporarily, or run it under Playwright's own `--trace on` to get a timeline instead of guessing from symptom variety alone.
