## Design system: AdminLTE v4 (raw HTML, no wrapper, no vendored JS)

**AdminLTE v4 (https://adminlte.io/) is the project's design system**, per [ADR-0042](docs/adr/0042-adminlte-design-system.md) (2026-09-08). This supersedes CoreUI ([ADR-0012](docs/adr/0012-coreui-design-system.md)) outright — big-bang, one branch, **zero `@coreui/*` imports may remain** in `frontend/src` or `frontend/tests`. CoreUI itself had superseded Tailwind (ADR-0009). Both of those older rules still bind in one direction: don't add a Tailwind class, and don't reintroduce a `@coreui/*` import.

- Packages: `admin-lte@4.9.1` + its declared peer `bootstrap@^5.3.8`. Icons: `@fortawesome/fontawesome-free`. Gone: `@coreui/react`, `@coreui/coreui`, `@coreui/icons`, `@coreui/icons-react`.
- CSS, imported once in `frontend/src/main.tsx`, **in this order** (AdminLTE's rules are authored to override Bootstrap's, not the reverse): `bootstrap/dist/css/bootstrap.min.css` → `admin-lte/dist/css/adminlte.min.css` → `@fortawesome/fontawesome-free/css/all.min.css` → `./index.css`.
- **AdminLTE v4 *is* Bootstrap 5 plus a layout/skin layer**, so almost every old CoreUI component maps to stock Bootstrap 5 markup (`CCard`→`div.card`, `CFormInput`→`input.form-control`, `CAlert`→`div.alert.alert-*[role=alert]`, `CTable`→`table.table`). AdminLTE's own contribution is the shell: `.app-wrapper` (a **CSS grid** — `.app-sidebar`/`.app-header`/`.app-main`/`.app-footer` must be its *direct* children, no intermediate wrapper div or the grid breaks), `.sidebar-menu` (needs Bootstrap's `nav flex-column` — AdminLTE's own rule sets only `white-space: nowrap`), `.app-content-header`/`.app-content` (compiled as `.app-main .app-content-header`, so they must be descendants of `.app-main`).
- **Raw HTML/JSX against the CSS is now the universal rule, not an exception.** No component-library wrapper at all — the JSX *is* the markup, diffable line-for-line against AdminLTE's demo HTML. This generalizes ADR-0037's 5-file pattern, which the codebase had already drifted toward three independent times (ADR-0037's shell, `FeaturedCard`, `WidgetStatsTile`) before a full AdminLTE-sourced login screen (PR #42) made it the obvious direction. **Use the library's own documented/rendered class names verbatim** — read them out of the shipped CSS or an RTL DOM dump (see `frontend/CLAUDE.md`), never invent one.
- **Hand-written markup owns its own accessible semantics.** CoreUI supplied several implicitly and they're easy to drop: `role="status"` on a spinner (`CSpinner` had it implicitly; 3 tests use `getByRole("status")`), `active`/`disabled` on the pagination `<li>` (not the inner control), `role="alert"` on feedback (but don't multiply alert-role nodes — a singular `getByRole("alert")` turns into a strict-mode failure), real `<label for>`, real `<table>`/`<tr>`/`<th>`, `<button>` not `<div>`. Every `data-testid` is load-bearing (~390 Vitest assertions, ~30 Playwright specs) — never rename, never drop.
- Icons: Font Awesome classes on an `<i>`, no component, no path arrays, no registry — `<i className="fa-solid fa-bars" aria-hidden="true" />`, or the `Icon` atom (`name` + `variant`: `solid`/`regular`/`brands`). Brand glyphs (Facebook, Google) need `variant="brands"`. Sizes are FA's own (`fa-lg`, `fa-2x`). **Still exactly one icon library** — do not add Bootstrap Icons back; the `bi bi-*` classes PR #42 left in the `Icon` atom were pointing at a font that was never loaded, and ADR-0042 fixed that by retargeting the atom, not by loading a second font.
- **Do not vendor AdminLTE's JS plugins or jQuery.** Every behavior is plain React state/effects toggling AdminLTE's own literal classes: sidebar = `sidebar-collapse`/`sidebar-open` **on `document.body`** (via `useEffect` + `document.body.classList`, because `#root` is inside `<body>` — and **clean them up on unmount** or classes leak between tests and across logout), base modifiers `layout-fixed sidebar-expand-lg` (**never bare `sidebar-expand`** — it publishes an empty breakpoint and applies the off-canvas rules at every width) plus `app-loaded` post-mount; mobile = `matchMedia("(max-width: 991.98px)")`, matching `push-menu.ts`'s own constant; treeview = `menu-open` on the `li.nav-item` + `nav nav-treeview` on the submenu `<ul>`; color mode = `data-bs-theme` on `<html>` + the `lte-theme` localStorage key. **We must render `.sidebar-overlay` ourselves** as the last child of `.app-wrapper` — AdminLTE's own JS injects it at runtime and we don't load that JS, so nothing else will.
- React Hook Form + Zod still own form state/validation (ADR-0009, unchanged) — every `register()` spread, `handleSubmit`, `forwardRef` survives; only the rendered element and its classes change.
- **Do not run two Bootstrap-family stylesheets together.** This is the same cascade-conflict rule ADR-0012 wrote against Tailwind + CoreUI, now applied to CoreUI + AdminLTE — both ship `.container`/grid/reset/`.card`/`.btn`/`.table` and disagree on tokens, so the winner depends on import order rather than intent. It's why ADR-0042 is big-bang: a phase boundary here is a *broken-cascade* boundary, not a cosmetic-inconsistency one.
- Tailwind is fully removed as of 2026-09-03 — `tailwindcss`/`postcss`/`autoprefixer` deps and `tailwind.config.js`/`postcss.config.js` are gone. Bootstrap 5 utilities only. Don't reintroduce a Tailwind class or config file.
- **Known live gotchas from the migration** (full list in ADR-0042's Consequences): `sidebar-dark-*`/`sidebar-light-*` **don't exist in v4** (zero occurrences in the shipped CSS — don't invent a skin class, use `bg-body-secondary` or `--lte-sidebar-*`); `btn-ghost-*` was CoreUI-only and is now an **unstyled** class the `Button` atom still emits; badges use `bg-*`, **not** Bootstrap 5.3's documented `text-bg-*` (8+ existing assertions check the exact class); `invalid-feedback` needs an explicit `d-block` when it isn't rendered as the adjacent sibling of `.is-invalid`; modals render **nothing at all when closed** (preserving `CModal`'s unmount semantics that negative `queryBy*` assertions depend on) and have ESC + backdrop but **no focus trap**; `--cui-is-mobile` is gone (AdminLTE defines no such property — it would silently read `""`); AdminLTE's `"Source Sans 3"` font is not bundled and falls through to the system stack; AdminLTE gives `.card` a `box-shadow` and floats `.card-title` left, so use `.card-header` + `.card-tools` rather than fighting it with utilities; `sidebar-mini`'s collapsed rail is a flat `4.6rem` — a narrower `3.1rem` value also exists in the shipped CSS but is gated on `.compact-mode`, a class this app never sets, so don't assume it applies just because it mentions `sidebar-mini` (confirmed by live measurement, SHELL-7, 2026-09-09 — check what *else* gates a rule before trusting a grep hit); AdminLTE's mini-sidebar hover-flyout for a `menu-open` group's children is JS-driven (`push-menu.ts`) and not vendored, so an opened group simply stays open when the rail is un-hovered and its children render inline (functional, just visually blank until hovered again) — there is no flyout to reimplement.

## Running the stack

```
cp .env.example .env
docker compose --profile dev up --build
```

Open `http://localhost:54593` (or the host's LAN IP, same port) — nginx is the single external entrypoint (`/api/*` → backend, `/*` → frontend), per [ADR-0010](docs/adr/0010-single-port-docker-compose-topology.md). `postgres-test` starts alongside but is idle until the integration suite runs against it.

**Never run ad hoc Docker commands against the main `testnexa` compose project when testing a change in progress.** Stand up an isolated test environment instead — validated recipe (run against AUTH-1, REQ-2, and REQ-3):

1. **Name it `testnexa-<purpose>-test`** (compose `-p` flag) — before picking a port, run `docker compose ls` and check for a stale one from a prior session that was never torn down (background/orchestrated work can die without cleaning up after itself, see "Working with agents" below).
2. **Random 5-digit port**, checked free with `lsof -i :<port>` and against `docker ps`.
3. **Build context is the worktree**, not the main repo root, or the isolated stack won't actually contain the branch's code: `docker compose -p testnexa-<purpose>-test -f docker-compose.yml -f docker-compose.override.test.yml --profile dev up --build -d` run from inside the worktree directory.
4. **Port override**: a `docker-compose.override.test.yml` in the worktree overriding `nginx-dev`'s `ports:` — Compose list-merges `ports` by default (appends, doesn't replace), so use the YAML `!override` merge tag on that key. Bind as `"<port>:80"`, not `"127.0.0.1:<port>:80"`, so it's reachable via both `localhost` and the host's LAN IP (same as main's own `0.0.0.0:54593->80`).
5. **Clone main's DB**, don't start empty: `docker exec testnexa-postgres-1 pg_dump -U testnexa -d testnexa -F c -f /tmp/clone.dump`, copy out, restore into the new stack's `postgres` service, then run `alembic upgrade head` inside the new backend container for any migration the branch adds on top of the clone.
6. **Backend has no dev volume mount** (unlike `frontend`, which bind-mounts `src`) — after any backend code edit, `docker compose build backend` (or `up --build`) again, or you're silently testing stale code.
7. **Tear down with `docker compose -p testnexa-<purpose>-test down -v`** when done — removes containers, network, and the cloned DB volume. **This command can silently no-op** — confirmed SHELL-7 (2026-09-09): `down -v` (and `down -v --remove-orphans`, and again with `--log-level debug`, and again with sandboxing disabled) returned exit `0` with zero output, and every container/volume/network was still there afterward. Not a permissions/sandbox issue — plain `docker stop`/`docker rm`/`docker volume rm`/`docker network rm` on the same names worked immediately. If `down` produces no "Stopping.../Removing..." lines at all (even a successful run normally prints several), don't retry it a third time — fall back straight to direct commands: `docker ps -a --filter name=<project>` for container names, `docker volume ls --filter label=com.docker.compose.project=<project>` and `docker network ls --filter label=com.docker.compose.project=<project>` to discover exact volume/network names, then `docker stop`/`docker rm` the containers and `docker volume rm`/`docker network rm` the rest. Full worked example (seed/cleanup script pattern too): [`e2e/CLAUDE.md`](e2e/CLAUDE.md).

**A `docker-compose.override.test.yml` is gitignored — it does not travel with `git worktree add`.** Untracked files exist only in the working tree that created them; a *new* worktree starts clean even though the file is still sitting at the main repo root from a past session. Confirmed 2026-09-06: a stray root-level override (port 17935, no running containers behind it, no commit history — just never cleaned up) was invisible inside a freshly created worktree; the fix was to write a fresh correct override file in the new worktree, not to "edit" one that wasn't there. Two takeaways: (a) don't assume a prior session's override file is reachable from wherever you're working now — check with `ls`/`git status --porcelain` in the actual worktree first; (b) a stray override file at repo root is the same class of cleanup miss as an untorn-down container (see "Working with agents" below) — `ls docker-compose.override*.yml` at repo root is worth a glance alongside the usual `docker compose ls` audit.

**Step 7's "tear down when done" isn't always the right call the instant one task's own verification finishes, if a closely related task is likely to follow in the same session.** A still-running isolated stack from an earlier task can be reused as a live behavioral oracle for a later one — confirmed useful 2026-09-07: an isolated stack stood up to verify a breadcrumb fix was still running (not yet torn down) when a follow-on task needed to know the *actual* runtime behavior of a `@coreui/react` component being replaced, and querying that stack directly (real browser, real click, read the resulting class) settled a question that a static source-code read had gotten wrong (see Testing section). This isn't a reason to leave stacks running indefinitely by default — still tear down once you're confident nothing else in the session will need the original, unmodified behavior to compare against — just don't tear one down reflexively the moment its own task's checklist is ticked if a plausible next step might still want it.

**`frontend/`'s Dockerfile `COPY . .` (the `dev`/`build` stages) copies the *host's* `node_modules` straight into the image if one exists on disk and nothing excludes it — `frontend/` had no `.dockerignore` at all until this was found, 2026-09-08 (the AdminLTE migration).** The `base` stage's own `RUN npm ci` (right after `COPY package.json package-lock.json* ./`) installs correctly every time — the bug isn't caching, it's stage ordering: the very next stage's `COPY . .` (meant to bring in `src`/`public`/config files for the dev server or the prod build) has no `.dockerignore` telling it to skip `node_modules`, so it silently overwrites the freshly-installed one with whatever the *host* checkout happens to have on disk that moment. Confirmed directly: after merging this session's CoreUI→AdminLTE swap and rebuilding the real `testnexa` stack (`docker compose --profile dev up --build`), `docker exec testnexa-frontend-1 ls node_modules` still showed `@coreui/*` present alongside the new `admin-lte` — the image's own `package.json` correctly had no CoreUI dependency, `npm ci` had correctly run against the new lockfile, but the host's own pre-migration `frontend/node_modules` (a leftover local install from before this session, never deleted) got copied on top of it by the very next `COPY . .` instruction. The fix was two-part: add `frontend/.dockerignore` (`node_modules`, `dist`) so this can't recur, and `rm -rf frontend/node_modules && npm ci` once on the host to clear the stale copy already sitting there. **Symptom to watch for: a rebuilt container running code that doesn't match its own `package.json`** — check `docker exec <container> ls node_modules/<suspect-package>` against what `package.json` inside that same container actually declares, don't trust "the build log said `npm ci`" as proof the image's dependency tree is actually correct, and check for a missing `.dockerignore` (`ls frontend/.dockerignore`) before suspecting Docker's build cache itself.

## Working with agents / long-running background work

A background or resumed sub-agent can die silently with no completion record if its parent process exits mid-task (observed twice now on the same class of task: a `ceo-orchestrator` given a multi-hour implement+test task stopped with no transcript marker after being resumed, then — resumed a second time with a `SendMessage`, given a clear "don't stop until done" instruction — stopped again with no completion record, REQ-4, 2026-09-06). **Treat this as the expected failure mode for any multi-hour orchestrated task, not a one-off**: don't assume a second resume will finish what the first one didn't. **Never take a sub-agent's self-reported "done" at face value, and don't stop verifying after the first check either** — after *every* resume or apparent stop, independently re-verify: `git status`/`git diff --stat` in the actual worktree, `docker ps`/`docker compose ls` for what's actually running, and re-run the test suites yourself before reporting results as fact. In practice this means: read whatever the agent *did* leave on disk (files, partial test output) before deciding whether to resume it again or just finish the remaining work directly — a stopped orchestrator's on-disk artifacts are often further along than its last transcript message suggests, and picking up from there is faster than a third resume attempt.

**[`e2e/CLAUDE.md`](e2e/CLAUDE.md) has the full worked recipe** (port/project naming, the `!override` gotcha, DB clone + verification, migrating, both-IP health-checking, and known-harmless failures when testing through this topology) — read it before improvising your own.

**A stopped agent can leave behind not just *incomplete* work but *actively reverted* work, disguised as the real implementation.** DASH-1's `ceo-orchestrator` (2026-09-07) died mid-task while doing legitimate mutation testing — deliberately swapping the real fix into a known-buggy version to prove its own new test suite actually catches the bug, meaning to swap the fix back before finishing. It never got to the "swap back" step. The file left on disk was syntactically fine, had a docstring, imported cleanly, and `git status` showed it as a normal new untracked file — nothing about the on-disk state screamed "broken" the way a half-written function or a merge-conflict marker would. Its own top comment (`// TEMPORARY MUTANT ... then reverted`) was the only tell, and only reading the file's actual content surfaced it — `git diff --stat`/`git status` alone (checking *that* something changed) would have missed it, since the file's mere existence looked correct. **When resuming or picking up after a stopped agent, don't just check that expected files exist — read their actual content, especially anything that looks intentionally temporary (comments saying "mutant"/"temporary"/"revert before done"/"DO NOT COMMIT") before trusting it's the real deliverable.** If the agent also left its own test files behind, those are strong ground truth for what the implementation *should* do even when the implementation file itself is wrong — reading the tests first made rewriting the correct version fast and unambiguous, rather than re-deriving intended behavior from the ADR alone.

**The independent-reverify habit above keeps paying off, not just for stopped orchestrators.** A PLAN-1 verification pass (2026-09-06) re-ran every layer of a sub-agent's self-reported "all green" results directly and caught four real things the transcript alone would have missed: an integration run that silently connected to the wrong Postgres (missing `DATABASE_URL`, see `backend/CLAUDE.md`), a "26 e2e failures" false alarm from an unset container-name override (see `e2e/CLAUDE.md`), a stale-diagnostic false positive on brand-new frontend files (see `frontend/CLAUDE.md`), and a broken hand-seed script of its own construction (`Actor()`-then-`User()`, see `backend/CLAUDE.md`). None of the four were flagged by the agent's own report as a concern — re-running the actual commands, not re-reading the summary, is what surfaced each one.

**Even a foreground (non-backgrounded) orchestrator call can legitimately return before the task is actually done.** Don't assume `run_in_background: false` means the tool call blocks until full completion — a `ceo-orchestrator` given a large multi-workstream task (PLAN-3, 2026-09-06: stand up an env, implement, write 4 layers of tests) returned mid-task with an honest status report and a resume handle ("waiting on the integration-test workstream... will report fully once it lands") rather than either finishing or dying silently. This is the *good* version of the known failure mode above, not a new bug — but it still means "don't return until every subagent is done" requires an explicit `SendMessage`-based resume loop (relay whatever the just-finished child reported, tell it to continue), not a single blocking call. Budget for at least one resume round-trip on any task big enough to spawn its own sub-agents.

**Two independent workstreams (two sub-agents, or a sub-agent and a manual run) hitting the same isolated stack's Postgres concurrently is a real false-positive source, not just a same-suite parallelism concern.** `e2e/CLAUDE.md`'s "concurrent-run" note already covers multiple Playwright workers/runs against one stack; PLAN-3 (2026-09-06) hit the same class of problem one level up — an orchestrator's backend-integration sub-agent and its e2e sub-agent both ran against the one isolated Postgres at the same time, and the orchestrator itself had to flag "every number in my report comes from my own *sequential* re-run, not theirs" before the results were trustworthy. If you fan work out across sub-agents against a single shared isolated stack, either serialize whichever steps touch the same DB, or treat any of their self-reported numbers as provisional until re-run one-at-a-time yourself.

**A plain background Bash command — not just a sub-agent — can also die silently, and the notification's status field alone is meaningless.** Confirmed 2026-09-07 (project-list-fix verification): a backgrounded `npx playwright test` run showed status `stopped` with a `[killed]` output file (zero real content) after a session gap — same "no completion record" failure class root `CLAUDE.md` already documents for `ceo-orchestrator`, but here it hit a bare shell command with no agent involved at all. Treat *any* long-running background command the same way: don't conclude success or failure from the notification status word, open the actual output file and check it has real content before deciding whether to trust it, resume it, or just re-run.

**Don't background a command yourself (a trailing `&` writing to a log file) while *also* passing the tool's own `run_in_background: true`.** Doing both double-backgrounds it: the tool tracks only the outer wrapper script, which — because it just starts the `&`'d job and returns — reports "completed" in seconds, while the actual long-running process keeps running fully undetached from the harness's own tracking. Confirmed same session: a `... > log 2>&1 &` wrapper reported instant completion while the real Playwright run underneath took 3.4 minutes, invisible to the notification system the whole time — only found by `ps aux | grep playwright` and manually tailing the log. Use the tool's own `run_in_background: true` directly on the real long-running command; if a script must detach a child process itself for some other reason, don't also mark that Bash call backgrounded — poll `ps`/the log file yourself instead of waiting on a notification that will never accurately reflect the child's real state.

**A stopped orchestrator can skip a whole recipe step silently, not just stop with incomplete work at the step it was on — and the stack it leaves behind can look fully healthy anyway.** SHELL-6 (2026-09-07): a `ceo-orchestrator` given "stand up an isolated env + implement + write 3 layers of tests" stood up the compose stack, got a green `/api/health`, implemented both the backend route and the frontend component, and wrote 2 of 3 test-layer files — but died before ever running the DB-clone step, and nothing in the stack's own state signaled that: containers up, health check green, only the *first* integration test run surfaced it (`UndefinedTableError`, see `backend/CLAUDE.md`). **A green health check proves the app booted, not that every setup step in the recipe actually ran** — after resuming/picking up a stopped orchestrator's isolated-env work, independently walk the recipe's own steps (`e2e/CLAUDE.md`) and verify each one's actual postcondition (DB row counts, `alembic_version`, not just "containers are Up"), don't assume a healthy-looking stack means the whole recipe completed.

**When a long verification session moves across several subdirectories (`backend/`, `frontend/`, `e2e/`, repo root) with other tool calls (Edit/Write) interleaved between `cd`s, don't rely on remembering which directory the shell is still in.** `cd` into each command chain explicitly (absolute path, or a leading `cd <dir> &&`) rather than assuming an earlier call's `cd` is still in effect — a stale assumption produced a `test.describe()`/`No tests found` Playwright error that read exactly like a real breakage (SHELL-6, 2026-09-07) and cost a confusing round-trip before the actual cause (running from the wrong directory) was found.

**A died agent can leave one file mid-refactor — imports changed, body not — and this doesn't announce itself the way a "disguised as correct" or "skipped a whole step" failure does; the diff's own size is the tell.** DS-2 (2026-09-08): a `ceo-orchestrator` given "implement DS-2 fully" died silently (again, no completion record — see below) after correctly migrating `EntityTable.tsx` and writing a well-reasoned `container/Table.tsx`, but `OrgHome.tsx`'s own migration was left exactly half-done: its `@coreui/react` import list had `CPagination`/`CPaginationItem`/`CTable`/`CTableBody`/`CTableHead` removed and a new `DEFAULT_PAGE_SIZE` constant added, but the JSX body still rendered raw `<CTable>`/`<CPagination>` and still referenced the now-deleted `PAGE_SIZE` — a file that would fail `tsc --noEmit` immediately, not a subtle behavioral gap. The tell wasn't a code smell inside the file — it was `git diff --stat` itself: a migration this size (replacing a hand-rolled table+pagination block with a shared container) should touch far more than the 27 lines/21 insertions this file's diff showed, once every other migrated file was 2-4x that size for the same class of change. **When picking up a died agent's work, compare each touched file's diff size against what the claimed change should plausibly require — a suspiciously small diff for a "full migration" is worth an immediate `tsc --noEmit`/build check before trusting it, not just a `git status` glance that the file was touched at all.**

**A backend response-*shape* change (not a route-reachability change) can break an existing frontend caller nothing in the same commit touched, and neither TypeScript nor Vitest mocks will catch it — only a real running instance will.** DS-2 (2026-09-08): changing `GET /orgs/{org_id}/role-assignments` from a bare array to the standard `{items,total,page,page_size}` envelope was the ADR's own explicit, deliberate decision — but `RoleAssignmentsPanel.tsx`/`lib/api/roleAssignments.ts` (the route's one existing caller, untouched by the orchestrator's own migration scope) still declared `Promise<RoleAssignmentSummary[]>` locally. `tsc --noEmit` was clean (the frontend's own type declaration was internally consistent, just wrong relative to what the server now actually returns — nothing in this codebase generates frontend types from the backend's Pydantic schemas, so nothing links the two), and the existing Vitest suite was clean too (its mocks were hand-typed to match the *old* shape, so they kept "returning" what the test expected regardless of what the real route now did). The break (`assignments.map is not a function`, an uncaught render exception with no error boundary, crashing the *entire* Dashboard page — not just the role-assignments panel) surfaced only when a real browser actually loaded the page against the real backend, found via a throwaway Playwright debug script per this file's own "verify empirically" testing note. **Before shipping any backend response-*shape* change (adding/removing/renaming a field, wrapping a bare list in an envelope), `grep -rn "<route path>" frontend/src/lib/api/` for every existing caller and update it in the same change — this is the same "audit for existing callers before changing a contract" discipline `backend/CLAUDE.md`'s route-restriction notes already teach, just for the response body instead of the route's reachability, and specifically NOT something the type system or mocked unit tests can be trusted to catch on their own.**

**A backgrounded shell command's `agentId`/task-id from a prior Claude Code session is not resumable in a new session, even via `ListAgents`/`SendMessage` — treat it as gone, not paused.** DS-2 (2026-09-08): a `ceo-orchestrator` launched via `Agent(..., run_in_background: true)` died silently mid-task (the standard, already-documented failure mode); a follow-up user message in a *new* session referenced the same task via its own auto-generated notification, but `ListAgents` in the new session didn't list it, and there was no way to `SendMessage` it a resume instruction — the agent's context, and the ability to continue it in place, existed only within its original session. **The recovery in this situation is not "resume the agent" (that handle is gone) but "read what it left on disk directly and continue the work yourself"** — same "on-disk artifacts often further along than the last transcript message" instinct this file's other died-agent notes already teach, just without the resume-round-trip option being available at all once the session boundary has been crossed.

**Every subsequent `docker compose` command against a named isolated stack must repeat *both* `-f` flags, not just the stack's original `up` — omitting them on a later rebuild silently recreates dependent services from the base compose file alone, dropping the override.** DS-2 (2026-09-08): after standing up `testnexa-ds2-test` correctly (both `-f docker-compose.yml -f docker-compose.override.test.yml`), a later mid-session `docker compose -p testnexa-ds2-test build backend` + `up -d --build backend` (no `-f` flags, habit from a plain single-service rebuild) recreated **`postgres` too** — not just the named `backend` service — using the base `docker-compose.yml`'s own defaults, silently dropping the override's exposed `5432:48214` port mapping (the named volume itself was untouched, so no data was lost, only the host-reachable port). `docker ps` still showed `postgres-1` as `Up (healthy)` with no visible sign anything had changed; the only tell was every `backend/tests/integration/` run refusing to connect to `localhost:48214` a few minutes later. **Treat the `-f docker-compose.yml -f docker-compose.override.test.yml` pair as mandatory on *every* compose invocation against an isolated stack for its whole lifetime, not just the initial `up` — recreating even a single named service can pull in the whole dependency graph under whatever config Compose was actually given that time**, and re-verify the override's own effect (`docker ps`'s port column, not just container status) after any rebuild, the same "verify the postcondition, not just that the command exited" discipline this file's DB-clone note already establishes for a different step.

**A sub-agent can die to an explicit provider error (a rate limit, not a silent stop) and still leave behind genuinely correct, unmodified-needed work — but only for the narrow scope it was actually given.** Confirmed EXEC-2 (2026-09-07): a `ceo-orchestrator` given "write and run an e2e spec for feature X" died mid-task with a `429`/session-limit error right after starting the Playwright install step, before ever confirming a green run. Independently reading its half-finished worktree found a complete, well-reasoned spec file — every `data-testid` it referenced was cross-checked against the real component and matched, its seed/cleanup scripts followed the established per-story pattern correctly, and it needed zero edits once actually run (twice, to rule out a fluke). **But its own scope never included checking sibling test files for a regression its own feature could trigger** — a new auto-appended-log side effect (this same session's own backend change) broke two *other*, pre-existing e2e specs' cleanup scripts, and only running those alongside the new spec (not something the agent was asked to do) surfaced it. Lesson: a died-mid-task agent's on-disk artifact can be trustworthy *within its literal assigned scope* without a second thought once independently verified — but a narrow scope is still narrow, and "did this feature's own change break anything nearby" is a separate check the agent was never asked to make, not a gap in its work.

**The above was about a narrow-scope task; a full-scope one (stand up an env + implement + write all 3 test layers + verify) can die the same way and still come back nearly complete — how far it got matters more than how big the ask was.** SHELL-7 (2026-09-09): a `ceo-orchestrator` given the entire task died to a `429`/session-limit error, but its transcript showed 98 tool calls over ~50 minutes and its on-disk state was implementation + all 3 test layers written + passing + committed-quality, missing only the final report. Independently re-running everything (tests, `tsc`, live env checks) confirmed all of it was correct and needed zero rework. Contrast the EXEC-2 case above (died at step 1 of many, ~narrow scope by necessity) with this one (died at the last step of a huge scope) — both are "trust but verify," but *when* in the task an agent died is a better predictor of how much independent work remains than the size of the original ask.

**`Agent(isolation: "worktree")` doesn't expose an explicit base-branch parameter the way `git worktree add -b <name> <base>` does, so the usual "`git log -3` the worktree before trusting it" defense (this file's own "Git / worktrees" section) isn't directly available before the agent's task even starts.** Verify the resulting work's correctness through its *content* instead — does it reference `data-testid`s, routes, or symbols that actually exist in the target files, cross-checked with a direct `grep`, not just "does it look plausible." Confirmed EXEC-2: every test-id the sub-agent's spec referenced was independently grepped against the real component source before the spec was trusted enough to run — this is what caught (by *not* catching anything, i.e. a clean cross-check) that the agent's worktree had in fact branched from the right place, without ever needing to inspect the worktree's own git history directly.

**A related, more basic version of the same gap: telling `Agent(isolation: "worktree", ...)` in its own prompt text to "work only inside `<a specific worktree path you already created>`" does not make it use that worktree** — the tool creates and hands the agent its own new auto-generated one (`.claude/worktrees/agent-<id>/`) regardless of what the prompt says, and the agent works there instead. Confirmed 2026-09-08 (the AdminLTE migration): a worktree was manually created (`git worktree add .claude/worktrees/design-system-adminlte -b design-system-adminlte main`) specifically so the orchestrator's prompt could point at it by path — the orchestrator instead worked in its own tool-assigned `.claude/worktrees/agent-a962893620c220749/`, and the manually-created one sat untouched at the base commit for the entire task, discovered only when `git status --porcelain` on the *expected* path kept showing zero changes while IDE diagnostics were clearly firing on live edits elsewhere. **When launching `Agent(isolation: "worktree")`, don't pre-create a worktree for it to use — `git worktree list` immediately after launch to find the path the tool actually assigned, and check/report progress against *that* one.** The manually-created, unused worktree in this case was harmless (just deleted once the mistake was found) but is exactly the kind of orphaned artifact this file's own "stray override file"/"untorn-down container" notes already warn about — clean it up (`git worktree remove` + `git branch -D`) once confirmed empty, don't leave it sitting there for a future session to puzzle over.

**A died sub-agent's own new test file can be a genuine bug-*discovery* artifact, not just partial implementation work to resume from — treat it as a lead to independently verify, not only as code to trust or distrust.** DASH-2's verification pass (2026-09-07): a `ceo-orchestrator` asked to "stand up an env, close test-coverage gaps, verify" died silently (no completion record) but left behind a well-reasoned backend integration test file, including one test explicitly titled as a "characterization test" proving a `409` on a code path nobody had ever exercised before — `DELETE /projects/{id}` against a Project created through the app's own real create route. Running that test confirmed a genuine, previously-unknown product defect (see `backend/CLAUDE.md`'s "delete-path completeness" note) that had existed since the route shipped, weeks earlier, simply because no prior test or UI caller had ever combined "row created via its own real create route" with "then deleted via the generic factory." The agent wasn't asked to hunt for this — it surfaced as a side effect of writing thorough, real-route-based test fixtures instead of minimal direct-ORM ones. **When picking up a died agent's on-disk test files, actually run them and read what they assert, even ones that look like routine coverage-gap filling** — a test's own docstring claiming to characterize "today's actual behavior" is worth a second look at whether that behavior is actually correct, not just whether the test passes.

**When even the tool's own `run_in_background: true` dies to a session gap (not the double-backgrounding mistake already documented above — a *properly* single-backgrounded command, killed anyway), `nohup ... > logfile 2>&1 & disown` detaches the process from the harness's own tracking entirely and survives where tool-level backgrounding didn't.** Confirmed DS-3 (2026-09-08): a `pytest`/`playwright test` pair launched via the tool's own `run_in_background: true` each showed `[killed]`/empty output after a session gap, twice — genuinely no progress, not a stale-notification false alarm (root cause: the harness process itself restarts across a session boundary, taking every process it was tracking with it, tool-level backgrounding included). Re-launched the exact same commands as `nohup env VAR=val cmd > /tmp/log 2>&1 & disown`, confirmed with `ps aux` that the PID survived detached from the shell, and polled `/tmp/log` directly (a plain file, unaffected by session boundaries) instead of relying on a task notification. This is a different failure mode from "double-backgrounding" (that one *finishes falsely fast because the wrapper backgrounds itself and returns*) — here the command was correctly single-backgrounded and still died, because the whole harness process — not just the shell — went away. **Reach for `nohup ...  & disown` + a plain log file specifically when a command needs to survive a session gap that might land mid-run, not as a routine replacement for `run_in_background: true`** (which is still correct and sufficient for anything that finishes within one session).

**A conversation's own context-refresh at a new session boundary is a free numbering/architecture-drift check — read what it re-injects before continuing a long-running numbered-artifact task, don't wait for a manual re-check.** DS-3 (2026-09-08): mid-task across a session gap, the next turn's system-reminder re-injected root `CLAUDE.md`'s *current* content verbatim — which already contained an `ADR-0043`/`components/shared/`-retired line from a sibling story (atomic-design tiering) that had merged to `main` while this session's own worktree sat untouched. The collision (this session's own new ADR, independently numbered `0043`) was found by *noticing the injected content disagreed with what this session had itself written minutes of wall-clock-equivalent earlier* — not by a deliberate `git fetch`/`git show origin/main:...` re-check (though that's still the right *confirming* step, per this file's own numbering-collision recipe below). **Treat a session boundary's own re-injected file contents as a first-pass drift signal worth reading closely — if a just-injected `CLAUDE.md`/doc excerpt names an ADR number, directory convention, or WBS row your own in-flight work also claims, that's the numbering-collision check firing itself, confirm it with the usual `git fetch` before either accepting or renumbering.**

**A long session's staleness risk isn't only numbered artifacts (ADR file numbers, WBS rows, Test-Design sections) — a sibling story merging mid-session can retire the *directory convention* your own in-flight code targets, which is a rebase-required blocker, not a renumber-required one.** DS-3 (2026-09-08): the same atomic-design-tiering merge above (ADR-0043) didn't just take a number — it deleted `components/shared/` outright and relocated every component there (`FormField`, `FeaturedCard`, `WidgetStatsTile`) into `atoms/`/`molecules/`/`organisms/`/`templates/`. This session's own new `InfoBox` component had been built at `components/shared/info-box/`, and `OrgHome.tsx`'s import of it now points at a location convention that no longer exists on `main` — not a cosmetic conflict, a `tsc --noEmit`-breaking one once rebased. **The existing "re-check `main`'s current state before finalizing a new number" recipe (below) needs a second half for a long session: also check whether a foundational location/architecture convention your own code depends on (a directory an ADR governs, not just a number) is still current** — `git log --oneline -10 -- docs/adr/README.md` or a quick skim of the ADR index's own newest rows will surface a "supersedes ADR-00XX's directory-location decisions"-shaped title before it surfaces as a broken import path at rebase time.

## Testing

Three layers, all real (not mocked-everything):

- **Backend unit** (`backend/tests/unit/`) — pytest, no DB/network.
- **Backend integration** (`backend/tests/integration/`) — pytest + httpx against a *live* server (`TEST_API_BASE_URL` env var), real Postgres. The package-level `conftest.py` skips the whole suite cleanly if no live server is reachable — don't fight that, bring the stack up first.
  - If a test file uses the shared `app.db.session.AsyncSessionLocal` engine directly for seeding/cleanup, the pytest run needs a **session-scoped event loop** (`asyncio_default_fixture_loop_scope = "session"` / `asyncio_default_test_loop_scope = "session"` in `pyproject.toml`, already set) — asyncpg connections can't hop event loops, and pytest-asyncio's default is a fresh loop per test.
- **Frontend unit** — Vitest + React Testing Library.
- **E2E** (`e2e/`) — Playwright, real browser, full stack, `E2E_BASE_URL` overridable.

Every FR/NFR traces to a test case in `docs/test-cases/`. When implementing a story, check that doc's coverage for the story ID before considering it done — 100% means every TC for *that story's own scope* has a passing automated test, not that every TC in the file (some belong to other, not-yet-built stories) is green.

**A task scoped narrowly as "close the test-coverage gap to 100%" can still require finishing a small slice of otherwise out-of-scope implementation, if one TC's literal wording names an integration point nothing has built yet.** DS-2's own coverage-audit pass (2026-09-08) found most of TC-DS-009..018 already satisfiable against the existing (if partly died-mid-task) implementation — except TC-DS-017 (the nested-table ARIA-exclusion proof), which specifically requires an *outer table already migrated onto the shared container* to have anything real to assert against; `ProjectDetail.tsx`'s Releases table hadn't been touched yet. Writing a test against unmigrated code would either be meaningless (asserting behavior of code that doesn't exist) or silently pass by testing nothing (a nested-`<ul>` check that's trivially true because nothing changed). The right call was migrating that one table (server mode, minimal footprint, not the other three ProjectDetail tables still pending) specifically to make the TC's own literal claim testable, then writing the test — not stretching the TC's wording to fit what already existed, and not silently skipping the TC as "blocked." **When a specific TC can't be satisfied by any test against the current code, that's a signal the task's own scope needs a small, explicitly-flagged implementation slice — not a reason to leave the TC uncovered or write a test that doesn't actually exercise the claim.**

**Match a TC's literal wording, not a semantically-adjacent assertion.** A test case that names a specific action (e.g. TC-REQ-004's "add 3 steps, **reorder**") needs a test that actually performs that literal action — an "add steps and edit one field" test doesn't satisfy a TC that also says "reorder," even though both fall under the same general "TestStep CRUD" umbrella. This gap shipped and sat undetected through one full doc-propagation pass before being caught (REQ-2, 2026-09-06) — when auditing coverage, read each TC's `Steps`/`Expected result` cells word-for-word against what the test file actually does, don't pattern-match on the general shape.

**A test file's own docstring claiming "TC-X is already covered by test Y + test Z" is a claim to verify, not a fact to trust.** EXEC-1's own coverage audit (2026-09-07) found exactly this: a well-written, specific-sounding docstring in `test_exec1_dashboard_and_history.py` named two real, passing tests as jointly covering TC-EXEC-001's literal "immediately readable via `GET /test-executions/{id}`" clause — but neither actually did an HTTP `GET` on that route; one read the row back via a direct ORM `session.get()` (proves the row exists, not that the route works), the other never read it back at all. The docstring read as authoritative specifically because it cited real test names and a real (if wrong) argument — that's what made it easy to accept without checking. **Whenever a coverage claim points at "see test X" instead of containing its own assertion, open test X and confirm its actual `assert` lines satisfy the TC's literal wording** — don't accept the pointer itself as coverage.

**A TC/test-design row written *before* the implementation exists can bake in a wrong assumption about EXISTING code, not just about the feature being planned.** SHELL-6's own test-design §31/TC-SHELL-018 (authored in a docs-only pass, before any code) assumed the sidebar's "Admin" nav group was permission-gated and named it as the assertion for "target org's own permissions govern post-switch rendering." It isn't — `AppSidebar.tsx` renders that group unconditionally whenever the route carries an `:orgId`, regardless of role. This wasn't caught at doc-review time (nothing in the doc pass touched `AppSidebar.tsx`) — it surfaced only when actually writing the e2e assertion against real rendered output, at which point the row had to be corrected before the test could be written at all. **When a test-case doc makes a specific claim about how an *existing* screen/component currently behaves (not just what the new feature should do), grep the actual source for that claim before writing the automated test against it** — a docs pass that never opens the file it's describing can get "this button is permission-gated" wrong exactly as easily as it can get a new feature's own behavior wrong, and the mistake won't surface until implementation, not at doc-review.

**`TestLevel`/`TestType` (and any other global-catalog lookup entity) ship with full CRUD but zero seeded rows** — confirmed empty on `main` itself, not just a freshly-cloned stack (2026-09-06). A fresh manual-test handoff hits this immediately: the `TestCase` create form's level/type dropdowns are empty, blocking the most basic manual walkthrough with no error, just nothing to select. Full CRUD existing is not the same claim as "usable out of the box" — if you're handing an environment to someone for manual testing and the story touches `TestCase` creation at all, seed a handful of rows first (same `docker exec -i <backend-container> python -` pattern as any other hand-seed) rather than assuming the catalog is populated. Whether these ship with a permanent default seed (like RBAC-4 seeds `Role`/`Permission`) is an open product decision for a future story/ADR, not something to silently decide inside a docs or verification pass.

**Reading a library's own source to predict its runtime behavior is not the same as observing it, and can actively mislead.** Migrating `AppSidebar` off `@coreui/react` (2026-09-07, ADR-0037), a static read of `CSidebar`'s TypeScript source produced a confident, wrong prediction about which CSS class (`show` vs `hide`) a mobile-viewport toggle click should apply — the source has real effect-timing/ordering subtlety (multiple `useEffect`s reading and writing overlapping state across renders) that doesn't resolve the way a linear read suggests. The mistake shipped, then was caught immediately by the existing e2e test (TC-SHELL-004) actually failing — not by re-reading the source harder. The fix came from running the *real, unmodified* component in a live browser (a still-running isolated stack from an earlier, unrelated task in the same session, reused specifically as a behavioral oracle) and reading the actual class output before/after a real click, then reverse-engineering the simplest rule that matched. **When hand-reimplementing a library component's behavior, verify the target behavior empirically against a live instance of the original before trusting a source-reading-derived prediction** — a component's source is a hint about what to test, not a substitute for testing it.

**A visual screenshot cannot reveal exact CSS class names, and this cost three real round-trips before the actual technique corrected course.** Matching the CoreUI free-template demo pixel-for-pixel (SHELL-2 breadcrumb, 2026-09-07) went through padding, then container type (`container` vs `container-fluid`), then vertical spacing as three *separate* mismatches, each only found after a screenshot comparison failed to explain the difference and the actual computed styles/class strings were pulled and diffed side-by-side. A `WebFetch` of the demo URL is even less useful for this than a screenshot — it converts the page to lossy markdown and loses all CSS/class/DOM structure entirely, good for reading text content, useless for visual/structural fidelity. **For any "make this match a reference site" task, skip straight to a real headless browser (Playwright) reading `getComputedStyle`/`className`/`outerHTML` on both sides — a screenshot is a sanity check on the result, not a diagnostic tool for the mismatch.**

**Reciting a previously-established "known harmless" explanation for a skip/failure without re-deriving whether it still applies under your *current* test configuration is the same trust-without-checking mistake this file already warns against for sub-agents — caught myself doing it, not just a sub-agent, EXEC-2 (2026-09-07).** `e2e/CLAUDE.md` documents a specific bare-`/health`-via-nginx skip as "known harmless" — but that explanation is conditional on `TEST_API_BASE_URL` pointing at nginx. Partway through EXEC-2's verification I switched `TEST_API_BASE_URL` to point directly at the backend container (to work around a *different*, unrelated skip), which structurally invalidates the nginx-specific explanation — bare `/health` is reachable directly on the backend. I nonetheless reported the run's 3 skips as "known-harmless" twice more afterward, from memory of the old explanation, without ever actually running `pytest -rs` to check what those 3 skips currently were. Whether they were in fact the same ones or something new was never confirmed. **A "known harmless" tag is scoped to the exact conditions that produced it — re-verify the tag still applies (rerun with `-rs`/`-v` and read the actual skip reason) any time a relevant variable changes (here: which URL `TEST_API_BASE_URL` points at), don't carry the old label forward from memory.**

**Don't rerun a verification command later in the same session against a stack you already tore down — check `docker ps` first, every time, not just the first time.** Confirmed EXEC-2 (2026-09-07): immediately after tearing down the isolated stack (containers, volumes, network all removed, confirmed clean), a later turn's habitual "run the integration suite" produced a 60KB wall of `Connection refused` skips — the command was copy-pasted from earlier in the session without checking the target was still up. Caught before it reached the user only because the raw output was inspected before summarizing it, not because anything in the command itself signaled the mistake (pytest's own skip-guard reports this as a clean, valid skip reason, not an error). Same instinct as this file's own "don't take a sub-agent's self-report at face value" rule, aimed at a much simpler failure mode: a stale assumption about environment state that a five-second `docker ps` would have caught before spending two minutes running (and then having to explain) a meaningless result.

**A CSS layout/height question cannot be answered from source alone, and Vitest/RTL can't answer it either (jsdom does no real layout — see `AppShell.tsx`'s own docstring) — write a throwaway script against a live isolated stack instead.** DASH-2's "make the content fill the content area" task (2026-09-07) was diagnosed and verified entirely via a disposable Node script (`require("@playwright/test")`, copied into `e2e/` so `node_modules` resolves, deleted immediately after) that logged in, navigated real routes, and diffed `getBoundingClientRect()` on the exact DOM path across several pages before and after each change — this is what distinguished "genuinely not filling" (`Dashboard.tsx`, ~104px of ~795px available) from "already fills via a different, pre-existing mechanism" (`OrgHome` and 4 other screens' own `min-vh-100` full-bleed convention, confirmed equal to the pixel) without guessing from either file. **When a user asks to extend a layout fix "to all pages," remeasure each page live rather than assuming the same root cause applies everywhere** — forcing a uniform code change onto a page that already achieves the goal a different way can be a no-op (adding `height:100%` to a plain unstyled wrapper div with nothing painted inside it changes nothing visible) or actively wrong (adding it to a `CCard` that sits *after* a sibling heading, rather than inside a `CCardBody`, makes the card overflow past its container by exactly the heading's own height — needs `flex-column`+`flex-grow-1` on the parent instead of a plain height utility). See `frontend/CLAUDE.md` for the exact class-level rules found.

## Architecture decisions are ADR-first

Every stack/architecture choice in this repo has an ADR in `docs/adr/` (MADR-style: Context/Decision/Consequences/Alternatives). Before making or changing one:

1. Check `docs/adr/README.md` — it might already be decided.
2. If you're changing a prior decision (like this file's CoreUI-vs-Tailwind change did to ADR-0009), write a new ADR and mark the old one's status `Partially superseded` / `Superseded`, don't silently edit history.
3. Requirements/WBS/API/Database docs get updated to match whenever an ADR changes something they document — see how ADR-0011 (login rate limiting) propagated across 7 docs in this repo's history for the expected scope of that propagation.

**Plan-with-open-questions before code (the MCP-1 working pattern).** For any non-trivial story, before writing code, draft a written plan that enumerates: scope, affected files, edge cases, **explicit open questions** with your recommended default for each, and the checklist you would execute if the user said "go with default." The user reads the questions, picks or adjusts one or two, replies "go with default," and you ship against a complete spec — no mid-flight "wait, should it be X?" interruptions. This cost ~10 minutes of plan-writing up front and saved the entire implementation cycle from ambiguity churn on MCP-1 (8 explicit questions, user answered with one word, the plan executed unchanged). The questions don't have to be exhaustive — the goal is "no decision surprises the user didn't see ahead of time," not "predict every choice up front."

**Not every task is a doc-propagation trigger — check applicability per doc before writing any of them.** Asked to update Requirement/WBS/ADR/Database/API/UI-Design/Sitemap/Test-Plan/Test-Design/Test-Case docs for a local dev-env port fix (gitignored `docker-compose.override.test.yml`, no code/schema/API/UI surface at all), the right call was a doc-by-doc "no ADR was triggered, so none of these apply" table, not writing something into all ten for the sake of completing the list (2026-09-06). Same instinct as the `TestLevel`/`TestType` seeding note above: whether a doc update is warranted is a judgment call to make and state explicitly, not something to do reflexively because a checklist named the doc.

**A second concrete "no new ADR" case, distinct from the port-fix example above: wiring a frontend screen to a backend route that already exists.** `OrgHome`'s Project-list bug fix (2026-09-07, found during EXEC-1's manual-test handoff) needed `GET /projects?org_id=` — but that route already shipped under ADR-0022's generic factory and was already in production use by the SHELL-3 dashboard widget's `getProjectsTotal`. The fix was `OrgHome` finally calling an existing, already-documented route instead of keeping its list in local `useState`. No new backend surface, no new architecture decision — just Requirements/WBS/Sitemap/Test-Plan/Test-Design correction notes and a new TC, explicitly justified in the commit rather than assumed. The general rule this and the port-fix case both instantiate: **a new ADR is warranted by a new architecture *decision*, not by every change that happens to touch a documented area** — check whether the thing you're building already has an ADR covering its shape before assuming one is needed.

**A UI Design Document's prose and any layout sketch it includes must agree with each other, not just each be internally sensible.** ADR-0032's UI Design Document described a new sub-list as going "directly below" an existing one in its prose, while its own ASCII layout sketch a few lines later showed it above — nobody caught the contradiction at doc-review time, so the implementer had to pick one (documented as an open judgment call in the completion report, not silently absorbed). Cheap to prevent, expensive to leave for later: when a doc pass includes both a prose description and a sketch/diagram of the same layout, read them against each other before considering the doc done, the same word-for-word discipline this file already asks for when auditing TC coverage against a test file.

**ADR-vs-implementation drift must surface in the completion report, not get silently absorbed.** When an ADR's prose describes a scope the implementation doesn't fully ship (e.g. ADR-0033 said "create_test_case → direct-link OR rigor-path" but MCP-1 only shipped the direct-link branch), the right move is to call the drift out explicitly in the final summary — what's shipped vs what the ADR documents, with a forward-pointer to whatever closes the gap. The ADR's own Status field should not be edited to match; instead, a "Drift" line in the completion report + a backlog WBS row (`5.2a` in MCP-1's case) is the honest record. Future readers grepping the ADR find the truth; future stories grep the WBS backlog find the gap to close.

**Code landing on `main` with zero doc propagation is now a confirmed, recurring pattern in this repo's history, not a hypothetical to guard against — a docs pass auditing one story should also glance at what else landed nearby.** DS-2's own docs pass (2026-09-07/08) found two independent instances of this in the same session: `feat(frontend): add Button atom + ButtonStack molecule` (PR #39) and `feat(frontend): add WidgetStatsTile shared component, replace OrgHome CWidgetStatsA/B` (PR #41) both merged to `main` with no ADR, no FR/NFR row, no user story — real shared-component surface (the exact kind DS-1/DS-2's own `components/shared/`-vs-`container/` distinction governed — `components/shared/` itself is retired 2026-09-08 by [ADR-0043](docs/adr/0043-atomic-design-tiering-for-frontend-components.md), `container/`'s own axis unaffected) that this repo's own ADR-first policy should have caught. Neither was this session's own scope to fix, and neither was silently absorbed into DS-2's docs — but the pattern itself is worth naming: **when doing a docs-propagation pass for one story, a quick `git log --oneline -20 -- frontend/src/components frontend/src/container backend/app/api/routes` (or similar) against the doc index's own last-updated point is a cheap way to catch a sibling gap already sitting on `main`, rather than assuming ADR-first only needs enforcing on your own current change.**

**A defect found AND fixed the same day, mid-verification-pass, still gets its own new ADR — don't retrofit the fix into the ADR whose own verification found it.** DASH-2's verification pass (2026-09-07) found that wiring a UI "Delete" button to an already-shipped route exposed a real, pre-existing FK-constraint bug (`role_assignment.project_id`'s `ON DELETE RESTRICT` permanently blocking deletion of any Project created through the app's own UI). The fix (change the FK to `CASCADE`) landed in the same session, a couple of hours later — but it got its own ADR (0040), not a silent edit to ADR-0039's own Decision/Consequences text. ADR-0039's Consequences section still reads exactly as it did when the defect was found ("deliberately NOT fixed in this same pass... needs its own ADR"), with a one-line addendum added pointing forward ("Resolved the same day, ADR-0040 — see that ADR for the fix"). This is the same "flag drift, don't silently absorb" instinct as the paragraph above, applied to timing rather than scope: **finding and fixing a bug fast doesn't collapse the two into one artifact** — the original ADR's text is a historical record of what was found and when, the new ADR is the record of the decision that fixed it, and a reader tracing history later needs both, not a rewritten single version that erases the fact a defect ever existed.

## Auth & security conventions (ADR-0003, ADR-0011)

- Passwords: argon2 via passlib, explicit cost params, never logged in plaintext anywhere (app logs, tracebacks, request-logging middleware).
- Human login: JWT access token (short-lived) + opaque refresh token, refresh token hash stored server-side (`refresh_token` table, revocable), raw refresh token delivered only via an httpOnly cookie — never in a JSON body.
- Login is rate-limited: 5 failed attempts per `(client_ip, email)` per 15 minutes → 429; resets on a successful login for that pair.
- Unknown email and wrong password return the **identical** generic 401 body — no user-enumeration leak, timing-safe (always run the password-verify code path, real hash or a fixed dummy hash).
- AI agents (`AIAgent`, joined-table-inheritance sibling of `User` under `Actor`) authenticate via a separate long-lived API-key bearer flow, never the human login route.
- **Seeded demo/test accounts must use a real-shaped email domain.** Inserting a `User` row directly (bypassing `POST /auth/signup`'s Pydantic validation) accepts any string in `email`, but `POST /auth/login`'s `EmailStr` validation permanently rejects IANA reserved special-use **TLDs** (`.local`, `.test`, `.invalid`, `.example`) with a `422` — the frontend then shows a generic "check your email and password" message that reads like wrong credentials, not a malformed address. `@example.com` itself is fine (verified against the live validator — only the reserved *TLDs* are blocked, not that specific second-level domain). Bit a real demo handoff, 2026-09-06 (see `backend/CLAUDE.md` for the full story).

## Multi-tenancy (ADR-0007)

Every tenant-scoped table carries a resolvable `org_id` path. Cross-tenant resource access returns **404**, never 403 — existence is never confirmable across an org boundary (NFR-1). Don't add a query that skips the `org_id` filter, generic or bespoke.

**When adding a new bespoke create route for an entity that already has a hand-written resolver** (`app/api/crud_factory.py`'s per-entity `resolve_org_id` functions), check the resolver's branches actually cover the row shape your new route produces — a resolver written before that create path existed has no branch for it, so the row inserts fine and then 404s as "unresolvable" on the very next read. See [ADR-0029](docs/adr/0029-testcase-resolver-direct-link-fallback.md) for the concrete case (REQ-2's direct-link `TestCase`) and `backend/CLAUDE.md` for the general rule. Test with a create-then-immediate-read round trip, not a create-only assertion — the latter cannot catch this class of bug.

## Git / worktrees

Feature work happens in an isolated git worktree (`.claude/worktrees/<name>`), one per story/task, so `main` and other in-flight work stay untouched. Don't `git stash` bare — the stash stack is shared across worktrees; use a WIP commit or a tagged `stash push -u -m "<unique-tag>"` instead.

**A worktree created before a docs-propagation pass finishes on `main` goes stale before implementation even starts.** This repo's own workflow is plan → confirm assumptions → write ADR/Requirements/WBS/etc. (on `main`) → *then* implement (in the worktree, on a later instruction) — but if the worktree was created at planning time (common, since `git worktree add` is one of the first steps), every doc commit that lands on `main` afterward is invisible to it. Confirmed 2026-09-06 (PLAN-3): the implementation worktree branched from a commit predating its own story's ADR/UI-Design-Document/Test-Design/Test-Case updates, so the shipped code referenced docs (`ADR-0033`, PLAN-3's UI Design Document) its own git history doesn't contain, and PLAN-2's screen section wasn't there for the new section to actually sit "directly below" the way the UI doc says — flagged as an open rebase-before-merge item rather than caught early. **Before handing a worktree to an implementation pass, `git log -1` it against the doc commits it's supposed to build on** — if the docs landed after the worktree was created, rebase the worktree onto `main` (or delete and recreate it) first, don't implement against a stale base and fix it at merge time.

**A valid alternative that sidesteps the staleness problem entirely: author the docs directly inside the worktree itself, as its own commit, rather than on `main` first.** EXEC-1 (2026-09-07) did this — the worktree was created, then the full ADR/Requirements/WBS/etc. propagation pass was written and committed straight into it (`docs(exec-1): ...`), with implementation landing in a second commit on the same branch. There is no rebase-timing risk here because nothing is landing on `main` out from under the worktree — the docs and the code that builds on them share one branch and one linear history. This only works if the docs genuinely belong to *this* worktree's own story (not a shared cross-story doc pass other worktrees also need); for a doc change multiple in-flight worktrees depend on, the original plan-on-`main`-then-rebase flow is still correct.

**A worse variant of the staleness problem: a brand-new worktree for a follow-on task defaults to branching off `main`, when it should branch off a specific in-progress, unmerged feature branch instead.** `git worktree add <path> -b <name>` with no explicit start-point branches off whatever's currently checked out — easy to do reflexively when a task is phrased as new ("convert the breadcrumb to raw HTML") but is actually a *continuation* of unmerged work sitting on another branch (the breadcrumb's own three pixel-parity fixes, `shell-breadcrumb-coverage`, not yet on `main`). Confirmed 2026-09-07 (the HTML-shell-migration task): a first worktree branched off `main` looked completely fine through several steps (ADR written and committed, a real DOM-dump probe ran and produced plausible-looking output, an isolated stack stood up healthy) — the actual defect (converting the *pre-fix* breadcrumb markup: no `container-fluid`, only 6 of 15 routes) was invisible until the DOM dump's own output was read closely enough to notice the classes didn't match what should have been there. **Before running `git worktree add`, ask "is there an unmerged branch this task should continue from, rather than `main`/HEAD?"** — if yes, pass it as the explicit start-point (`git worktree add <path> -b <name> <base-branch>`), not the default. If a worktree already exists and you're unsure, `git log -3 --oneline` it and eyeball whether the commits match what you expect the task to build on, the same instinct as the staleness check above but for the *branch*, not just *how recent `main` is*.

**When resuming or picking up after a stopped orchestrator, checking the worktree's branch/base is now part of the standard re-verification list, not optional.** The root cause above (wrong base) was found only because the whole worktree was discarded and redone from scratch after independently re-deriving the correct base — a `git log --oneline -5` on the worktree the very first time it was inspected would have caught it immediately, before any of the agent's other (otherwise perfectly fine) work was trusted. Add this to the existing "read what's on disk" checklist: `git status`/`git diff --stat` for uncommitted work, `docker ps`/`docker compose ls` for what's running, re-run test suites yourself — **and now also `git log --oneline -5` (or `git merge-base` against the branch you expected) to confirm the worktree's own history actually starts where the task needed it to.** A wrong base doesn't announce itself; everything built on top of it can look locally correct while being globally wrong.

**A worktree's own base-check at creation time is not enough for a long-running session — `main` keeps moving while you work, and every numbered doc artifact (ADR file number, WBS row number, Test-Design section number) is a landmine if two branches independently pick the same one.** Confirmed EXEC-2 (2026-09-07): the worktree branched cleanly from `main` at creation, `git log -1` checked and fine — but the session ran long enough (implementation, a full test pass, a sub-agent round-trip, more testing, this retro) that `main` advanced ~27 commits in the meantime, including two other stories (SHELL-6, then SHELL-2's own raw-HTML migration) merged via their own PRs. Neither branch could see the other's in-flight numbering choices — and the collision compounded: SHELL-2 had *already* renumbered its own ADR from a first-choice `0036` to `0037` after hitting SHELL-6's prior claim on `0036`, so by the time this worktree's own docs pass ran, **both `0036` and `0037` were taken**, not just `0036`. The result, found only during an end-of-session retro, hours later: EXEC-2's own doc-propagation pass had independently claimed `ADR-0036`, WBS row `11.20`, and Test-Design `§31` — all three colliding, needing renumbering to `0038`/`11.21`/`§32`, the actual next-free values at merge time, not the ones that looked free when the worktree was created. Even this file (`CLAUDE.md`) drifted the same way: `main`'s copy had picked up two other stories' retro paragraphs this worktree's copy never received, reconciled by hand during the same merge. This is not a new failure class for this repo — `git log` shows it's happened at least twice before this session alone (`0754f8a docs(admin-2): renumber ADR-0025 -> ADR-0026`, `1fd2060 ...resolve ADR-0024 numbering collision`), now three times counting SHELL-2's own — but it had never been written up as a standing rule, only fixed ad hoc each time it was hit. **The fix is not "check once at worktree creation" — it's "before finalizing any new ADR/WBS-row/Test-Design-section number, re-check `main`'s current state, not just your own worktree's":**

```
git fetch origin main   # or: git log --oneline HEAD..origin/main | head
git show origin/main:docs/adr/README.md | tail -5
git show origin/main:docs/test-design/2026-09-03-test-design.md | grep -n "^## " | tail -3
git show origin/main:docs/wbs/2026-09-03-project-scaffold-wbs.md | grep -n "^| 11\." | tail -3
```

Do this **right before writing the ADR file, and again right before merging** — a session that's still going after `main` has moved needs a second check, and a third if it keeps going; the number that was free at the start of the session is not guaranteed free at the end of it. If a collision is found, renumber your own worktree's new artifacts (never main's already-merged ones) before merging — same posture the historical fixes above already took. This is cheap insurance (one `git fetch` + three `git show`s) against a real merge-time mess (three separate documents needing hand-renumbering, cross-references to fix in each, plus a `CLAUDE.md` prose reconciliation).

**This risk isn't bounded to one continuous session either — a story worked across several separate top-level conversations over real wall-clock time hits the identical collision every time work resumes, not just within one long session.** Confirmed again, SHELL-7 (2026-09-08→09, docs pass / implementation pass / coverage-audit pass / teardown pass as four separate conversations): `main` merged two other stories' own `ADR-0044`/`ADR-0045`/WBS `11.27`-`11.28`/`§35`-`§36` in the gap, colliding with SHELL-7's own `ADR-0044`/`11.27`/`§35` — caught the same way the DS-3 paragraph below describes (a session-start context-refresh re-injecting `CLAUDE.md` content that disagreed with this branch's own numbers), then confirmed with `git fetch` and renumbered (`0044`→`0046`, `11.27`→`11.29`, `§35`→`§37`). A "continue" message from the user carries no implication that anything got re-checked in between — treat every fresh session on a long-lived branch as its own numbering-collision checkpoint, same as a long single session needs a second/third check.

**A transient network failure on that same `git fetch` can silently make `git log HEAD..origin/main` compare against stale data instead of erroring — check the fetch's own output before trusting the count.** Confirmed 2026-09-07 (DASH-2's own docs-and-fix pass): `git fetch origin main` failed outright (`Failed to connect to github.com port 443`) partway through a long session, but the very next `git log --oneline HEAD..origin/main | wc -l` still returned a number — comparing against whatever `origin/main` ref was left over from the *last successful* fetch, with zero indication anything had failed. One read in this exact session showed a startling "9 commits behind" that turned out to be exactly this (a failed fetch immediately followed by a stale comparison); a retried fetch a few seconds later succeeded and the true count was back to 0. **Read the fetch command's own output (or check its exit code) before trusting whatever `git log`/`git show origin/main:...` says next** — a failed fetch doesn't make the following commands fail too, it just makes them quietly answer a question about an older point in time.

**A long session juggling both the main checkout and a worktree can silently write to the wrong one, even when every individual `Edit`/`Write` call uses a full absolute path — not caught myself doing this until `git status` on `main` showed the damage.** EXEC-3's docs pass (2026-09-08): after reading files out of the worktree earlier in the session, a batch of doc edits used paths of the shape `/Volumes/.../testnexa/docs/adr/...` — correct-looking, but missing the `.claude/worktrees/exec-3-raise-defect/` segment, so every edit actually landed on the **main checkout**, not the worktree. Nothing about the tool calls themselves errored or warned; the mistake was only caught because a routine `git status`/`git diff --stat` sanity check on `main` (done out of habit, not because anything looked wrong) showed five modified files sitting on a branch that should always be clean. **The recovery, since the stash stack is shared across worktrees (this file's own opening line): `git stash push -u -m "<tag>"` on `main` to lift the changes off it, then `cd` into the actual worktree and `git stash pop`** — this moves uncommitted work between checkouts without re-typing any of it, and confirmed clean (`git status --porcelain` on `main` showing nothing beyond pre-existing untracked harness dirs) before continuing. **The actionable habit: after any batch of edits during a session that has touched both a worktree and the main checkout, `git status --porcelain` on *both* before moving on — not just the one you meant to be working in** — a full absolute path reads as unambiguous but is exactly as typo-prone as a relative one when the two checkouts share most of their directory structure.

**Two fully independent isolated Docker Compose stacks (different projects, different sessions, no shared Postgres) can still crash a Playwright Chromium process via plain host CPU/RAM contention — this is a different failure class from the already-documented same-stack-concurrent-run note.** EXEC-3 (2026-09-08): a full e2e suite run (`--workers=1`, one browser, one isolated stack) produced 24 failures clustered on plain `page.goto("/login")` timeouts and one `Protocol error (Runtime.callFunctionOn): Internal server error, session closed` — reading exactly like a real app-level regression or a broken login flow. `docker stats --no-stream` at that moment showed a **second, entirely unrelated isolated stack** (`testnexa-ds3infobox-test-*`, a different session's own task) with its backend container at 134% CPU on the same host. Confirmed as the actual cause, not the code under test: the exact same spec re-run alone (no other stack competing) passed clean three separate times, and two *pre-existing, untouched* specs (EXEC-1/EXEC-2) failed identically in the same batch run — a regression in EXEC-3's own new code cannot explain a failure in files EXEC-3 never touched. **When a full e2e run against a healthy, correctly-isolated stack still produces widespread browser-level timeouts/crashes, `docker stats --no-stream` before concluding it's a real bug** — Compose-project isolation only isolates containers/networks/volumes from each other, not the host's own CPU/memory, and another session's concurrent isolated stack is exactly as capable of starving your browser process as a resource-heavy step in your own.

**The 4th confirmed instance of the "wrote to `main` instead of the worktree" mistake above happened to the very next session (DS-3, 2026-09-08) despite the note already existing** — the prose warning alone isn't sufficient; the fix that actually works is running `git status --porcelain` on the worktree **before the first edit** of any docs-only pass, not just "after a batch." Caught this time only because the very first `git commit` inside the worktree said "nothing to commit" — a strong, unambiguous signal, but one that arrives after every edit has already gone to the wrong checkout and needs recovering (this time via `cp` each touched file from `main` into the worktree + `git checkout --` to restore `main`, a valid alternative to the stash-based recovery above when the touched-file set is small and known). **Make the pre-edit `git status --porcelain` on the target worktree the literal first tool call of any worktree-scoped task, not an occasional habit** — a check that only fires reactively (after a commit fails, or "after a batch") has now let the same mistake through three separate times.

**Unlike every prior "rerun the failing spec alone, it comes back clean" instance this file documents (including the very entry directly above), one spec broke that pattern outright — 4 different reruns, 4 different failure symptoms, never a clean pass, with `docker stats` confirming no sibling-stack contention on the final attempt.** DS-3 (2026-09-08): `exec1-record-execution.spec.ts` (pre-existing, untouched by this story) failed differently each time it was rerun alone against an otherwise-idle host — a "Signing in..." hang, then `page.goto("/login")` timing out entirely, then a genuine assertion mismatch (`dashboard-tile-pass-count` stuck at `"—"` instead of resolving to `"0"`), then a `page.getByLabel(/password/i).fill()` timeout — across roughly an hour of wall-clock time, with the isolated stack's own backend logs showing zero errors throughout. Every other spec run in the same window (the story's own new spec, twice; `shell-full-template.spec.ts`'s 4 cases) passed clean and consistent. **This was reported to the user as "flaky, likely still-unidentified host contention, not confirmed as a code regression" rather than either "safe to ignore" or "proven broken"** — the honest state is that this repo's own established "rerun alone resolves it" heuristic did not hold here, and that discrepancy itself is worth escalating (rerun once more on a verifiably idle host, or add a `console.log`/network-trace to the spec's own login step) before merging, not silently accepted as another instance of the already-documented pattern just because it superficially resembles one.
