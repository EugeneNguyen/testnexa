# ADR-0013: Refresh token rotation & session-persistence policy

**Date:** 2026-09-03
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0003](0003-auth-token-strategy.md) (auth & token strategy — establishes DB-revocable refresh tokens but not a rotation policy), [AUTH-2 story](../user-stories/2026-09-03-auth-stories.md), [AUTH-2 scope plan](../superpowers/plans/2026-09-03-auth-2-session-persistence-plan.md)

## Context

ADR-0003 decided *that* refresh tokens are DB-backed and revocable, but not the mechanics of `POST /auth/refresh` itself: whether a refresh token is reused across its whole lifetime or rotated on each use, what a rotated token's expiry should be, whether losing org access mid-session should be re-checked, and what "protected route" proves the whole flow works end to end. AUTH-2's acceptance criteria require both a silent, transparent renewal and real revocability (Marcus's compliance-context requirement) — these two pull in different directions if the rotation mechanics aren't pinned down, so this is a real architecture decision, not an implementation detail.

## Decision

- **Rotate on every use, single-use tokens.** `POST /auth/refresh` revokes the presented `RefreshToken` row (`revoked_reason="rotated"`) and issues a brand-new opaque token + row + cookie in the same response, alongside the new access token. A refresh token that's already been used once is unconditionally rejected (401) if presented again — this is what makes a leaked-and-replayed refresh token detectable/boundable rather than silently reusable for its full 30-day life.
- **Rotated tokens inherit the original session's absolute expiry, not a fresh 30 days per rotation.** The new row's `expires_at` is copied verbatim from the token it replaces (not recomputed as `now + 30d`). Since this propagates through every rotation in a chain, a session that started at login and is refreshed continuously can never silently outlive `JWT_REFRESH_TTL_DAYS` (30) from its true start — no schema change needed, `expires_at` copy-forward is sufficient, no separate "session id"/chain-root column required.
- **`/auth/refresh` re-checks active `OrgMembership`**, same as login: if the user now has zero `active` memberships (suspended/removed since login), reject with the same `403 no_active_organization` login uses. This is a non-destructive check — the refresh token itself is *not* revoked by this rejection, only the current attempt fails; if the org membership is reactivated before the token's `expires_at`, a later refresh attempt succeeds normally. Without this check, a compliance-context admin action (suspend a member) would have no effect on that member's already-issued session until the access token's own 15-minute TTL happened to lapse *and* the refresh endpoint had no reason to look past the token row — silently undermining the story's own "admin can revoke access immediately" premise.
- **No reuse-grace-window.** A rotated-out token presented again (whether from a genuine replay/theft or an honest multi-tab race, see Consequences) is rejected outright, no short grace period during which the immediately-prior token is still honored. Simplicity and a harder revocation guarantee are prioritized over smoothing the rare multi-tab race.
- **`GET /auth/me` is added as the minimal protected (bearer-token) route** this story needs to make the silent-refresh flow observable/testable at all — no other route requires an access token yet. Returns `{actor_id, email, actor_type}` only; the API design doc's fuller "+ resolved permission codes" contract is deferred until an RBAC story exists to resolve them, not blocked on that.
- **`RefreshToken.token_hash` gets a unique index** (not previously specified) — the refresh route's core operation is a `WHERE token_hash = ?` lookup on every renewal, a hot path once sessions persist across restarts; leaving it unindexed was fine when nothing read the column by value (AUTH-1 only ever wrote it), but AUTH-2 makes it a lookup key.

## Consequences

**Positive:** a stolen refresh token has a bounded window of usefulness (until the legitimate client's next refresh rotates it out, at which point *both* the thief's and the legitimate session's copies of the old token are dead — the legitimate client simply gets a new one transparently, the thief doesn't); absolute session lifetime is capped regardless of how often it's silently renewed, closing the "refresh forever, never re-authenticate" gap a naive per-rotation-reset policy would leave open; re-checking org membership on refresh makes admin revocation-by-suspension actually immediate rather than eventually-consistent on the access token's own TTL; the token_hash index turns the new hot-path lookup from a table scan into an index seek.

**Negative / Trade-offs:** genuine multi-tab race — two tabs whose access tokens expire within the same few hundred milliseconds can both fire `/auth/refresh`; the second one to have its `Set-Cookie` applied may present an already-rotated-out token and get a false 401, forcing that tab into a full re-login even though the session is objectively still valid in the other tab. Accepted as a known, documented gap for this pass (see AUTH-2 scope plan §3/§4) rather than silently absorbed by a grace window that would weaken the single-use guarantee this ADR is built around. Org-membership re-check adds one more query to the refresh path (acceptable — refresh is not a high-frequency-per-second route, it's bounded by the 15-minute access-token TTL).

## Alternatives considered

- **Reusable refresh token (no rotation), revoke-only on explicit action** — rejected: a leaked token stays valid for its full remaining lifetime with no way to detect the leak from usage pattern alone; weaker fit for a compliance persona than rotation.
- **Rotation with a fresh 30-day `expires_at` on every renewal** — rejected: turns "30-day refresh TTL" into "at most 30 days *since the user's last visit*," i.e. unbounded in practice for anyone using the app at least monthly. The absolute-expiry-inherited approach still requires a genuine re-login every 30 days regardless of activity, which is the actual security property ADR-0003 implied.
- **Reuse-grace-window (e.g. honor the immediately-prior rotated-out token for 5–10s)** — deferred, not rejected outright: a real mitigation for the multi-tab race, but adds complexity (a second valid-token state beyond "current"/"revoked") for a rare, self-resolving failure mode (worst case: one tab's user re-logs-in). Revisit if it proves disruptive in practice.
- **Skip the org-membership re-check on refresh** — rejected: would leave a suspended user's already-issued session silently renewable until its access token's next natural 15-minute expiry coincides with some other check catching it — there is no other check today, since RBAC enforcement on generic routes isn't built yet. Checking at the one choke point that does exist (refresh) is cheap and closes a real gap.
