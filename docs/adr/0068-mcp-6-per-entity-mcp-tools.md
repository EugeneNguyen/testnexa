# ADR-0068: MCP-6 — one MCP tool per entity per action (`tn_<entity>_<action>`)

## Context

ADR-0065 (MCP-5) shipped full CRUD over every entity through **six reflective tools** — `list_entities`, `get_entity`, `create_entity`, `update_entity`, `delete_entity`, `describe_entity` — each taking a `resource: str` argument naming the entity (`"requirements"`, `"test-cases"`, ...). That was the right call for reaching full coverage in one pass: 6 tool definitions covering ~30 entities, with `app/mcp/tool_registry.py` doing the dispatch.

In use, the reflective shape has a specific cost that only shows up on the client side, and it is not a small one:

1. **`resource` is a value the model must get right from prose, with nothing to check it against.** The tool's JSON Schema says `resource: string` — every one of ~30 valid slugs, and every invalid one, type-checks identically. A wrong slug is a runtime `404 not_found`, discovered only after the call.
2. **`tools/list` doesn't say what is actually possible.** The advertised surface is 6 tools; the real surface is ~146 entity/action capabilities. Nothing in the tool list tells a client that `test_log` cannot be updated, that `permission` is read-only, that `release` has only a create, or that `organization` has no flat list. Under ADR-0065 those refusals were correct but *late* — a `405` envelope at dispatch time, which the model has to spend a call to discover.
3. **One input schema has to cover every entity's arguments**, so it degenerates to the loosest shape that fits all of them: `fields: dict[str, Any]`, `scope: dict[str, str]`. Per-entity specificity was pushed into `describe_entity`, an extra round trip.
4. **Every tool name is a collision candidate in a multi-server client session.** `create_entity`/`get_entity` are exactly the names a second, unrelated MCP server would plausibly also publish.

The underlying dispatch built by ADR-0065 is sound and is not in question here — the registry, the direct-call-into-the-REST-handler pattern (ADR-0033 decision 2), the plain-arg `list` refactor, and the `_actor_membership_exists` fix all stay exactly as they are. What changes is only **how the same capabilities are advertised**.

A second, smaller inconsistency this resolves: ADR-0033's own two MCP-1 tools (`create_test_case`, `list_test_cases`) survived MCP-5 unchanged, sitting beside the reflective family. `test_case`'s create was therefore reachable two ways under two different names — `create_test_case(requirement_id=..., title=...)` and `create_entity(resource="test-cases", fields={...})` — with the hand-wired one supporting only the direct-link path while the registry executor supported both it and REQ-3's rigor path. Two names, one capability, differing behaviour.

## Decision

1. **One MCP tool per entity per supported action, generated — not hand-listed — from `TOOL_REGISTRY`.** `app/mcp/tools/entity_tools.py`'s `register_tools()` walks the registry and calls `mcp.add_tool(fn, name=..., description=...)` once per (entity, action) row. `add_tool` rather than the `@mcp.tool()` decorator specifically because name and description are computed per entity; a decorator only takes a literal at the definition site, which is the hand-listing this ADR exists to remove. Each generated function's signature carries **only that action's real arguments** — `list(scope, filters, search, sort, page, page_size)`, `get(id)`, `create(fields)`, `update(id, fields)`, `delete(id)`, `describe()` — and **no `resource` argument on any of them**: the entity is the tool's identity, not one of its inputs. Result: **146 tools** (119 CRUD actions across 30 resources + 27 `describe`).
2. **The advertised surface is exactly each entity's real REST surface — enforced by omission, not by refusal.** The actions generated for an entity are its `CrudEntityConfig.full_methods` (ADR-0055 — **not** `methods`; `project`'s bespoke `get`/`update`/`create` live at the same URLs the generic factory doesn't register, and a diff against `methods` false-positives on exactly that entity, per `backend/CLAUDE.md`'s own note), plus its declared `BESPOKE_EXTRA_ACTIONS`, plus `describe` where a config exists at all. MCP-5's "MCP never grants a capability REST doesn't have" AC is preserved and strengthened: an unsupported pair is not refused at call time, it is **never advertised** — a client cannot call what it was never offered.
3. **Naming: `tn_<resource>_<action>`, using each route module's own literal `resource="..."` string, verbatim.** `tn_organization_get`, `tn_project_create`, `tn_requirement_list`, `tn_test_case_update`. No abbreviations, no pluralization, no re-spelling — the entity segment is copied from the config, so a rename there propagates rather than drifting. The `tn_` prefix namespaces all 146 against other MCP servers mounted in the same client session (Context §4). Built in exactly one place, `tool_registry.tool_name()`; nothing else concatenates the string. Parsing back is right-to-left on the action, since resource slugs contain underscores (`tn_test_case_defect_link_get` → `test_case_defect_link` + `get`).
4. **`TOOL_REGISTRY` re-keys from the plural, hyphenated route slug to the singular, snake_case `resource` value.** ADR-0065 keyed on `_resource_path(config.resource)` (`"test-cases"`) deliberately, so a client that had just called `describe_entity` could reuse that exact string on the next call. That rationale disappears with the `resource` argument itself, and a hyphen inside a tool-name segment reads as a word break (`tn_test-cases_get`). The plural slug is untouched everywhere REST itself uses it — `GET /entities/{resource}/schema`, the frontend's `:entity` route segment, `ALL_ENTITY_CONFIGS`'s own keys. `ENTITY_CONFIGS_BY_RESOURCE` provides the singular-keyed view.
5. **MCP-1's two hand-wired tools are retired, folded into the scheme, and `app/mcp/tools/test_cases.py` is deleted.** `create_test_case` → `tn_test_case_create` (the registry executor, which supports *both* the direct-link and rigor paths, so this is a strict capability gain, not a port). `list_test_cases` → `tn_test_case_list`, a new bespoke registry row wrapping `list_test_cases_for_requirement` — without it `test_case` would have no `list` at all, since the generic factory registers none. Both old names must be **absent**, not merely outnumbered: leaving either registered would publish two differently-named tools for one capability, which is the specific inconsistency Context's last paragraph names. `app/mcp/tools/generic_crud.py` is likewise deleted, its `_materialize`/`_raise_as_tool_error`/`_validation_error_response` helpers moving to `entity_tools.py` unchanged.
6. **Argument placement follows one uniform rule, stated in every generated description.** A bespoke route's parent id — a URL path parameter on REST — rides inside `fields` for a `create` (`{"requirement_id": ..., "title": ...}`) and inside `scope` for the one bespoke `list` (`{"requirement_id": ...}`), mirroring how every generic entity's own scope field is already passed. This is what MCP-1's tools did differently (`requirement_id` as its own top-level argument), and is the one caller-visible behavioural change in this ADR.
7. **Each tool ships a generated, per-entity description.** With 146 tools, `tools/list` descriptions are the only signal a model has for choosing among them, so each names the entity, the REST route it mirrors, the required scope key or parent id where one exists, and points at that entity's own `describe` tool. Generated at import time from the config (`label`, `scope_field`) plus two small hand-declared maps for the bespoke parent-id/scope-key facts, which are properties of a route's URL shape and exist in no config.
8. **A diff-based completeness test is mandatory, not optional** (`tests/unit/test_mcp_tool_naming.py`). At 146 tools a single missing entity or action is invisible — that capability just quietly stops being reachable, the same silent-degradation shape ADR-0055's `FieldMeta` note and MCP-5's own registry test already describe. Every assertion is a set difference against `ALL_ENTITY_CONFIGS`/`full_methods`, never a hardcoded name list (which would drift with the thing it polices), and it runs in both directions: no registry row without a tool, no tool without a row, no action beyond `full_methods` ∪ declared bespoke extras, and every pre-ADR-0068 name asserted gone.

## Consequences

- **146 tools is a large `tools/list` payload, and that is the real cost of this ADR** — roughly 60 KB of JSON on the initialize/list round trip, and a proportionally larger slice of a client's context budget than 6 tools consumed. Accepted deliberately: the payload is paid once per session, whereas the reflective shape's costs (a wrong `resource` slug, a `405` discovered by calling, an extra `describe_entity` round trip for field shapes) are paid per mistake, repeatedly, and are exactly the failure modes an agent is worst at recovering from. Clients that filter or lazily load tool lists benefit further from the prefix. **If this proves too heavy in practice, the mitigation is a narrowing one — publishing a configurable entity subset — not a return to reflective tools**; that would be its own ADR.
- **`unsupported_method_response()`/`unknown_entity_response()` become defensive rather than routinely reachable.** Nothing removes them (the generic executors still guard on a missing handler, and the registry still promises those shapes), but no client call reaches them any more: the SDK rejects an unadvertised name first, with its own plain-text `Unknown tool: <name>` rather than this app's `{code, message, field_errors}` envelope. That is a *different* error shape from ADR-0033 decision 4's parity guarantee — but decision 4 is about errors from this application's own code, and an unknown tool name never reaches it. Stated here because two test cases had to be corrected for exactly this (below).
- **Two MCP-5 test cases needed genuine correction, not just renaming** — recorded here rather than silently absorbed:
  - **TC-MCP-017** asserted three entity/action pairs return `405`/`{"detail": "Method Not Allowed"}`. Both halves changed: the mechanism (absence from `tools/list`, per Decision §2), and one of its three named examples — `test_case` *does* now have a `list`, because Decision §5 folded MCP-1's nested list in. Replaced with `permission` (genuinely read-only via the factory) so the TC still names three real, still-unsupported pairs, and the test now also asserts the positive side of each entity, so a missing tool proves method-gating rather than a wholesale registration failure.
  - **TC-MCP-022** asserted `describe_entity(resource="releases")` returns the same `404 not_found` REST gives. `describe` is now generated only where a `CrudEntityConfig` exists, so `tn_release_describe` is never registered. The claim's *intent* — a client cannot obtain a schema for `release` over MCP, exactly as REST cannot — is preserved by asserting the tool's absence plus REST's own unchanged `404`, rather than by asserting an error envelope this app never produces.
- **A client configuration pinned to the old tool names breaks outright.** There is no aliasing or deprecation window: `create_entity`, `list_entities`, `create_test_case` et al. are gone as of this change. This is the intended behaviour (Decision §5's "absent, not outnumbered"), and is safe here because the MCP surface has no external consumers yet beyond this repo's own tests and manual client checks — it would not be, later.
- **`app/mcp/tools/` is now a single module.** ADR-0033's own "one additional file pair per route" roadmap is now fully retired in both directions: MCP-5 replaced it with one reflective module, MCP-6 replaces that with one generative module. A new bespoke route needs one registry executor + one `BESPOKE_EXTRA_ACTIONS` row and its tool appears; a `CrudEntityConfig.methods` change needs nothing at all.
- **No REST, database, schema, RBAC, or frontend surface changes**, with one exception recorded as an Amendment below — every other permission gate, tenant boundary (NFR-1's 404-not-403), validation path and response shape is the same code as before, verified by the full backend integration suite (328 passed, plus the 2 pre-existing bare-`/health`-via-nginx known-harmless failures this repo's own `backend/CLAUDE.md` already documents) against a live isolated stack, including MCP-5's own TC-MCP-016..023 coverage running unchanged in substance against the renamed tools.
- **One explicitly-scoped extra fix, flagged rather than smuggled:** `test_mcp_sdk_client_handshake_and_tools_list_over_lan_ip`'s hardcoded `LAN_MCP_BASE_URL = "http://192.168.25.203:54594/mcp/"` (a dead LAN IP and a port that never matched main's nginx) is now `E2E_LAN_MCP_BASE_URL`, skipping when unset — the exact fix `backend/CLAUDE.md` already names and explicitly records as not-yet-done. Done here because this change rewrites that test's own tool-surface assertions anyway, and a permanently-red test masks real regressions in precisely the surface under test.

### Amendment (2026-09-14, pre-merge, same-story correction): `test_condition_authoring.py`'s two bespoke routes never got ADR-0065's own `_actor_membership_exists` fix

This ADR's own Related line above claims ADR-0065's `_actor_membership_exists` fix (the `AIAgent`-aware `OrgMembership` check, `backend/CLAUDE.md`'s own documented rule) is "kept verbatim" project-wide. That was true of `crud_factory.py`'s generic-factory gates — it was never true of `app/api/routes/test_condition_authoring.py`, a bespoke module ADR-0028/REQ-3 wrote *before* ADR-0065 existed and which was never revisited when the `AIAgent`-aware helper shipped. Both of its routes — `create_test_condition_for_requirement` (backs `tn_test_condition_create`) and `create_test_case_for_test_condition` (backs `tn_test_case_create`'s rigor-path branch) — still called the older, `User`-only `_org_membership_exists(db, org_id, actor.actor_id)`, which always evaluates false for an `AIAgent` actor (whose `actor_id` has no row in `user`, per `backend/CLAUDE.md`'s own "OrgMembership existence check must accept AIAgent actors" note). Both routes therefore 404'd every `AIAgent` caller unconditionally, regardless of a real, valid `OrgMembership` on the human the agent was acting on behalf of — invisible until this story's own `tn_test_case_create` rigor-path integration test (`test_tn_test_case_create_dispatches_the_rigor_path_when_given_a_test_condition_id`) became the first thing, ever, to call either route as an `AIAgent`. Same shape as ADR-0065's own precedent (a pre-existing gate bug, invisible until an MCP tool became the first caller to exercise the combination), just in a module that precedent didn't touch.

**Fix:** both call sites swapped to `_actor_membership_exists(db, org_id, actor)`, same import already used elsewhere in this codebase for exactly this purpose. No REST-visible behavior change for human `User` callers (the helper falls back to `actor.actor_id` for them, identical to the old check) — confirmed by the full integration suite passing unchanged for every non-`AIAgent` test. A companion test-file correction landed in the same commit: `test_create_entity_risk_item_rejects_both_and_neither_scope_fields` asserted `field_errors` keyed by both `{"requirement_id", "test_plan_id"}`, but `crud_factory.py`'s `scope_validation_error` has only ever keyed the error by the scope's own `primary_field` (`requirement_id` alone) — a test-assertion bug caught by running the newly-written test against the real route, not a second product defect.

## Alternatives considered

- **Keep ADR-0065's six reflective tools as-is.** Rejected — Context §1–§4. The dispatch is fine; the advertisement is what fails the client.
- **Publish both surfaces, reflective and per-entity.** Rejected. Two names per capability is the exact inconsistency Decision §5 removes for `test_case`; generalizing it to all 30 entities would double the tool count while making "which one should I call?" a new question with no good answer.
- **Per-entity tools with fully-typed `fields` (real named parameters per entity instead of a `dict`).** Tempting — it would give `tn_requirement_create` a schema listing `project_id`/`title`/`description` explicitly, closing the last gap `describe` fills. Rejected for this pass: it means synthesizing a signature from each entity's Pydantic create/update schema at import time, which is a substantially more fragile generator (defaults, enums, optionality, `Annotated` metadata) for a benefit `tn_<entity>_describe` already delivers in one cheap call. Worth revisiting as its own ADR once the naming scheme has seen real client use.
- **A different prefix, or none.** `testnexa_` is clearer but adds 8 characters to all 146 names, pushing the longest (`tn_requirement_test_condition_link_describe`, 43 chars) close to the 64-character ceiling several MCP clients enforce. No prefix at all was rejected outright per Context §4.
- **Keep the plural, hyphenated registry key and transform it for the name** (`test-cases` → `tn_test_cases_get`). Rejected — it would make the tool name a *derived* spelling rather than the config's own literal string, reintroducing exactly the second-hand-kept-spelling drift Decision §3 avoids, for no gain.
