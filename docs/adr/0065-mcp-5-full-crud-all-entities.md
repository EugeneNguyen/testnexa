# ADR-0065: MCP-5 — full CRUD, all entities, registry-driven MCP tool surface

**Date:** 2026-09-14
**Status:** Partially superseded by [ADR-0068](0068-mcp-6-per-entity-mcp-tools.md)
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0033](0033-mcp-server-architecture.md) (MCP server architecture — direct-call dispatch, per-tool bearer resolution; this ADR generalizes its "one additional file pair per route" roadmap into a registry-driven surface instead), [ADR-0022](0022-generic-crud-router-factory.md) (the generic CRUD factory this ADR's reflective tools dispatch onto), [ADR-0055](0055-admin-3-backend-driven-entity-schema.md) (`entity_registry.py`/`ALL_ENTITY_CONFIGS`, `derive_entity_schema` — both reused verbatim, not re-derived), [User Stories: MCP-5](../user-stories/2026-09-03-ai-agent-mcp-stories.md), [API Document §6](../api/2026-09-03-api-design.md), [TC-MCP-016..023](../test-cases/2026-09-03-test-cases.md)

## Context

MCP-1..3 (ADR-0033) opened a narrow, hand-wired MCP tool surface — `create_test_case`/`list_test_cases`/`update_test_case`/`create_test_execution`/`read_requirement` — one bespoke tool per REST route, each a direct-call dispatch onto that route's own handler function. ADR-0033's own roadmap ("Positive" consequences) explicitly planned to continue this shape: "one additional file pair... and 4 lines of `@mcp.tool()` per route" for MCP-2/MCP-3. That shape is fine at 2–5 tools; it does not scale to full CRUD across the ~27 entities the generic CRUD factory (ADR-0022) serves plus the ~13 bespoke mutating routes documented in API Document §4 — hand-wiring each would mean ~100+ near-identical tool functions, and every future route change would need a second, manually-kept-in-sync MCP-side edit.

**A real, pre-existing defect blocks this story outright, found during planning, not during a later verification pass.** `app/api/crud_factory.py` defines its own `_actor_membership_exists` (added EXEC-2, `AIAgent`-aware — resolves `acting_on_behalf_of_user_id` for an agent caller instead of the actor's own `actor_id`) — but never calls it. Both of the factory's shared gates, `_fetch_and_gate` (item-level `get`/`update`/`delete`) and `_resolve_scope_for_write` (`create`/`list`'s scope check), still call the older `_org_membership_exists(org_id, actor.actor_id)` directly. That check is `OrgMembership.user_id == actor.actor_id` — always `false` for an `AIAgent`, whose `actor_id` is its own, not its accountable human's. **Every one of the 27 generic-factory entities has therefore 404'd "not found" for any `AIAgent` caller, unconditionally, since ADR-0022 shipped** — silent until now because no MCP tool has ever called into the generic factory; MCP-1..3's bespoke tools all dispatch onto `assets.py`/`execution.py` routes, which already call the correct helper. This is a required fix to make this story's own feature reachable at all, not an unrelated drive-by — same posture DS-2's "coverage audit needed a small implementation slice" precedent already established for this repo.

## Decision

1. **Reflective, registry-driven MCP tools, not one hand-wired tool per route.** Five generic tools — `list_entities`, `get_entity`, `create_entity`, `update_entity`, `delete_entity` — each parameterized by `resource: str` (the same plural API-slug key `ALL_ENTITY_CONFIGS`/`GET /entities/{resource}/schema` already use), plus a sixth, `describe_entity`, wrapping the already-existing `derive_entity_schema` so an agent can self-discover a given entity's required fields before calling `create_entity`/`update_entity` — the same self-description ADR-0055 already built for the frontend, reused verbatim for MCP clients instead of re-derived.
2. **One entity-action registry is the single source of truth for both surfaces.** A new `backend/app/mcp/tool_registry.py` maps every `resource` slug to `{list, get, create, update, delete}`, each entry either `("generic", CrudEntityConfig)` (dispatches into the refactored `crud_factory.py` plain-arg functions, decision 4) or `("bespoke", handler_fn, kwargs_builder)` (dispatches directly onto the named bespoke route handler, same `Depends`-bypass pattern ADR-0033 decision 2 already established). This registry starts from `ALL_ENTITY_CONFIGS` (ADR-0055) for every generic-factory entity and adds bespoke rows for the ~13 mutating bespoke routes API Document §4 documents (`TestCase` ×2 create paths, `TestCondition`, `TestExecution`, `Defect`, `TestLog`/comment, `Project`, `Organization`, `OrgMembership`/invite, `RoleAssignment`, `TestSuiteTestCase`/`TestPlanTestSuite` link-add, `Release`). Excluded on purpose: `/auth/*`, invite-accept flows, `/orgs/{org_id}/agents` — human-identity/token/meta surfaces, not agent-actionable data CRUD.
3. **The registry, not developer discipline, is what keeps MCP synced with REST going forward.** A future new bespoke mutating route or a `CrudEntityConfig.methods` change updates one registry row; both the REST surface and the MCP tool surface read the same row. New standing rule added to `backend/CLAUDE.md` (same-commit convention, matching the resolver/gate-completeness rules already there): any new mutating route's registry row lands in the same commit as the route itself.
4. **`crud_factory.py`'s `list` closure is refactored to accept plain arguments instead of reading `Request.query_params` directly** — the one generic-factory operation that couldn't be called the MCP-1 direct-dispatch way as-is. The extracted function is called by both the existing REST route (which still parses the raw query string) and `list_entities` (which receives already-typed arguments from the MCP tool call). No behavior change on the REST side — same filter/search/sort/pagination logic, just callable from two places instead of one.
5. **Fix the `_actor_membership_exists` gap in the same change.** `_fetch_and_gate`/`_resolve_scope_for_write` switch to `_actor_membership_exists`, matching what `assets.py`/`execution.py`/`execution_authoring.py` already do. This is a strict widening for `AIAgent` callers only (a `User` actor's `actor_id` IS the value `_actor_membership_exists` resolves to, so its behavior for human REST callers is unchanged, verified with a regression test asserting exactly that) — no REST-visible behavior change for any existing human caller, only a working MCP surface for the agent case that already had this exact fix elsewhere.
6. **Method gating is enforced by the registry, not re-derived per tool call.** Calling `create_entity`/`update_entity`/`delete_entity` against a `resource` whose config doesn't register that method (`TestCase`'s missing factory `create`, `TestLog`'s missing everything but `get`/`list`, the 4 link tables' missing everything but `get`/`list`) returns the same error shape a REST client hitting the unregistered route would get — MCP never grants a capability REST doesn't have for that entity, per Story MCP-5's own AC.
7. **`RiskItem`'s branching scope (`requirement_id` **or** `test_plan_id`, exactly one)** is handled identically to REST's existing 2-tuple `scope_field` mechanism — `create_entity`/`list_entities` accept both as optional parameters, `422` if both or neither are set, same as the REST route.

## Consequences

**Positive.** One codebase-wide registry replaces what would otherwise be 100+ hand-wired tool functions; a future entity or route change is a one-line registry edit, not a parallel MCP-side implementation pass. Fixing the `_actor_membership_exists` gap makes an entire, previously-nonfunctional class of MCP call (every generic-factory entity) work for the first time — closing MCP-2/MCP-3's own backlog note in ADR-0033 as a side effect: `update_test_case`/`create_test_execution`/`read_requirement`-shaped needs are now all reachable via the generic tools without their own bespoke wiring, so **MCP-2 and MCP-3 are subsumed by this story rather than needing separate implementation** (their own hand-wired tools, if already shipped, stay as thin aliases or are retired in favor of the generic ones — an implementation-time choice, not a doc-time one).

**Negative / Trade-offs.** `create_entity`/`update_entity`'s JSON Schema is necessarily generic (`resource: str` + `fields: dict[str, Any]`) rather than per-entity typed parameters — an MCP client cannot introspect a specific entity's required fields from the tool's own schema the way MCP-1's `create_test_case` (individually-typed parameters) allowed; `describe_entity` closes most of that gap by letting a client fetch the shape first, but this is a discoverability step MCP-1's narrower, hand-typed tools didn't need. Every mutating call's payload validation now happens against the entity's own Pydantic `create_schema`/`update_schema` at dispatch time rather than at the MCP transport layer, same as REST's own validation timing — no weaker check, just one hop later than a fully-typed tool signature would give.

**Drift note.** ADR-0033's own roadmap named MCP-2 ("update test case") and MCP-3 ("execution + requirement read") as the next two hand-wired tools. This ADR does not implement either of those specific tool names — it implements the general mechanism that makes their underlying REST calls reachable via `update_entity`/`create_entity`/`get_entity` instead. ADR-0033's Status line is updated to point here rather than to two now-superseded, never-built tool names.

### Partially superseded by ADR-0068 (2026-09-13)

**[ADR-0068](0068-mcp-6-per-entity-mcp-tools.md) replaces Decision §1's reflective, `resource`-parameterised tool shape** with one generated tool per entity per action (`tn_<entity>_<action>`). **Decisions §2–§5 are untouched and are what ADR-0068 builds on** — the entity-action registry, the same-commit standing rule, the plain-arg `list` refactor, and the `_actor_membership_exists` fix all stay exactly as decided here; only the six tools that sat on top of the registry are replaced by ~146 generated ones dispatching onto the identical executors.

The prose above is left as written, per this repo's own "don't rewrite an ADR's history" convention — including this ADR's own third Alternative ("Per-entity typed tools generated at import time from each `CrudEntityConfig`... Rejected — reintroduces the ~100-tool-surface problem"), which ADR-0068 **deliberately reverses**. That rejection was an honest call on the evidence available at the time; ADR-0068's Context §1–§4 sets out what using the reflective surface subsequently showed (an unvalidatable `resource` string, capabilities invisible in `tools/list`, a necessarily-loose shared input schema, and collision-prone generic names) and argues the tool-count cost is the cheaper of the two. ADR-0068 does *not* reverse the second half of that alternative — its generated tools still take a `fields: dict`, not synthesized per-entity typed parameters, and `describe` still closes that gap.

## Alternatives considered

- **Continue ADR-0033's one-hand-wired-tool-per-route shape for every remaining entity.** Rejected — ~100+ near-duplicate tool functions, and every future route change needs a second, easy-to-forget MCP-side edit; this is exactly the drift the new standing rule (decision 3) is meant to prevent structurally rather than by discipline.
- **A single mega-tool (`crud(resource, action, ...)`)** instead of 5 verb-named tools. Rejected — worse discoverability for an MCP client's own tool-listing UX (`list_entities`/`create_entity`/etc. read as intent-revealing function names; a single `crud()` pushes the same information into a string argument an LLM caller has to get exactly right) for no registry-size savings (the registry itself is one data structure either way).
- **Per-entity typed tools generated at import time from each `CrudEntityConfig`** (metaprogramming a `create_requirement`/`create_project`/... function per entity, each with real typed parameters). Rejected — reintroduces the ~100-tool-surface problem decision 1 explicitly avoids, just generated rather than hand-written; `describe_entity` gets most of the typed-parameter discoverability benefit without the tool-count cost.
