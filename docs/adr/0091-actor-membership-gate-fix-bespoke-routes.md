# 0091. Seven bespoke routes 404'd every `AIAgent` caller — `_org_membership_exists` never adopted `_actor_membership_exists`

**Status:** Accepted
**Decider:** xuanbinh91@gmail.com (CTO)
**Date:** 2026-09-18
**Related:** [ADR-0090](0090-agent-org-self-discovery.md) (whose own verification pass found this defect, same day), `backend/CLAUDE.md`'s "`OrgMembership` existence check must accept AIAgent actors" note (the standing rule this fix finally applies everywhere), [ADR-0033](0033-mcp-server-architecture.md)/[ADR-0065](0065-mcp-5-full-crud-all-entities.md) (which fixed the *generic factory's* own gate for this exact class of bug — this ADR is the bespoke-route sibling that never got the same fix)

## Context

Immediately after shipping ADR-0090's `tn_agent_org_list`, using it to discover an org id and then calling `tn_test_suite_test_case_create` as that same `AIAgent` returned `404 not_found` ("Test suite not found") against a real, existing suite the same agent could `tn_test_suite_get` successfully — the tell that the 404 was a membership-resolution bug, not a real "doesn't exist" state.

Root cause: `test_suite_membership.py`/`test_plan_membership.py`'s own `_load_suite_for_actor`/equivalent gate called `_org_membership_exists(db, org_id, actor.actor_id)` — the plain, `User`-only helper `backend/CLAUDE.md` already documents as a standing trap (`OrgMembership.user_id` FKs `user.actor_id`; an `AIAgent`'s own `actor_id` never matches, so the check always returns `False` for an agent regardless of its `acting_on_behalf_of_user_id`'s real membership). ADR-0033/MCP-1 fixed this for `assets.py`'s own routes at the time, and ADR-0065/MCP-5 fixed the *generic factory's* shared gate — but seven other bespoke, hand-written routes across five separate modules were written after or alongside those fixes and never adopted `_actor_membership_exists`, because nothing enforces that every new bespoke route re-derives the lesson.

An audit (`grep -rn "_org_membership_exists(db, .*, actor\.actor_id)"`) found the full blast radius: five MCP-reachable creates (`projects.py::create_project`, `org_memberships.py::invite_member`, `role_assignments.py::create_role_assignment`, `releases.py::create_release`, `test_cycle_creation.py::create_test_cycle_for_plan`) plus two REST-only routes (`roles.py::list_roles`, `rbac_routes.py`'s `GET /orgs/{org_id}/permissions/mine`) — all silently 404-ing every `AIAgent` caller, including project creation itself, the most basic MCP write there is.

## Decision

Every flagged call site swapped from `_org_membership_exists(db, org_id, actor.actor_id)` to `_actor_membership_exists(db, org_id, actor)` (the canonical, `AIAgent`-aware helper in `crud_factory.py`). Four modules (`projects.py`, `org_memberships.py`, `role_assignments.py`, `releases.py`, `roles.py`, `rbac_routes.py`) had their own **local** copy of `_org_membership_exists`, per this codebase's established per-module `_error()`-style duplication convention — each now imports `_actor_membership_exists` from `crud_factory.py` instead, and the now-dead local copy is deleted outright (not left commented-out), except in `role_assignments.py`, which keeps its local copy for its one remaining legitimate caller (`_org_membership_exists(db, org_id, target_user.actor_id)`, checking a *different* user's membership, not the caller's own — genuinely correct as-is, untouched). `test_cycle_creation.py` already imported the helper from `crud_factory.py` directly, so only the import name changed.

`projects.py`'s own `_actor_has_org_standing` (used by `get_project`/`update_project`) is a **different**, pre-existing, already-correct mechanism for the same question — it branches on `isinstance(actor, AIAgent)` and checks the agent's own direct `RoleAssignment` rows rather than resolving via `acting_on_behalf_of_user_id`. It was not touched or reconciled with `_actor_membership_exists`'s different mechanism (transitive `OrgMembership` via the behalf-user) — two competing designs for "does this agent belong to this org" now coexist in this codebase, and unifying them is a separate, larger design question outside this fix's scope. `create_project` was moved onto the dominant, already-used-almost-everywhere pattern (`_actor_membership_exists`) rather than onto `_actor_has_org_standing`, for consistency with the other six fixes in this same pass.

`agents.py`'s three `_org_membership_exists(actor.actor_id)` call sites were audited and left untouched — each is preceded by a hardcoded human-only gate (`isinstance(actor, User)` check, 403 for any `AIAgent`), so `actor` is guaranteed a `User` by the time the membership check runs; the bug pattern requires a route that both accepts `User | AIAgent` *and* reaches the membership check for either type, which these three do not.

## Consequences

- An `AIAgent` can now: create a project (`tn_project_create`, previously **completely broken for agents**), invite an org member, create a role assignment, create a release, create a test cycle, add a test case to a suite, and include a suite in a test plan — seven previously-silent 404s closed in one pass.
- New integration test `test_adr91_actor_membership_gate_fix.py`: 3 tests proving the three most severe previously-broken paths (project creation, suite membership, plan-suite membership) now succeed for a real `AIAgent` bearer key whose only standing is its `acting_on_behalf_of_user_id`'s active `OrgMembership` + an inherited (ADR-0083 bootstrap-fallback) `org_admin` grant — never the agent's own `Actor` row directly.
- No schema change, no migration, no new permission code, no behavior change for any `User` caller (every fixed helper call already branches `isinstance(actor, User)` internally and produces byte-identical behavior for that branch).
- Verified against an isolated stack cloned from `main` (`testnexa-adr91-test`): backend unit **915/915**, new integration file **3/3**, full suite **1331/1341** (10 pre-existing failures re-confirmed structurally unrelated — identical set to ADR-0090's own verification pass, none in any file this ADR touches).
- **The general lesson, worth restating**: `backend/CLAUDE.md`'s own standing rule ("any new route gated on org membership and taking a `User | AIAgent` actor should use `_actor_membership_exists`") existed and was followed by *most* new bespoke routes going forward — but it does nothing to catch a route written *before* the rule was written, or a route whose author simply didn't re-read that file's note. A rule stated in prose is not a completeness check; a `grep -rn "_org_membership_exists(db, .*, actor\.actor_id)"` sweep is what actually found all seven, in one pass, after the fact. A future story wiring a *new* MCP capability onto an *existing* bespoke route should run this same grep against the specific route first, rather than trusting that "the rule exists" means every route already follows it.

## Alternatives considered

- **Delete `_org_membership_exists` everywhere and force every caller onto `_actor_membership_exists`.** Rejected for `role_assignments.py`'s one remaining use (checking a *target* user's membership, not the caller's) — that call is correct as a plain `User`-keyed check (a `RoleAssignment`'s target is always a `User`, never an `AIAgent`), and forcing it through the actor-aware helper would be a needless signature change for a callsite that was never broken.
- **Reconcile `_actor_has_org_standing`'s `RoleAssignment`-based mechanism with `_actor_membership_exists`'s `OrgMembership`-based one into a single helper.** Rejected as out of scope — both are individually correct answers to "does this agent belong to this org," just via different data; picking one as canonical and migrating the other is a real design decision this fix's narrow "make the broken routes work" scope shouldn't fold in unreviewed.
