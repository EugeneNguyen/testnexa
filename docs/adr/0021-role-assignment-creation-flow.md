# ADR-0021: RoleAssignment creation flow — membership gate, body-validation posture, project-scoped enforcement fix

**Date:** 2026-09-03
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0004](0004-rbac-design.md) (RBAC design), [ADR-0007](0007-real-multi-tenancy.md) (tenancy, NFR-1), [ADR-0015](0015-ai-agent-credential-mechanics.md) (404-vs-403 boundary, `has_permission`/`require_permission` project_id design), [ADR-0017](0017-project-creation-flow.md) (`Project` route shape this story builds on), [RBAC-3 user story](../user-stories/2026-09-03-rbac-tenancy-stories.md#story-rbac-3-assign-roles-org-wide-or-project-scoped), [RBAC-3 scope plan](../superpowers/plans/2026-09-03-rbac-3-assign-roles-plan.md)

## Context

RBAC-3 is the first story to build an actual endpoint for creating a `RoleAssignment` — until now every row was an auto-grant side effect of another route (signup, `POST /orgs`, `POST /orgs/{org_id}/projects`). It's also the first story to exercise `has_permission`'s `project_id` branch (written ahead of need by AUTH-4/ADR-0015) end-to-end over real HTTP, surfacing a latent gap: PROJ-1's `GET`/`PATCH /projects/{id}` routes call `has_permission` without passing `project_id`, so a project-scoped-only grant — including the creator's own auto-assigned `test_manager` role on the project they just made — never satisfies those checks. Four questions needed a decision, none of which the RBAC-1/PROJ-1 precedent settles directly:

1. **Cross-org `role_id`/`project_id` in the create request body** — validation failure (`422`) or existence-hiding (`404`, per NFR-1)?
2. **Membership precondition** — must the target `User` already hold an `OrgMembership` in `org_id` before a `RoleAssignment` can be created for them?
3. **List endpoint** — is `GET /orgs/{org_id}/role-assignments` in scope alongside create?
4. **The `has_permission` project_id gap** in `projects.py` — fix now, or defer as a known limitation the way RBAC-1 deferred TC-RBAC-002?

## Decision

- **`422`, not `404`, for a cross-org `role_id` or `project_id` in the request body.** NFR-1/ADR-0007's cross-tenant-404 rule protects against confirming a *resource's existence across an org boundary via a path/fetch*. Here the caller has already cleared the 404-vs-403 boundary on `org_id` itself (proving org membership) before either field is even looked at; rejecting a body field that doesn't resolve *within the org the caller is already known to belong to* is ordinary request validation, the same posture `slug`/`(org_id, name)` collisions already take (`organizations.py`, `projects.py`). No enumeration leak: the response never distinguishes "that role/project doesn't exist" from "it exists in a different org."
- **Creating a `RoleAssignment` for a `User` actor requires an existing `OrgMembership` (any status) for that user in `org_id`; `422` if absent.** The story text itself says "assign a Role to a **member**" — a `RoleAssignment` for a `User` with zero standing in the org is not a real grant, it's an orphaned row. Any-status (not active-only) so an `org_admin` can pre-provision or adjust a `suspended` or still-`invited` member's roles ahead of reactivation, consistent with RBAC-2's own rule that suspension keeps `RoleAssignment` rows intact rather than erasing them. `AIAgent` actors are exempt entirely — no `OrgMembership` row ever exists for one (same precedent `agents.py`/`organizations.py` already establish: an agent's org relationship is never represented by `OrgMembership`).
- **`GET /orgs/{org_id}/role-assignments` ships alongside `POST`.** Same reasoning PROJ-1's ADR-0017 gave for shipping `GET /projects/{id}` alongside `POST`/`PATCH`: a create-only endpoint with no way to read grants back is not a usable admin flow, and the route costs nothing beyond the create route's own 404-vs-403 + `require_permission` plumbing, reused verbatim.
- **Fix `get_project`/`update_project` to pass `project_id` into `has_permission`, now, not deferred.** Unlike TC-RBAC-002 (blocked because no route existed at all for the affected entities), the route exists, the fix is a one-line argument addition to an existing call, and leaving it unfixed would make AC2 ("permissions from a project-scoped role apply within that project") demonstrably false for the single realistic case the schema already produces (a project's own creator, project-scoped `test_manager` only). Deferring a *known, cheap, already-diagnosed* bug is a different judgment call than deferring a *route that doesn't exist yet* — RBAC-1's deferral precedent doesn't transfer.

## Consequences

**Positive:** `RoleAssignment` creation gets the same validation rigor (body-field `422`s, no cross-org enumeration) and 404-vs-403 boundary every other org-scoped route already has — no new pattern invented. The membership gate keeps `RoleAssignment` rows meaningful without inventing new machinery RBAC-2 doesn't have yet (any-status check, not a dependency on RBAC-2's still-unbuilt invite flow). The `has_permission` fix closes a gap AUTH-4's own docstring explicitly flagged as "RBAC-3's coverage obligation," and does so as a real HTTP-level fix (`GET`/`PATCH /projects/{id}` now correctly recognize project-scoped grants) rather than a unit-test-only workaround — TC-RBAC-008/009/010 get real HTTP proof through `Project`, not a synthetic route built just to satisfy the test.

**Negative / Trade-offs:** The membership-gate check adds one more DB round-trip to the create route (an extra `OrgMembership` existence query beyond the 404-vs-403 boundary's own). The `422`-for-cross-org-project_id decision means an `org_admin` fat-fingering another org's project UUID gets "validation failed" rather than an existence-hiding `404` — a deliberate, narrow exception to NFR-1's general rule, scoped specifically to body-field validation on a route where org membership is already proven; any *future* route resolving a foreign-org id must re-derive whether it's a body-validation case (this ADR's posture) or a path/fetch case (NFR-1's default `404`) rather than assuming one answer applies everywhere.

## Alternatives considered

- **`404` for cross-org `role_id`/`project_id`, mirroring NFR-1 literally** — rejected: the field is caller-supplied in a body the caller already proved org membership to reach, not a path segment whose existence is itself the sensitive fact; `404` here would just be a less-informative `422` wearing NFR-1's clothes for no isolation benefit.
- **No membership gate — any `Actor` row is a valid `RoleAssignment.actor_id`, as the schema alone already allows** — rejected: the story's own "member" framing and the audit-quality argument (an orphaned grant to a non-member is confusing, not merely permissive) outweigh the marginal complexity of one extra any-status check.
- **Defer the `has_permission` project_id fix to a follow-up story, ship RBAC-3 test coverage against `has_permission()` directly instead of real HTTP** — rejected: the fix is small, already fully diagnosed, and leaving AC2 unproven against a real route for a story literally about project-scoped enforcement would be a credibility gap in exactly the claim RBAC-3 exists to make.
- **List endpoint deferred (create-only)** — rejected: matches PROJ-1's own "ship GET alongside POST/PATCH, cost is near-zero" reasoning; no reason to treat `RoleAssignment` differently.

## Addendum (2026-09-03): Role Assignments UI

RBAC-3 originally shipped API-only (no story text or frontend precedent asked for a screen). The CTO subsequently asked for one. Bounded-scope decision, made in chat rather than re-opening this ADR's own decision list: the "New Role Assignment" form (`RoleAssignmentsPanel.tsx`, mounted in `OrgHome.tsx`) needs a way to pick a `role_id` and an `actor_id`. Neither has a listing endpoint that predates this addition — `role_id` gets one now (`GET /orgs/{org_id}/roles`, new, `role.read`-gated, same 404-vs-403 pattern as every other org-scoped route — see API Document), populating a dropdown of the 5 system roles + this org's custom roles. `actor_id` stays a raw UUID paste: building a member/agent-listing endpoint is real RBAC-2/AUTH-4-list scope, not something to smuggle into a UI-only addendum. This is a deliberately asymmetric, honestly-labeled interim state, not a considered final design for the actor picker.
