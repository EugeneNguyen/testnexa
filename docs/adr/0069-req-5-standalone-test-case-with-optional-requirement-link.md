## Context

Today a `TestCase` can only be created via one of two bespoke, atomically-linked, parent-scoped routes: `POST /requirements/{id}/test-cases` (direct-link, REQ-2) or `POST /test-conditions/{id}/test-cases` (rigor path, REQ-3). Both require a path-supplied parent id. The generic CRUD factory's own `POST`/`GET /test-cases` were deliberately excluded from the start (ADR-0022's `TestCase` footnote), specifically because `create` needed to also write a link-table row the factory has no mechanism for (ADR-0028's "audit for a matching bespoke route" rule) — there was never a shape of `TestCase` creation that didn't need a parent's link row written atomically, until now.

Real teams also write test cases with no formal Requirement or TestCondition at all — exploratory/ad-hoc testing, a case written before its requirement is captured, or a case that simply never needs traceability. Nothing in this codebase lets a caller do that: every create path forces a parent. Separately, the project-mode sidebar (ADR-0051) already ships a "Test cases" nav entry pointing at `/projects/:projectId/admin/test-cases` — but that route is currently a dead end (`_TEST_CASE_CONFIG.methods` has neither `list` nor `create`), so the link has never actually worked.

This ADR closes both gaps with one mechanism: `TestCase` gets a *direct* project scope, exactly the shape `TestSuite` already has, so it becomes a normal generic-factory-served entity with no atomic link-table write required — a standalone case has no link row to write at all. The already-existing sidebar entry starts working with no frontend route change.

## Decision

1. **New nullable `TestCase.project_id` column** (`Uuid`, FK → `project.id`, `ON DELETE RESTRICT`, same delete posture as every other core test-asset FK). Nullable because the two pre-existing paths (direct-link, TestCondition-mediated) never set it — their own link tables/`test_condition_id` chain remain the resolver's more specific source of truth for those rows.
2. **`_TEST_CASE_CONFIG` (`app/api/routes/assets.py`) is unrestricted for exactly this one new shape**: `methods` gains `list`+`create`; `scope_field="project_id"` (mirrors `_TEST_SUITE_CONFIG` verbatim); a new `create_schema`, `CreateStandaloneTestCaseRequest` (`project_id`, `title`, `test_level_id`, `test_type_id`, optional `preconditions`/`expected_result`/`status` — the exact same fields `CreateTestCaseRequest` already has, `project_id` added since the factory's create convention takes the scope field in the body, per `crud_factory.py`'s own documented "a query param on list, a body field on create" rule). No link-table row is written — a standalone case has nothing to atomically link, which is exactly the property that makes this safe to route through the plain factory unlike `TestCondition`'s create (ADR-0028).
3. **`resolve_test_case_org_id` gains a 4th branch**, inserted **third**, after the two link-table branches and before the `TestSuiteTestCase` fallback: `test_condition_id` set → `TestCondition` chain (unchanged) → any `RequirementTestCaseLink` (unchanged, ADR-0029) → **`project_id` set → `Project.org_id` (new)** → any `TestSuiteTestCase` (unchanged) → unresolvable → `404` (unchanged). Position rationale: a case can have `project_id` set *and* later gain a `RequirementTestCaseLink` (decision 4 below) without contradiction — the more specific Requirement-mediated branch already resolves first, so `project_id` only ever actually fires for a case with no Requirement/TestCondition traceability yet, which is exactly "standalone."
4. **New bespoke retrofit route, `POST /test-cases/{id}/link-requirement`** (body: `{requirement_id}`), gated `test_case.update`. Attaches an *existing* `TestCase` to a `Requirement` after the fact by inserting a `RequirementTestCaseLink` row — the same table REQ-2's own create route writes, just decoupled from creation time. Rejects:
   - `404` if the path `TestCase` or the body's `requirement_id` doesn't resolve, or the caller has no `OrgMembership` in the resolved org (existence-hiding, NFR-1) — same 404-vs-403 boundary every bespoke route in this codebase uses.
   - `422 validation_error` if the `Requirement` resolves to a different `project_id` than the `TestCase`'s own (same org, cross-project — same posture NFR-38/NFR-41 already established for suite/plan membership).
   - `409 already_linked_to_requirement` if the `TestCase` already has *any* Requirement traceability — `test_condition_id IS NOT NULL`, or an existing `RequirementTestCaseLink` row — deliberately not layering a second traceability path onto a case that already has one; this route is for a genuinely standalone case only. Not layered as a second create route: a case created via REQ-2/REQ-3 already has its link, so this route is only ever meaningfully callable against a `project_id`-scoped standalone case in practice, though the check itself is stated generally (any existing link, not "was this case standalone"), since that's the property that actually matters.
   - `project_id` is left set, not cleared, once a link is added — it's a harmless historical marker ("this case started standalone"), and the resolver's own branch ordering (decision 3) means the now-more-specific `RequirementTestCaseLink` branch resolves first regardless.
5. **No unlink route, no retrofit-to-TestCondition route** — out of scope for this story (CTO decision, this task's scope confirmation). A standalone case can gain a Requirement link; it cannot be un-linked or attached to a `TestCondition` after the fact via this ADR. Either is a small, symmetric follow-on if a future story needs it.
6. **`test_case.create`/`.read` are reused as-is** — both already granted to every role that needs them (`tester`, `test_manager`, `org_admin`) since ADR-0028's RBAC bundle extension. No RBAC migration.
7. **No new frontend route.** The project-mode sidebar's existing "Test cases" nav item (ADR-0051) already points at `/projects/:projectId/admin/test-cases`; it starts rendering a working list + "New Test Case" button the moment `_TEST_CASE_CONFIG` is unrestricted, with zero navigation/routing change. `EntityFormPage`'s existing `test-case` edit page gains one new conditional action, "Link to Requirement," shown only when the loaded case has no existing Requirement/TestCondition traceability (mirrors the existing `test-case`-only "Defects" section EXEC-3 already added the same way, per that ADR's own precedent for a single-entity conditional addition to the generic edit page).

## Consequences

**Positive:** the sidebar's `TestCase` nav entry — reachable since ADR-0051, non-functional until now — starts working with zero frontend change. Teams that don't want Requirement/TestCondition process overhead (the same adoption-friction concern ADR-0006 already named) get a third, genuinely parent-free authoring path. The retrofit route means "start standalone, formalize traceability later" is a real, supported workflow, not a one-way door.

**Negative / Trade-offs:** `TestCase` now has three independent "how did this row come to exist" shapes (direct-link, TestCondition-mediated, standalone) plus one retrofit transition between the third and the first — more branches for any future reader of the resolver or the traceability views (FR-TRACE-1/2) to hold in their head. `TRACE-1`'s Requirement-detail traceability view was already documented as needing to distinguish 2 path shapes (ADR-0006's own Consequences); it now needs to distinguish 3, plus the retrofit transition, though this ADR does not itself change `TRACE-1`'s implementation — flagged as drift for that story's own next touch, not silently absorbed. `project_id` is a column with no purpose once a case gains a Requirement link — a minor, accepted schema footprint (same class of "column stays set after superseded by a more specific relationship" the codebase already accepts nowhere else explicitly, but structurally harmless: never read once the link branch resolves first).

## Alternatives considered

- **New bespoke atomic route, `POST /projects/{id}/test-cases`, instead of unrestricting the generic factory** — rejected: a standalone case writes no link-table row at all, so there is nothing atomic to protect; routing it through the plain factory (like `TestSuite` already does) is strictly simpler and reuses `EntityListPage`/`EntityFormPage` for free, whereas a bespoke route would need its own frontend page or modal that ADR-0051's routing-consistency decision (its own "Alternatives considered") already argued against introducing per-entity.
- **A new dedicated `TestCasesPage.tsx` reachable from the sidebar, instead of fixing the existing generic-admin route** — rejected per explicit CTO direction (this task's own scope confirmation) and consistent with ADR-0051's decision to route every project-scope nav entry through the uniform generic-admin surface, not a per-entity bespoke page.
- **Allow the retrofit route to also attach a `TestCondition`, not just a `Requirement`** — deferred, not rejected: the task's own scope explicitly named "link to Requirement," and a symmetric `TestCondition` retrofit is a small, independent follow-on if ever needed, not a design constraint this ADR needs to preempt.
- **DB `CHECK` constraint enforcing `project_id`/`test_condition_id` mutual exclusivity** — rejected per explicit CTO direction: application-layer enforcement only, consistent with how the pre-existing two-path coexistence was never DB-enforced either (ADR-0006's `test_condition_id` nullability is the only schema-level signal; the direct-link path's own "no `test_condition_id`" invariant is enforced by the route body, not a constraint).
