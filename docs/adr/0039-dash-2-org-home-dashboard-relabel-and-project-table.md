# ADR-0039: DASH-2 relabels `OrgHome` "Dashboard" (heading/sidebar/breadcrumb only) and extends its Project table with ID column, Edit/Delete modals, and client-side search/sort/pagination

**Date:** 2026-09-07
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0017](0017-project-creation-flow.md) (Project creation, the bespoke create/read/update routes this story leaves untouched), [ADR-0022](0022-generic-crud-router-factory.md) (generic factory — `GET`/`DELETE /projects` already shipped here), [ADR-0018](0018-admin-shell-sidebar-layout.md) (sidebar's single nav-item-list extension point), [ADR-0035](0035-dash-1-root-redirect-and-dashboard-placeholder.md) (DASH-1 — the separate, unrelated `/dashboard` placeholder this ADR explicitly does NOT touch), [ADR-0037](0037-shell-components-raw-html-not-coreui-react.md) (raw-HTML shell chrome `AppSidebar`/`AppBreadcrumb` this story edits)

## Context

Two requests landed together for `OrgHome` (`/orgs/:orgId`, PROJ-1/ADR-0017's org-scoped landing screen): (1) relabel it "Dashboard" everywhere a user sees its name (heading, sidebar nav item + an icon, breadcrumb trail), and (2) turn its existing minimal Project list into a real management table — an `ID` column, `Edit`/`Delete` row actions, and search/sort/pagination.

**Naming collision, flagged and deliberately not resolved here.** DASH-1 (ADR-0035, 2026-09-07) already shipped a separate, unrelated screen at the *global* route `/dashboard` — an intentionally empty placeholder reached via `/`'s auth-state redirect for a logged-in visitor, explicitly not org-scoped, with its own ADR text noting "whether it becomes org-scoped... is an open question for that future story." This story is not that future story: it renames `OrgHome`'s own *label*, it does not touch `/dashboard`'s route, screen, or ADR-0035's decision. The practical result: two different screens both display the word "Dashboard" to a logged-in user (`/dashboard`, empty; `/orgs/:orgId`, the org's project list) — an accepted, temporary overlap, not a bug, until a future story explicitly decides to consolidate them (see Consequences).

**Second, smaller context point:** `DELETE /projects/{id}` has existed since ADR-0022's generic factory shipped (`_PROJECT_FACTORY_CONFIG`, `methods={"list", "delete"}`) but had zero frontend callers — no story had asked for Project deletion in the UI until now. `project.delete` is already a real seeded permission (`project` is one of the 23 full-CRUD RBAC resources, [RBAC-4](0016-organization-bootstrap-creation-flow.md)'s seed catalog) and `org_admin`'s bundle (defined as "every permission in the catalog") already grants it — no RBAC migration is needed, only wiring the existing route to a UI action.

## Decision

1. **Relabel, not re-route.** `OrgHome` stays mounted at `/orgs/:orgId`. Three surfaces change their displayed text from "Org home"/"Org Home"/"Org: {orgId}" to "Dashboard": the page's own `<h1>` heading, `AppSidebar.tsx`'s nav item (`key`/`data-testid`/`to` all stay `org-home`/`sidebar-nav-org-home`/`/orgs/:orgId` — only the visible label string changes, so no test needs updating for those), and `AppBreadcrumb.tsx`'s route-derived label table. The sidebar's Dashboard nav item additionally gets a `cilSpeedometer` icon (`@coreui/icons` + `@coreui/icons-react`, per root `CLAUDE.md`'s existing icon convention) — the only nav item with one; no other item gets an icon in this pass, per the story's literal, narrow ask.

2. **Project table gets a real management UI, still client-side.** Columns become ID / Name / Standards profile / Actions (Edit, Delete). The old click-to-edit-in-place `standards_profile` field is replaced by a dedicated "Edit Project" modal (React Hook Form + Zod, same structural pattern as the existing "New Project" modal) that edits `name` and `standards_profile` together — a bigger, more consistent editing surface than the field-at-a-time affordance it replaces. A "Delete" button opens a confirm modal (mirrors `EntityListPage`'s own `rowPendingDelete` + `useMutation` pattern) and calls the already-shipped `DELETE /projects/{id}` — the first frontend caller of that route. Search (name substring, case-insensitive) and sort (ID/Name column headers, click-to-toggle asc/desc) and pagination (page size 10, `CPagination`) are all implemented **client-side**, over the list `listProjects()` already fetches in full (it pages through every row up front — see that function's own docstring) — no new backend query parameter, no change to `crud_factory.py`.

## Consequences

**Positive:** Consistent "Dashboard" branding across heading/sidebar/breadcrumb for the org's landing screen. Project list becomes a real CRUD surface (create/read/update/delete all reachable from the UI, matching what the backend has supported since ADR-0017/ADR-0022) with the same search/sort/pagination affordances a user would expect of any list, at zero backend cost.

**Negative / accepted trade-offs:**

- **The naming overlap with `/dashboard` (ADR-0035/DASH-1) is unresolved by this ADR, on purpose.** A user who has visited both `/dashboard` (empty) and `/orgs/{id}` (their projects) sees "Dashboard" twice, meaning two different things. Fixing this — merging the two screens, making `/dashboard` redirect into the org context, or renaming one of them again — is explicitly deferred to a future story with its own scoping pass, the same way ADR-0035 itself deferred "should `Dashboard` become org-scoped" outward. Until then this is documented drift, not a hidden bug (see the Sitemap and Requirements updates in this same pass).
- **Client-side search/sort/pagination does not scale indefinitely.** `listProjects()` fetches every row for the org before any filtering/sorting/paging happens client-side. This is fine at today's expected project-per-org counts and matches this codebase's existing precedent (`EntryExitCriteria`/`RoleAssignmentsPanel` sections on the same screen are also unpaginated client-side lists) — it is not fine for an org with, hypothetically, thousands of projects. Revisit with server-side `?q=`/`sort=`/pagination (the generic factory already supports `?q=` search via `search_fields`, just not configured for `Project`, and has zero `order_by` support at all today) if real usage ever approaches that scale.
- **`Edit` now changes `name` too, not just `standards_profile`.** A rename through this modal reuses the same `(org_id, name)` uniqueness collision handling `createProject`/the old inline edit never needed to (only `standards_profile` was editable before). This is desired (the modal should let you fix a typo'd project name) but is a slightly larger edit surface than the story's own literal "table needs an Edit button" ask strictly required — called out here rather than silently expanded.

**Addendum (2026-09-07, found during isolated-env verification — a real functional defect, not a documentation or test-coverage gap):** the new "Delete" button **cannot actually delete any Project created through the app's own UI**. `POST /orgs/{org_id}/projects` (ADR-0017, step 5) unconditionally inserts a project-scoped `test_manager` `RoleAssignment` for the creator, and `role_assignment.project_id` FKs `project.id` with `ON DELETE RESTRICT` — so `DELETE /projects/{id}` against any such Project always `409 restrict_blocked`. This was invisible until now because no story had ever called `DELETE /projects/{id}` from a UI before this one; the route's own existing test coverage (pre-DASH-2) only ever exercised `create`/`read`/`update`, never `delete` on a project the create route itself produced. Confirmed reproducible with a dedicated characterization test (`test_delete_project_created_via_api_is_blocked_by_creator_role_assignment`, `backend/tests/integration/test_projects.py`) — every Project created via `POST /orgs/{org_id}/projects` in this codebase's entire history has at least this one `RoleAssignment`, so the Delete button as shipped is a dead affordance for the only kind of Project a real user can ever create.

**This is deliberately NOT fixed in this same pass.** Closing it requires an actual product/architecture decision this ADR did not scope: cascade-delete the creator's `RoleAssignment`(s) when a Project is deleted (changes `ON DELETE RESTRICT` to `CASCADE` for this one FK, or adds explicit cleanup logic to a new bespoke delete route), or accept the current behavior and change the UI (e.g. surface the 409 as a clear "this project still has role assignments" message, or hide/disable Delete until a cascade path exists). Any of these is a new architecture decision needing its own ADR, not a silent patch inside this one. Flagged here per this repo's own "flag drift, don't silently absorb" convention (see root `CLAUDE.md`'s ADR section) — the Delete button ships as-is, with the confirm modal's existing 403/error-alert handling at least surfacing the `409`'s message text rather than failing silently, but a normal `org_admin` clicking Delete on any real project will see an error, not success, until a follow-up story resolves this.

## Alternatives considered

- **Consolidate `/dashboard` and `/orgs/:orgId` into one screen right now**, resolving the naming collision instead of just flagging it. Rejected for this pass — no story asked for that consolidation, and ADR-0035 explicitly scoped that decision to a future story once `/dashboard` actually needed real content; deciding it as a side effect of an "Org Home" relabel task would be scope creep past what was asked.
- **Server-side search/sort/pagination**, adding `search_fields=("name",)` to `_PROJECT_FACTORY_CONFIG` and a new `order_by` query-param mechanism to `crud_factory.py`. Rejected for this pass — `listProjects()` already fetches the full list, the generic factory has zero sort support to build on top of (a real backend feature, not a one-line config change), and there is no evidence yet that any org's project count needs it. Revisit if that assumption stops holding (see Consequences).
- **Keep the old click-to-edit-in-place `standards_profile` field alongside a new Edit-modal for `name` only.** Rejected — two different editing affordances for two fields on the same row is more confusing than one modal editing both, and the story's own literal ask ("Edit" button) reads as a single, obvious action per row.
