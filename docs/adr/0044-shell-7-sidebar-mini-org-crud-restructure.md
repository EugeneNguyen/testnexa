# ADR-0044: SHELL-7 sidebar-mini layout + org-scoped CRUD nav restructure

**Date:** 2026-09-08
**Status:** Accepted — no code written this pass, per explicit instruction (docs-only, plan already confirmed with the CTO; implementation is a separate, later authorization)
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0018](0018-admin-shell-sidebar-layout.md) (original sidebar), [ADR-0020](0020-admin-shell-full-template-parity.md) ("UI Elements" nav group, unaffected), [ADR-0022](0022-generic-crud-router-factory.md) (generic CRUD router factory — `orgScopedEntities` registry this ADR regroups, no route change), [ADR-0036](0036-shell-6-organization-switcher-header-dropdown.md) (org switcher, unaffected — different header control), [ADR-0042](0042-adminlte-design-system.md) (AdminLTE v4 — `sidebar-mini` is one of its own shipped body-class modifiers, not a new mechanism), [ADR-0043](0043-atomic-design-tiering-for-frontend-components.md) (`AppSidebar`/`AppShell` current locations: `components/organisms/app-sidebar/`, `components/templates/app-shell/`), [SHELL-7 user story](../user-stories/2026-09-04-admin-shell-sidebar-stories.md#story-shell-7-mini-sidebar--org-scoped-crud-nav-restructure), [SHELL-7 UI Design Document](../ui-design/2026-09-08-shell-7-sidebar-mini-org-crud-restructure-ui-design.md)

## Context

Two independent, CTO-requested changes to the existing `AppSidebar`/`AppShell` shell (ADR-0018/ADR-0020/ADR-0042), bundled into one story because both touch the same two files:

1. **Sidebar-mini layout.** The shell today only ever fully collapses/expands the sidebar (`sidebar-collapse` on `<body>`, per ADR-0042's `AppShell` state machine) — desktop collapse hides the sidebar's nav labels and icons together, behind a header toggle. AdminLTE v4 ships a second, additive body class, `sidebar-mini`, that changes what "collapsed" means: combined with `sidebar-collapse`, the sidebar narrows to an icon-only rail (`min-width: 4.6rem`, `3.1rem` when the pointer isn't hovering it — confirmed directly in the shipped `admin-lte@4.9.1` CSS) instead of disappearing, and expands back to full width on hover without changing the underlying collapsed/expanded state `AppShell` already tracks. No new state machine — `sidebar-mini` is a constant, mount-time body class exactly like the existing `layout-fixed`/`sidebar-expand-lg` pair.
2. **Org-scoped CRUD nav restructure.** `AppSidebar.tsx`'s `orgScopedEntities` registry (ADR-0025's `:entity` routing) — 8 entities (`Role`, `RoleAssignment`, `Permission`, `TestDesignTechnique`, `TestLevel`, `TestType`, `Organization`, `OrgMembership`) — renders today as one flat, single "Admin" `nav-treeview` group. Under `sidebar-mini`'s icon-only collapsed state a single flat 8-item group has no way to show which entity is which — AdminLTE's own icon-only convention is one icon per group/item, and a flat dump of 8 same-icon rows defeats that. Splitting the flat list into a small number of named, individually-iconed groups fixes both the icon-legibility problem *and* the CTO's separate, standing ask that org-scoped CRUD read as organized categories rather than one undifferentiated bucket.

## Decision

- **`AppShell`'s `BASE_BODY_CLASSES` gains `sidebar-mini`**, alongside the existing `layout-fixed`/`sidebar-expand-lg`. Written and removed by the same mount/unmount `useEffect` that already owns the other two — no new effect, no new cleanup path. Nothing else about `AppShell`'s collapse/expand/mobile state machine changes: `sidebar-mini` only changes what CSS the existing `sidebar-collapse` class paints, it does not add a third state.
- **`AppSidebar.tsx`'s org-scoped `navGroups` splits the current single `Admin` group into three groups**, each with its own icon (mini-mode requirement) and its own `data-testid`:
  - **`Access Control`** (`fa-solid fa-user-shield`, `sidebar-nav-group-access-control`): `Role`, `Permission`, `RoleAssignment`, `OrgMembership`.
  - **`Catalogs`** (`fa-solid fa-layer-group`, `sidebar-nav-group-catalogs`): `TestDesignTechnique`, `TestLevel`, `TestType`.
  - **`Organization`** (`fa-solid fa-building`, `sidebar-nav-group-organization`): `Organization`.
  - The existing flat `Members` item gains an icon too (`fa-solid fa-users`) — under `sidebar-mini`, an item with no icon at all renders as an empty collapsed rail slot, which is a real regression the restructure would otherwise introduce for the one item this ADR doesn't touch the grouping of.
  - `orgScopedEntities`' own registry (`frontend/src/pages/admin/registry.ts`) is **not reordered or re-keyed** — the 3 new groups are a presentation-layer partition applied in `AppSidebar.tsx` only (a `key -> group` lookup, keyed off each entry's existing `key`), so `:entity` route paths, `FkAutocomplete` ref lookups, and every other registry consumer are unaffected.
  - Nav order, top to bottom: `Dashboard`, `Members` (existing flat items, unchanged) → `Access Control` → `Catalogs` → `Organization` → `UI Elements` (ADR-0020 scaffolding, unchanged, unconditionally last).
  - The existing `Admin` group (`sidebar-nav-group-admin`) and its 8 children's `data-testid`s (`sidebar-nav-admin-*`) are retired by this split — every consuming Vitest/e2e assertion referencing the old group/child testids is updated in the same implementation pass (not deferred), per root `CLAUDE.md`'s "every `data-testid` is load-bearing" rule.
- **`UI Elements` (ADR-0020) is explicitly untouched** — not CRUD, not backed by any FR/story, out of this restructure's scope by the CTO's own confirmed default.

## Consequences

**Positive:** Mini-sidebar gives desktop users a persistent, low-chrome nav rail without losing icon-level recognizability, standard AdminLTE UX. Splitting one undifferentiated 8-item CRUD dump into 3 named, purpose-grouped sections makes the sidebar self-describing at a glance (an admin looking for "who can do what" goes straight to Access Control, not a flat alphabetical-ish list) and makes the icon-only collapsed rail actually legible instead of 8 indistinguishable rows.

**Negative / Trade-offs:** `sidebar-mini`'s collapsed-hover-to-expand interaction is AdminLTE's own plugin-JS-driven behavior upstream (`push-menu.ts`'s hover listeners) — this repo deliberately does not vendor AdminLTE's JS (ADR-0042), so the hover-expand is pure CSS (`:hover` selectors already present in the shipped stylesheet, confirmed — `.app-sidebar:hover` rules exist independent of any JS), but any AdminLTE mini-sidebar behavior that *does* require JS (if found during implementation) is out of reach without hand-rolling it, same standing constraint every other AdminLTE feature in this codebase already accepts. Group-collapsed-click-vs-hover-flyout interaction under `sidebar-mini` needs live verification against a real instance before implementation is trusted (root `CLAUDE.md`'s "reading source ≠ observing behavior" lesson) — flagged as an implementation-time verification step, not resolved by this ADR. Three new `data-testid`s replace one retired group's worth — every existing test referencing `sidebar-nav-group-admin`/`sidebar-nav-admin-*` breaks until updated in the same change; this is scoped, bounded churn (one component + its own test files), not a repo-wide rename.

## Alternatives considered

- **Keep one flat `Admin` group, add icons only** — rejected: doesn't address the CTO's separate, explicit ask that org CRUD read as organized categories; a flat 8-icon list under mini mode is still 8 indistinguishable icon-only rows if several entities share a plausible icon (e.g. `Role`/`Permission`/`RoleAssignment` are all "who can do what," differentiating them by icon alone rather than by which group they sit in is weaker signal).
- **More granular groups (one per entity, 8 groups)** — rejected: defeats the point of grouping at all, and would leave several single-item groups, no better than the flat list it replaces.
- **Move `UI Elements` into one of the new groups or delete it** — rejected per CTO's confirmed default: out of scope, no FR/story backs it, this ADR doesn't touch it.
- **Reorder `orgScopedEntities` itself in the registry** (rather than partitioning presentation-side in `AppSidebar.tsx`) — rejected: the registry's order/keys are consumed by more than the sidebar (route generation, `FkAutocomplete`), so changing it to serve one consumer's grouping need risks an unrelated regression elsewhere; a `key -> group` lookup local to `AppSidebar.tsx` gets the same visual result with zero blast radius outside that one file.
