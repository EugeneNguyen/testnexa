# ADR-0036: Shell components use raw HTML/Bootstrap classes, not `@coreui/react`

**Date:** 2026-09-07
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0012](0012-coreui-design-system.md) (CoreUI design system — **partially superseded**, see below), [ADR-0018](0018-admin-shell-sidebar-layout.md) (admin shell sidebar+navbar layout — **partially superseded**, see below), [ADR-0020](0020-admin-shell-full-template-parity.md) (full template parity, unaffected)

## Context

SHELL-2's breadcrumb (ADR-0020) went through three real, measured mismatches against the CoreUI free-template demo across one session (2026-09-07) before landing correctly — wrong padding, wrong container type (`container` vs `container-fluid`), wrong vertical spacing. Each was only found by pulling the demo's actual rendered markup/computed styles and diffing against ours; `@coreui/react`'s component API (`<CContainer>`, `<CBreadcrumb>`) sits between the code and the demo's literal HTML, so matching it pixel-for-pixel meant guessing at what props produce what markup rather than reading the demo's own `<div class="container-fluid px-4">` and writing exactly that.

Direct CTO instruction (2026-09-07): the CoreUI React wrapper library made following the demo harder, not easier, and the preference now is to write raw HTML/Bootstrap classes directly, matching the demo's markup 1:1, hand-built rather than mediated through a component library's own API.

## Decision

**Scope of this ADR: the shell chrome only** — `AppShell`, `AppHeader`, `AppSidebar`, `AppFooter`, `AppBreadcrumb` (5 files). This is the surface that gets pixel-compared against the CoreUI demo; it is also the smallest, most self-contained slice of the app that exercises every category of concern this migration raises (static markup, an interactive toggle, a route-derived list, dark/light mode). The remaining ~35+ files using `@coreui/react` (bespoke workflow screens' `CCard`/`CModal`/`CForm*`, the generic admin CRUD surface's `CTable`/`EntityForm`, `CWidgetStatsA/B`, UI-element reference pages) are **out of scope for this ADR** and stay on `@coreui/react` until a future story migrates them — see Consequences for why incremental, not big-bang.

- **CSS is unchanged.** `@coreui/coreui/dist/css/coreui.min.css` stays the single import (`main.tsx`) and the design system (ADR-0012's CSS/token layer is NOT superseded — only its "build UI from CoreUI's React components first" clause is, for the 5 files in scope). Raw markup in these 5 files uses CoreUI/Bootstrap's own class names (`container-fluid`, `breadcrumb`, `sidebar`, `header`) — the same classes `@coreui/react`'s components themselves rendered, just written by hand instead of generated by a component. Verified by dumping each component's actual current rendered DOM (React Testing Library, before deleting any `@coreui/react` import) rather than guessing.
- **No new npm dependency.** `@coreui/coreui` (already installed, unchanged) ships `dist/js/bootstrap.bundle.js` — real, unmodified Bootstrap 5 JS (confirmed: it's the literal upstream file, not a CoreUI fork, bundled alongside CoreUI's own `coreui.bundle.js`) — available if a future migration needs it. **As actually implemented, neither of the two interactive pieces in this scope (`AppHeader`'s color-mode dropdown, `AppSidebar`'s nav-group expand/collapse) ends up using it** — both are a plain `useState` boolean toggling the same CSS classes Bootstrap's own JS would toggle (`dropdown-menu.show`, `nav-group.show`), plus a small click-outside listener for the dropdown. Managing a vanilla-JS component instance's lifecycle (init on mount, dispose on unmount, ref plumbing) inside React is a well-known sharp edge for an interaction this small; a boolean toggle has an identical visual/behavioral result with less code and no lifecycle to get wrong. Recorded here as the actual decision, not the originally-floated option, per this repo's own "ADR-vs-implementation drift must surface" convention.
- **`AppSidebar`'s show/hide** (currently `CSidebar`'s `visible`/`onVisibleChange` prop pair) becomes a plain React `useState` boolean toggling a CSS class (`hide`) on a raw `<div class="sidebar sidebar-dark ...">`, mirroring CoreUI's own rendered markup. **Explicit, accepted regression:** `CSidebar`'s `isInViewport`-geometry-based auto-collapse-on-mobile-breakpoint-transition behavior (`AppShell.tsx`'s own pre-existing docstring documents this in detail — the exact behavior ADR-0018 adopted CoreUI specifically to avoid hand-rolling) is **not** reimplemented at the same fidelity. The hand-rolled version handles manual toggle correctly (verified by the existing TC-SHELL-004 test) but does not replicate the geometry-check auto-close-on-breakpoint-change behavior — flagged here as a known, accepted gap, not silently dropped.
- **Dark/light mode** (currently `useColorModes`, a CoreUI React hook) becomes a plain `useState` + `useEffect` pair: on toggle, `document.documentElement.setAttribute('data-coreui-theme', mode)` (the same attribute CoreUI's CSS already reads — confirmed via existing `TC-SHELL-012` test asserting `toHaveAttribute("data-coreui-theme", ...)`) plus a `localStorage` read on mount / write on change. No new logic beyond what `useColorModes` already did; this is a faithful, same-behavior port, not a simplification.
- **`AppBreadcrumb`'s route table logic is unchanged** — only the render function's JSX changes (raw `<nav aria-label="breadcrumb"><ol class="breadcrumb ...">` instead of `<CBreadcrumb>`/`<CBreadcrumbItem>`). Same `ROUTE_BREADCRUMBS` array (all 15 routes, per this session's earlier coverage-extension pass), same `matchPath` resolution, same active/link-vs-text logic, same `container-fluid px-4 py-3` wrapper this session already fixed twice.

## Consequences

**Positive:** the exact class of bug this session hit three times (guessing at what `@coreui/react` props produce, rather than reading and copying the demo's own markup) cannot recur in these 5 files — the JSX *is* the markup, diffable against the demo's HTML line-for-line. No new dependency. No visual change (same CSS, same classes).

**Negative / Trade-offs:**
- **`AppSidebar`'s mobile auto-collapse fidelity gap**, above — a real, accepted regression against `CSidebar`'s built-in geometry-check behavior, re-flagged here rather than left to be discovered later.
- **`AppSidebar`'s "UI Elements"/"Admin" nav-group expand/collapse** loses `CNavGroup`'s own JS-measured smooth height animation — the hand-rolled version toggles `display: none`/`block` directly (instant, not animated). Open/closed state and which links are reachable are identical either way; no existing TC or test asserts on the animation itself.
- **Scope is incremental, not the whole app** — `@coreui/react` is still a live dependency for ~35+ other files. This is a deliberate choice, not an oversight: a big-bang rewrite of `CModal` (focus trap, ESC-to-close, backdrop-click, ARIA), `CTable`, and every `EntityForm`/RHF integration in one pass has a much higher regression surface (accessibility-sensitive behavior, not just markup) than this session has budget to verify layer-by-layer. Each future migration (a bespoke screen, or the generic admin surface) should get its own scoped pass with its own before/after test verification, the same discipline this ADR's own 5-file scope got.
- Two component libraries' worth of markup convention now coexist in the same codebase (`@coreui/react` components in unmigrated files, raw HTML in these 5) until the rest migrates — a contributor needs to know which convention a given file uses. Mitigated by: every migrated file's own docstring states it plainly (see each file's own header comment).

## Alternatives considered

- **Migrate the entire app in one pass** — rejected: blast radius (~40+ files) and behavioral risk (Modal focus-trap, Table sort/pagination, RHF form-binding) far exceed what a single session can verify to the same standard as this ADR's 5-file scope. Revisit per-screen, incrementally.
- **Switch to `react-bootstrap`** (a different pre-built component library, also Bootstrap-based) — rejected: doesn't satisfy the actual stated preference ("build the element myself") — still a component library mediating between code and the demo's markup, just a different one.
- **Drop `@coreui/coreui`'s CSS too, move to stock `bootstrap` npm package** — rejected: would require re-deriving every CoreUI-specific template style (sidebar dark scheme, widget stat cards, color tokens) that this session just finished pixel-matching against the demo, for zero visual benefit — the demo *is* CoreUI's own template, styled by CoreUI's own CSS.
- **Reimplement `CSidebar`'s full geometry-check auto-collapse behavior by hand** — rejected for this pass: real engineering effort for a mobile-breakpoint edge case, disproportionate to this ADR's actual driver (pixel-matching static/breadcrumb markup on desktop). Flagged as the one accepted gap above rather than silently scoped out.
