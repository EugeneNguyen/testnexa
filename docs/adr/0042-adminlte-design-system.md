# ADR-0042: AdminLTE v4 + Bootstrap 5 + Font Awesome replaces CoreUI as the project's design system, raw HTML repo-wide, no vendored plugin JS

**Date:** 2026-09-08
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0012](0012-coreui-design-system.md) (CoreUI design system — **superseded by this ADR**), [ADR-0037](0037-shell-components-raw-html-not-coreui-react.md) (shell chrome raw-HTML-not-`@coreui/react` — **superseded by this ADR**: its *pattern* is generalized repo-wide, its CoreUI-specific class names and its incremental-scope stance are both reversed), [ADR-0009](0009-frontend-stack.md) (frontend stack — RHF + Zod + Vite + React Router + TanStack Query all unchanged), [ADR-0018](0018-admin-shell-sidebar-layout.md) / [ADR-0020](0020-admin-shell-full-template-parity.md) (admin shell — **partially superseded**, CoreUI-component and CoreUI-template-parity claims only), [ADR-0026](0026-sidebar-dark-color-scheme.md) (sidebar dark scheme — **partially superseded**, its mechanism no longer exists in v4), [ADR-0023](0023-frontend-shared-component-location.md) / [ADR-0041](0041-ds-2-table-container-shared-pagination.md) (`components/shared/` / `container/` location conventions — unchanged, only the markup inside those components changes), [AdminLTE v4](https://adminlte.io/)

## Context

ADR-0012 picked CoreUI in September 2026 on a "component library purpose-built for admin/dashboard tools" premise, and every shell/screen ADR since has been written against it. Two things have since changed that premise, both evidenced in this repo's own history rather than argued in the abstract.

**First, the React wrapper made following the reference demo harder, not easier.** ADR-0037 recorded this directly: SHELL-2's breadcrumb went through *three separate measured pixel mismatches* against the CoreUI free-template demo in one session — wrong padding, `container` vs `container-fluid`, wrong vertical spacing — each found only by pulling the demo's real rendered markup and diffing computed styles. `@coreui/react`'s component API sat between the code and the demo's literal HTML, so matching the demo meant guessing which props emit which markup instead of reading `<div class="container-fluid px-4">` and writing exactly that. The CTO's instruction at the time was explicit: write raw HTML/Bootstrap classes, hand-built, matching the demo 1:1.

**Second, the codebase had already drifted that way on its own, three independent times, and a fourth arrival made the drift a fork in the road rather than a style question.** ADR-0037's shell chrome (5 files, 2026-09-07) was the first; `FeaturedCard` in `components/shared/` was the second, from a plain product ask with no migration framing ("don't use `@coreui/react`, use `@coreui/coreui`/Bootstrap instead"); `WidgetStatsTile` (PR #41) was the third, replacing `CWidgetStatsA`/`CWidgetStatsB` outright. Root `CLAUDE.md` had already stopped calling this a migration hack and started calling it "an accepted, precedented alternative." Then PR #42 landed a full login screen — atoms / molecules / organisms / templates — **sourced from AdminLTE's own markup**, not CoreUI's. At that point the team was working from AdminLTE's demo while the design system of record was CoreUI, and the gap between the two was being absorbed file-by-file in every new screen.

This ADR ratifies the direction the codebase was already taking and names the design system whose demo the team is actually building against. It is a change of *which* CSS the raw markup targets and a promotion of "raw markup" from exception to universal rule — not a new idea imposed on an unwilling codebase.

PR #42 also left one question dangling that this ADR has to answer: `components/atoms/icon/icon.tsx` emits Bootstrap Icons classes (`bi bi-<name>`) against a font that is **never loaded**, because root `CLAUDE.md` mandated `@coreui/icons`/`CIcon` and only `coreui.min.css` was imported. Its own docstring flags the consequence honestly — "glyphs will render blank until the open question... is resolved. Do not silently add the `bootstrap-icons` CDN link to fix this — it's an architecture decision, not a scaffolding detail." This is that decision.

## Decision

### Packages and CSS

- **AdminLTE v4 (`admin-lte@4.9.1`) is the project's design system**, with its declared peer dependency **`bootstrap@^5.3.8`**. AdminLTE v4 *is* Bootstrap 5 plus a layout/skin layer, so Bootstrap is the base contract and AdminLTE supplies the admin shell (`.app-wrapper` grid, sidebar, content header) on top of it.
- **CSS entry, imported once in `frontend/src/main.tsx`, in this order**: `bootstrap/dist/css/bootstrap.min.css`, then `admin-lte/dist/css/adminlte.min.css`, then `@fortawesome/fontawesome-free/css/all.min.css`, then `./index.css`. Order is load-bearing — AdminLTE's rules are authored to override Bootstrap's, not to be overridden by them.
- `@coreui/react`, `@coreui/coreui`, `@coreui/icons`, and `@coreui/icons-react` are **removed**. Zero `@coreui/*` imports remain anywhere in `frontend/src` (or `frontend/tests/` — historical layout, superseded 2026-09-09 by [ADR-0049](0049-frontend-co-locate-unit-tests.md), Vitest specs now live co-located next to their source).

### Icons: Font Awesome Free

- **`@fortawesome/fontawesome-free` is the project's icon library**, replacing `@coreui/icons` + `@coreui/icons-react`. Still one icon library, not two — the same constraint ADR-0012 set, pointed at a different package.
- Icons render as CSS classes on an `<i>` element (`<i className="fa-solid fa-bars" aria-hidden="true" />`), not as a `CIcon` component fed a path array. There is no icon registry to configure.
- **This resolves PR #42's dangling open question.** The `Icon` atom's `bi bi-*` output becomes `fa-{variant} fa-{name}`, with a new `variant` prop (`"solid" | "regular" | "brands"`, default `"solid"`) so brand glyphs (Facebook, Google in the social-auth panel) can be reached; `name`/`spaced`/`className` and the `aria-hidden="true"` an existing test asserts are all kept. The atom now renders against a font that is actually loaded — the blank-glyph state its docstring describes ends here.
- Bootstrap Icons is **not** adopted. Adding it alongside Font Awesome would reintroduce exactly the second-icon-library situation ADR-0012 ruled out; the correct fix for PR #42's markup was to retarget the atom, not to load the font it happened to be written against.

### Raw HTML/JSX against the CSS, repo-wide

- **No component-library wrapper at all.** Every screen and component is written as raw HTML/JSX against Bootstrap 5 / AdminLTE class names. ADR-0037's pattern — the JSX *is* the markup, diffable line-for-line against the demo's HTML — becomes the universal rule rather than a 5-file exception.
- The class names used must be the library's own, read from the shipped CSS or from a real rendered DOM dump — never invented. This is ADR-0037's discipline verbatim, and `frontend/CLAUDE.md`'s "dump the rendered DOM with RTL rather than reading the library's source" note remains the technique of record for deriving them.
- **Accessible semantics are part of the contract, not a side effect of the old components.** CoreUI rendered real `<table>`/`<tr>`/`<th>`, real `<label for>`, `role="alert"` on feedback, `role="status"` on spinners, `<button>` rather than `<div>`. Hand-written markup must carry those explicitly — `CSpinner`'s implicit `role="status"` and `CPaginationItem`'s `active`/`disabled` classes landing on the `<li>` are the two that are easiest to lose and are both asserted by existing tests.
- ADR-0023's `components/shared/` and ADR-0041's `container/` location conventions are untouched. Where a component lives is orthogonal to what markup it emits.

### AdminLTE's own JS plugins and jQuery are NOT vendored

- **`admin-lte`'s JS bundle and jQuery are not loaded.** Every interactive behavior the app uses is reimplemented as plain React state/effects against AdminLTE's literal CSS class contract, read out of `node_modules/admin-lte/src/ts/*.ts` and the shipped CSS:
  - **Sidebar collapse/toggle** — state classes on `document.body`, not the sidebar element: `sidebar-collapse` (collapsed), `sidebar-open` (mobile explicit-open), with `layout-fixed sidebar-expand-lg` as base modifiers and `app-loaded` added post-mount. Applied via `useEffect` writing `document.body.classList` (React's root sits *inside* `<body>`, so JSX cannot express these) and **cleaned up on unmount** — `<body>` is outside React's tree and will otherwise leak classes between tests and across logout.
  - **Mobile breakpoint** — `matchMedia("(max-width: 991.98px)")` with a `change` listener, matching `push-menu.ts`'s own `991.98px` constant and `sidebar-expand-lg`'s published `content: "991.98px"`. Not a raw resize handler.
  - **`.sidebar-overlay`** — AdminLTE's own JS injects this click-outside scrim at runtime; since we don't load that JS, **we render it ourselves** as the last child of `.app-wrapper` with an `onClick` that collapses the sidebar.
  - **Treeview nav groups** — `menu-open` on the `<li className="nav-item">`, `nav-treeview` on the submenu `<ul>`, `aria-expanded` on the direct-child `.nav-link`. The existing React `useState<Set<string>>` open-group approach in `AppSidebar.tsx` is kept; only the class names change.
  - **Color mode** — `data-bs-theme` on `<html>` (was `data-coreui-theme`), `localStorage` key `lte-theme` (was `coreui-react-color-scheme`), values `light`/`dark`/`auto` with `auto` resolving via `prefers-color-scheme`.
  - **Dropdowns, modals, toasts** — a `useState` boolean toggling Bootstrap's own `.show` class, plus a click-outside listener for dropdowns; the exact `useDropdown` pattern already in `AppHeader.tsx`.
- **Why:** managing a vanilla-JS component instance's lifecycle (init on mount, dispose on unmount, ref plumbing, double-init on StrictMode remount) inside React is a well-known sharp edge, and for behaviors this small a boolean toggling the same class the plugin would have toggled has an identical result with less code and nothing to get wrong. ADR-0037 already made exactly this call for `AppHeader`'s color-mode dropdown and `AppSidebar`'s nav groups and it held for a month with no regression — this ADR generalizes a decision that has already been tested in production, not a fresh bet.
- `data-lte-toggle="sidebar"` / `data-lte-toggle="treeview"` are kept on the trigger elements for convention parity with AdminLTE's own markup, but nothing listens for them; the real wiring is the React handler.

### Big-bang scope — explicitly reversing ADR-0037's incremental stance

- **Every `@coreui/*` import is removed in one branch.** ADR-0037 deliberately chose incremental ("a big-bang rewrite of `CModal`, `CTable`, and every `EntityForm`/RHF integration in one pass has a much higher regression surface than this session has budget to verify layer-by-layer") and that reasoning was correct *for the change it was describing* — a migration from `@coreui/react` components to raw HTML **against the same `coreui.min.css`**, where the two conventions could coexist indefinitely because both resolved to the same stylesheet.
- **That coexistence property does not hold here, and its absence is what makes the reversal defensible.** CoreUI's CSS and AdminLTE's CSS are both Bootstrap-family: both ship `.container`/`.container-fluid`, a grid, a reset, and `.card`/`.btn`/`.table` rules, and the two disagree on token values, spacing, and (for the shell) structural layout — `.app-wrapper`'s CSS grid vs. CoreUI's flex `.wrapper`. Loading both means a cascade fight whose winner depends on import order, not on which component asked for which look. This is precisely the argument **ADR-0012 itself made** against running Tailwind and CoreUI together, applied to its own successor.
- A phased rollout therefore does not mean "some files look old for a while" — it means **shipping a broken cascade for the duration of the phase**, with every unmigrated screen rendering against whichever stylesheet happened to load last. Given the choice between a large one-pass regression surface and a knowingly-broken intermediate state, one pass is the smaller risk. The mitigation is verification breadth, not staging: `tsc --noEmit` clean, the full Vitest baseline (65 files / 390 tests) green, and every `data-testid` and accessible role preserved verbatim so ~390 unit assertions and ~30 Playwright specs remain the regression net.

### Unchanged

- **Tailwind stays removed.** No `tailwindcss`/`postcss`/`autoprefixer` dependency, no `tailwind.config.js`/`postcss.config.js`, no Tailwind class anywhere. Bootstrap 5 utilities only. ADR-0012's cascade-conflict reasoning applies to AdminLTE's Bootstrap-family CSS identically.
- **React Hook Form + Zod keep owning form state and validation** (ADR-0009, unchanged) — every `register()` spread, `handleSubmit`, and `forwardRef` survives; only the rendered element and its classes change. The rest of ADR-0009's stack (Vite, React Router, TanStack Query) is likewise untouched.

## Consequences

**Positive:** one design system, and it is the one whose demo the team is actually working from — the PR #42 login screen no longer sits in a different design language from the rest of the app. The class of bug ADR-0037 hit three times (guessing what props a wrapper emits instead of reading the reference's own markup) cannot recur anywhere, not just in 5 files. The "which convention does this file use" split ADR-0037 accepted as a known cost is closed rather than extended. PR #42's blank-icon open question is resolved with a loaded font instead of a second icon library. Dependency count drops by one net package (four `@coreui/*` out, three in) and the app no longer carries a React component library it renders almost none of.

**Negative / Trade-offs — real, verified, and accepted:**

- **`sidebar-dark-*` / `sidebar-light-*` do not exist in AdminLTE v4.** The entire skin family was removed upstream — verified as **zero occurrences** in the shipped `dist/css/adminlte.css`. ADR-0026's dark sidebar therefore cannot be delivered by its own documented mechanism (`CSidebar colorScheme="dark"` → the shipped `sidebar-dark` class); v4 expresses this through `--lte-sidebar-*` CSS custom properties or a nested `data-bs-theme="dark"` on the `.app-sidebar` element instead. The implementation defaults to `bg-body-secondary` — AdminLTE's own demo default — and does **not** invent a skin class. **This is a visible visual change to the sidebar, flagged here rather than discovered later**, and ADR-0026 is partially superseded accordingly. Whether the sidebar should be restored to a dark treatment via `--lte-sidebar-*` is a new product decision for a future story, not something this ADR silently settles.
- **Every existing user's saved color-mode preference is orphaned, once.** The `localStorage` key moves `coreui-react-color-scheme` → `lte-theme` (AdminLTE's own key, per `color-mode.ts`); nothing migrates the old value. A user who had explicitly chosen dark gets the default on their next visit and must re-pick. Accepted: a one-time reset of a presentation-only preference (NFR-28 — client-side only, no server round-trip) is not worth a migration shim that would have to be carried forever.
- **`btn-ghost-*` is a CoreUI-only button variant with no Bootstrap or AdminLTE equivalent.** The `Button` atom keeps its `ghost` prop and keeps emitting `btn-ghost-{color}` — an existing assertion (`Button.test.tsx`) checks for exactly `btn-ghost-info`, and the class is harmless — but **it is now unstyled**: a ghost button renders with no variant styling until a future decision either adds the rule to `index.css` or retires the prop. Flagged, not silently papered over with `btn-link`.
- **Modals are hand-rolled and focus-trapping is not reimplemented.** ESC-to-close (matching CoreUI's default `keyboard` behavior), the backdrop, `aria-modal`, `aria-labelledby`, and an `aria-label="Close"` dismiss button are all reproduced; **keyboard focus is not trapped inside an open modal**, which `CModal` did provide. This is a genuine accessibility regression against the prior behavior, accepted for this pass and recorded here rather than omitted — closing it is a candidate for its own story. (Render-nothing-when-closed *is* preserved, matching `CModal`'s unmount semantics that several negative `queryBy*` assertions depend on.)
- **AdminLTE sets `$font-family-sans-serif: "Source Sans 3"`, a font this project does not bundle.** Text falls through to the system stack, so the app will not look byte-identical to AdminLTE's own demo screenshots. Deliberately not fixed: adding a Google Fonts link is a new external runtime dependency for a self-hosted, sovereignty-motivated product, which is its own decision, not a styling detail to slip in here.
- **ADR-0037's "escape hatch" changes identity.** That ADR noted `@coreui/coreui` shipped a real, unmodified Bootstrap 5 bundle (`dist/js/bootstrap.bundle.js`) as available-if-ever-needed. With `@coreui/coreui` gone, that hatch is now the actual `bootstrap` npm package — the same code, reached directly rather than as a transitive artifact of a design system we no longer use. Nothing imports it today and this ADR does not authorize doing so; it is recorded so a future reader looking for ADR-0037's fallback knows where it went.
- **`AppSidebar`'s mobile auto-collapse fidelity gap (ADR-0037) is not closed by this migration and its detection mechanism changes.** `AppSidebar` currently reads `--cui-is-mobile` off `getComputedStyle` to detect the breakpoint; **AdminLTE defines no such custom property**, so that read would silently return `""` and the mobile branch would never fire — replaced by `matchMedia("(max-width: 991.98px)")` per the Decision above. `frontend/CLAUDE.md`'s note recommending the `--cui-is-*` technique is superseded by this ADR.
- **AdminLTE restyles `.card-title` with `float: left` and gives `.card` its own `box-shadow`.** Card header layouts that looked correct under CoreUI may need `.card-header` + AdminLTE's own `.card-tools` (`float: right`) slot rather than utility classes fighting the float. Named here because it is the most likely source of a "why does this card look wrong" question during and after the migration.

## Alternatives considered

- **Stay on CoreUI, keep migrating to raw HTML file-by-file (ADR-0037's stated path)** — rejected: it would have arrived at raw markup anyway, but targeting the wrong stylesheet. PR #42 already shipped AdminLTE-sourced markup, so continuing down ADR-0037's path means indefinitely maintaining screens written against one demo while the design system of record points at another — the drift widens with every new screen rather than closing.
- **AdminLTE v3** — rejected: v3 is jQuery-based and Bootstrap 4-era. Adopting it would either mean vendoring jQuery (contradicting the no-vendored-plugin-JS decision above for a much larger surface) or hand-reimplementing against an older Bootstrap that the rest of the ecosystem has moved off. v4's Bootstrap 5 base is also what makes the CoreUI→raw-Bootstrap class mapping nearly one-to-one, which is most of why this migration is tractable at all.
- **Adopt a React wrapper for AdminLTE** — rejected on the direct evidence of ADR-0037: the wrapper is what made pixel-matching the demo hard in the first place. Swapping one component library's abstraction over the demo's HTML for another's reproduces the exact problem this ADR exists to remove, and no such wrapper for v4 has the maintenance track record to justify a new dependency.
- **Stock Bootstrap 5 with no admin theme** — rejected: it would mean hand-authoring the entire admin shell (sidebar grid, collapse states, content header, treeview nav, footer placement) that AdminLTE ships as tested CSS, for no benefit — the team is working from AdminLTE's demo, so we would be reimplementing that demo's layer by hand. This is the mirror of ADR-0037's own rejection of dropping `@coreui/coreui`'s CSS for stock Bootstrap, and the reasoning survives the change of theme.
- **Phased / incremental rollout, screen by screen (the ADR-0037 posture)** — rejected on the cascade-conflict argument in the Decision: the two stylesheets cannot coexist, so a phase boundary is a broken-rendering boundary, not a cosmetic-inconsistency boundary. ADR-0012 made this same call against Tailwind + CoreUI; the reasoning applies unchanged to CoreUI + AdminLTE.
- **Keep `@coreui/icons` for icons while moving the CSS to AdminLTE** — rejected: `CIcon` requires a `@coreui/react`-family runtime and icon path arrays, so keeping it would keep a React component library alive for one component class only. It would also leave `WidgetStatsTile`'s already-broken `icon="cilFolder"` name-string prop (a latent bug — `CIcon` cannot resolve a name string without a global registry this app never set up) unfixed rather than converted to a Font Awesome class string.
