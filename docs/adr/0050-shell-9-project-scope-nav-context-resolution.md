# ADR-0050: SHELL-9 resolves org nav context on project-scoped routes (sidebar + breadcrumb), giving them a way back to the Projects list

**Date:** 2026-09-09
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0018](0018-admin-shell-sidebar-layout.md) (sidebar's single nav-item-list extension point, AC5), [ADR-0027](0027-generic-admin-crud-ui-and-backend-completion.md) (entity registry + `useAdminRouteContext`'s own pre-existing project→org resolution, generalized by this ADR — note `useAdminRouteContext.ts`'s own docstring misattributes this to "ADR-0025," a stale in-code comment this ADR does not repeat or fix), [ADR-0042](0042-adminlte-design-system.md) (raw-HTML shell, current `AppSidebar.tsx`/`AppBreadcrumb.tsx` markup), [ADR-0046](0046-shell-7-sidebar-mini-org-crud-restructure.md) (SHELL-7, the org-scoped nav this story now also renders on project routes), [ADR-0047](0047-proj-4-projects-page-sidebar-entry.md) (PROJ-4, the "Projects" nav item this story's "back to list" need reuses — no new nav item invented), [ADR-0022](0022-generic-crud-router-factory.md) (`GET /projects/{id}`, reused verbatim, no new route), [ADR-0041](0041-ds-2-table-container-shared-pagination.md) (`container/`'s own "new top-level dir once a second sibling needs it" precedent, cited in Decision §1)

## Context

`AppSidebar`/`AppBreadcrumb` derive all org-scoped nav content from `useParams<{orgId}>()`. Every route under `/orgs/:orgId/...` has that param; every route under `/projects/:projectId/...` (`ProjectDetail`, `TestPlanDetail`, `TestCycleDetail`, and the 20 project-scoped generic-admin pages) does not — `orgId` is only resolvable there by fetching the `Project` row and reading its own `org_id` field.

The practical effect, confirmed by reading `AppSidebar.tsx` directly rather than assumed: on every project-scoped screen, `orgId` is `undefined`, so both `navItems` and `navGroups` compute to empty arrays. The sidebar renders only the brand — no Dashboard, no Projects, no Members, no admin groups, nothing. `AppBreadcrumb` has the same gap by original design (its own docstring calls this out as deliberate — "org is only resolvable via a `GET /projects/{id}` fetch, which this component deliberately does not do") and renders a bare, unlinked "Project" segment instead of a real trail.

This is the literal defect the task names: opening a project (e.g. `/projects/01a084ca-.../`) leaves the sidebar effectively blank and gives the user no click-path back to the org's Projects list — the browser back button or a hand-edited URL are the only ways out.

**One consuming page already solved this exact sub-problem for itself**, independently: `useAdminRouteContext.ts` (ADR-0027's entity registry), used only by the 20 project-scoped generic-admin pages, already resolves `orgId` by fetching the current `Project` via the registry's own `getEntity` when `:orgId` is absent from the route. This story generalizes the same idea (route param, else fetch-the-project-and-read-`org_id`) to the two components that need it repo-wide (`AppSidebar`, `AppBreadcrumb`) but were never plumbed into that admin-only resolver, rather than duplicating the fetch a third and fourth time inline.

No backend, schema, or RBAC change is required — `GET /projects/{id}` (ADR-0017/ADR-0022) already returns `org_id`.

## Decision

1. **New shared hook, `useResolvedOrgId()`, in a new `frontend/src/hooks/` directory** (first file there — this repo has no top-level `hooks/` yet; `useAdminRouteContext`/`useEntityScope` live inside `pages/admin/` because they're admin-surface-specific, and `usePermissions` lives in `auth/` for the same reason — a hook consumed by two `components/organisms/*` siblings with no admin/auth affinity gets its own top-level location, the same "new top-level thing gets a home once a second sibling needs it" precedent `container/` set for DS-2's shared `Table`). Behavior:
   - `orgId` route param present (`/orgs/:orgId/...`) → return it directly, no fetch.
   - `orgId` absent, `projectId` present (`/projects/:projectId/...`) → `useQuery({queryKey: ["project", projectId], queryFn: () => getProject(projectId)})` (`lib/api/projects.ts`'s existing `getProject`, unchanged) and return its `org_id`.
   - Neither present (`/orgs/pick`) → `undefined`, same as today.
   - Also returns the query's `status` (`pending`/`error`/`success`) and, when resolved via fetch, the `ProjectSummary` itself (`name` in particular — needed for the breadcrumb below) so callers don't issue a second fetch for the same row.
   - **Cache key is the plain entity key `["project", projectId]`**, not `useAdminRouteContext`'s own `["admin-route-project-org-id", projectId]` — deliberately, so a project-scoped admin page (which uses the other hook) and a sidebar/breadcrumb on that same page (this hook) don't dedupe against each other by accident under two different keys that happen to fetch the same row; a future pass could unify both under one key, out of scope here since it touches the already-shipped admin surface.
2. **`AppSidebar.tsx` swaps its raw `useParams().orgId` read for `useResolvedOrgId()`.** Everything downstream (`navItems`, `navGroups`, `ORG_ENTITY_GROUPS`) is unchanged — it already branches on "is `orgId` truthy," not on which route produced it. The practical effect: the full org nav (Dashboard, **Projects** — PROJ-4's existing item, no new nav entry invented — Members, Access Control/Catalogs/Organization, UI Elements) now renders identically whether the current screen is `/orgs/:orgId` or any `/projects/:projectId...` screen. **This *is* the "way back to the project list"** the task asks for: click "Projects," land on `/orgs/:orgId/projects`. No bespoke back-link/breadcrumb-only affordance is added — reusing the item PROJ-4 already ships avoids two different sidebar entries pointing at conceptually the same place (the same duplicate-surface reasoning ADR-0047's own Alternatives section already rejected for its own scope).
3. **`AppBreadcrumb.tsx`'s `ROUTE_BREADCRUMBS` table gains a resolved-org root segment on all 5 project-scoped patterns**, replacing the bare unlinked "Project" label:
   - `/projects/:projectId` → `Projects` (linked, `/orgs/:orgId/projects`) → `{project.name}` (active)
   - `/projects/:projectId/admin/:entity[/:id/edit]` → `Projects` (linked) → `{project.name}` (linked to `/projects/:projectId`) → `{entity label}` [→ `Edit`]
   - `/projects/:projectId/test-plans/:testPlanId` → `Projects` (linked) → `{project.name}` (linked) → `Test Plan`
   - `/projects/:projectId/test-plans/:testPlanId/test-cycles/:testCycleId` → `Projects` (linked) → `{project.name}` (linked) → `Test Plan` (linked) → `Test Cycle`

   `matchPath`'s existing `params` callback signature can't reach `useResolvedOrgId()` (it's a plain function, not a component) — `AppBreadcrumb` calls the hook once at the top of its own body (same as `AppSidebar`) and passes `{orgId, projectName}` into the matched config's `segments()` alongside the existing route `params`, a small signature widening of `RouteBreadcrumbConfig["segments"]`, not a rewrite of the `matchPath` resolution logic itself.
4. **Loading/error/404 fallback: render today's degraded state, don't invent a new one.** While the `useResolvedOrgId()` fetch is pending, or if it errors/404s (deleted/foreign project), `orgId` is `undefined` — sidebar renders its existing empty-nav state (same as `/orgs/pick` today, no new loading skeleton per this story's own confirmed default), and breadcrumb's existing `segments.length === 0 → null` graceful-degradation path fires for that route until/unless the fetch resolves. No crash, no raw route param ever rendered — same invariant TC-SHELL-008 already pins for the pre-existing unmapped-route case, now also proven for the fetch-pending/fetch-failed case.
5. **No change to `useAdminRouteContext`, `useEntityScope`, or any project-scoped admin page** — those already resolve `orgId` correctly for their own permission checks; this story only extends the same *idea* to the two components that lacked it, without touching or refactoring the existing admin-surface resolver (smallest blast radius, per this repo's own "check what already has an ADR before assuming one is needed" convention — the resolution *pattern* isn't new here, only its consumers are).

## Consequences

**Positive:** every project-scoped screen (`ProjectDetail`, `TestPlanDetail`, `TestCycleDetail`, all 20 project-admin pages) gains a fully populated sidebar and a real, name-bearing breadcrumb trail for the first time — closing the exact dead-end this task named, via the org-scoped nav that already exists rather than a bespoke new affordance. `useResolvedOrgId()` is reusable by any future project-scoped bespoke screen that needs `orgId` outside the admin surface.

**Addendum (2026-09-09):** the sidebar-content decision this ADR made (render the org nav verbatim on project routes) was reversed the same day, on direct CTO instruction after reviewing the live result — see [ADR-0051](0051-shell-10-project-scope-entity-nav.md). This ADR's own text above is left as-written; it correctly describes what was built and why, at the time. `useResolvedOrgId()` itself (the hook, its `orgId` resolution) and the breadcrumb work are unaffected by that reversal and remain exactly as this ADR describes.

**Negative / accepted trade-offs:**

- **One extra network round trip on first paint of any project-scoped screen** that doesn't already fetch the `Project` row itself (`ProjectDetail` already does, for its own header; `TestPlanDetail`/`TestCycleDetail` do not today) — mitigated, not eliminated, by the shared `["project", projectId]` react-query cache key: a screen that also calls `getProject(projectId)` under that same key dedupes against the sidebar's/breadcrumb's own fetch instead of tripling it. See NFR-55.
- **Two independent `["project", projectId]`-shaped queries now exist in this codebase** (this story's plain key, `useAdminRouteContext`'s own `["admin-route-project-org-id", projectId]`) fetching the identical row under different keys on the 20 project-admin pages specifically (sidebar/breadcrumb use this story's key, the page itself uses the admin one) — a deliberate, named non-unification (Decision §1), not an oversight; unifying them is a small future cleanup, not required for this story's own scope.
- **Breadcrumb trails on all 5 project-scoped route patterns grow by one segment** (`Projects` root, previously absent entirely) — every existing e2e/Vitest assertion on those trails' exact segment count/text needs updating in the same change (see Test Plan risk row); no assertion content for *other* (org-scoped) routes' breadcrumbs changes.
- **`AppSidebar`/`AppBreadcrumb` each go from a pure, dependency-free `useParams()` read to a data-fetching component** (react-query) — both already sit inside `QueryClientProvider` (confirmed: `useAdminRouteContext` proves react-query is already available at this depth of the tree), so no new provider wiring is needed, but both components are no longer render-only with respect to network state the way they were on launch day.

## Alternatives considered

- **A dedicated new "Back to Projects" sidebar/breadcrumb-only link, independent of PROJ-4's own "Projects" item.** Rejected — once the org nav renders at all on project routes, PROJ-4's existing item already does this; a second, differently-labeled entry pointing at the same URL is the exact anti-pattern ADR-0047 itself rejected for a different pair of items.
- **Read `org_id` off `AuthContext`'s login-time org list instead of fetching the `Project` row.** Rejected — `AuthContext`'s org list has no `project_id → org_id` mapping at all (it's a list of orgs the user belongs to, not a project index), and building one client-side would require fetching every org's project list up front, a strictly worse trade than one small `GET /projects/{id}` call scoped to exactly the project in view.
- **Reuse `useAdminRouteContext` directly in `AppSidebar`/`AppBreadcrumb` instead of a new hook.** Rejected — that hook is typed and scoped around the admin registry (`EntityConfig`, `getEntity`), a dependency `AppSidebar`/`AppBreadcrumb` have no other reason to take on; a small, registry-free `useResolvedOrgId()` is the minimal shared surface, at the cost of the two-cache-key trade-off named above.
