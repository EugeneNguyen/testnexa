# ADR-0017: Project creation flow — bespoke route shape, role auto-assignment, standards_profile inheritance

**Date:** 2026-09-03
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0004](0004-rbac-design.md) (RBAC design), [ADR-0007](0007-real-multi-tenancy.md) (real multi-tenancy, 404-vs-403 boundary), [ADR-0015](0015-ai-agent-credential-mechanics.md) (404-vs-403 boundary precedent, `require_permission`'s path-param contract), [ADR-0016](0016-organization-bootstrap-creation-flow.md) (sibling bespoke-creation-route precedent this ADR follows), [PROJ-1 user story](../user-stories/2026-09-03-project-release-stories.md#story-proj-1-create-a-project), [PROJ-1 scope plan](../superpowers/plans/2026-09-03-proj-1-create-project-plan.md)

## Context

PROJ-1 is the first story to build a real create/read/update route for `Project` — and, by extension, the first tenant-scoped CRUD route for any entity below `Organization` itself. Three open questions surfaced that ADR-0016 didn't need to answer (org creation has no parent-entity scoping question, since `Organization` is the tenant root):

1. **Route shape.** The API Document §3 lists `Project` under the eventual generic CRUD factory's path convention (`/projects`, `/projects/{id}`, org resolved indirectly, no `org_id` in the path) — but that factory doesn't exist yet, and every org-scoped route built so far (`agents.py`, `organizations.py`) is bespoke, with `org_id` explicit in the path so `require_permission`'s existing `request.path_params["org_id"]` read and the established any-status-`OrgMembership` 404-vs-403 check apply as-is.
2. **Creator's project-scoped role.** AC1 says the creator is "auto-assigned a project-scoped role appropriate to their action (e.g. `test_manager` if they're already `org_admin`)" — an example, not a full rule. RBAC-4's seeded bundles mean only `org_admin` currently holds `project.create` at all; no other seeded role can reach this code path today.
3. **`standards_profile` default.** `Organization.default_standards_profile` has existed in the schema since the initial migration (07 ERD-sourced) but has never been read by any route — its evident purpose (an org-wide default a new Project inherits) was never wired up.

## Decision

- **`POST /orgs/{org_id}/projects` for create; `GET /projects/{id}` and `PATCH /projects/{id}` for read/update.** Create is bespoke and path-scoped, matching `agents.py`/`organizations.py`'s established shape exactly — zero new plumbing, reuses `require_permission` and the any-status-`OrgMembership` 404-vs-403 check verbatim. Read/update drop `org_id` from the path (the `Project` row itself carries `org_id`, resolved by fetching the row first, same as a future generic-factory item-route would do) — this deliberately anticipates the eventual factory's item-route shape so `Project`'s read/update routes don't need to be rebuilt when the factory lands. The API Document's `Project` listing under §3 (generic factory) gets a footnote, mirroring the existing `Organization`\* footnote: create is bespoke, read/update aren't (yet — the factory may absorb them unchanged later, since their contract already matches).
- **Creator always gets a project-scoped `test_manager` `RoleAssignment`, unconditionally.** Not dynamic role-selection logic keyed off the creator's org-level role — that logic has no second case to handle today (only `org_admin`'s seeded bundle includes `project.create`), so building it now would be speculative generality against a requirement that doesn't exist yet. If a future story lets a custom per-org role also hold `project.create`, this decision is revisited then, with a real second case to design against.
- **`standards_profile` inherits `Organization.default_standards_profile` when omitted from the create payload.** The request schema distinguishes "field omitted" (`exclude_unset`) from "field explicitly `null`" — omitted inherits the org default (itself possibly null); explicit (including explicit `null`) always wins. This is the first code to read `default_standards_profile` since it was migrated in.
- **`GET /projects/{id}` ships alongside `POST`/`PATCH`** even though no AC names it directly — `PATCH` needs fetch-by-id internally regardless, and a create-without-any-way-to-read-it-back route is not a usable flow for the frontend slice this story also ships.
- **TC-PROJ-002 (no orphaned Requirement/TestSuite/TestPlan outside a Project) is schema-enforced already** (non-nullable `project_id` FKs, present since the initial migration) but not *execution*-testable yet — none of those three entities has a create route of its own (the generic CRUD factory that would provide one is unbuilt). Marked covered-at-schema-level, execution-deferred to whichever story adds the first of those routes — same posture ADR-0016/RBAC-1 took for TC-RBAC-002, which this story's `GET`/`PATCH /projects/{id}` routes now make achievable in the *other* direction (cross-org Project access).

## Consequences

**Positive:** Zero new RBAC plumbing — `require_permission`, `has_permission`, and the 404-vs-403 boundary all apply unmodified to the create route; the read/update routes are forward-compatible with the eventual generic factory's item-route contract, so they won't need a rewrite when §3's factory is built, only a possible re-registration. `default_standards_profile` finally has a consumer, closing a schema/behavior gap that's existed since the initial migration. The role-assignment rule is trivially testable (one case, not a matrix) and honestly documents its own limitation rather than half-building generality for roles that can't reach this code path yet.

**Negative / Trade-offs:** `Project`'s three routes don't share one consistent path shape (`org_id` in the path for create, absent for read/update) — a deliberate split, but a reader unfamiliar with the reasoning could mistake it for an inconsistency rather than a bridge to the future factory shape; documented here and in the API Document footnote specifically to head that off. The unconditional-`test_manager` rule is a known simplification that will need revisiting the moment a custom org role can hold `project.create` — flagged in this ADR and the PROJ-1 scope plan so it isn't mistaken for a considered general rule later. `standards_profile` inheritance is inferred product intent (the column's existence implies it, no AC states it explicitly) — if that inference is wrong, only one route's default-fallback logic needs correction, not a schema change.

## Alternatives considered

- **Match the API Document's documented `/projects` path exactly (org_id in the request body for create), building a `has_permission`-with-explicit-org_id inline check instead of reusing `require_permission`** — rejected: doesn't reuse the existing path-param-scoped dependency or the established 404-vs-403 check pattern as cleanly, for a benefit (matching a not-yet-built factory's documented shape precisely) that's purely cosmetic until the factory exists to enforce it project-wide anyway.
- **Dynamic creator-role mapping** (inspect the creator's org-level role, choose a project-scoped role via some explicit mapping table) — rejected as speculative: today there is exactly one reachable case (`org_admin` → `test_manager`), so a mapping table would have one real entry and N imagined ones; revisit when a second case actually exists.
- **No `standards_profile` inheritance — always require it explicit or always null if omitted** — rejected: leaves `Organization.default_standards_profile` permanently dead code with no consumer, contradicting the column's evident purpose in the 07 ERD; the inheritance rule is cheap to implement and reverse if wrong.
- **Skip `GET /projects/{id}`, ship only `POST`/`PATCH`** — rejected: `PATCH` already requires fetch-by-id internally, so the marginal cost of exposing it as its own route is near zero, and the frontend slice needs a read path regardless.
