# ADR-0014: Logout — idempotent single-session revocation policy

**Date:** 2026-09-03
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0003](0003-auth-token-strategy.md) (auth & token strategy — establishes DB-revocable refresh tokens), [ADR-0013](0013-refresh-token-rotation-policy.md) (rotation mechanics `POST /auth/refresh` uses — this ADR reuses its compare-and-swap revoke pattern), [AUTH-3 story](../user-stories/2026-09-03-auth-stories.md), [AUTH-3 scope plan](../superpowers/plans/2026-09-03-auth-3-logout-plan.md)

## Context

ADR-0003 decided refresh tokens are DB-backed and revocable; ADR-0013 pinned down how `POST /auth/refresh` rotates them. Neither addresses the explicit, user-initiated case: what should `POST /auth/logout` actually revoke, how should it behave when the presented refresh cookie is missing, foreign, or already dead, and — since an access token stays valid until its own short TTL lapses regardless of logout (AUTH-3 AC2) — what should the client do about the token it's holding in memory. These are real policy choices, not mechanical details: get the idempotency or the scoping wrong and logout either errors on the very conditions it exists to make harmless, or revokes a session it has no business touching.

## Decision

- **`POST /auth/logout` is authenticated** (bearer access token via the existing `get_current_actor` dependency, same as `GET /auth/me`) and revokes **only the current session's** refresh token — not every `RefreshToken` row for the user ("log out everywhere" is explicitly out of scope; AUTH-3's own acceptance criteria says "their **current** refresh token").
- **Idempotent by design, not by accident.** Missing cookie, hash not found, already-revoked/rotated-out, or a cookie whose row belongs to a different `user_id` than the authenticated caller — all four collapse to the same outcome: `204 No Content`, nothing revoked, no error. Logout's job is "make sure this session is dead"; in every one of those cases it already is. Only a missing/invalid **access** token (rejected by `get_current_actor` before the handler runs) produces a non-2xx response.
- **Revocation reuses ADR-0013's atomic compare-and-swap**, not a plain ORM attribute-mutation + commit: `UPDATE refresh_token SET revoked_at = now(), revoked_reason = 'logout' WHERE token_hash = :hash AND user_id = :authenticated_user_id AND revoked_at IS NULL`, checked by `rowcount`. The `user_id` clause is new relative to `/auth/refresh`'s version of this pattern (which has no cross-user ambiguity to guard against, since it only ever sees the token's own claimed owner) — here it closes the case where the authenticated caller's bearer token and their `refresh_token` cookie name different users, so logout can never revoke a session it doesn't own. `revoked_reason` gains a second value, `"logout"`, alongside `/auth/refresh`'s existing `"rotated"` — no schema/enum change, the column is already free-text.
- **Response is `204 No Content`, no body** — logout returns no data (unlike every other auth route, which returns tokens, org data, or identity), so no response schema is introduced. The `refresh_token` cookie is cleared on the response with the same `httponly`/`samesite`/`secure` attributes it was set with, so the browser drops it rather than retaining an orphaned value.
- **Client-side token clearing is unconditional, not gated on the network call succeeding.** `AuthContext.logout()` always clears the in-memory access token and redirects to `/login`, whether `POST /auth/logout` returns `204`, fails outright (network error), or 401s and gets silently recovered by `apiFetch`'s existing refresh-and-retry interceptor first. The alternative — blocking the "logged out" UI state on a confirmed server round-trip — was rejected: AUTH-3 exists specifically for the shared/public-machine scenario, where the local device no longer holding a usable token is the actual security property being delivered, and it must not be held hostage to network reachability.

## Consequences

**Positive:** logout can never itself become a source of user-facing errors during routine use (double-clicks, a slow tab that already lost its session another way, a browser that dropped the cookie) — every one of those is a no-op 204, not a confusing failure. Reusing ADR-0013's CAS pattern means there is exactly one way `RefreshToken` rows get revoked in this codebase, not two divergent implementations to keep in sync. The `user_id` scoping closes a real (if narrow) cross-session revocation vector for free.

**Negative / Trade-offs:** a genuine network failure during logout leaves the server-side refresh token live while the client believes it is logged out — accepted as a known gap for this pass (see AUTH-3 scope plan §3/§4) rather than adding retry logic or a "logout may not have fully completed" warning, which would slow down the one moment (walking away from a shared machine) where speed matters most. The idempotent-204-on-every-failure-mode design also means logout is a poor observability signal on its own (a client can't tell from the response whether it revoked a real session or a no-op) — acceptable because logout isn't a security *boundary* like login/refresh, it's a best-effort cleanup action; nothing depends on distinguishing those cases.

## Alternatives considered

- **Revoke all sessions for the user ("log out everywhere") on every logout** — rejected: contradicts AUTH-3's stated scope (current session only) and would surprise a user with multiple legitimate concurrent sessions (e.g. desktop + mobile) by silently killing the others. A dedicated "log out everywhere" action, if ever needed, is a distinct future story, not this one.
- **404/401 when the presented refresh cookie doesn't match any live row for the caller** — rejected: distinguishing "nothing to revoke" from "revoked something" leaks information about session state with no defensive value (unlike login's user-enumeration concern, there's no attacker-relevant secret here) and forces the frontend to branch on a case it doesn't need to care about.
- **Block the client-side clear until the server confirms revocation (e.g. spinner + error toast on failure)** — rejected for this pass: adds UI complexity and, worse, a failure mode where a user on a public machine can't complete "log out" at all because the network hiccuped, directly undermining the story's own premise.
