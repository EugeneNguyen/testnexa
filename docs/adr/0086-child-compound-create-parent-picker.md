# 0086. `child_compound_creates` gains a parent-picker for the arm whose scope isn't the bespoke route's own placeholder

**Status:** Accepted
**Decider:** xuanbinh91@gmail.com (CTO)
**Date:** 2026-09-17
**Related:** [ADR-0084](0084-test-cycle-project-scope.md) (the `project_id` scope arm this closes the create gap for), [ADR-0079](0079-child-compound-create.md) (`child_compound_creates` itself — its own docstring named this exact gap as "not yet supported"), [ADR-0078](0078-compound-create-through-bespoke-routes.md)/[ADR-0080](0080-standalone-list-page-compound-create.md) (`compoundParentField`/`pickerScopeParams`, the helpers this reuses verbatim rather than inventing new ones)

## Context

`TestCycle`'s generic `create` is deliberately disabled (`ADR-0033`) — the real create is the bespoke `POST /test-plans/{id}/test-cycles`, reached via `child_compound_creates`. Before ADR-0084, the only scope arm was `test_plan_id`, and the bespoke route's own path placeholder is `{test_plan_id}` — the record being listed already *is* the parent, so `EntityListPage`'s existing `child_compound_creates` support (ADR-0079/0080) needed no picker: the far field and the path placeholder were always the same field.

ADR-0084 gave `TestCycle` a second scope arm, `project_id`, so it lists directly under a project (`/projects/:projectId/admin/test-cycles`) the same way every other project-scoped entity does. But the bespoke create route still only understands `test_plan_id` — a project-scoped list has no `test_plan_id` in its own route context, so the create modal had nothing to submit against. The CTO found this directly: **"i don't see add function, why? in test cycles"** — the project-scoped Test Cycles admin screen had no "New" button at all, because `EntityListPage`'s `childCompoundCreate` lookup only ever matched a declaration whose `far_field` equals the *current* scope field, and no such declaration existed for the `project_id` arm.

This is precisely the gap `EntityRelationTab.tsx`'s own pre-ADR-0086 docstring for `compoundParentField` already named: a `child_compound_creates` declaration whose path placeholder differs from the current scope field needs a picker for that placeholder's own entity first — supported for the many-to-many relation-tab case (`EntityRelationTab.tsx`), never for the standalone-list-page case (`EntityListPage.tsx`) until now.

## Decision

1. **Backend** (`_TEST_CYCLE_CONFIG.child_compound_creates`, `planning.py`): add a second `CompoundCreateAction`, `far_field="project_id"`, same `path_template`/`permission`/`links_automatically` as the existing `test_plan_id` arm, plus `parent_entity="test-plan"`/`parent_label="Test plan"`/`parent_label_field="identifier"` — the parent-picker fields `EntityRelationTab.tsx`'s mechanism already declares and consumes.

2. **`_TEST_CYCLE_CONFIG.create_schema`** changes from `None` to `CreateTestCycleRequest` (the bespoke route's own body schema). This does **not** register a generic `POST` route — `make_crud_router`'s own gate is `"create" in methods AND create_schema is not None`, and `"create"` stays absent from `methods`. It exists purely so `derive_entity_schema` marks `release_id`/`environment_id`/`name` writable+required (they're real fields on the bespoke form ADR-0086 now renders) instead of permanently `readOnly` — the pre-ADR-0086 assumption ("there is no form here") is what set `create_schema=None` in the first place, and ADR-0086 is exactly the ADR that makes that assumption false.

3. **`EntityListPage.tsx`**: when the active `childCompoundCreate` declaration's path-template placeholder (`compoundParentField`) differs from the list's own `scope.field`, render an `FkAutocomplete` parent picker above the create form (scoped via `pickerScopeParams`, reusing `TestPlan`'s own shape-B `project_id` scope resolution — no second `ScopeSelector` step), gate the form on a parent being picked, and lock **both** the picked parent field and the list's own scope field in the submitted form (not just the picked parent) — an early draft locked only the compound parent, leaving the page's own scope field (`project_id`) rendered as a live, empty, confusing picker in the create modal even though the value was already known from the route.

4. **`EntityForm`** gains `fkRouteParams`/`fkExtraParams` props, threaded to every `fk` field's `FkAutocomplete`/`FkSelect`. Closes a second, previously-latent gap this same change surfaced: `release_id` (`Release`'s own bespoke, path-placeholder-scoped list, `/projects/:projectId/releases`) and `environment_id` (`Environment`'s plain `?project_id=` query-scoped list, ADR-0058 shape B) had never before been *editable* fields on any generic `EntityForm` — until ADR-0086 made them writable (point 2), both fields were always `readOnly`/disabled, so nothing had ever needed to scope their own search. `EntityListPage` passes the current route's `{projectId}` (as `fkRouteParams`) and `{project_id}` (as `fkExtraParams`) unconditionally; both are no-ops for a ref entity whose `listPath` needs neither.

## Consequences

- The project-scoped Test Cycles admin screen (`/projects/:projectId/admin/test-cycles`) now has a working "New" button: pick a Test Plan, then fill Release/Environment/Name — the same real, cross-project-validated bespoke route the pre-existing TestPlanDetail form already used, reached through the generic admin surface for the first time.
- No new REST route, no new permission code, no migration. `TestCycle`'s reachable REST surface is unchanged — only the generic admin form's own field-writability derivation and its own create-modal picker logic changed.
- **Found and fixed live, same pass, not caught by the unit-test suite**: the first draft's `lockedValues` locked only the picked compound parent, leaving `project_id` an empty, unlocked, confusing picker in the create form. Caught via a live-browser click-through against the real running `main` stack (locally-minted token via the `/auth/refresh`-mock technique, no credential write) — a passing unit-test suite had no way to catch this, since every existing test fixture for this mechanism only ever had one scope arm to begin with.
- **A second, independent live-only defect found the same pass**: `EntityForm`'s `fk` field render path never threaded `routeParams`/`extraParams` to `FkAutocomplete`/`FkSelect` — a gap invisible until this ADR gave `TestCycle` its first-ever *editable* `fk` fields whose own ref entity needs route/query scoping (`release_id` needs `routeParams`, `environment_id` needs `extraParams`; verified directly — `GET /environments` 422s "project_id is required" with neither). Fixed by adding `fkRouteParams`/`fkExtraParams` to `EntityForm`, passed from `EntityListPage`'s already-resolved route context.
- Verified end-to-end against the real running `main` stack: seeded one `Release`/`Environment` row for a project that had none (both pre-existing gaps in the seed data, unrelated to this change), picked a Test Plan → picked a Release → picked an Environment → filled Name → submitted → new `TestCycle` row appeared in the list with zero errors. Probe rows and seed data deleted afterward.
- Backend unit 915/915 (3 pre-existing assertions in `test_adr79_child_compound_create.py` generalized for a second declaration per entity — a placeholder-equals-far-field check, a declaration-count/`EXPECTED_DECLARATIONS` dict, and a `CLASSIFICATION` bucket flip from `"open"` to `"closed"`; one assertion in `test_plan3_route_boundaries.py` corrected to check `"create" not in methods` — the actual route-registration invariant — rather than `create_schema is None`, which point 2 above makes no longer true). Frontend `tsc --noEmit` clean; Vitest 793/793 (3 new tests in `EntityListPage.childCompoundCreateParentPicker.test.tsx`).

## Alternatives considered

- **Widen `crud_factory` to support a join-scoped generic `create`** instead of a picker on top of the existing bespoke route. Rejected for the same reason ADR-0084 rejected widening the factory for `list`: bigger, more invasive, and the bespoke route's own cross-project `release_id`/`environment_id` validation (ADR-0033) has no generic-factory equivalent to fall back on — the picker is strictly smaller and reuses machinery (`compoundParentField`/`pickerScopeParams`) already built and tested for the many-to-many case.
- **Give `TestCycle` a real, separate `create_schema`-driven generic route** instead of reusing the bespoke one through a picker. Rejected outright — this is the exact `create` restriction ADR-0033 put in place specifically to keep the two-independent-field cross-project check (`release_id`/`environment_id` each validated against the target `TestPlan`'s own `project_id`) from having a second, weaker path around it.
