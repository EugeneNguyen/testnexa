# ADR-0015: AI agent credential mechanics & minimal-RBAC-now decision

**Date:** 2026-09-03
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0003](0003-auth-token-strategy.md) (auth & token strategy — the parent decision this refines, same relationship [ADR-0013](0013-refresh-token-rotation-policy.md) has to ADR-0003 for the human side), [ADR-0004](0004-rbac-design.md) (RBAC design), [ADR-0007](0007-real-multi-tenancy.md) (real multi-tenancy), [AUTH-4 user story](../user-stories/2026-09-03-auth-stories.md), [AUTH-4 scope plan](../superpowers/plans/2026-09-03-auth-4-agent-bearer-auth-plan.md)

## Context

ADR-0003 decided AI-agent auth is a long-lived opaque API key, argon2-hashed at rest, revoke-and-reissue only — but left the key's on-the-wire format, how `get_current_actor` distinguishes it from a human JWT, and the credential-issuance route's permission-check mechanics undecided. Scoping AUTH-4 surfaced a bigger gap: `require_permission`/`has_permission` (`app/core/rbac.py`) are still stubs, and RBAC-1..5 (org bootstrap, invites, role assignment endpoints, seeded system roles) are entirely unbuilt — no `orgs.py` route file exists, no `Permission`/`Role` seed data exists. AUTH-4's AC2 ("agent hitting a permission its role doesn't grant → 403, same RBAC path as a human") is untestable against an `NotImplementedError` stub. This is also the first place in the codebase an org-scoped route (`/orgs/{org_id}/agents`) has to decide the 404-vs-403 boundary concretely, rather than just citing NFR-1 in the abstract.

## Decision

- **Raw key format:** `tnx_agent_<key_prefix>_<secret>` — `key_prefix` is 8 URL-safe characters, `secret` is `secrets.token_urlsafe(32)` (43 URL-safe characters). The literal `tnx_agent_` string lets `get_current_actor` cheaply branch on bearer-token shape (`startswith` check) before attempting a JWT decode, instead of decode-and-catch as the discriminator.
- **`key_prefix` doubles as a lookup-narrowing index, not just a display hint.** Argon2 hashes are salted and non-deterministic, so `AIAgent.key_hash` can't be looked up by equality. `key_prefix` is extracted from the presented raw key and used for `SELECT ... WHERE key_prefix = :prefix AND revoked_at IS NULL` before the argon2 verify — narrowing to (in practice) zero or one candidate row instead of a full-table verify-every-active-agent scan.
- **`AIAgent.last_used_at`** (new nullable `timestamptz` column) is the AC3-required `AuthIdentity.last_login_at`-equivalent for agent sessions. Updated on **every successful agent-bearer authentication** (not throttled to MCP-session boundaries) — an agent key is presented per-request with no separate session-establishing exchange the way a human JWT is, so "last used" is the closest true analogue, and simplicity wins over write-amplification optimization given this persona's explicit low-priority status.
- **`has_permission`/`require_permission` are implemented now, by AUTH-4, minimally.** Scope: the generic 4-table resolution (`RoleAssignment` → `Role` → `RolePermission` → `Permission`, org-wide grants only — `project_id IS NULL`) that any org-scoped permission check needs. This is self-contained plumbing, not RBAC-1..5's own business flows (org bootstrap, invites, seeded system roles, project-scoped grants) — those stay separately scheduled. Tests seed `Role`/`Permission`/`RoleAssignment` rows directly via fixtures, the same fixture-bypass precedent AUTH-1 set for `User`/`Organization`/`OrgMembership`. Two `Permission` catalog rows (`ai_agent.create`, `ai_agent.update`) are seeded via an Alembic data migration — scoped to exactly what this story's own routes need, not the full canonical catalog (RBAC-4's job).
- **404-vs-403 boundary for org-scoped routes, established here as the codebase's first instance:** the route checks the requester has *any* `OrgMembership` in the path's `org_id` first — none (including a nonexistent `org_id`) → 404, consistent with NFR-1's "cross-tenant existence is never confirmable." Membership present but `require_permission` fails → 403. Every future org-scoped route inherits this split.
- **Credential issuance/revocation is human-only**, enforced as a hardcoded check independent of `RoleAssignment` contents — mirrors RBAC-5's double-enforcement pattern for Approval (an agent can't be granted, accidentally or otherwise, the ability to mint or kill agent credentials).

## Consequences

**Positive:** AC2 becomes testable without pulling RBAC-1..5 forward wholesale; the 404/403 split gets decided once, deliberately, instead of being improvised inconsistently by whichever story builds the next org-scoped route; `key_prefix`'s role as a real lookup key (not just a UI nicety) is documented before implementation, avoiding an O(n) argon2-verify-every-agent scan; `last_used_at` closes the AC3 gap without inventing a new generic audit-log mechanism (07's still-unresolved open question #3), consistent with this repo's existing per-concern audit-field pattern (`LoginAttempt`, `RefreshToken.revoked_reason`, `AuthIdentity.last_login_at`).

**Negative / Trade-offs:** `has_permission`/`require_permission`'s project-scoped branch is implemented (per RBAC-3's documented design) but not exercised by AUTH-4's own tests — RBAC-3 still owns that coverage, a partial-implementation seam future work must respect rather than silently duplicate. One extra `UPDATE` per authenticated agent request (`last_used_at`) is acceptable at this persona's expected scale but would need revisiting if agent-driven traffic ever became high-throughput. Seeding only 2 permission codes now means the full RBAC allow/deny matrix (Test Design §3) still can't run end-to-end until RBAC-4 lands its seed migration — AUTH-4 only unblocks its own two routes.

## Alternatives considered

- **Block AUTH-4 on RBAC-3/RBAC-4 landing first** — rejected: turns a "Should"-priority, exploratory-persona story into a dependency chain on two "Must"-priority but larger, unstarted stories, with no requirement that RBAC-1..5's own business flows (invites, project-scoped grants, seeded role UI) actually be built to satisfy AUTH-4's AC2.
- **Decode-and-catch JWT-vs-key discrimination** (try `decode_token`, fall back to key lookup on failure) instead of a literal-prefix `startswith` check — rejected: conflates two genuinely different failure modes (malformed/expired JWT vs. "this was never a JWT") behind one exception-handling path, and is more expensive on the common case (every agent request would first pay a failed JWT-parse attempt).
- **Full-table argon2-verify scan instead of `key_prefix`-narrowed lookup** — rejected: correct at small scale but a deliberate footgun once an org has more than a handful of agents; `key_prefix` was already reserved as a column for GitHub-PAT-style display, reusing it as a lookup key costs nothing extra.
- **`last_used_at` updated only on `mcp_session_ref` change (session-start semantics) instead of every request** — considered, not chosen: cheaper on writes, but adds "did the session change" tracking complexity for a persona this story explicitly says not to prioritize polish for.
