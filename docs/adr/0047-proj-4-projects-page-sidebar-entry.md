# ADR-0047: PROJ-4 gives Project CRUD its own sidebar-reachable page, amending ADR-0039's placement on "Dashboard"

**Date:** 2026-09-09
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0039](0039-dash-2-org-home-dashboard-relabel-and-project-table.md) (DASH-2 — put full Project CRUD on `OrgHome`/"Dashboard"; this ADR amends its placement decision only, not its Project-CRUD behavior), [ADR-0040](0040-role-assignment-project-cascade-delete.md) (Delete cascade fix, unaffected), [ADR-0041](0041-ds-2-table-container-shared-pagination.md) (shared `Table` container, unaffected — `ProjectsPage.tsx` reuses it verbatim), [ADR-0017](0017-project-creation-flow.md) (Project creation flow, unaffected), [ADR-0018](0018-admin-shell-sidebar-layout.md) (sidebar's single nav-item-list extension point, AC5 — this story uses exactly that extension point), [ADR-0022](0022-generic-crud-router-factory.md) (generic factory `GET`/`DELETE /projects`, unaffected)

## Context

Every backend route Project CRUD needs already shipped (`POST /orgs/{org_id}/projects`, `GET /projects/{id}`, `PATCH /projects/{id}`, `GET /projects?org_id=`, `DELETE /projects/{id}` — ADR-0017/ADR-0022) and the full management UI (table, Edit modal, Delete confirm modal, search/sort/pagination) already shipped on `OrgHome`/"Dashboard" (ADR-0039). What didn't exist: a sidebar nav entry a user could click to reach Project management directly — the only way in was via the org's landing screen, which DASH-2 had by then relabeled "Dashboard" and loaded with two summary widgets and `RoleAssignmentsPanel` alongside the Project table.

This story's literal ask ("add project CRUD to the side menu") could have been satisfied two ways: (a) add a "Projects" nav item that links to the existing `/orgs/:orgId` route (zero code move, but two differently-labeled sidebar items pointing at the same page reads as a UX bug, not a feature), or (b) give Project CRUD its own dedicated route and nav entry, trimming "Dashboard" back down to a true summary screen. Per the plan-with-open-questions pass for this story, (b) was the confirmed default — it's also the more legible shape long-term: "Dashboard" as a landing/overview screen and "Projects" as the entity-management screen are two different jobs that happened to share one URL only because no sidebar existed yet when ADR-0039 was written.

No backend or database change is required anywhere in this story — every route Project CRUD needs already existed; this is a pure frontend relocation.

## Decision

1. **New route, `/orgs/:orgId/projects`, new component `ProjectsPage.tsx`.** The entire Project CRUD block — table (ID/Name/Standards profile/Actions), "New Project" modal, Edit modal, Delete confirm modal, client-side search/sort/pagination (DS-2's shared `Table` container in client mode) — moves out of `OrgHome.tsx` into this new file **verbatim**: every `data-testid`, Zod schema, and API call is the same code ADR-0039/ADR-0040/ADR-0041 already shipped, not rewritten. Only the page's own heading changes ("Projects", not "Dashboard") and the mount route changes.
2. **New flat sidebar nav item, "Projects".** `AppSidebar.tsx`'s single nav-item-list extension point (ADR-0018 AC5) gains one entry, `sidebar-nav-projects` → `/orgs/:orgId/projects`, positioned between "Dashboard" and "Members". **No icon** — DASH-2/TC-SHELL-021 established "Dashboard is the only sidebar item with an icon" as an explicit, tested invariant (its own "icon-exclusivity" negative-check class); this story deliberately leaves that invariant unchanged rather than silently expanding it, the same "story's own literal ask" posture ADR-0039 itself took for the same invariant.
3. **`OrgHome.tsx`/"Dashboard" trims down to a true summary screen.** What remains: the two stat widgets (FR-SHELL-3, unchanged) and `RoleAssignmentsPanel` (RBAC-3, unchanged). The "Members" quick-link button stays (a pre-existing convenience affordance, independent of the sidebar's own separate `Members` item).
4. **The Project-count widget becomes a link to the new page**, wrapped in a `<Link to="/orgs/:orgId/projects">` — the widget itself (query, count-sourcing, `data-testid`) is untouched; only its container changes from a bare `<div>` to an anchor. This avoids duplicating the Project table in two places while still giving "Dashboard" a one-click path into Project management.
5. **Breadcrumb entry added**, `/orgs/:orgId/projects` → Dashboard (linked) → Projects (active), inserted before the generic `/orgs/:orgId` catch-all pattern (the same ordering rule `AppBreadcrumb.tsx`'s own docstring already documents for `/orgs/pick`).

## Consequences

**Positive:** Project management is now reachable from anywhere in the shell via one click, not gated behind first loading the org's summary screen. "Dashboard" becomes a more legible summary-only screen, resolving (for this one screen) the "table living somewhere a screen named 'Dashboard' arguably shouldn't own everything" tension implicit in ADR-0039's own accepted trade-offs. Zero backend/schema/RBAC change — every route, permission gate, and 404-vs-403 boundary Project CRUD relies on is exactly what ADR-0017/ADR-0022/ADR-0040 already shipped.

**Negative / accepted trade-offs:**

- **This amends, not reverses, ADR-0039.** ADR-0039's own Decision/Consequences text is left exactly as written (per this repo's "flag drift, don't silently absorb" convention) — it correctly describes what shipped and when. This ADR's Decision section above is the record of what changed and why, cross-referenced from both directions (ADR-0039 gains a one-line forward-pointing addendum, this ADR names ADR-0039 as "Related" above).
- **Existing e2e specs' navigation flow changed.** `project-create.spec.ts`/`release-create.spec.ts`/`ds2-table-container.spec.ts` all used to interact with the "New Project" modal and Project table directly on `/orgs/:orgId` (real UI navigation, no raw `page.goto`) — each now clicks the sidebar's new "Projects" item first. No assertion content changed, only the navigation step count; all three re-verified green against a fresh isolated stack (`testnexa-proj4-test`, 2026-09-09) — on the implementation's own worktree branch (`proj-3-sidebar-crud`, commit `4610efc`), not yet merged into `main` as of this ADR's own docs-only landing (see WBS 11.30's addendum).
- **DASH-2's own TC-PROJ-019..024 rows (Test-Cases doc) named "Load OrgHome/Dashboard" as their setup step** — now stale for those 6 rows specifically (the table itself moved, the assertions did not). Corrected in place per this repo's own "revise, don't silently leave stale" doc convention (see Test-Cases doc's own recompute note for this pass), not struck through — the *behavior* TC-PROJ-019..024 assert is still exactly true, just reachable via a different page now.
- **No new icon on the "Projects" sidebar item, by deliberate choice (Decision §2).** A future story could reconsider DASH-2's "one icon only" invariant if the sidebar's own visual language changes generally — not decided here.

## Alternatives considered

- **Point a new "Projects" nav item at the existing `/orgs/:orgId` route, no code move.** Rejected — two sidebar items ("Dashboard" and "Projects") both resolving to the same URL is a worse user-facing result than the story's own literal ask; a user clicking "Projects" and landing on a screen headed "Dashboard" reads as a bug.
- **Keep the Project table on "Dashboard" too, in addition to the new page (duplicate surfaces).** Rejected — maintaining two live copies of the same CRUD surface (or one real + one link-through) is the classic dual-surface-drift trap this repo's own ADR-first policy exists to avoid; one canonical location is simpler and matches how every other entity in this app (Roles, Test Plans, etc.) already works — one page, reached via nav.
- **Add an icon to the new "Projects" item, matching the Project-count widget's own `fa-solid fa-folder`.** Considered, rejected for this pass specifically to avoid silently expanding DASH-2's tested "Dashboard is the only icon item" invariant without a story that actually asks for a broader icon treatment — see Consequences.
