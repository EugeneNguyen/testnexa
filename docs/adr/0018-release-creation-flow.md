# ADR-0018: Release creation flow — project-path-scoped bespoke routes, `test_manager` RBAC bundle extension, triple-permission audit query gate

**Date:** 2026-09-04
**Status:** Accepted
**Deciders:** xuanbinh91@gmail.com (CTO)
**Related:** [ADR-0004](0004-rbac-design.md) (RBAC design), [ADR-0007](0007-real-multi-tenancy.md) (real multi-tenancy, 404-vs-403 boundary), [ADR-0017](0017-project-creation-flow.md) (sibling bespoke-route precedent this ADR extends one level down the resource tree), [PROJ-2 user story](../user-stories/2026-09-03-project-release-stories.md#story-proj-2-create-a-release-and-target-test-cycles-to-it), [PROJ-2 scope plan](../superpowers/plans/2026-09-03-proj-2-create-release-plan.md)

## Context

PROJ-2 adds `Release`, the first resource scoped under `Project` rather than directly under `Organization`. `Release` and `TestCycle` are both migrated already (initial schema) and both listed in the API Document's generic-CRUD-factory entity table — but, same as ADR-0017 found for `Project`, that factory doesn't exist yet. Four open questions surfaced, resolved with the user 2026-09-04:

1. **Route shape and path scoping.** No `org_id` is available to scope by directly — `Release` hangs off `Project`, which itself hangs off `Organization` — so the existing `require_permission`(path-param) dependency doesn't fit `POST .../releases` as cleanly as it fit `POST /orgs/{org_id}/projects`.
2. **RBAC bundle reachability.** RBAC-4's seeded catalog already contains `release.create`/`.read`/`.update`/`.delete`, but only `org_admin`'s bundle (defined as "every permission") includes them — `test_manager`, despite already holding full `test_cycle` CRUD, holds none of `release.*`. Marcus, PROJ-2's persona, is framed as a compliance-focused `test_manager`, not necessarily an `org_admin`.
3. **Audit query response shape.** AC2 requires answering "what was tested for release X" as one queryable unit — ambiguous whether the query response should nest `TestExecution` data or just return `TestCycle` rows for a caller to chase separately (no `GET .../executions` route exists to chase with, today).
4. **Audit query permission gate.** A `release.read`-scoped view that also exposes `TestCycle`/`TestExecution` data could be gated on `release.read` alone (matching every other bespoke route's single-permission-per-route posture) or on all three resources' `.read` permissions.

`TestCycle` itself has **no create route** in this codebase — that's FR-PLAN-3's scope, a separate not-yet-built story. AC2's "when a TestCycle is created and linked to it" is therefore schema-level only for this ADR (the FK is already non-nullable, migrated); this ADR governs querying an existing link, not creating one.

## Decision

- **`POST`/`GET /projects/{project_id}/releases` for create/list; `GET /releases/{id}` and `GET /releases/{id}/test-cycles` for single-fetch and the audit query — no `PATCH`/`DELETE` (no AC asks for Release edit/delete).** Create/list carry `project_id` in the path and fetch the `Project` row first to resolve its `org_id` for the 404-vs-403 boundary, then call `has_permission` directly (not `require_permission`, which reads `org_id`/`project_id` off *path* params — there is no `org_id` path segment here, same reasoning ADR-0017 used for `GET`/`PATCH /projects/{id}`). Single-fetch and the audit query drop `project_id` from the path entirely, resolving `org_id` from the fetched `Release` → `Project` chain — one more hop than `Project`'s own row-resolved routes, same pattern extended one level.
- **`test_manager`'s seeded bundle gains `release.create`/`.read`/`.update`** via a new Alembic data migration (existence-checked insert, same idempotent-re-run posture as `d33d66f4b3c3_seed_ai_agent_permissions.py`) — not `.delete`, since no delete route exists to reach it. This is a deliberate, considered bundle change (unlike ADR-0017's "leave it `org_admin`-only, flagged as a known simplification" call for `Project`) — `test_manager` already holds full `test_cycle` CRUD, so withholding `release.*` from the same role was an oversight in the original RBAC-4 seed, not a considered restriction, and Marcus's persona needs to reach `release.create` without being `org_admin`.
- **`GET /releases/{id}/test-cycles` nests each `TestCycle`'s `TestExecution`s in the response**, not a cycles-only list requiring N follow-up calls (there's no `GET .../executions` route to make those calls against anyway). This matches the audit-evidence framing directly: one call answers "what was tested for release 2.3."
- **That endpoint gates on all three — `release.read` AND `test_cycle.read` AND `test_execution.read`**, `403` if any is missing (checked as three separate `has_permission` calls, not a partial/degraded response for a partial grant). This is a deliberate departure from the rest of the codebase's one-permission-per-bespoke-route posture (e.g. `test-plans/{id}/approve` gates on `test_plan.approve` alone) — justified because this one route is the sole place `TestExecution` data is exposed without a `test_cycle_id` in the request path, so `release.read` alone would let a Release-only viewer see execution data they hold no direct permission for.
- **Release listing's `target_date` sort pins `NULLS LAST` explicitly for both `asc` and `desc`**, not Postgres's implicit per-direction default (`NULLS LAST` for `ASC`, `NULLS FIRST` for `DESC` unless overridden) — AC3 ("listable/sortable by target date") reads as "releases without a target date sort to the end regardless of direction," and relying on the engine default would silently flip that for `desc` queries.

## Consequences

**Positive:** Reuses every RBAC/tenancy primitive as-is (`has_permission`, the any-status-`OrgMembership` 404-vs-403 check, flush-then-catch-`IntegrityError`), same zero-new-plumbing posture ADR-0017 established. `test_manager` becomes the practical owner of the full Release/TestCycle/TestExecution audit chain it's already positioned for by its existing `test_cycle.*` grant — closes a real gap rather than deferring it as a known simplification. The nested-executions response directly serves the story's own "queryable unit" framing without inventing a second endpoint. Pinning `NULLS LAST` removes a subtle direction-dependent behavior flip that would otherwise be invisible until someone sorted descending.

**Negative / Trade-offs:** The triple-permission gate is the first bespoke route in this codebase requiring more than one permission code, a small precedent departure that needs to stay documented here so a future reader doesn't assume it's this route's bug rather than its design. The RBAC bundle migration is a second data migration touching seeded system-role rows (after `d33d66f4b3c3`) — low risk given the existence-checked-insert pattern is already proven, but it does mean `test_manager`'s bundle is no longer fully defined by the original RBAC-4 migration alone; a reader auditing `test_manager`'s permissions must know to check both migrations. `Release`/`TestCycle` remain excluded from the API Document's generic-factory entity list, same accumulating debt ADR-0017 flagged for `Project` — two entities down, the factory itself still unbuilt.

## Alternatives considered

- **Leave `test_manager` without `release.*`, `org_admin`-only reachability** (mirroring ADR-0017's Q2 exactly) — rejected: unlike `Project.create` (where no other seeded bundle comes close to CRUD-adjacent), `test_manager` already holds full `test_cycle` CRUD, making the `release.*` gap look like an oversight rather than a considered boundary, and Marcus's persona specifically needs it.
- **`GET /releases/{id}/test-cycles` returns cycles only, gated on `release.read` alone**, leaving executions to a future `GET /test-cycles/{id}/executions` route — rejected: that route doesn't exist and isn't in this story's scope to add, so this alternative would ship AC2 only half-satisfied (queryable cycles, not transitively queryable executions) until some future, unscheduled story closes the gap.
- **Build the generic CRUD router factory now**, serving `Release`/`TestCycle` through it instead of bespoke routes — rejected, same YAGNI reasoning ADR-0017 used: two entities isn't enough usage to justify the factory's own design cost yet; revisit once a third or fourth bespoke-route entity makes the duplication cost clearly exceed the factory's build cost.
- **Rely on Postgres's default `NULLS FIRST`/`NULLS LAST` behavior per sort direction** instead of pinning explicitly — rejected: correct today only by accident of the default matching intent for `ASC`; a `desc` sort would silently put undated releases first, which reads as "most urgent" rather than "unscheduled," the opposite of the intended audit-review order.
