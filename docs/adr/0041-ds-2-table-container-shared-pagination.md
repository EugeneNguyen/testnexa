# ADR-0041: DS-2 shared `Table` container (table + pagination + page-size selector), `src/container/` location, page-size max raised to 100

**Date:** 2026-09-07
**Status:** Accepted — every decision here (the `container/` location, two pagination modes, 10/25/50/100 page sizes with a reset-to-page-1 on change, backend max `page_size` 100, `role-assignments`' envelope) stands unchanged. **Markup only is superseded by [ADR-0042](0042-adminlte-design-system.md)** (2026-09-08): the page-size selector is a raw `<select className="form-select form-select-sm">` rather than a `CFormSelect`, and the table/pagination chrome is raw `table.table` + `nav > ul.pagination > li.page-item > button.page-link`. One behavioral consequence worth knowing when reading this ADR's tests: under CoreUI the *active* page item rendered as a `<span>` with its `onClick` silently dropped; hand-rolled, every page item is a real `<button>` with a live handler — see `frontend/CLAUDE.md`.

**Related:** [ADR-0012](0012-coreui-design-system.md) (CoreUI design system), [ADR-0022](0022-generic-crud-router-factory.md) (generic CRUD pagination convention, NFR-6), [ADR-0023](0023-frontend-shared-component-location.md) (frontend shared-component location — amended by this ADR), [ADR-0027](0027-generic-admin-crud-ui-and-backend-completion.md) (`EntityTable`), [ADR-0039](0039-dash-2-org-home-dashboard-relabel-and-project-table.md) (DASH-2 — the Project table's own bespoke pagination, partially superseded by this ADR), [DS-2 user story](../user-stories/2026-09-04-design-system-component-stories.md#story-ds-2-reusable-table-container-pagination--page-size-selector), [DS-2 UI Design Document](../ui-design/2026-09-07-ds-2-table-container-ui-design.md)

## Context

A direct product ask (not a business-case discovery this time — DS-1's own business case explicitly scoped itself to one narrow, evidenced opportunity, `FormField`; this is a second graduated instance requested directly, same posture root `CLAUDE.md`'s "raw-HTML-instead-of-`@coreui/react`... not a special case" precedent already established for a different component class): build one reusable table container (table + pagination + page-size selector, 10/25/50/100) and reuse it everywhere a table renders today.

An audit (2026-09-07) found six independent table implementations in `frontend/src/`, no two alike:

| Location | Pagination? | Page-size selector? |
|---|---|---|
| `components/crud/EntityTable.tsx` (generic admin CRUD, 24 entities) | Yes — `CPagination`, driven by caller-supplied `page`/`pageSize`/`total` props | No — caller (`EntityListPage.tsx`) hardcodes `PAGE_SIZE = 25` |
| `pages/workflows/OrgHome.tsx` (Project table, labeled "Dashboard" per [ADR-0039](0039-dash-2-org-home-dashboard-relabel-and-project-table.md), shipped the same day this ADR was written) | Yes — own `CPagination`, client-side over an already-fully-fetched+search-filtered+sorted array | No — hardcodes `PAGE_SIZE = 10` |
| `RoleAssignmentsPanel.tsx` | No — renders the full array | No |
| `pages/workflows/OrgMembers.tsx` | No — renders the full array | No |
| `pages/workflows/ProjectDetail.tsx` (outer-level Release/TestSuite/RiskItem tables) | No — renders the full array | No |
| `pages/workflows/TestPlanDetail.tsx` (test plans list) | No — renders the full array | No |

Separately, the backend's generic pagination convention (`page`/`page_size`, NFR-6, [ADR-0022](0022-generic-crud-router-factory.md)) hardcodes `page_size`'s default **and max** at 25 (`crud_factory.py`'s `_MAX_PAGE_SIZE`), and `GET /orgs/{org_id}/role-assignments` has no pagination at all — a bare `list[RoleAssignmentSummary]`, no `page`/`page_size` params, no envelope. A page-size selector offering 100 as an option is meaningless if the backend silently clamps every request to 25 regardless, and `role-assignments`' table can't be driven by the same container as every other screen while its backing route has no pagination contract to drive.

## Decision

- **New `frontend/src/container/Table.tsx`** — a *smart* component (owns `page`/`pageSize` state and the actions that change them), not a presentational one dropped into `components/shared/`. This is a deliberate departure from ADR-0023's `components/shared/` bucket, which that ADR scoped explicitly to markup-composition primitives with no state/action ownership of their own (`FormField` holds no state). `Table` genuinely differs on that axis — it owns pagination state and exposes `onPageChange`/`onPageSizeChange`, closer to a container/presentational split than a shared UI primitive. **`frontend/src/container/` is established as a new top-level `src/` convention by this ADR**, amending ADR-0023 to add a third axis (`shared/` = stateless composition, `crud/` = generic-entity-shape-driven, `container/` = stateful cross-screen behavior) rather than forcing `Table` into either existing bucket.
- **Two pagination modes**, both driven by the same component:
  - **Server mode** (`EntityTable`, `RoleAssignmentsPanel`, `OrgMembers`, `ProjectDetail`'s outer tables, `TestPlanDetail`): caller passes the *current page's* `items`/`total` (from a `{items,total,page,page_size}` envelope) plus `page`/`pageSize`/`onPageChange`/`onPageSizeChange`; the container re-fetches on either callback.
  - **Client mode** (`OrgHome`'s Project table only): caller passes the *full* already-filtered/sorted array; the container slices it locally for the current page. This preserves [ADR-0039](0039-dash-2-org-home-dashboard-relabel-and-project-table.md)'s explicit, still-valid decision that Project search/sort stay client-side with no backend round trip — this ADR does not reopen that call, only replaces the *pagination chrome* `OrgHome` hand-rolled around it with the shared container. `OrgHome`'s own `SortableHeader`/search-input markup stays bespoke, passed to the container as its header/toolbar slot.
  - The container itself doesn't know or care which mode is active — both are "a page of rows + a total count," just sourced differently by the caller.
- **Page-size selector**: a `CFormSelect` offering `10`/`25`/`50`/`100`, changing it resets to page 1 (both modes). No persistence (component state only — resets on unmount/reload, matching every other bespoke screen's existing no-persistence convention today).
- **Backend max page_size: 25 → 100**, hardcoded as a literal `100` at each of the three call sites that currently hardcode `25` (`crud_factory.py`'s `clamp_pagination` default, `org_memberships.py`, `releases.py`) — no shared named constant introduced, matching the CTO's explicit instruction to keep this a plain literal rather than adding cross-module coupling for a single-digit-of-call-sites change. `page_size`'s **default** stays 25 (unchanged) — only the ceiling moves, so an existing caller that never specifies `page_size` sees no behavior change.
- **`GET /orgs/{org_id}/role-assignments` gains pagination**: `page`/`page_size` query params (default 25, max 100, same clamp helper), response becomes the standard `{items, total, page, page_size}` envelope — closing the one remaining table-backing route with no pagination contract, so `RoleAssignmentsPanel` can be driven by the container in server mode like every other retrofitted screen. This is a **breaking response-shape change** for any existing caller (none exist outside `RoleAssignmentsPanel.tsx` itself, confirmed by grep) — no deprecation path needed.
- `EntityTable.tsx` is refactored to consume the new container internally rather than maintaining its own `CPagination` block — its external prop contract (`fields`, `config`, permission callback) is unchanged, only its internal pagination/page-size chrome moves onto the shared implementation.

## Consequences

**Positive:** One table+pagination+page-size implementation instead of two divergent bespoke ones (`EntityTable`'s and `OrgHome`'s) plus four unpaginated ones. Every list-backing screen gains a working page-size selector (10/25/50/100) for the first time — today, none do. The backend's 25-row ceiling, which silently made "100" a meaningless UI option, is raised to actually match. `role-assignments` joins every other list route's pagination contract, closing a structural inconsistency that predates this story.

**Negative / Trade-offs:** `OrgHome`'s Project table pagination chrome, which shipped via ADR-0039 hours before this ADR, is replaced rather than reused — a short-lived bespoke implementation, not a wasted one (ADR-0039's own search/sort decision stands, only the pagination widget itself is swapped). Two pagination *modes* in one component is more surface area than a single server-only design would need — accepted because `OrgHome`'s already-shipped, deliberately-client-side search/sort (ADR-0039) would otherwise be forced into either a regression (drop search/sort) or a second, unshared pagination implementation (defeating this ADR's own purpose). Raising `page_size`'s ceiling to 100 raises the worst-case single-response payload 4× for every generic-CRUD entity, not just the ones a human actually selects 100 for via the UI — accepted risk, tracked as a Test Plan risk row (mitigated by the clamp itself still being a hard, enforced ceiling, not an unbounded escape hatch).

## Alternatives considered

- **Server-mode-only, force `OrgHome` to drop client-side search/sort or add a backend `order_by`/`?q=` param** — rejected: ADR-0039 explicitly decided against a backend round-trip for Project search only hours before this ADR, on a "confirmed: adding `order_by`/sort support at all today... out of scope" basis; reopening that call is out of scope for a pagination-container story and would silently re-litigate a decision the CTO doc-reviewed same-day.
- **`components/shared/Table.tsx`** — rejected per explicit CTO direction: the component owns state/actions (page, pageSize, the callbacks that change them), which is exactly the axis ADR-0023 drew `components/shared/`'s boundary around excluding.
- **Extend `EntityTable.tsx` in place, no new container** — rejected: `EntityTable` is coupled to `EntityConfig`/`FieldConfig` (ADR-0023's `components/crud/` axis, generic-entity-shape-driven); every bespoke screen's table has a different row shape with no `EntityConfig` behind it, so a component the bespoke screens can actually consume has to be config-shape-agnostic, which `EntityTable` structurally isn't.
- **Named constant (`_MAX_PAGE_SIZE = 100`) instead of a literal** — rejected per explicit CTO direction: three call sites is not enough call-site duplication to justify the indirection at this codebase's current scale.
- **Defer `role-assignments` pagination to a later story** — rejected per explicit CTO direction ("add now"): leaving one table-backing route unpaginated would mean the container's server mode has no path to drive `RoleAssignmentsPanel`, defeating "reuse for all current tables."
