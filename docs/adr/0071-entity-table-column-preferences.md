## Context

`EntityTable` (`frontend/src/components/organisms/entity-table/entity-table.tsx`) renders exactly one column per `config.fields` entry with `showInTable !== false`, in the order the served schema lists them, identically for every user of every org — `const tableFields = config.fields.filter((f) => f.showInTable !== false)` is the whole of it. There is no way to hide a column, and no way to move one.

That was fine while the surface was small. It is not fine now: this is the single rendering path for ~28 admin pages (ADR-0027's final scope), several of which are genuinely wide — an entity carrying its own fields plus FK columns plus `created_at`/`updated_at` audit columns overflows horizontally at laptop width, and the columns a given person actually reads are a small, *personal* subset of that. `showInTable` is the backend's own answer to "is this field a table column at all" (ADR-0055), and it is deliberately a single global answer: it is declared once in `CrudEntityConfig.field_meta`, serves every caller identically, and is the right place for "this field is structurally not tabular." It is the wrong place for "Priya doesn't care about `updated_at` on the Defect list" — that is per-person taste, changes daily, and must not require a backend deploy.

ADMIN-4 (ADR-0056) established the shape of the answer for the adjacent problem (row *order*): a header affordance on `EntityTable`, state owned one level up in `EntityListPage`, and a backend query parameter doing the actual work. Column visibility/order is the same *kind* of user-facing control and a structurally different *kind* of state: it never reaches the server at all.

## Decision

1. **A new "Columns" button in `EntityTable`'s own `.card-header .card-tools`**, beside the existing search box and the caller-supplied `headerActions` (the same flex row ADMIN-4's own header affordances already live in — no new header region). It opens a new **`ColumnPreferencesModal`** organism (`frontend/src/components/organisms/column-preferences-modal/`, per ADR-0043's tiering — it composes existing primitives and owns its own draft state, which is an organism, not a molecule). The modal lists every field the entity's **served schema** exposes as a table column, i.e. exactly the `showInTable !== false` set — the same source the rendered columns themselves come from (`GET /entities/{resource}/schema`, ADR-0055), never a second, independently-derived list. A field the backend says is not a table column is not offerable here; this feature narrows the served set, it never widens it.

2. **Checkbox per field (show/hide) + Up/Down buttons per field (reorder), plus a "Reset to defaults" action** that clears the stored preference outright (not "re-writes a preference equal to the default" — see decision 6 for why the distinction matters when the schema later changes). The first row's Up and the last row's Down are disabled, the ordinary boundary posture for a move-in-list control.

   **Up/down, not drag-and-drop, deliberately.** No drag library is a frontend dependency today, and none of the hand-written-markup primitives this repo standardised on (root `CLAUDE.md`'s "raw HTML/JSX against the CSS" rule) supplies dragging. Adding one would be a new dependency decision with its own accessibility, touch-target and testability surface — this story declines it explicitly rather than smuggling it in as an implementation detail. Up/down buttons are also directly assertable in Vitest without a pointer-event harness, which drag-and-drop is not.

3. **Persistence is `localStorage`, keyed per entity** — `testnexa.column-prefs.<config.resource>`, where `resource` is the snake_case per-entity slug (`requirement`, `test_case`) that already exists on `EntityConfig` as the permission-code resource segment, so two entities can never collide on one key. The stored value is versioned:

   ```json
   {"v": 1, "order": ["title", "status", "created_at"], "hidden": ["created_at"]}
   ```

   **Every read and every write is wrapped in `try`/`catch`.** `localStorage` can throw outright (a private window, blocked site data, a storage-quota failure on write) and can return `null` or garbage on read; in every one of those cases the surface degrades to the config's own default column set and order and keeps working. A preference is a convenience, never a precondition for rendering the table (NFR-71).

4. **`EntityTable` owns this state itself** — not `EntityListPage`, which owns `page`/`pageSize`/`sort`/`filters`/`search`. This is a deliberate departure from ADR-0056's own state-ownership decision, and the reason is the line those four share and this one doesn't: **each of them maps to a backend query parameter**, so each belongs to the component that owns the list query. Column visibility and order map to nothing server-side — the same rows come back either way — and affect only what this one component paints. Pushing them up to `EntityListPage` would mean prop-plumbing state through a boundary it has no use for, and would silently exclude every *other* `EntityTable` caller (present and future) from the feature. Owning it in `EntityTable` means every caller gets it with zero prop changes and zero opt-in. In-repo precedent for a component owning its own `localStorage`-persisted preference: `AppHeader`'s color mode (ADR-0054), which is likewise a per-browser rendering preference with no server-side counterpart. **`EntityListPage.tsx` needs no change at all for this story.**

5. **Two classes of always-visible ("locked") field, a deliberate judgment call:**
   - **(a) the config's `detailLinkField` when `detailPath` is set** (ADR-0060's mechanism — `Project.name` is the only instance today). That cell carries the only navigation from the list into the entity's real detail workspace; hiding it strands the user on a list they cannot click through, with no error and no obvious way to recover.
   - **(b) whichever field is the *last remaining visible* one.** The modal disables that checkbox dynamically, so an admin cannot walk the list down to zero and leave a table that is nothing but an actions column.

   Locked fields render as a **disabled, checked** checkbox — visibly present and visibly not changeable, rather than silently absent from the list (which would read as a missing field, not a protected one). The apply layer **force-restores** a locked field even when a stored preference marks it hidden, so a preference written before a config changed — or hand-edited in devtools — cannot strand a user either. Locking governs visibility only: a locked field can still be **reordered** freely.

6. **Forward/backward compatibility rules, applied every time a stored preference is merged with the live schema** (the schema is served by the backend and can change under a stored preference at any deploy):
   - a name in the stored `order`/`hidden` that the schema no longer serves is **ignored**;
   - a schema field absent from the stored `order` is **appended** in config order — so an entity that *gains* a column later shows it, rather than silently dropping it for everyone who ever opened the Columns modal (the failure mode that makes a naive "stored order is the order" implementation quietly wrong);
   - an unparseable/corrupt/wrong-`v` stored value falls back to config defaults wholesale rather than partially applying.

7. **The pure logic lives in `frontend/src/lib/columnPreferences.ts`**, separate from both the modal and the table: `loadColumnPreferences` / `saveColumnPreferences` / `clearColumnPreferences` / `applyColumnPreferences` / `lockedFieldNames` (plus the key builder and the parse/merge helpers they compose). The merge/ordering/locking rules in decisions 5 and 6 are where the real risk sits, and they are all decidable from plain data — a field list and a stored object — with no DOM involved, so they are unit-testable directly rather than only through a rendered table.

**Explicitly out of scope, and not deferred-by-omission:** no backend change of any kind (no route, no schema field, no migration, no permission code); no server-side or cross-device persistence; no per-user server-side preference profile; no column *resizing*; no drag-and-drop.

## Consequences

**Positive:** a wide admin list becomes readable without a backend deploy, a config edit, or an ADR — the exact per-person, changes-daily class of preference that should never have been going through `field_meta`. Because `EntityTable` owns the state (decision 4), every current and future caller gets it for free, including `EntityListPage`'s ~28 entity pages and any later non-`EntityListPage` caller. `showInTable` keeps its single, global meaning ("is this field tabular at all") instead of accumulating a second, user-taste meaning it was never designed to carry. And because the merge rules (decision 6) are additive-by-default, a backend field addition still reaches users who already have a stored preference — a gap that only shows up months later, once schemas have actually changed, and is expensive to retrofit.

**Negative / Trade-offs:**

- **`localStorage` is per-browser and per-device, and invisible to everyone else.** A user who hides a column on their laptop still sees it on their phone, sees it again in a private window, and loses the preference entirely when site data is cleared. Nobody — not an admin, not a support engineer, not this repo's own test suites — can read another user's preferences, so "the list looks different for me than for you" is a real support conversation this design accepts. Making it cross-device means a per-user server-side table, a route, RBAC, and an ADR of its own; that is a genuinely different decision, deliberately not made here (see Alternatives).
- **A stale or corrupt client-side preference can silently hide data from the person who set it.** This is the sharpest edge of the whole feature: a hidden column shows no error and leaves no marker — it simply isn't there, and a user who forgot they hid it can reasonably conclude the data is missing rather than hidden. The three mitigations are all in the Decision (always-available "Reset to defaults"; corrupt values falling back to defaults wholesale rather than partially; locked fields force-restored so navigation is never lost), and this is carried as an explicit new Test Plan §14 risk row, not just a note here.
- **This is the second state-ownership pattern on one surface.** `EntityListPage` owns four query-mapped controls; `EntityTable` now owns a fifth control that is not query-mapped. The rule separating them is stated in decision 4 and is a real rule, not an accident — but a future reader adding a *sixth* control has to apply it rather than pattern-match on the nearest neighbour, and getting it wrong in either direction (a server-backed control stranded in `EntityTable`, or a purely-visual one plumbed through `EntityListPage` for no reason) would be invisible in `tsc` and in any mocked unit test.
- **`container/Table.tsx`'s own docstring explicitly forbids persisting *its* transient state** ("Do not 'improve' this into `localStorage`/a URL param", ADR-0041/TC-DS-018). That instruction is untouched and still correct: it governs `Table`'s pagination/page-size state, which is per-visit and query-mapped. This ADR persists a different thing (which columns exist at all) in a different component one layer up (`EntityTable`, which *composes* `Table`). The proximity is close enough to mislead, so it is named here deliberately — a future reader who greps `localStorage` and lands on that docstring should not conclude this ADR violated it.
- **Up/down reordering is slower than dragging** for a large field list, and some entities have a lot of fields. Accepted as the cost of not adding a dependency; if it becomes a real complaint, the modal's internals can be swapped without touching `columnPreferences.ts`, the storage shape, or any of the six TCs' own claims.

## Alternatives considered

- **A drag-and-drop reorder library (`dnd-kit`, `react-beautiful-dnd`, or similar)** — rejected: a new frontend runtime dependency is its own architecture decision in this repo (ADR-0009/ADR-0042's line on what may be added), and this story's value does not depend on the interaction being drag-shaped. It also cuts against the "hand-written markup against the CSS, no component-library wrapper" rule the design system settled on, and would make the reorder behavior materially harder to assert in Vitest (a pointer-event harness instead of two `click`s). Not rejected permanently — swapping the modal's internals later changes no stored data and no TC claim.
- **Server-side, per-user column preferences (a `user_column_preference` table + routes)** — rejected for this story, and explicitly *not* by accident: it would genuinely fix the per-device trade-off above. But it needs a new table, a migration, a create/update route pair, an RBAC answer for "who can read whose preferences," a tenant-scoping answer (per-org? per-user across orgs?), and NFR-1's existence-hiding posture applied to a brand-new resource — i.e. an ADR of its own, not a clause in this one. Shipping the client-side version first is not a blocker for that: `applyColumnPreferences`'s signature takes a preference object, not a storage mechanism, so a future server-backed source substitutes at the load/save boundary without rewriting the merge rules.
- **A URL query parameter (`?columns=title,status`)** — rejected on two counts. It doesn't actually persist: a fresh navigation to the entity list from the sidebar produces a bare URL with no parameter, so the user's choice evaporates every time they navigate rather than deep-link, which is the common case. And it bloats every admin URL with a long field list that is meaningless to anyone the link is shared with — while also, unlike `localStorage`, *leaking* one person's preference to whoever receives the link. (Shareability is the one thing the parameter genuinely buys; nothing in this story asked for it.)
- **`EntityListPage`-owned state, matching ADR-0056's column-sort precedent** — rejected per Decision §4: sort maps to a backend query parameter and therefore belongs with the list query; column visibility/order maps to nothing server-side. Following the precedent here would prop-plumb state through a component with no use for it and would exclude every non-`EntityListPage` `EntityTable` caller from the feature for no gain.
- **Extending `FieldMeta.show_in_table` to carry per-user state, or adding a second backend-declared "default visible" flag** — rejected: `show_in_table` answers a global, structural question and must keep exactly one meaning (ADR-0055's whole point is one source of truth for field *shape*). Per-person taste is not field shape, and routing it through a backend config would put a deploy in the loop for a preference that changes daily.
- **No locked fields at all — let a user hide anything, including the detail link** — rejected: hiding `detailLinkField` on a `detailPath` entity removes the only navigation into that entity's detail workspace (ADR-0060), and hiding every field leaves an actions-only table. Both are silent, recoverable-only-if-you-know-about-the-Columns-button states; a disabled checkbox costs nothing and makes the constraint visible at the moment the user would otherwise trip over it.
