## 1. Introduction

This plan governs testing of the project scaffold: a full-stack ISTQB/IEEE829-aligned test management tool (backend API, frontend SPA, MCP server, Docker infra) implementing 36 physical tables across 28 business entities, JWT auth for human and AI-agent actors, multi-tenant RBAC, and login rate limiting. Purpose: verify every FR/NFR in the Requirements Document before any release is considered scaffold-complete.

## 2. Test items

- Backend REST API (FastAPI) — all routes in the [API Document](../api/2026-09-03-api-design.md)
- Frontend SPA (React/Vite) — generic CRUD surface (28 entity pages, `entityConfigs`/`components/crud`/`pages/admin`, permission-driven hide/disable via `usePermissions`, [ADR-0027](../adr/0027-generic-admin-crud-ui-and-backend-completion.md)) + bespoke workflow screens + the persistent admin shell (sidebar, navbar, breadcrumb, footer, dashboard stat widgets, dark/light mode toggle) wrapping every `ProtectedRoute` screen, plus the template-parity UI-element reference pages (Colors/Typography/Icons — no FR backing, see Requirements Document), plus the `components/shared/` layer (`FormField`, DS-1) that bespoke workflow screens compose their forms from, plus the `/` root redirect guard and the empty `Dashboard` placeholder at `/dashboard` (DASH-1, [ADR-0035](../adr/0035-dash-1-root-redirect-and-dashboard-placeholder.md)) that replaced LANDING-1's public `LandingPage`
- MCP server stub — 5 tools per API Document §6
- Alembic migrations — schema migration + seed data migration
- Docker Compose stack — full-stack integration surface (`dev` and `prod` profiles)

## 3. Features to be tested

All FR-* items in the [Requirements Document](../requirements/2026-09-03-project-scaffold-requirements.md) §2 (Auth, RBAC/Tenancy, Project/Release, Requirement/TestCase authoring, Planning, Execution/Defect, Governance, Taxonomy/Admin CRUD, Traceability, MCP, Layout/Navigation), and all NFR-* items in §3 (tenant isolation, immutability, hashing, storage bounds, error-shape consistency, pagination, permission parity, responsive-shell behavior).

## 4. Features not to be tested

Out of scope per the design spec, and therefore out of scope here too: IEEE 829/29119-3 document-format export, SSO/OIDC/SAML/LDAP provider auth flows (schema exists, no working auth logic), AI test-case generation, billing/usage metering.

## 5. Approach

| Layer | Technique | Tooling |
|---|---|---|
| Backend unit | Isolated model/service logic, no DB/network | pytest + pytest-asyncio |
| Backend integration | Real dockerized Postgres (`postgres-test` service), HTTP-layer assertions, full RBAC allow/deny matrix per role | pytest + httpx |
| Frontend unit | Generic CRUD components (`EntityTable`/`EntityForm`) + bespoke workflow screens, mocked API layer | Vitest + React Testing Library |
| End-to-end | Full docker-compose stack via `localhost:8080`, real browser | Playwright |

Test-design techniques applied per feature area are detailed in the [Test Design](../test-design/2026-09-03-test-design.md) document (equivalence partitioning, boundary value analysis, decision tables for the RBAC matrix, state-transition testing for status-field lifecycles).

## 6. Item pass/fail criteria

- A route/feature **passes** when every acceptance criterion in its source user story (`docs/user-stories/`) has a corresponding green test at the appropriate layer (unit and/or integration and/or E2E per §5).
- A route/feature **fails** if any acceptance criterion lacks coverage, or any covered criterion's test is red.
- NFR-1 (tenant isolation) and NFR-9 (RBAC matrix) are release-blocking: no scaffold build is considered complete with a known cross-tenant leak or an unverified permission-denial path.
- NFR-11 (login rate limiting) is release-blocking for AUTH-1: `POST /auth/login` must not ship without the 429 throttle verified at the HTTP layer, not just unit-tested in isolation.
- NFR-12/NFR-13 (refresh rotation, org re-check) are release-blocking for AUTH-2: `POST /auth/refresh` must not ship without single-use rotation and the revoked/expired-token 401 path verified at the HTTP layer ([ADR-0013](../adr/0013-refresh-token-rotation-policy.md)) — a refresh endpoint that silently allows indefinite reuse of one token defeats the story's own revocability requirement.
- NFR-14 (logout idempotency/scoping) is release-blocking for AUTH-3: `POST /auth/logout` must not ship without (a) an integration test proving the revoked refresh token is actually rejected by a subsequent `POST /auth/refresh`, and (b) the idempotent-204 path verified for missing/foreign/already-revoked cookies ([ADR-0014](../adr/0014-logout-session-revocation-policy.md)) — a logout that silently no-ops on the happy path, or errors on the idempotent paths, defeats the story's "log out on a shared machine" premise either way.
- AUTH-4's AC2 (an `AIAgent` hitting a permission its role doesn't grant → 403, same RBAC path as a human `User`) is release-blocking for AUTH-4 specifically, even though AUTH-4 itself is a "Should"-priority story — the acceptance criterion exists precisely to prove the unified-Actor RBAC claim (07 principle #6), so it isn't optional polish. NFR-17/NFR-18/NFR-19 ([ADR-0015](../adr/0015-ai-agent-credential-mechanics.md)) are verified at the same HTTP-integration layer as NFR-9's RBAC matrix, not unit-tested against mocked permission logic alone.
- NFR-21 (RBAC-1 bootstrap closure + concurrency guard) is release-blocking for RBAC-1: `POST /auth/signup` must not ship without (a) an integration test proving it 409s once an `Organization` already exists, and (b) the concurrent-first-signup race test (TC-RBAC-020) proving `pg_advisory_xact_lock` actually serializes the two calls, not just a happy-path single-caller test ([ADR-0016](../adr/0016-organization-bootstrap-creation-flow.md)) — a bootstrap guard that only works absent concurrency isn't a guard. **TC-RBAC-002** (cross-org isolation on Project/Requirement/TestCase) is explicitly **not** achievable within RBAC-1's own scope — no CRUD routes exist yet for those entities (§3 of the API Document is still design-only) — and is not treated as a blocking gap for this story; it becomes release-blocking once whichever story adds the first tenant-scoped CRUD route lands, and that route must reuse the `/orgs/{org_id}/agents*` 404-vs-403 pattern ADR-0015 established.

- **PLAN-1** ([ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md)) is release-blocking on three points, none of them `TestPlan`'s own entity CRUD (already covered generically by ADMIN-2's factory — **TC-PLAN-001** requires no new route code, only a fixture asserting `status` defaults to `draft`): **TC-PLAN-002** must assert the coverage query end-to-end, not just the membership add — include a `TestSuite` with ≥1 member `TestCase`, then call `GET /test-plans/{id}/test-cases` and assert that exact `TestCase` is present, not merely that `POST /test-plans/{id}/test-suites/{suite_id}` itself returned `201`; a plan with the same `TestCase` reachable via 2 different included suites must also be asserted to appear exactly once (the deduplication claim), a case a single-suite fixture cannot catch. **TC-PLAN-003** is release-blocking on both directions of its own claim, not just the positive path: `draft`→`approved`→`superseded` via sequential `PATCH` calls must succeed, **and** a `draft`→`superseded` direct `PATCH` in a fresh fixture must be independently asserted `409 invalid_status_transition` — a test that only exercises the valid sequence would not catch a transition guard that was never wired in at all (the pre-ADR-0031 behavior: any `status` value, any order, silently accepted). The same-state and backward-transition cases (`approved`→`approved`, `approved`→`draft`) are additionally release-blocking per Test Design §5's own explicit inclusion of the idempotent-re-approval case — a guard that only checks "is this a known valid pair" without also rejecting the *reverse* of a valid pair could pass a naive test suite that only tries the two documented-forward transitions. Cross-project include rejection and duplicate-include `409` (the ADR-0031 decisions mirroring ADR-0030's own two) carry the same release-blocking rationale REQ-4's own equivalent risk note already established — CTO-confirmed decisions with no prior codebase precedent, easy to under-implement (skip the project-match check, or reuse a generic `422` IntegrityError handler instead of a dedicated `409` branch) without a dedicated test catching it.

- **PLAN-2** ([ADR-0032](../adr/0032-plan2-entry-exit-criteria-visibility.md)) is release-blocking on two points, neither of them `EntryExitCriteria`'s own entity CRUD (already covered generically by ADMIN-2's factory, zero new route code — **TC-PLAN-004** requires no new backend assertion, only a fixture proving all 4 `type` values round-trip through the existing generic routes and list scoped to one `test_plan_id`): **TC-PLAN-005** must assert AC2's literal "one view" claim end-to-end against the real nested route, not a mocked/isolated component render — seed a `TestPlan` with both an `exit`-type row **and** an `entry`- or `suspension`-type row, a `TestCycle` under it, then call `GET /releases/{id}/test-cycles` and assert the response's `exit_criteria` contains only the `exit` row, never the other type — a fixture with only one criteria row (or only `exit`-type rows) cannot distinguish "correctly filtered" from "never had anything else to filter out." A `TestCycle` under a plan with **zero** `exit` rows must independently assert `exit_criteria: []` in the same test file, not an omitted field — a naive nested-serialization implementation could return `null` or drop the key entirely for the empty case, both of which would break a frontend that assumes an always-iterable array. The route's new quadruple permission gate (`entry_exit_criteria.read` added to the existing triple) is release-blocking the same way NFR-26's original triple was for PROJ-2 — an actor lacking only the new fourth permission but holding the original three must still get `403`, tested as its own independent case, not inferred from "the other three already work."

- **MCP-1** ([ADR-0033](../adr/0033-mcp-server-architecture.md), FR-MCP-1, NFR-43) is release-blocking on the AC1 "same validation and permission check as REST" claim — AC1's "no separate, weaker code path" wording is the entire architectural contract (direct-call dispatch into existing route handlers, ADR-0033 decision 2), and the cheapest possible proof of that contract is the cross-permission negative: an AIAgent with `test_case.read` only, calling `create_test_case`, must get `permission_denied` with the exact API Doc §1 envelope a human caller would see — a copy-pasted weaker check (e.g. just verifying the agent's bearer key, not the per-tool permission) would pass any positive create test and silently ship a weaker code path. **TC-MCP-008** (the cross-project negative on this same test class — agent holds `test_case.create` but the route resolves to a project the agent has no `OrgMembership` in via `acting_on_behalf_of_user_id`) is the matching `404 not_found` negative; both must assert against the API Doc §1 body shape, not a tool-specific error envelope, per ADR-0033 decision 4's "MCP tool errors map to MCP `isError=True` with the API Document §1 envelope" contract. **TC-MCP-003**'s schema-parity assertion (same row fetched via REST and MCP must match field-for-field, per MCP-1 AC3) is release-blocking the same way ADR-0029's create-then-immediate-read assertion was for REQ-2: a parity test that only checks one of the two surfaces' response shape leaves the other free to drift. **TC-MCP-009** (no `Authorization` header → `invalid_token`) is release-blocking on the no-enumeration posture — same generic 401 body the REST surface returns for every `get_current_actor` rejection reason (auth-4/ADR-0015); an MCP-1 implementation that distinguishes "missing header" from "wrong key" from "revoked" would re-introduce the user-enumeration leak ADR-0011 explicitly closed on the human side.
- **PLAN-3** ([ADR-0033](../adr/0033-plan3-test-cycle-creation-and-execution-scope-check.md)) is release-blocking on three points: **TC-PLAN-006** must assert both FK links in the same test — a `TestCycle` created via `POST /test-plans/{id}/test-cycles` must be independently confirmed linked to both the path `TestPlan` and the body `release_id`, then immediately read back via `GET /test-cycles/{id}` (the generic factory's own item route) to prove no resolver-completeness gap exists for this row shape (`backend/CLAUDE.md`'s standing warning — a create-only assertion cannot catch a resolver that inserts fine and 404s on the very next read). The cross-project `422` on `release_id`/`environment_id` is release-blocking the same way ADR-0030/ADR-0031's own precedent-setting cross-project checks were — a CTO-confirmed decision with no schema-level enforcement behind it, easy to under-implement (skip the project-match check for one of the two fields, or reuse a generic `422` for both a genuinely-missing FK and a cross-project one, collapsing a `404` case into a `422`) without a dedicated test catching it; both `release_id` and `environment_id` need their own independent cross-project fixture, not one exercising the other. **TC-PLAN-008** (execution scope enforcement) must assert the negative case — a `TestCase` genuinely outside the plan's coverage rejected `422` — **and** a positive case in the same test file (a covered `TestCase` accepted `201`), since a scope-check implementation that always rejects (or always accepts) would each pass half of a test suite that only asserted one direction; the fixture must also independently confirm the covered `TestCase` reaches the plan via the same `TestSuiteTestCase`/`TestPlanTestSuite` join `GET /test-plans/{id}/test-cases` (PLAN-1) already proves correct, not a hand-picked ID that happens to work. The generic factory's `POST /test-executions` removal is release-blocking for this story specifically, since it's the fix for the exact bypass the story's own AC3 exists to prevent — a `TestExecution` created via a still-reachable unrestricted route would silently defeat the scope check for anyone who used it (same shape as REQ-3's TC-REQ-011).

- **EXEC-1** ([ADR-0034](../adr/0034-exec-1-test-execution-recording-dashboard.md)) is release-blocking on two points, neither of them the create route itself (already release-blocking-and-covered under PLAN-3's own criterion above, since ADR-0033 built it first): **TC-EXEC-002** (live dashboard aggregation) must seed a genuinely mixed fixture — at least one `TestExecution` of each of the four `result` values in one `TestCycle` — and assert all four filtered-list `total` counts independently, not just one value's count generalized to "the mechanism works"; a fixture with only one `result` value present cannot distinguish "correctly filtered per value" from "returns the cycle's total regardless of the `result` filter." **TC-EXEC-003** (re-execution preserves history) must record the same `test_case_id`+`test_cycle_id` pair twice with two different `result`s and assert, in the same test, that (a) two distinct `TestExecution` rows exist, (b) both are independently readable via `GET /test-executions/{id}`, and (c) the first row's `result`/`actual_result` are unchanged after the second `POST` — a test asserting only "two rows exist" could still pass against an implementation that silently mutated the first row's other fields on the second call.

- **EXEC-2** ([ADR-0038](../adr/0038-exec-2-append-only-test-log.md)) is release-blocking on the "appends, never overwrites" claim specifically — **TC-EXEC-004** must assert both halves in one test: after correcting a `pass` execution to `fail`, the *original* `status_change` log row (`from=null, to=pass`) is byte-for-byte unchanged **and** a second row (`from=pass, to=fail`) now exists — a test asserting only "a new row exists" cannot distinguish a genuine append from an implementation that edited the first row in place and inserted a coincidental second one. **TC-EXEC-006** (ordered timeline) must assert strict `logged_at`-ascending order pairwise across 3+ entries, not merely that all expected entries are present — a shuffled-order bug would still pass a presence-only assertion. The Q6 no-op classes (a `PATCH` with no `result` field, and a `PATCH` setting `result` to its current value) are release-blocking as two independent negative cases, since an implementation checking only field-presence (not an actual value change) would pass the first and fail the second, or vice versa. The `agent_action`-override class (Q3) is release-blocking because it's the only mechanism satisfying AC1's third trigger ("when an agent takes an action") at all — a test suite exercising only human actors would never catch a regression that silently stopped distinguishing agent-originated log rows.

- **EXEC-3** ([ADR-0044](../adr/0044-exec-3-raise-defect-from-execution.md)) is release-blocking on three points: **TC-EXEC-007** must assert the atomic create+link directly — a create-then-immediate-read confirming both the new `Defect` row (via `GET /defects/{id}`) **and** its `TestCaseDefectLink` row (via `GET /test-case-defect-links?test_case_id=`) exist, not inferred from the `201` alone, since a route that inserts `Defect` but silently skips the link (the exact class of gap REQ-3's own TC-REQ-005/006 already exist to catch for their own atomic routes) would still return `201` and pass a response-shape-only test. **TC-EXEC-011** (the new non-`fail` rejection case) is release-blocking because it's AC1's own literal precondition ("Given a TestExecution with result fail") — an implementation that accepts a `POST` against a `pass`/`blocked`/`skipped` execution would silently violate the story's own stated scope with no test catching it otherwise. **TC-EXEC-012** (the `test_manager` RBAC bundle extension, same shape as TC-REQ-010/TC-PROJ-017) is release-blocking as the only test that would catch the migration silently failing to apply or the bundle silently reverting to `.read`-only — same standing risk this Test Plan's own risk table already tracks for `test_manager`'s prior four extensions. **TC-EXEC-009**'s sharpened most-recent-first assertion must be pairwise across 2+ defects from 2+ different executions of the same `TestCase`, not merely "all expected defects are present" — a fixture with only one defect, or an unordered-but-complete response, would each pass a presence-only assertion identically.

## 7. Suspension criteria and resumption requirements

- **Suspend** integration/E2E testing if the `postgres-test` service or the docker-compose stack itself fails to start — a broken environment invalidates all downstream results.
- **Suspend** a feature area's testing if its Alembic migration fails to apply cleanly to a fresh DB — schema must be correct before behavior can be verified.
- **Resume** once the blocking infra/migration issue is fixed and the baseline (empty DB, fresh `docker compose up`) is confirmed green again.
