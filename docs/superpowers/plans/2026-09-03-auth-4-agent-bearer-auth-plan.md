**Date:** 2026-09-03
**Status:** Approved — open questions confirmed 2026-09-03, no implementation yet
**Story:** [AUTH-4](../../user-stories/2026-09-03-auth-stories.md) (`docs/user-stories/2026-09-03-auth-stories.md`, lines 48-59)
**Spec context:** [ADR-0003 auth/token strategy](../../adr/0003-auth-token-strategy.md), [ADR-0004 RBAC design](../../adr/0004-rbac-design.md), [ADR-0007 real multi-tenancy](../../adr/0007-real-multi-tenancy.md), [API design §2](../../api/2026-09-03-api-design.md), [07-erd-draft.md](../../product-discovery/07-erd-draft.md), [RBAC-tenancy stories](../../user-stories/2026-09-03-rbac-tenancy-stories.md), [AUTH-2 plan](2026-09-03-auth-2-session-persistence-plan.md) (prior slice, merged)

## 0. Repo state

AUTH-1/2/3 are merged. `get_current_actor` (`app/core/rbac.py`) resolves a bearer JWT to a `User` only. `require_permission`, `has_permission`, `require_human_actor` are all `NotImplementedError` stubs — **no route in the codebase enforces a permission today**; only two routers are mounted (`auth.py`, `health.py`). `generate_api_key`/`hash_api_key`/`verify_api_key` in `app/core/security.py` are stubs explicitly reserved for this story.

`AIAgent` (`app/models/actor.py`) already has `key_hash`, `key_prefix`, `issued_at`, `revoked_at`, `acting_on_behalf_of_user_id` (FK → `user.actor_id`, `NOT NULL`, `RESTRICT`) — these were added ahead of schedule "per AUTH-4" and are already in the initial Alembic migration. It has **no** `last_used_at`-style column yet.

`Role`/`Permission`/`RolePermission`/`RoleAssignment` tables exist but are **completely unseeded** — RBAC-1..5 (org creation/bootstrap, invites, role assignment endpoints, seeded system roles, human-only Approval enforcement) are un-built stories with zero API surface (no `orgs.py` route file exists at all). AUTH-1's integration tests already established the precedent of seeding `User`/`Organization`/`OrgMembership` directly via test fixtures, bypassing the (non-existent) bootstrap API — this plan follows the same precedent for `Role`/`Permission`/`RoleAssignment`.

API design doc §2 already reserves the contract shape for this story: `POST /orgs/{org_id}/agents` (`ai_agent.create`, org_admin only) and `POST /orgs/{org_id}/agents/{agent_id}/revoke` (`ai_agent.update`) — issuing/revoking one-time API keys. Neither route exists yet; this plan defines both.

## 1. Scope

**In scope for AUTH-4:**

- **`generate_api_key()` / `hash_api_key()` / `verify_api_key()`** (`app/core/security.py`): raw key format `tnx_agent_<key_prefix(8 url-safe chars)>_<secret(43 url-safe chars via secrets.token_urlsafe(32))>`. `key_prefix` is stored in `AIAgent.key_prefix` both for admin-facing display (like a GitHub PAT's visible prefix) and as an indexed narrowing key before the argon2 verify (argon2 hashes aren't equality-lookupable, so a raw key alone can't `SELECT ... WHERE key_hash = ...`; `key_prefix` lets the lookup go straight to a single candidate row instead of scanning/verifying every active `AIAgent`). `hash_api_key` = argon2 (reuse the existing `_pwd_context`, per ADR-0003 "stored argon2-hashed at rest"). Raw key is returned once, at issuance, and never stored.
- **`get_current_actor` extended to a second bearer scheme**: branch on a static, cheap check — `credentials.credentials.startswith("tnx_agent_")` — before attempting JWT decode. Agent branch: extract `key_prefix` (chars between the two known-length segments), `SELECT AIAgent WHERE key_prefix = :prefix AND revoked_at IS NULL`, `verify_api_key` the full raw key against the candidate's `key_hash`, 401 (same generic `invalid_token` shape as the human path — no distinct error code, same no-enumeration posture) on no match/revoked/verify-failure. On success, update `AIAgent.last_used_at = now()` (see below) and return the `AIAgent` row. Return type becomes `User | AIAgent`; every existing caller (`GET /auth/me`) updated to branch on `actor_type`.
- **`last_used_at` column on `AIAgent`** (new Alembic migration, additive, nullable `timestamptz`): the AC3 "`AuthIdentity`-equivalent tracking (a `last_login_at`-style field for agent sessions)" requirement. Updated on every successful agent-bearer authentication (not just at credential issuance) — an agent key is presented directly per-request (no separate "login" exchange the way a human gets a session-scoped JWT), so "last used" is the closest analogue to `AuthIdentity.last_login_at` that's actually observable. Write cost is one extra `UPDATE` per authenticated agent request; acceptable per the story's own "exploratory persona, no UX/perf priority ahead of AUTH-1/2/3" note.
- **Minimal, generic `has_permission()` / `require_permission()`** (`app/core/rbac.py`): resolve `RoleAssignment` → `Role` → `RolePermission` → `Permission` for `(actor_id, org_id, code)`, org-wide (`project_id IS NULL`) rows counting for any project. This is self-contained permission-resolution plumbing — it doesn't require any of RBAC-1..5's own routes (org bootstrap, invites, seeded system roles) to exist, only rows in those four tables, which tests seed directly. Needed because AC2 is an explicit, testable acceptance criterion ("same RBAC path as a human `User`") and is currently unimplementable against a stub. `require_human_actor` stays untouched/stubbed (RBAC-5's job, unrelated to this story).
- **Two Permission catalog rows** seeded via an Alembic *data* migration (additive, matches RBAC-4's stated pattern of seeding via data migration rather than UI): `ai_agent.create`, `ai_agent.update`. This story does not seed the full canonical permission catalog or system roles (`org_admin`, `ai_agent_scoped`, etc.) — that's RBAC-4's job. AC2's own test demonstrates the RBAC-*mechanism* generically (seeds an arbitrary custom `Permission`/`Role`/`RoleAssignment` pair via fixture, not dependent on `test_plan.approve` or `ai_agent_scoped` existing).
- **`POST /orgs/{org_id}/agents`** (new route, `app/api/routes/agents.py`): body `{agent_name, model_or_provider?, acting_on_behalf_of_user_id}`. Requires human `User` bearer auth (agents cannot issue their own credentials — enforced the same way RBAC-5 enforces human-only Approval: a hardcoded check, not just relying on `ai_agent.create` never being granted to an agent's role) + `require_permission("ai_agent.create")` scoped to `org_id`. Validates `acting_on_behalf_of_user_id` is an active `OrgMembership` of that org. Creates `Actor(actor_type=ai_agent)` + `AIAgent` row, `issued_at=now`, `revoked_at=NULL`. Returns `{agent_id, agent_name, api_key (raw, shown once), key_prefix}` — raw key never persisted, never logged.
- **`POST /orgs/{org_id}/agents/{agent_id}/revoke`**: same human-only + `require_permission("ai_agent.update")` gate, sets `AIAgent.revoked_at = now()` (idempotent — revoking an already-revoked agent is a no-op 200, not a 404/409, mirroring `RefreshToken`'s revoke-is-idempotent posture). A revoked agent's existing bearer key immediately 401s on `get_current_actor` (checked via `revoked_at IS NULL` in the lookup, not a separate cache/blocklist).
- **404-vs-403 boundary for the new org-scoped routes** (first routes in the codebase to need this, sets precedent): route checks the requester has *any* `OrgMembership` in `org_id` first — no membership (or `org_id` doesn't exist) → 404, consistent with NFR-1/ADR-0007 ("cross-tenant existence is never confirmable"). Membership present but `require_permission` fails → 403.
- **RBAC enforcement demonstration for AC2**: rather than gating a real business route (none exist yet outside auth), the test proves AC2 by calling `POST /orgs/{org_id}/agents/{agent_id}/revoke` (or a second synthetic `require_permission`-gated route in the test) with an `AIAgent` bearer credential whose seeded `RoleAssignment` grants some other permission but not the one being checked — asserting 403. This keeps AC2's proof inside AUTH-4's own surface rather than reaching into a not-yet-built business route.
- `GET /auth/me` extended: `actor_type` branches to `"ai_agent"`, response includes `agent_name` when applicable (schema change, additive).
- `backend/tests/unit/test_security.py` additions: `generate_api_key`/`hash_api_key`/`verify_api_key` roundtrip, wrong-key rejection, key-prefix format.
- `backend/tests/integration/test_agents.py` (new): issuance (org_admin-equivalent succeeds, non-admin 403, cross-tenant `org_id` 404), revocation (idempotent, revoked key 401s on next use), AC1 (agent bearer key → `created_by`-equivalent resolves to the `AIAgent`, proven via `GET /auth/me`), AC2 (agent lacking a permission → 403, same shape as a human's 403), `last_used_at` updates on successful agent auth, human-only issuance/revocation gate (an `AIAgent` bearer credential calling `POST /orgs/{org_id}/agents` → 403).

**Explicitly out of scope (belongs to later stories):**

- RBAC-1..5's own feature surface: org creation/bootstrap flow, invite-by-email, `RoleAssignment` CRUD endpoints, seeded system roles (`org_admin`, `test_manager`, `tester`, `auditor`, `ai_agent_scoped`) beyond the two permission rows this story's own routes need, and `require_human_actor`/RBAC-5's Approval-endpoint enforcement.
- MCP server implementation itself (how Claude Code/Cursor actually presents the bearer key) — this story only builds the API-side credential mechanism the MCP finding (06) and Actor design (07) require structurally; no MCP transport/tool code.
- Real `created_by`/`executed_by` wiring on business entities (`TestCase`, `TestPlan`, `Execution`, etc.) — none of those routes exist yet in this codebase. AC1 is verified at the mechanism level (`get_current_actor` correctly resolves an `AIAgent`, not a `User`, from an agent bearer key) via `GET /auth/me`, not by auditing real business-entity attribution that doesn't exist to audit.
- Credential rotation UI/flow — ADR-0003 explicitly says revoke-and-reissue only, no rotation.
- Rate-limiting agent-key auth attempts (ADR-0011's throttle covers `POST /auth/login` only; a brute-force-guessing concern for `tnx_agent_...` keys is real but is a separate NFR decision, not silently bundled in here).
- Frontend UI for issuing/revoking agent credentials — story note explicitly deprioritizes UX polish for this flow; backend mechanism + API only.
- `AuthIdentity.last_login_at` — noted as currently unset by the human login route too (pre-existing gap); not touched by this story.

## 3. Edge cases

- **Revoked agent key reused**: `revoked_at IS NOT NULL` excluded at the lookup `WHERE` clause, not checked-then-rejected after fetch — same "can't distinguish revoked from never-existed" posture as the human 401 path.
- **Key-prefix collision**: two independently generated `key_prefix` values colliding (8 url-safe chars, ~2^47 space) is astronomically unlikely but not impossible; lookup by `key_prefix` alone must not assume uniqueness — iterate candidates (there will realistically be 0 or 1) and argon2-verify each until one matches or all fail, rather than `.first()`-and-trust.
- **`acting_on_behalf_of_user_id` points at a user who is later suspended/removed from the org**: the FK is `RESTRICT`, so the row can't be deleted out from under it, but the referenced user's `OrgMembership.status` can still change to `suspended` after the agent is issued. Out of scope to re-validate this on every agent request (mirrors AUTH-2's open question about re-checking membership on every refresh) — flagged, not silently handled either way.
- **Agent issuing/revoking another agent's credential**: blocked structurally by the human-only gate on both routes, independent of whatever `RoleAssignment` an agent might (mistakenly) hold for `ai_agent.create`/`ai_agent.update` — same defense-in-depth pattern as RBAC-5's Approval enforcement.
- **`org_id` in the path belongs to a real org but the caller (human or agent) has zero membership there**: 404, not 403 (§1 "404-vs-403 boundary").
- **`has_permission` with an org-wide (`project_id IS NULL`) `RoleAssignment` vs. a project-scoped one**: this story's own routes are org-scoped only (no `project_id` concept for agent issuance), so only the org-wide resolution path is exercised/tested here; the project-scoped branch is implemented (per RBAC-3's documented design) but not exercised by AUTH-4's own tests — RBAC-3's own story is responsible for that coverage.
- **Concurrent revoke + in-flight request using the same key**: no atomicity concern equivalent to refresh-token rotation's CAS race — revocation is a one-way flag flip (`revoked_at` set once), not a rotate-and-replace; a request already past the `get_current_actor` lookup when revocation commits completes normally (same as any short-lived-JWT-vs-revoked-refresh-token race elsewhere in the app), a subsequent request re-checks and 401s.

## 4. Open questions

1. **`has_permission`/`require_permission` implementation now vs. blocking on an explicit RBAC-3/RBAC-4 story first.** AC2 is a hard, testable acceptance criterion that's unimplementable against the current stub. Assumption/recommendation: implement the generic 4-table resolution now (org-wide grants only, since that's all this story needs) as self-contained plumbing, seeded via test fixtures — not the RBAC-1..5 business flows themselves. This unblocks AUTH-4 without taking on RBAC-1..5's scope. **Confirm this split is acceptable**, or say if RBAC-3/4 should land first and AUTH-4 should wait.
2. **404-vs-403 precedent for org-scoped routes** (§1) — this is the first place in the codebase this decision gets made concretely. Assumption: no-membership → 404, membership-but-no-permission → 403. **Confirm**, since every future org-scoped route (RBAC-1..5 and beyond) will likely copy this pattern.
3. **`last_used_at` update cadence** — assumption: every successful agent-bearer authentication (i.e., every request), not throttled/debounced per MCP session. Given this persona's low-priority/exploratory status, simplicity over write-amplification optimization seems right, but **confirm** — an alternative is updating only when `mcp_session_ref` changes (session-start semantics), which is cheaper but adds complexity to track "session changed."
4. **Raw key format `tnx_agent_<prefix>_<secret>`** — no existing convention in the repo to match against (this is the first API-key-shaped credential). **Confirm the format/prefix string is fine**, or suggest a different literal (e.g. matching a future public brand prefix).
5. **AC2's proof surface** — since no real business route (`TestCase`, `TestPlan`, etc.) exists yet to demonstrate "an agent hitting a permission it lacks," the plan proves AC2 using AUTH-4's own routes (agent calling `.../revoke` without `ai_agent.update`). **Confirm this is acceptable** as the AC2 test's proof surface for this story, with a note that RBAC-3/4/5 or the first business-entity story should add a second, more "real" demonstration once such a route exists.
