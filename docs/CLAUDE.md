# CLAUDE.md — docs

Guidance for editing `docs/`. Read the root `CLAUDE.md` first (ADR-first policy, doc-propagation-applicability judgment call, the worktree-vs-docs-timing note under "Git / worktrees"). This file covers gotchas specific to editing the docs themselves, found the hard way during the PLAN-1/PLAN-2/PLAN-3 documentation passes (2026-09-06).

## New `TC-<AREA>-NNN` IDs: grep the whole file for the highest existing number, don't eyeball the section you're editing

`docs/test-cases/2026-09-03-test-cases.md`'s per-feature-area tables are **not** appended in ID order over time — a story's own placeholder rows (e.g. PLAN-3's `TC-PLAN-006/007/008`, written speculatively during an earlier planning pass) can sit *above* a later story's rows in the table (PLAN-2's `TC-PLAN-012/013`) even though the later story's IDs are numerically higher. Eyeballing "what's the highest number in the rows near where I'm inserting" undercounts.

This nearly shipped a real collision: a PLAN-3 documentation pass assigned new rows `TC-PLAN-012`/`TC-PLAN-013`, not noticing PLAN-2 had already claimed those exact IDs a few rows down in the same table. Caught only because a later grep (`grep -n "TC-PLAN-0"`) surfaced the whole file's actual ID list before the edit was considered done — the numbers were renumbered to `015`/`016`/`017` before anything shipped.

**Before assigning any new `TC-<AREA>-NNN` ID, run `grep -n "TC-<AREA>-[0-9]" docs/test-cases/*.md` first and take the max, not the highest number visible in the table region you're about to edit.**

## The API design doc's asterisk-count footnote convention is fragile — count exactly, don't eyeball

`docs/api/2026-09-03-api-design.md` §3 marks each entity's factory-serving footnote with a literal run of `\*` characters (`\*`, `\*\*`, `\*\*\*`, ...) matched purely by count, not a name or number — e.g. `TestCase`\*\*\*\*\* and `Defect`\*\*\*\*\* deliberately share 5 asterisks because they cite the same footnote text. Adding a new footnote requires knowing the exact count already in use so you neither collide with an existing marker (silently merging two unrelated footnotes) nor skip one (leaving a marker with no matching footnote, or vice versa).

This bit the PLAN-3 documentation pass directly: a first attempt at a new `TestExecution` footnote used 15 `\*`s by miscount, and a cross-reference in the `TestCycle` footnote pointed at the wrong count entirely. Caught by counting mechanically (`python3 -c "print(r'\*\*\*\*\*\*\*\*\*\*\*\*'.count('\\\\*'))"` — or just `grep -n '^\\\*' docs/api/2026-09-03-api-design.md` to list every existing marker and its line) rather than by eye, before it shipped.

**Before adding a new asterisk-marker footnote in that section: `grep -n '^\\\*' docs/api/2026-09-03-api-design.md` to enumerate every existing marker, count characters programmatically (not by eye) for both the new marker and any cross-reference to it, and verify the count is unique.** If this section needs even one more footnote after the current set, it's worth proposing named/numbered footnotes (`[^testcycle]`) instead of asterisk-counting — the convention was already borderline unreadable at 15 markers.

## Superseding a row (FR/NFR/TC/WBS) in place: strike it through, don't delete it

When an ADR supersedes an earlier one and that earlier decision has its own rows in Requirements/Test-Design/Test-Cases/WBS (an FR, an NFR, a `TC-*` case, a WBS line), the convention this repo settled on (DASH-1, 2026-09-07, superseding LANDING-1/ADR-0024) is: **strikethrough (`~~text~~`) the stale row's content in place, add a one-line "superseded by X" note pointing at the new row/ADR, and keep it in the table** — don't delete the row outright. This mirrors the ADR index's own `Status: Superseded by NNNN` convention (never delete an ADR file) and keeps a coverage/traceability table's row count auditable across history (a reader can grep `~~` to find every superseded claim, and a deleted row leaves no trace that a decision ever existed or changed). Exclude struck-through rows from any total/count in the same table (e.g. Test Cases' coverage-summary total) and show the arithmetic in the recompute note, same as any other total change — don't silently drop the count without saying why it moved.

## Code can land on `main` with zero doc propagation — a docs pass for one story should glance at what else shipped nearby, not just its own scope

See root `CLAUDE.md`'s "Architecture decisions are ADR-first" section for the full write-up (two confirmed instances in one session, DS-2, 2026-09-08) — a cheap `git log` sweep against the doc index's own last-updated point can catch a sibling story's undocumented merge before it compounds into a bigger reconciliation later.

## Doc-propagation and implementation-worktree timing

See root `CLAUDE.md`'s "Git / worktrees" section — a worktree created before a docs-propagation pass lands on `main` will implement against a stale doc set. This is a doc-authoring-side risk too, not just an implementation-side one: if you know an implementation worktree already exists for the story you're documenting, say so in the completion report so whoever implements knows to rebase first, rather than letting it surface later as a merge-time surprise.

## The `TC-<AREA>-NNN` grep discipline above generalizes to every other numbered doc artifact — and to checking `main`, not just your own worktree

The `TC-ID` note above is about not eyeballing *this worktree's own copy* of one file. The bigger risk in a long session is the same collision *against `main`*, for **any** numbered artifact this repo hands out sequentially: ADR file numbers (`docs/adr/00NN-*.md`), WBS row numbers (`docs/wbs/`'s `11.NN` completion-log rows), and Test-Design section numbers (`## NN.` headings). Confirmed EXEC-2 (2026-09-07): a worktree that branched cleanly from `main` at creation time independently claimed `ADR-0036`, WBS row `11.20`, and Test-Design `§31` — all three already real, already-merged, already-different content from a separate story (SHELL-6) that landed on `main` *after* the worktree was created but *before* this worktree's own docs pass was written. See root `CLAUDE.md`'s "Git / worktrees" section for the full write-up and the `git fetch`/`git show origin/main:...` check to run before finalizing any new number — the actionable habit belongs there since it's a git-workflow discipline, not a docs-content one, but it's exactly the same class of mistake this file's own `TC-ID` note already warns against, just scoped to `main` instead of one file.

## The same literal fact stated in two places in the docs can silently disagree — grep for the claim elsewhere before considering a fix done, not just where you found it wrong

Two independent instances in one pass, EXEC-2 (2026-09-07): (1) the API design doc's own §4 route table and its §5 read-only-routes table each listed `GET /executions/{id}/logs`'s gating permission — one said `test_execution.read`, the other said `test_log.read`, a contradiction sitting in the same document for what was, at the time, an unbuilt/reserved route (so neither had ever been checked against a real running server). (2) The Test-Design and Test-Cases docs both separately asserted `TestLog`'s `PATCH`/`DELETE` returns `404` — wrong in both places identically (the real, already-existing, already-passing test asserts `405`), because whoever wrote the second copy years earlier had no reason to doubt the first. **Neither mismatch was found by re-reading the section being edited — both were found by building/running the real feature and checking the actual behavior against every place a claim about it appears, not just the one place prompting the edit.** When you fix a factual claim (an HTTP status code, a permission code, an endpoint's own shape) found wrong in one doc, `grep` for the same claim across `docs/` before considering the fix done — the second copy doesn't announce itself, and won't be caught by anyone who only reads the file they were already editing.

## A docs-only pass's own "no code written this pass"/"not yet automated" status phrases go stale the moment a later same-branch commit lands the code — grep for them explicitly when auditing coverage

This is the same forward-pointing-addendum pattern as the note below, but for a documentation *status claim about itself* rather than a claim about the product. SHELL-7 (2026-09-08→09): the docs-only pass wrote "Docs-only pass, no code written" into the Test Cases coverage note and "no code written this pass, per explicit instruction" into the WBS row and ADR status line — all three were accurate when written. A later, separate coverage-audit conversation on the *same branch* found the implementation (with all 7 TCs' real automated tests) had landed in between, but the three status lines still read as if nothing had shipped — not wrong exactly, just stale, the same trap the "same-day-fixed defect" note below describes for an ADR's Consequences section. **Before considering a coverage-audit or "is this done" task finished, `grep -rn "no code written this pass\|docs-only pass\|not yet automated" docs/` for the story in scope** — a hit doesn't mean the claim is false, it means it needs checking against the branch's actual current commits, and a forward-pointing addendum (not a rewrite) if code has since landed.

## A same-day-fixed defect gets a forward-pointing addendum on the ADR that found it, NOT the strikethrough-and-supersede treatment the "Superseding a row" note above describes

These are two different situations that can look similar at a glance. **Strikethrough-and-supersede** (the note above) is for a row whose *claim is now false* — a prior FR/NFR/TC that a newer decision has actively overridden, where leaving the old text unmarked would mislead a future reader into thinking it's still accurate. **A forward-pointing addendum** is for a row whose claim is *still exactly true* — an ADR's own Consequences section correctly describing a defect it found (e.g. ADR-0039, DASH-2, 2026-09-07: "the Delete button 409s for every UI-created Project... deliberately NOT fixed in this same pass") stays word-for-word accurate even after the defect is fixed a few hours later by a separate ADR (0040) — the original text is still a true description of what was found and when, not a stale claim to strike out. The fix: leave the original ADR's prose untouched, add one line — **"Resolved the same day, [ADR-NNNN](...) — see that ADR for the fix"** — immediately after it, and write the fix as its own new ADR rather than editing the first one's Decision/Consequences to pretend the defect was caught before shipping. Using strikethrough here would be wrong in the other direction: it would make the original ADR look like it mis-predicted something, when it was actually the correct, working verification process finding a real bug exactly as designed. See root `CLAUDE.md`'s ADR-first section for the full write-up of why the fix needs its own ADR at all rather than folding into the one that found it.

**A pre-merge, same-story correction is a third case this doesn't cover, and gets a lighter treatment than a new ADR number: an in-place `### Amendment` subsection inside the same ADR.** DASH-2/ADR-0040 above is specifically about a defect found in code that had already **shipped and merged** — the original ADR's Decision was accurate *at the time it shipped*, and a real, separate architectural fix (an FK constraint change) was needed later, which is why it earns its own number. BRAND-1 (2026-09-09, ADR-0048) hit two corrections that don't fit that shape: (1) a docs-before-code ADR's own predicted mechanism (`currentColor` inheriting through an `<img src>` mount) turned out wrong the moment the implementation pass actually ran it against a live instance — normal for this repo's plan-then-implement flow, nothing had shipped yet for the "wrong" version to be a defect *in*; (2) the CTO reversed one Decision clause (no logo in the header) via direct instruction after a live manual look, same day, still on the unmerged branch — a design-detail correction, not a distinct architectural decision that would justify its own ADR number the way ADR-0040's schema change did. Both were handled as a numbered `### Amendment (date, reason)` subsection appended to ADR-0048's own Consequences section (two separate amendments, one per correction, each naming what changed and why) rather than either a silent rewrite of the Decision text or a new ADR-0049/0050. **Use the size of the underlying decision to pick the treatment: a distinct architectural/schema/contract change that outlives this one story gets its own new ADR (DASH-2/ADR-0040's shape); a same-branch, still-unmerged correction to this story's own Decision (whether found by running the code or by the CTO's own live review) gets an in-place `### Amendment` subsection in the same ADR** — either way, the original Decision/Consequences prose stays untouched and the correction is additive, never a silent edit.

## A coverage-summary total computed incrementally (old total + this pass's delta) silently inherits any drift already sitting in the old total — recompute by direct summation, don't trust the running number

`docs/test-cases/2026-09-03-test-cases.md`'s own coverage-summary table has a "recompute" convention every story pass follows: state the row's old count, the new count, the delta, and the new grand total. This works exactly as long as every prior pass's own recompute was itself correct — but nothing checks that assumption, and the table has been edited by a different story/session almost every time. EXEC-3's own recompute pass (2026-09-08) found the Test Execution & Defects row itself was already wrong before EXEC-3 touched anything: `TC-EXEC-010` (added by an earlier EXEC-1 pass) had never been folded into that row's stated count, so "9" should have already been "10." Fixing that one row's undercount wasn't enough on its own, either — summing the **entire table's actual listed values** column-by-column (not "old total + known deltas") turned up a *second*, unrelated one-point drift in the grand total that predated even the TC-EXEC-010 gap and had no single attributable cause found. **When recomputing this table's total after any row change, sum every row's literal value directly (`awk`/mental arithmetic across the whole column) and use that as the new total, rather than trusting "old total + this pass's own delta"** — an incremental formula only catches drift *your own pass* introduces; it silently carries forward anything already wrong, exactly the way this repo's own `TC-<AREA>-NNN` numbering note already warns against for eyeballing one section instead of grepping the whole file. If the direct sum disagrees with what incremental math would have produced, say so explicitly in the recompute note (which row's stale count caused it, if findable) rather than quietly overwriting the total with no explanation for the jump.

## `git checkout <sha> -- <docfile>` to land a branch's own docs onto a `main` that has moved since is a silent whole-file overwrite, not a merge

See root `CLAUDE.md`'s "Git / worktrees" section for the full incident (PROJ-4, 2026-09-09) — restated here since it's specifically a docs-handling mistake, worth knowing before reaching for the same shortcut on any future docs-only landing pass. The command replaced `docs/adr/README.md` and 6 sibling files wholesale with a stale worktree branch's own snapshot — deleting a sibling story's (SHELL-7's) own already-merged ADR-index row outright and reverting the Sitemap's own already-correct admin-group restructure back to its pre-SHELL-7 shape. `git checkout <sha> -- <path>` has no concept of `main` having moved since the branch diverged; it just replaces the working-tree file with that exact historical blob. **When a docs-only pass needs to land a branch's already-written content onto a `main` that's advanced since, re-derive each file's own delta by hand (`Edit` calls against `main`'s *current* content) or use a real diff/apply that surfaces conflicts — never a raw `checkout <sha> -- <file>`.** Caught only by reviewing `git diff --cached` before committing, not by anything in the checkout command itself.

## A story ID can have more than one independently-authored, overlapping doc/implementation pass in flight at once — check `git log --all`/`git branch -a` for the story name, not just `main`'s current state, before trusting the first copy you find

Confirmed at the very start of the SHELL-9 task (2026-09-09): `main`'s own working tree had a stray, incomplete, uncommitted PROJ-4 doc pass sitting in `git status` — but a `git log --all --oneline | grep -i proj-4`/`git branch -a` sweep found a *second*, fully complete PROJ-4 effort (full ADR/Requirements/WBS/etc. propagation **plus** a working, tested implementation, Vitest 422/422, 5 e2e specs green) already committed on a separate, unmerged branch (`proj-3-sidebar-crud`, commit `4610efc`) — a real, working deliverable the uncommitted stray copy on `main` gave no hint of. Partway through the same session, a *third* independent PROJ-4 doc pass then landed directly on `main` itself (commit `3eaca9b`), overlapping but not identical to either of the other two. None of the three efforts knew about the others while being authored — each was written as if it were the only PROJ-4 work in progress, a predictable consequence of this repo's own now-well-documented pattern of multiple concurrent sessions treating the same repo as a shared resource with no coordination mechanism beyond `git fetch`.

**Before starting or continuing any story's docs/implementation pass, `git log --all --oneline | grep -i <story-id>` and `git branch -a` for the story's own name** — not just checking `main`'s current state or the one worktree you happen to be looking at. A stray uncommitted diff, a fully-merged-looking commit on `main`, and a complete implementation on some other unmerged branch can all coexist for the same story ID simultaneously, and only the branch/commit sweep surfaces all of them at once. When multiple overlapping efforts are found, the complete/tested one (working code + passing tests, not just prose) is the one to build on — a docs-only pass, however polished, is not evidence of more progress than a branch with actual passing tests, and the reverse is also true (see root `CLAUDE.md`'s own "ADR-vs-implementation drift" note for the general principle this instantiates).
