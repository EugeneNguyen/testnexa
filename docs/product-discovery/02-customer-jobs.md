# 02 — Customer Jobs (Jobs-to-be-Done)

Jobs are written in JTBD form (situation → motivation → outcome), derived from the ISTQB test process model (planning, monitoring & control, analysis, design, implementation, execution, completion — [ISTQB Glossary](https://astqb.org/assets/documents/ISTQB_glossary_of_testing_terms_2.3.pdf)) and cross-checked against feature emphasis across TestRail, Kiwi TCMS, Xray, Zephyr, Squash TM in the research above. Frequency and importance are **HYPOTHESES** ranked from secondary-source emphasis (how much each capability is foregrounded in vendor marketing, comparison articles, and complaint patterns) — not from primary interview data. Must be validated with real QA managers/engineers before being used to scope an MVP.

## Ranked jobs

| Rank | Job (When... I want to... so I can...) | Frequency | Importance | Evidence basis |
|---|---|---|---|---|
| 1 | When I have a set of requirements/features to verify, I want to design and organize test cases into reusable suites, so I can execute them consistently across releases without rebuilding from scratch each time. | Continuous (core daily activity) | Critical | Every tool in the category leads with this (TestRail, Kiwi TCMS, Xray, Squash TM feature descriptions) |
| 2 | When a release is planned, I want to select which test cases/suites apply to it and track execution status (pass/fail/blocked) in real time, so I can tell stakeholders whether we're ready to ship. | Every sprint/release cycle | Critical | Core to "test plan," "test run," "test execution" workflows across all tools; explicitly named in TestRail/Kiwi TCMS feature sets |
| 3 | When a test fails, I want to log a defect and link it to the exact test case/step and requirement that failed, so I can give developers full context without re-explaining. | Multiple times per sprint | Critical | Bug-tracker integration (Jira, Bugzilla, GitHub Issues, GitLab Issues) called out as a headline feature for Kiwi TCMS, TestRail, Xray, Zephyr |
| 4 | When auditors, customers, or regulators ask "prove you tested requirement X," I want a traceability matrix from requirement → test case → result, so I can produce evidence without manually reconstructing it. | Per audit cycle (regulated industries); rare but high-stakes elsewhere | Critical for regulated segment, Moderate elsewhere | Squash TM's requirement-traceability emphasis; IEC 62304 traceability-matrix requirement ([Jama](https://www.jamasoftware.com/requirements-management-guide/medical-devices/iec-62304/), [Ketryx](https://www.ketryx.com/blog/iec-62304-requirements-traceability-matrix-rtm-in-jira-a-guide-for-medical-device-companies)) |
| 5 | When automated tests run in CI, I want results to flow into the same system as manual test results, so I can see one unified picture of quality instead of two disconnected views. | Every CI run (high frequency for teams with automation) | High, rising | Kiwi TCMS "official reporters" for Playwright/Cypress/pytest; Allure TestOps built specifically to ingest Allure Report output; CI/CD integration named as standard expectation across sources |
| 6 | When I need to report status upward, I want dashboards/metrics (coverage %, pass rate, defect trends) generated automatically, so I don't have to hand-build slides every week. | Weekly/per-release | High | "Visual reports," "advanced reporting and business intelligence" named for Kiwi TCMS and Squash TM; reporting customization is also a top *complaint* area (see 03) |
| 7 | When my team grows or a new hire joins, I want role-based access control and clear ownership of test assets, so I can prevent accidental edits/deletions and enforce review workflows. | Occasional (org events) but persistent need | Moderate-High | "Role-based access control," "custom workflows and approval processes" named for Kiwi TCMS, Squash TM |
| 8 | When I'm evaluating whether my testing follows a recognized standard, I want the tool's terminology and process to match ISTQB/ISO 29119 vocabulary, so I can train new testers consistently and communicate unambiguously with auditors, contractors, and other companies. | Low frequency (setup/onboarding), but foundational | Moderate — high for the specific regulated/training segment, low for generalist Agile teams | Directly the premise of the original idea; not evidenced as a mainstream buying driver in competitor marketing (none of TestRail/Xray/Zephyr/Kiwi TCMS/Squash TM lead with "ISTQB compliant" language) — flagged as **ASSUMPTION requiring validation**, see note below |
| 9 | When my organization has data-residency, security, or budget constraints, I want to self-host the entire system on my own infrastructure, so I can control cost, data location, and uptime without vendor dependency. | One-time decision, persistent constraint | High for a defined subset (regulated/security-conscious/cost-sensitive orgs), Low/irrelevant for SaaS-first teams | Explicit 2026 trend evidence: GDPR/data-residency as a named SaaS-avoidance reason ([Autonoma](https://getautonoma.com/blog/gdpr-compliant-test-automation)); TestRail, Squash TM, Kiwi TCMS all offer this as differentiator from Jira-native tools |
| 10 | When I'm new to a testing role or studying for certification, I want to practice test design techniques (equivalence partitioning, boundary value analysis, decision tables) inside a real tool, so I can build muscle memory before using it on the job. | Rare, one-time per person (training period) | Low for production buyers, potentially high for a training-market niche | Inferred, not directly evidenced in search results — **HYPOTHESIS**, needs direct validation with ISTQB training providers |

## Key insight

**INSIGHT:** Jobs #1–#3 (design, plan/execute, defect-link) are table stakes — every competitor already does these adequately, so they cannot be the basis of differentiation. Job #4 (traceability/audit) and #9 (self-hosting/data control) are the two jobs where "self-hosted + standards-aligned" is a genuinely different value proposition rather than a cheaper clone of existing tools. Job #8 (explicit ISTQB terminology/process alignment) is the one most directly tied to the original idea, but has the *weakest* evidence of being an active, monetizable buying driver — no competitor markets on it, meaning either (a) it's genuine whitespace, or (b) it's not something customers pay for. This must be resolved via customer interviews before committing scope — see 06 (not yet produced) for validation plan.

## What must be true for this idea to work (carried into later docs)

1. There exists a meaningful population of teams that need jobs #4 + #9 together (audit-grade traceability AND self-hosting) and are currently underserved. **HYPOTHESIS.**
2. Job #8 (ISTQB terminology/process fidelity) is either (a) a real purchase driver for a subset of buyers (e.g., procurement checklists in regulated tenders), or (b) valuable as a trust/marketing signal even if not a hard requirement. **ASSUMPTION, needs interviews with regulated-industry QA managers and procurement stakeholders.**
3. These teams are not already fully served by Squash TM (open-core, already covers requirement traceability + self-hosting) or Kiwi TCMS (open-source, active, Docker-native). **This is the central threat to the idea — see 05 Competitor Map.**
