## 1. Technique selection by feature area

| Feature area | Primary technique(s) | Why |
|---|---|---|
| Auth (login, tokens, logout) | Equivalence partitioning (valid/invalid credentials, valid/expired/revoked/rotated-out refresh tokens, active/suspended/invited/zero org memberships, idempotent-no-op logout classes) | Small, well-defined input classes |
| Login rate limiting | Boundary value analysis (attempt count at 4, 5, 6 within the window; just-inside vs. just-outside the 15-minute window) | NFR-11/ADR-0011 — classic BVA target, same as pagination/attachment limits below |
| RBAC / permission checks | Decision table (role × permission code → allow/deny) | Combinatorial — the exact case ISTQB recommends a decision table for |
| Multi-tenancy isolation | Equivalence partitioning (same-org vs. cross-org resource) + boundary (org with 0 vs. 1 vs. 2+ orgs) | Isolation bugs cluster at the org-boundary edge |
| TestPlan / TestExecution / Defect status | State transition testing | Each has an explicit enum lifecycle (draft→approved→superseded; pass/fail/blocked/skipped; open→...→closed) |
| Requirement→TestCondition→TestCase traceability (2 paths) | Equivalence partitioning (direct-link class vs. TestCondition-mediated class) + state coverage of "0 linked test cases" boundary | ADR-0006 explicitly requires both classes tested, not just one |
| Generic CRUD (28 entities) | Equivalence partitioning per field type (string/enum/FK/date) applied once, reused across entities via `entityConfigs/` | Avoids writing 28 near-duplicate test suites — one technique, applied generically, matches how the UI itself is built (ADMIN-2) |
| Pagination / filtering | Boundary value analysis (page_size at 0, 1, 25, 26; empty result set; last-page boundary) | Classic BVA target |
| Attachment size/type limits | Boundary value analysis (at limit, one byte over, disallowed mime type) | NFR-7 |
| TestLog immutability | Negative testing (attempt update/delete, expect route not to exist / 405 or 404) | Verifying an absence, not a behavior |
| Admin shell (sidebar + navbar) | Equivalence partitioning (org-context-present vs. absent, current-route-active vs. not) + state coverage (sidebar visible/collapsed) | Layout is a small, enumerable set of UI states, not a combinatorial one |
| Admin shell extras (breadcrumb, footer, dashboard widgets, dark/light toggle) | Equivalence partitioning (route-with-known-breadcrumb-segment vs. root; theme=light vs. dark vs. unset-defaults-to-system) + state coverage (toggle on/off, persisted vs. fresh session) | Same small-enumerable-state shape as the base shell; widget counts additionally verified against seeded fixture data, not just "renders a number" |
| Shared `FormField` component + Login/Signup migration | Equivalence partitioning (error-present vs. absent, default vs. explicit `type`) + regression/negative testing (pre-migration behavior reproduced exactly) | Small, enumerable prop-driven states for the component itself; the migration's own risk is regression, not new-behavior combinatorics |
| ~~Public landing page (LANDING-1)~~ — superseded, see row below | ~~Equivalence partitioning (no-session vs. authenticated-session, each its own render/redirect outcome)~~ | ~~Small, binary auth-state partition, same shape as the admin shell's org-context classes above~~ |
| Root redirect + empty Dashboard (DASH-1) | Equivalence partitioning (no-session vs. authenticated-session, each its own redirect target) + boundary (the `isInitializing` in-flight instant) | Same binary auth-state shape LANDING-1 used, narrowed to `accessToken` alone (drops the `orgContext` partition entirely — deliberate, ADR-0035) |
| TestSuite membership, many-to-many (REQ-4) | Equivalence partitioning (same-project valid add vs. cross-project invalid add vs. duplicate-add conflict) + boundary (0 vs. 1 vs. 2+ suites per case, 0 vs. N cases per suite) | Small, well-defined relationship classes around one join table — same shape as the RBAC decision table's per-cell independence, not combinatorial |
| TestPlan↔TestSuite membership + status-transition guard (PLAN-1) | Equivalence partitioning (same-project valid include vs. cross-project invalid include vs. duplicate-include conflict, same shape as REQ-4's row above) + state transition testing (the `status`-transition guard's legal-vs-illegal pair table) + boundary (0 vs. 1 vs. 2+ suites per plan, deduplication at 1 vs. 2+ suites sharing a common TestCase) | Two independent small state spaces composed on one entity — the membership join reuses REQ-4's own technique verbatim, the `status` guard extends §5's existing state-transition table with a schema-unenforced application-layer check |
| TestCycle creation + execution scope-check (PLAN-3) | Equivalence partitioning (same-project valid `release_id`/`environment_id` vs. cross-project invalid, each field independently — same shape as REQ-4/PLAN-1's own cross-project classes, applied twice per create) + a second, independent equivalence partition (`TestCase` covered by the plan vs. not, reusing PLAN-1's own coverage-query join as the partition boundary) | Two independent cross-entity validation checks on two different routes, each the same "same-org, cross-project → 422" shape this codebase has now applied three times (REQ-4, PLAN-1, PLAN-3) — no new technique, deliberate reuse |

## 2. Auth — equivalence classes

**Valid classes:** correct email+password with ≥1 active org membership → 200; valid non-expired access token → request succeeds; valid non-revoked, non-expired, not-yet-used refresh token → new access token issued + new refresh token issued (rotation).
**Invalid classes:** wrong password → 401 generic message; unknown email → 401 **identical** generic message (no enumeration leak, tested explicitly as its own case — response body/timing must not differ from the wrong-password case); expired access token → 401; revoked refresh token → 401 + forced re-login; **rotated-out refresh token (already consumed by a prior refresh) → 401**, tested as a distinct case from "explicitly revoked" even though both return the same generic body ([ADR-0013](../adr/0013-refresh-token-rotation-policy.md) — single-use enforcement is the mechanism under test, not just the revoked-flag path); missing refresh cookie entirely → 401; AIAgent key used on a human-only route → 403.
**Org-membership classes at login (distinct from the credentials check above — all use correct credentials):** exactly 1 `active` membership → 200, `org_context: "auto"`; 2+ `active` memberships → 200, `org_context: "picker"`; 0 `active` memberships (none at all, or only `suspended`/`invited`) → 403 `no_active_organization`, no token issued — tested as its own case, distinct from the 401 credentials-failure class, since the failure reasons and status codes must not be conflated.
**Org-membership classes at refresh (ADR-0013 — same partition re-applied at a second choke point):** ≥1 active membership at refresh time → normal rotation proceeds; 0 active memberships (e.g. suspended after login, before this refresh) → 403 `no_active_organization`, refresh token itself left un-revoked — tested as distinct from the token-validity classes above, since this failure is about the actor's current standing, not the token's own state.
**Rotation-chain class:** a token rotated N times still enforces the *original* session's `expires_at` on refresh N+1 — tested by asserting the Nth-generation token's `expires_at` equals the 1st generation's, not `now + 30d`.
**Logout classes (ADR-0014 — deliberately equivalence-partitioned around idempotency, not just success/failure):** valid session + valid refresh cookie → `204`, `RefreshToken.revoked_reason="logout"`, a subsequent `POST /auth/refresh` with the same cookie now 401s (the actual revocation assertion, not just the `204` status — a route that always returns `204` without revoking anything would pass a status-only test). **Idempotent-no-op class (all collapse to the same `204`, tested as one equivalence class with multiple representative members, not four separate behaviors):** no refresh cookie present, cookie hash not found, cookie already revoked/rotated-out, cookie belongs to a different `user_id` than the authenticated caller. **Invalid-access-token class:** missing/expired/malformed bearer token → 401 (same generic `get_current_actor` body `GET /auth/me` uses) — the one and only non-2xx outcome this route has. **Isolation class:** two `RefreshToken` rows for the same user (or two different users) — logging out session A must leave session B's refresh usable, tested as a distinct case from the single-session rotation isolation `TC-AUTH-008` already covers for `/auth/refresh`, since logout's cross-user `WHERE` clause is new relative to that route.
**Rate-limit class:** 6th failed attempt for the same `(client_ip, email)` pair within the 15-minute window → 429 `rate_limited`, regardless of whether attempt 6 itself used correct credentials (the throttle fires before the credentials check completes evaluating a new attempt); a successful login resets the counter for that pair, tested explicitly (attempt 3 fails, attempt 4 succeeds, attempts 5–8 fail — must take 5 more failures to trigger 429, not fail on attempt 2 post-reset).

**AIAgent bearer-key classes ([ADR-0015](../adr/0015-ai-agent-credential-mechanics.md)):** valid, non-revoked `tnx_agent_...` key → `get_current_actor` resolves the `AIAgent` (not any `User`) and updates `last_used_at`; revoked key (`revoked_at` set) → 401, same generic `invalid_token` body as every other rejection, `last_used_at` **not** updated (rejection happens at the lookup, before any update); well-formed-looking key whose `key_prefix` matches a real row but whose secret segment fails the argon2 verify (e.g. a truncated/corrupted key sharing another key's prefix by chance) → 401, tested as a distinct case from "prefix not found at all" to prove the lookup-narrowing step doesn't short-circuit the verify; bearer token that doesn't start with `tnx_agent_` → falls through to the JWT-decode branch as today (no new failure mode introduced for the human path).

## 3. RBAC — decision table (representative slice)

Full table generated mechanically from the seeded `Permission` catalog (~100 codes, 29 resources — [Database Document](../database/2026-09-03-database-design.md) §3.3) × 5 system roles at test-authoring time (per Master Test Plan §14 risk mitigation); representative slice below illustrates the shape:

| Permission code | org_admin | test_manager | tester | auditor | ai_agent_scoped |
|---|---|---|---|---|---|
| `test_plan.approve` | ✅ | ✅ | ❌ | ❌ | 🚫 (structurally excluded, never seeded) |
| `test_case.create` | ✅ | ❌ | ✅ | ❌ | ✅ |
| `test_case.delete` | ✅ | ❌ | ✅ | ❌ | ❌ (no delete in the ai_agent bundle) |
| `test_case.read` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `requirement.export_rtm` | ✅ | ✅ | ❌ | ✅ | ❌ |
| `org_membership.create` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `role.create` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `.read` (any of the 29 resources) | ✅ | resource-dependent | resource-dependent | ✅ (all) | resource-dependent |
| `.delete` (any resource) | ✅ (all) | resource-dependent | ❌ | ❌ | ❌ (never, by design) |

`org_admin` has no ❌ cells at all — its assertion is "bundle size == full catalog size", not a per-code allow/deny walk. Every other ❌/✅/🚫 cell is a distinct test case: authenticate as an actor holding exactly that role, call the route gated by that permission code, assert the resulting status code (200/201 for ✅, 403 for ❌, 403-and-unconditional for 🚫 — RBAC-5's double-enforcement means the 🚫 cells are tested twice: once confirming the permission was never seeded, once confirming the endpoint rejects it even if it somehow were).

**AUTH-4's slice of this table ([ADR-0015](../adr/0015-ai-agent-credential-mechanics.md)):** `has_permission`/`require_permission` themselves are implemented by AUTH-4, but only the org-wide-grant branch (`RoleAssignment.project_id IS NULL`) is exercised by AUTH-4's own tests, against a fixture-seeded custom `Role`/`Permission`/`RoleAssignment` (not the full 5-system-role catalog, which doesn't exist until RBAC-4's seed migration lands). The project-scoped branch is RBAC-3's coverage obligation — see §18, satisfied against `Project` (the tenant-scoped resource PROJ-1 already built) rather than a synthetic route.

## 4. Multi-tenancy isolation — equivalence classes + boundary

- **Class A (same-org access):** Actor in Org X requests a resource in Org X → 200.
- **Class B (cross-org access):** Actor in Org X requests a resource in Org Y → 404 (never 403 — NFR-1). Tested against every entity type that carries an `org_id` path, not just one representative entity, since the router factory (ADMIN-2) is generic but a per-entity regression is still possible if a bespoke route forgets the filter. First concretely exercised against `Project` (PROJ-1, `GET`/`PATCH /projects/{id}`) — TC-RBAC-002's originally-blocked scope, now achievable for this one entity. Extended to `Release` (PROJ-2, `GET /releases/{id}` and `GET /releases/{id}/test-cycles`) one level deeper in the resource tree, same boundary re-derived via the fetched `Release`'s `Project`. **Class B'** (RBAC-3, body-field variant, [ADR-0021](../adr/0021-role-assignment-creation-flow.md)): a `role_id`/`project_id` supplied in `POST /orgs/{org_id}/role-assignments`'s body that resolves in a *different* org than the caller's already-proven `org_id` → `422`, deliberately **not** `404` — the caller already cleared Class C's boundary on `org_id` itself before this check runs, so there's no existence-hiding purpose left for a 404 here; tested as its own equivalence class specifically to confirm this isn't Class B's 404 by another name.
- **Boundary — org count (instance level, RBAC-1, [ADR-0016](../adr/0016-organization-bootstrap-creation-flow.md)):** 0 orgs on a fresh instance → first signup creates one + grants org_admin; ≥1 org already exists → `POST /auth/signup` returns `409 signup_closed` instead, tested as a distinct case from the 0-org success path, not just "signup always works." Two simultaneous first-signup calls (race class) → exactly one `Organization` results, the loser's request either 409s or is serialized to run second by the advisory lock (either outcome acceptable, "two orgs created" is the only failure).
- **Boundary — org count (per-user, at login, AUTH-1 — see §2's org-membership classes for the full case list):** exactly 1 active org membership for a user → auto-select, no picker; 2+ → picker shown; 0 active memberships → 403, login rejected, distinct from both of the above.
- **Class C (org-scoped route, no membership at all vs. membership-but-no-permission — NFR-19, [ADR-0015](../adr/0015-ai-agent-credential-mechanics.md)):** first exercised by `/orgs/{org_id}/agents*`. Caller with zero `OrgMembership` in the path's `org_id` (including a nonexistent `org_id`) → 404, same existence-hiding rule as Class B. Caller with an `OrgMembership` in that `org_id` but lacking the route's `require_permission` code → 403. The two must be tested as distinct cases against the same route, not conflated — a caller who's a member of the org but merely under-permissioned must never see a 404 (that would incorrectly imply the org itself is unreachable), and a genuine outsider must never see a 403 (that would confirm the org exists).
- **Class D (any-org permission gate, `POST /orgs` only — RBAC-1, [ADR-0016](../adr/0016-organization-bootstrap-creation-flow.md)):** deliberately does NOT follow Class C's shape, since there is no target org to apply a 404-vs-403 boundary against. Actor holding `organization.create` org-wide in *at least one* org they belong to → 200/201, regardless of which org that grant is in. Actor holding it nowhere (including an actor with zero org memberships at all, and an actor whose only grant is project-scoped, `project_id` non-null) → 403, one flat outcome, no 404 variant.

## 5. State transition testing

**TestPlan.status:** `draft → approved → superseded`. Invalid transitions tested as negative cases: `draft → superseded` directly (should be rejected — must pass through `approved`), `approved → approved` (idempotent re-approval — define as rejected, a new plan version is the correct path per GOV-1), `approved → draft` (backward transition, also rejected). As of PLAN-1 ([ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md)), this table is enforced by an application-layer guard on the generic `PATCH /test-plans/{id}` route itself (`409 invalid_status_transition` on any pair not in the legal-transitions table), not merely documented intent — see §27 for the full equivalence-class breakdown. The guard checks transition *legality* only, independent of GOV-1's own separate human-only *authority* gate on its dedicated `/approve` route (not yet built) — the two are deliberately not conflated into one check, per ADR-0031.

**TestExecution.result:** `pass | fail | blocked | skipped` — no transition graph (each execution is a new row per EXEC-1, not a mutable state machine), but re-execution behavior itself is tested: creating a second TestExecution for the same TestCase+TestCycle pair must insert, never update, the prior row.

**Defect.status:** `open → ... → closed` (exact intermediate states are an implementation choice deferred to the eventual task plan) — test that `status` is a structured enum, not free text (NFR-5), and that no transition path allows skipping tenant/permission checks.

**OrgMembership.status:** `invited → active` (on signup completion), `active → suspended → active` (admin action) — tested per RBAC-2, including the specific assertion that a `suspended` member's `RoleAssignment` rows remain in the DB (queryable) while all API calls under that membership 403/401.

## 6. Traceability path coverage (ADR-0006)

Both classes must appear in the same test project, not just individually:
- **Class 1 — direct path:** Requirement → RequirementTestCaseLink → TestCase (`test_condition_id IS NULL`).
- **Class 2 — TestCondition-mediated path:** Requirement → RequirementTestConditionLink → TestCondition → TestConditionTestCaseLink → TestCase (`test_condition_id IS NOT NULL`).
- **Boundary — zero coverage:** Requirement with no links of either kind → RTM/detail view must show an explicit "0 test cases cover this requirement" state (TRACE-1), tested as a distinct case from "links exist but all are Class 2," to catch a query that silently drops the direct-link class.

## 7. Generic CRUD — technique applied once, reused per entity

Rather than 28 bespoke test suites, one parametrized equivalence-partitioning suite runs against every entity in the [Database Document](../database/2026-09-03-database-design.md) §3 driven by its `entityConfigs/` field-type declarations:

- **string field:** empty string (boundary), max-length+1 (boundary), valid string (valid class).
- **enum field:** each declared enum value (valid classes), a value outside the enum (invalid class).
- **FK field:** existing id in the same org/project (valid), existing id in a different org/project (invalid — cross-tenant FK, must reject), non-existent id (invalid).
- **date field:** valid ISO date, malformed string (invalid class).

Permission-parity is tested once generically (any entity, lacking `.create`/`.update`/`.delete` → action button hidden **and** API still rejects — ADMIN-2's explicit non-bypass requirement) rather than 28 times. §18 below extends this section with the specific classes ADR-0021's per-entity tenant-resolution depth requires — the equivalence classes above (field-type validation) generalize cleanly across all 20 factory-served entities, but the *cross-tenant 404 boundary* does not, since it depends on each entity's own resolver chain, not just its field types.

## 8. Boundary value analysis — pagination & attachments

**Pagination:** `page_size=0` (reject or clamp — define as clamp-to-1), `page_size=25` (default, valid), `page_size=26` (reject or clamp to max — define as clamp-to-25 per NFR-6), empty result set (`total=0`, empty `items`), exact last-page boundary (`page` beyond `total/page_size` → empty `items`, not an error).

**Attachments:** file at exactly the configured size limit (valid), one byte over (rejected), allowed mime type (valid), disallowed mime type (rejected) — limits themselves are configurable per NFR-7, so this suite must read the configured limit rather than hardcoding a number.

**Login throttle (NFR-11/ADR-0011):** 4th failed attempt for a `(client_ip, email)` pair (still allowed, 401), 5th failed attempt (still allowed, 401 — the 5th failure itself is not throttled, it's what *causes* the next attempt to be throttled), 6th attempt (429, regardless of credential correctness), a successful attempt between failures resets the count to 0 for that pair. Window boundary: an attempt just inside the 15-minute window from the first counted failure still counts toward the threshold; an attempt just after the window has elapsed since the oldest counted failure does not.

## 9. Negative testing — immutability

**TestLog:** attempt `PATCH`/`DELETE` against any TestLog row → `405 Method Not Allowed`, not a 403 from a permission check — the path exists (under `GET`/`list`), the method doesn't, which is FastAPI/Starlette's own distinction between "no route at all" (404) and "route exists under a different method set" (405); either way the absence of a mutating path is structural, per EXEC-2 and the Database Document's schema-level immutability note. **Correction (EXEC-2, 2026-09-07):** this cell originally said `404`; verified against the live route and corrected to the actual `405` — `test_admin2_execution_trace.py::test_test_log_list_get_and_no_write_routes` asserts this directly, and its own comment names the same FastAPI/Starlette distinction restated above.
**Approval:** attempt `DELETE` on an Approval row → no such route exists; superseding a plan creates a new record, the original is asserted still present and unchanged.

**AIAgent credential human-only gate ([ADR-0015](../adr/0015-ai-agent-credential-mechanics.md)):** an `AIAgent` bearer credential calling `POST /orgs/{org_id}/agents` or `.../revoke` → 403 `actor_forbidden`, unconditionally, even if that agent's `RoleAssignment` happens to grant `ai_agent.create`/`.update` — same double-enforcement pattern as RBAC-5's Approval check, tested the same two ways (permission never seeded to an agent-eligible role bundle in practice; endpoint rejects it even if it somehow were).

## 10. AIAgent credential lifecycle — state coverage

`AIAgent` has no enum status field, but `revoked_at` behaves as a one-way state flip (`NULL` → set), analogous in test shape to the state-transition techniques in §5:

- **Issuance:** `POST /orgs/{org_id}/agents` with valid `acting_on_behalf_of_user_id` (active `OrgMembership` in `org_id`) → `AIAgent` row created, raw key returned once; response body's `api_key` is asserted absent from any subsequent response (identity/list views, if any exist for `AIAgent` via the generic CRUD surface, must never re-expose it — only `key_prefix`).
- **Revocation:** `revoked_at` set once → subsequent revoke calls on the same agent are idempotent (200, unchanged `revoked_at`), not an error — tested as a distinct case from "revoke a nonexistent agent_id" (404).
- **Post-revocation reuse:** the same raw key, presented again after revocation, → 401, tested immediately after the revoke call in the same test to rule out a caching/eventual-consistency gap.
- **`last_used_at` progression:** `NULL` at issuance (never used yet) → set on first successful authentication → advances (not reset) on each subsequent successful authentication, tested across at least 2 authenticated calls to confirm it's a running "last used," not a write-once "first used" field.

## 11. MCP-specific design notes

Every MCP tool test asserts **contract parity** with its backing REST route (MCP-1's "no divergent data contract" requirement) — the same request/response fixture is run through both the REST endpoint and the MCP tool, and the two response bodies are diffed as part of the test, not just independently asserted against a hardcoded expectation. The MCP-1 case shifts the parity assertion from "shape" (the broader TC-MCP-003 schema check) to "shape + identity": the same row is created via `create_test_case` and immediately re-fetched via `GET /requirements/{id}/test-cases`, and the two response bodies are asserted field-for-field equal (with the MCP response unwrapped from its `structuredContent` envelope and the REST response unwrapped from its `{items, total, ...}` envelope down to the inner object). A test that only asserts each surface's response independently against a hand-coded expected value would not catch a one-sided drift in either side's serialization.

**Per-tool bearer-key resolution equivalence classes (the same shape as AUTH-4's `get_current_actor` classes, but on the MCP side):** missing `Authorization` header → 401 `invalid_token`, indistinguishable from "wrong bearer value" → 401 `invalid_token`, indistinguishable from "revoked bearer" → 401 `invalid_token`, indistinguishable from "non-`tnx_agent_` bearer (e.g. a human JWT presented to MCP)" → 401 `invalid_token`. The generic-401-posture property is asserted as a single class ("every rejection shape is the same body") not as four independent cases — a tool that distinguishes "missing" from "wrong" from "revoked" re-introduces the user-enumeration leak ADR-0011 explicitly closed on the human side, and the only test that catches it asserts the four responses' bodies as a single equality set. The corresponding success class (a valid `tnx_agent_<prefix>_<secret>` resolving to its `AIAgent` row, stamping `last_used_at` per ADR-0015) is exercised once per MCP tool that handles a mutating or permission-gated action — same posture as `test_auth_*.py`'s TC-AUTH-030's two-call progression assertion.

**Permission-gate parity:** MCP-1 AC1's "same permission check as REST" wording is proven by the cheapest negative that proves it: an AIAgent with `test_case.read` only, calling `create_test_case`, must get `403 permission_denied` with the exact API Doc §1 envelope — `{"code": "permission_denied", "message": "You do not have permission to perform this action.", "field_errors": null}`. A weaker MCP-only check (e.g. "is the bearer key valid?") would pass any positive create test and silently ship the weaker path the AC explicitly forbids; the negative case is the only test that exercises `has_permission` from the MCP tool side at all, distinct from every existing REST-route permission test which already covers `has_permission` for the `User`-actor path.

**`_actor_membership_exists` boundary (the AIAgent-correct NFR-1 check, MCP-1-specific reframing of NFR-19):** a route gated by `_org_membership_exists(db, org_id, actor.actor_id)` — the older shape every pre-MCP-1 bespoke route used — silently 404s *every* MCP-originated request against an `AIAgent` caller, because `OrgMembership.user_id` FKs `user.actor_id` (not `actor.id`) and an `AIAgent` has no `user` row of its own. MCP-1 introduced `_actor_membership_exists` in `assets.py` to resolve this; future routes that take a `User | AIAgent` actor and gate on `OrgMembership` must use the new helper, not the old one — and the only test that catches a regression to the old shape is one that exercises an `AIAgent` caller against the route. The cross-tenant `404` (NFR-1) + the same-tenant `403 permission_denied` (NFR-9) classes both need `AIAgent`-caller fixtures added to them as their own distinct cases, not assumed satisfied by the `User`-caller fixtures already in `test_admin2_crud.py` and friends — the route's gate code is one of two shapes (User-only or User-or-AIAgent), and the test suite's coverage has to match the gate's actual shape or a branch slips through untested.

**MCP error-envelope mapping:** MCP-1 AC3 says "same shape/fields as the REST API's TestCase schema — no divergent data contract between the two access paths" — the same property holds for the error path, not just the success path. Every MCP tool that surfaces an error must re-raise it as a FastMCP `ToolError` carrying the API Doc §1 envelope verbatim (`{"code", "message", "field_errors"}`), not a tool-specific or framework-default error body. The test for this class asserts the envelope equality at the body level, not by checking `isError=True` alone (which would also pass for a tool that returns its own bespoke error shape inside the `isError=True` envelope) and not by checking `field_errors` shape alone (which would pass for a tool that returns the right `code` but the wrong `field_errors` key shape, e.g. nested Pydantic's default `{"detail": [...]}`).

**In-process ASGI-dispatch is *not* the chosen pattern (ADR-0033 decision 2 Alternatives).** The MCP tool body invokes the route handler function directly with explicit `actor=`/`db=` overrides — bypassing FastAPI's `Depends(get_current_actor)`/`Depends(get_db)` defaults — rather than running the request through an in-process `httpx.AsyncClient(transport=ASGITransport(app))` call against the live FastAPI app. The reason matters for the test design: the direct-call path means a "round trip through both surfaces" assertion only exercises the route's body code once per call, not twice (once in REST via ASGI, once in MCP via direct call) — a test that asserts both surfaces ran the same SQL by counting `session.execute()` calls would see 2 in an ASGI-dispatch implementation and 1 in the direct-call implementation. The chosen direct-call shape's coverage guarantee is structural, not testable: the route handler function *is* the only code under test in both the REST and MCP paths, so any single-surface test (REST) already covers both. The TC-MCP-003 parity assertion still belongs as an extra class because it's the cheapest proof of the AC3 "no divergent contract" claim a reviewer can read, not because it's the only thing catching a drift.

## 12. RBAC-4 seed migration — idempotency (negative/regression testing)

**Re-run class:** apply the seed migration to a fresh DB, record `role`/`permission`/`role_permission` row counts, apply it a second time (simulating a redeploy re-running migrations), assert identical counts — no duplicate system-role rows, no unique-constraint error surfaced to the caller. Distinct from a plain "insert succeeds" happy-path test, since the risk here is silent duplication, not a crash.
**Constraint-boundary class:** attempt to insert a second `Role` row with `name='org_admin'`, `org_id=NULL` directly (bypassing the migration's own existence check) → rejected by the partial unique index at the DB level, proving the constraint — not just the migration's own care — is what prevents duplicates.
**Non-interference class:** insert a custom `Role` with `org_id` set to a real org and `name='org_admin'` (same name as a system role) → succeeds, proving the partial index scopes only to `org_id IS NULL` rows and doesn't block per-org custom-role naming.

## 18. RBAC-3 RoleAssignment creation & project-scoped enforcement — equivalence classes ([ADR-0021](../adr/0021-role-assignment-creation-flow.md))

**`POST /orgs/{org_id}/role-assignments` mechanics classes:** actor with `role_assignment.create` in `org_id`, valid `role_id` + `actor_id` (+ optional `project_id`) → 201, row created with exactly the fields given (`project_id` omitted → `NULL`, org-wide). Actor with no `OrgMembership` in `org_id` at all → 404 (Class C, reused). Actor with membership but no `role_assignment.create` → 403. `role_id` resolving to a *different* org's custom `Role` (`Role.org_id` set to some other org) → 422 (Class B', §4) — a system-template `role_id` (`Role.org_id IS NULL`) is always valid regardless of `org_id`. Unknown `actor_id` (no `Actor` row at all) → 422. `project_id` resolving to a *different* org's `Project` → 422 (Class B'). Duplicate `(actor_id, org_id, project_id, role_id)` → 422 (unique-constraint `IntegrityError`, same shape as `organizations.py`'s slug collision), tested as a distinct case from "first grant succeeds."

**`OrgMembership` precondition class (AC-adjacent, [ADR-0021](../adr/0021-role-assignment-creation-flow.md)):** target `actor_id` resolves to a `User` with zero `OrgMembership` rows in `org_id` → 422. Target `User` with an `OrgMembership` in `org_id` of **any** status (`invited`, `active`, or `suspended` — not active-only) → gate passes, tested with a `suspended`-status membership specifically to prove the check isn't accidentally active-only. Target `actor_id` resolves to an `AIAgent` → gate skipped entirely regardless of any `OrgMembership` state (an `AIAgent` never has one) — tested as its own positive case, not inferred from the `User` classes.

**Org-wide vs. project-scoped resolution classes (AC1/AC2/AC3 — the story's core claim, tested against the real `GET`/`PATCH /projects/{id}` routes per [ADR-0021](../adr/0021-role-assignment-creation-flow.md)'s fix, not `has_permission()` in isolation):**
- **Org-wide class (AC1):** grantee has one `RoleAssignment` with `project_id = NULL` granting `project.read`/`.update` → `GET`/`PATCH` succeeds against *every* Project in the org, not just one — tested against at least 2 distinct Projects in the same org to prove "every," not "the first one tried."
- **Project-scoped class (AC2):** grantee has one `RoleAssignment` scoped to Project A only → `GET`/`PATCH` Project A succeeds; the identical call against Project B (same org, same permission code, no separate grant) → 403 — tested as one paired case (both projects, one actor, one test), not two independent tests that could each pass by accident.
- **No-implicit-access class (AC3):** actor has an `OrgMembership` in the org (any status) but zero `RoleAssignment` rows anywhere in it → 403 on any Project in that org — proves `OrgMembership` alone confers nothing, the negative-space case decision tables (§3) don't otherwise cover.
- **Regression class (the concrete bug this story fixes):** a Project's own creator, who per PROJ-1/ADR-0017 is auto-granted *only* a project-scoped `test_manager` `RoleAssignment` (not org-wide), can now `GET`/`PATCH` the project they just created without also holding org-wide `org_admin` — tested by asserting success for a creator actor stripped down to exactly that one grant (no other `RoleAssignment` rows), not the usual `org_admin` creator fixture that would mask the regression.

**AIAgent grantee class (AC4):** `RoleAssignment` created with `actor_id` = an `AIAgent`'s `actor_id` → identical resolution to the `User` classes above when that `AIAgent` later authenticates (bearer key) and calls `GET`/`PATCH /projects/{id}` — same org-wide/project-scoped/no-access outcomes, proving `has_permission`'s join chain treats `Actor.id` uniformly regardless of `actor_type` (07 principle #6).

**List class:** `GET /orgs/{org_id}/role-assignments` with actor holding `role_assignment.read` → returns both an org-wide and a project-scoped row seeded in the same org, neither filtered out; a row belonging to a *different* org never appears (Class B, §4, reused). Actor with no `OrgMembership` in `org_id` → 404; membership without `role_assignment.read` → 403.

## 19. ADMIN-2 generic CRUD router factory — additional equivalence classes ([ADR-0022](../adr/0022-generic-crud-router-factory.md))

**Resolver-depth class (extends §4's Class B/C to every tenant-resolution shape, not just `Project`/`Release`'s direct-column case):** at least one representative entity per depth is tested against the same cross-org 404 boundary — direct column (`Requirement` via `project_id`), one-hop (`TestCondition` via `requirement_id`), branching (`RiskItem`, whichever of `requirement_id`/`test_plan_id` is set), multi-hop (`TestCase` via `test_condition_id`→`requirement_id`, or `Defect` via its 3-hop chain), and global-catalog (`TestLevel`, no tenant at all — see the Global-catalog class below instead of a 404 boundary). A pass on `Project`/`Release` alone does not generalize to "the factory's tenant isolation works" — each resolver is separately hand-written code (ADR-0022), separately testable, separately breakable.

**Unresolvable-tenant class (distinct from cross-org — same org, but no resolvable chain at all):** a `TestCase` with `test_condition_id IS NULL`, no `RequirementTestCaseLink`, and no `TestSuiteTestCase` link → `GET`/`PATCH`/`DELETE /test-cases/{id}` → `404`, tested as its own case distinct from both "cross-org" (Class B) and "global catalog, no tenant by design" (below) — a factory implementation that conflates "resolver returned `None`" with "this entity has no tenant at all" would wrongly serve this row via the `has_permission_in_any_org` fallback instead of hiding it. **Not** this class (§24 covers it instead): `test_condition_id IS NULL` *with* a `RequirementTestCaseLink` — REQ-2's own direct-link shape, resolvable since [ADR-0029](../adr/0029-testcase-resolver-direct-link-fallback.md); this class narrowed from two missing links to three when that gap-fill landed.

**Global-catalog class (no `OrgMembership` boundary applies at all):** `TestLevel`/`TestType`/`TestDesignTechnique`/`Permission` list/create/item routes gated via `has_permission_in_any_org` — actor holding the resource permission org-wide in *any* org they belong to → success, regardless of which org; actor holding it nowhere → `403`, never `404` (there's no tenant existence to hide, so no 404-vs-403 boundary applies here at all, distinct from every tenant-scoped entity above).

**`Role` null-`org_id` read/write split class (NFR-33):** a system-role template (`org_id IS NULL`) → `GET /roles/{id}` succeeds (via the global-catalog fallback) but `PATCH`/`DELETE /roles/{id}` → `404` — tested as two distinct assertions against the *same* row, since an implementation could easily 404 both or neither instead of splitting by method.

**Scope-required-on-list/create class:** `GET /requirements` with no `?project_id=` → `422` (not an empty list, not every Requirement across every project); `POST /requirements` with no `project_id` in the body → `422`, same posture. Tested against at least one entity with a direct scope column and one with a resolved-via-parent scope column (e.g. `Requirement` vs. `TestCondition`), since the validation point differs (the scope value itself vs. a value that must additionally resolve to a real parent row).

**RESTRICT-delete class (NFR-31):** `DELETE` on a row still referenced by a RESTRICT FK (e.g. a `TestCase` with an existing `TestStep`) → `409`, tested as a distinct status from `422` (a `DELETE` on a row that fails Pydantic validation isn't a real scenario, but a `DELETE` on a nonexistent id — `404` — and a RESTRICT-blocked delete — `409` — must not collapse into the same code). `DELETE` on an unreferenced row → `204`/`200`, positive case, proving the `409` path isn't firing unconditionally.

**`RiskItem` both-FKs-set class:** `POST /risk-items` with both `requirement_id` and `test_plan_id` set → `422`, tested as distinct from "neither set" (also `422`, but via the DB `CHECK` rather than the factory's own validator — both must reject, for different underlying reasons, and a test suite that only tries "neither" would miss a validator that forgot the "both" case).

**Search/filter class (NFR-32):** an entity with `search_fields` configured (e.g. `Requirement`) — `?q=<substring>` matches rows via `ILIKE` across the configured columns, case-insensitive, partial match. An entity with none configured (e.g. `TestSuite`, at least initially) — `?q=<anything>` returns the same result as omitting it entirely (silently ignored, not `422`), tested as its own case so "search not implemented for this entity" is provably a no-op, not an unhandled parameter causing an error.

**`RoleAssignment` overlap note:** this factory's `RoleAssignment` config registers only `get`/`update`/`delete` (§3 of the API Document), deliberately not `create`/`list` — §18 above already covers those two verbs' equivalence classes under RBAC-3; nothing here duplicates that coverage.

## 20. DS-1 FormField component & Login/Signup migration — equivalence classes + regression testing ([ADR-0023](../adr/0023-frontend-shared-component-location.md))

## 27. PLAN-1 TestPlan membership, coverage query & status-transition guard — equivalence classes ([ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md))

`TestPlan`'s own identifier/scope/approach/staffing/schedule CRUD introduces no new technique — already covered generically by §19's ADMIN-2 classes (`TestPlan` is a direct-resolver-depth entity, same shape as `Requirement`/`TestSuite`). This section covers the many-to-many membership routes, the derived coverage query, and the `status`-transition guard this story adds.

**Many-to-many include class (TC-PLAN-002, same shape as §26's TC-REQ-008):** a `TestSuite` included in `TestPlan` A and a *different* `TestSuite` included in `TestPlan` B (same project) → both `TestPlanTestSuite` rows exist afterward, queried directly, each plan's membership independent of the other.

**Coverage-query class (TC-PLAN-002, AC2's core claim):** `TestPlan` with 2 included `TestSuite`s, each with ≥1 member `TestCase` → `GET /test-plans/{id}/test-cases` returns the union of every member `TestCase` across both suites. **Deduplication boundary:** the same `TestCase` is a member of 2 of the plan's included `TestSuite`s → it appears in the coverage query's result exactly once, not twice — tested with a fixture engineered specifically to exercise this (a single-suite fixture cannot distinguish "deduplicated" from "never had a duplicate to begin with," per the Master Test Plan's own risk note). **Zero-coverage boundary:** a freshly created `TestPlan` with no suites included yet → `GET` returns `200` with an empty list, not `404` — same "valid, common state" posture ADR-0030's zero-membership case established for `TestSuite`.

**Live-membership class (same shape as §26's TC-REQ-009):** `TestPlan` with 2 included `TestSuite`s → `GET /test-plans/{id}/test-suites` returns both. Remove one via `DELETE`, then call `GET` again *and* re-call the coverage query, in the same test → the suites list reflects the removal, **and** the coverage query no longer includes any `TestCase` that was only reachable via the removed suite (unless it's also a member of a still-included suite) — tested as a sequenced triple (add-state, remove, both post-remove reads), not two independent assertions.

**Cross-project rejection class (ADR-0031 decision #1, same shape as §26's TC-REQ-012 but a direct-column check on both sides, no branching resolver):** a `TestSuite` whose `project_id` differs from the target `TestPlan`'s `project_id`, same org → `POST /test-plans/{id}/test-suites/{suite_id}` → `422`, never `404`.

**Duplicate-include class (ADR-0031 decision #2, same shape as §26's TC-REQ-013):** a `TestSuite` already included in the target `TestPlan` → a second `POST` for the same pair → `409 already_included_in_plan`, distinct from `422` and distinct from `TestSuiteTestCase`'s own `already_in_suite` (a different relationship, its own code) — tested as a positive-then-negative pair in one test.

**Remove-non-member class (same shape as §26's remove-non-member class):** `DELETE /test-plans/{id}/test-suites/{suite_id}` for a suite that was never included (or already removed) → `404` — same deliberate asymmetry with `POST`'s `409`-on-already-true.

**Cross-org 404 boundary (reuses §4/§19's Class B/C verbatim):** a `TestPlan` or `TestSuite` belonging to a different org than the caller's own membership → `POST`/`DELETE`/`GET` on any of the four routes (including the coverage query) → `404`. Membership present but missing `test_plan.update`/`.read` → `403`.

## 28. PLAN-2 EntryExitCriteria visibility — equivalence classes ([ADR-0032](../adr/0032-plan2-entry-exit-criteria-visibility.md))

`EntryExitCriteria`'s own identifier/type/condition_text CRUD introduces no new technique — already covered generically by §19's ADMIN-2 classes (one-hop resolver depth, same shape as `TestCondition`/`TestCycle`). This section covers only the two new visibility surfaces this story adds: `TestPlanDetail`'s full-CRUD section (no new backend behavior to test beyond the existing generic routes, already covered) and the nested `exit_criteria` field on the Release→TestCycle audit query.

**Type-filter class (TC-PLAN-005's core claim, AC2's literal "exit criteria" wording):** a `TestPlan` with both an `exit`-type row and a row of one other type (`entry`, `suspension`, or `resumption`) → `GET /releases/{id}/test-cycles`'s nested `exit_criteria` for a `TestCycle` under that plan contains the `exit` row only, the other type absent — tested with a mixed-type fixture specifically, since a single-type fixture cannot distinguish "correctly filtered" from "nothing else existed to filter."

**Zero-exit-criteria boundary:** a `TestCycle` whose parent `TestPlan` has zero `exit`-type rows (regardless of whether it has other-type rows) → `exit_criteria: []` in the response, never an omitted key or `null` — same "valid, common state, not an error" posture the executions list's own empty case (ADR-0019) already established for this same route.

**Multi-cycle-same-plan batching class (structural, not a response-shape assertion):** 2+ `TestCycle`s targeting different Releases but sharing one parent `TestPlan` → both cycles' `exit_criteria` reflect that one plan's rows correctly — proving the batched-by-`test_plan_id` query (ADR-0032's Decision) produces the same correct result as a naive per-cycle query would, at lower query count; the query-count reduction itself is a code-review criterion, not independently machine-asserted.

**Quadruple-permission-gate class (extends §19's `RoleAssignment`-permission classes to a fourth AND'd code on one route):** an actor holding the pre-existing triple (`release.read`, `test_cycle.read`, `test_execution.read`) but **not** `entry_exit_criteria.read` → `403` — tested as its own independent case, not inferred from "the triple alone used to be sufficient before this story," since a naive additive implementation could easily leave the route's permission check unchanged while only editing its response-building code.

**Full-CRUD-in-page class (`TestPlanDetail`'s new section, frontend-only — the backend routes it calls are already covered by §19):** add/edit/delete of a criteria row from this section round-trips through the same generic routes the admin surface's own page already exercises — verified as "the same config, same routes, rendered in a second place," a code-review/structural criterion for the reuse claim, not a second backend behavioral test suite.

**Status-transition-guard classes (the story's own state-transition extension of §5):** requested `status` in `{draft→approved, approved→superseded}` → `200`, update applied. Requested `status` in `{draft→superseded, approved→draft, draft→draft, approved→approved, superseded→anything}` → `409 invalid_status_transition`, tested as independent negative cases (not inferred from one another — a guard checking only "is this one of the two known-good pairs" could still wrongly accept an untested illegal pair if the negative-space check is coded as an incomplete allow-list rather than an exhaustive legal-pairs table). **Non-status-field independence:** a `PATCH` body with no `status` key, only `identifier`/`scope`/etc., is unaffected by the guard regardless of the plan's current `status` — tested against a `superseded` (terminal-state) plan specifically, to prove the guard scopes to the `status` field alone, not the whole route.

**Authority-vs-legality boundary (ADR-0031's own explicit non-goal, tested as an absence, not a positive assertion):** an actor holding only `test_plan.update` (no `test_plan.approve`, no human-only gate applicable, since GOV-1's `/approve` route doesn't exist yet) can still legally move a plan `draft→approved` via the plain `PATCH` — this is the accepted interim gap ADR-0031's Consequences documents, not a defect; no test in this section asserts it should be rejected, and a future GOV-1-scoped test narrowing this is that story's own addition, not a regression of this one.

**Permission-visibility class (AC4, NFR-36) — hidden vs. disabled vs. absent, three distinct states not to be conflated:** an actor lacking `<resource>.create` → the "New" button is absent from the DOM entirely (`queryByRole` returns null), not merely `disabled`. An actor lacking `<resource>.update`/`.delete` on an entity with **no** `update`/`delete` in its config at all (`Permission`, `TestLog`, the 4 link tables) → those actions are absent for every actor regardless of permission, distinguished as its own case from a permission-driven absence (a bug that always-hides these buttons "by permission" would coincidentally pass a naive test but fail the moment such an actor is ever granted the (nonexistent) permission code). `usePermissions`' cached snapshot going stale mid-session (permission revoked after the page loaded) is explicitly **not** a UI-hiding responsibility — tested by confirming the write call itself still gets `403` even with a stale-permissive cached snapshot, proving the hook is UX-only per NFR-10/NFR-37.

**Scope-selector class (`RiskItem`/`Attachment`):** before a scope selection is made, `EntityTable` does not mount and no list request fires (a spied `apiFetch` records zero calls) — distinct from "mounts and shows an empty/error state," since the backend would `422` an unscoped list call (§18/API Document §1) if one were mistakenly sent. After selecting a `Requirement` (for `RiskItem`) the list request carries `?requirement_id=<id>`; after selecting a `TestPlan` instead, `?test_plan_id=<id>` — the two branches of `RiskItem`'s scope toggle are tested as distinct cases, not inferred from one exercising the other.

`TestCycle`'s own `test_plan_id`/`name`/`start_date`/`end_date` fields introduce no new technique for the fields themselves — the same field-level equivalence classes §19's ADMIN-2 section already established for string/date columns apply. Independently, an `environment_id` whose resolved `project_id` differs → same `422`. **Registry/no-entity-specific-code class (AC1, structural):** adding a 29th config object to the registry (a throwaway test-only entity config, mocked backend) makes it render via `EntityListPage`/`EntityFormPage` with zero other file changes — a code-review/structural criterion (same posture as TC-SHELL-006) proving the "add a config file, not a component" claim, not something a runtime assertion alone establishes.

`POST /test-cycles/{id}/executions`'s own boundary classes (404-vs-403, the PLAN-3 scope-check's both directions, the `executed_by_actor_id` stamping class, the generic-route-removal regression class) are already covered by §29 — this story reuses that route verbatim and adds no new boundary to it. This section covers only what §29 explicitly deferred: the dashboard's aggregation correctness and the re-execution-history claim.

**Live dashboard aggregation class (TC-EXEC-002, FR-EXEC-1 AC2's own literal claim):** a `TestCycle` seeded with a genuinely mixed set of `TestExecution` rows — at least one `pass`, one `fail`, one `blocked`, one `skipped` — must have each of the four `GET /test-executions?test_cycle_id=<id>&result=<value>&page_size=1` calls return a `total` matching that value's seeded count exactly, all four asserted in the same test. The backend's own `422` (§29) remains the actual enforcement boundary regardless of what this test proves about the picker.

## 24. REQ-2 direct TestCase authoring — equivalence classes ([ADR-0006](../adr/0006-test-condition-optional.md), [ADR-0029](../adr/0029-testcase-resolver-direct-link-fallback.md))

REQ-2 does not introduce a new technique for the create/link shape itself — §17's "Class 1 — direct path" already names `Requirement → RequirementTestCaseLink → TestCase (test_condition_id IS NULL)` as one of the two traceability-chain equivalence classes ADR-0006 requires tested. This section covers what's specific to REQ-2's own atomic create+link route and the resolver gap-fill it exposed.

**Atomic create-and-link class (TC-REQ-003):** `POST /requirements/{id}/test-cases` → `201`, response `test_condition_id: null`, and a `RequirementTestCaseLink` row exists for `(requirement_id, test_case_id)` — asserted as two separate checks (response shape, DB row), not just the response, since a route that returns a plausible-looking `TestCaseSummary` without actually inserting the link row would still pass a response-only assertion. `test_level_id`/`test_type_id` omitted from the body → `422` — required non-nullable FKs on `TestCase` itself, unrelated to ADR-0006's TestCondition-optional lightweness (a common misreading risk: "lightweight path" does not mean "every FK is optional").

**Resolver gap-fill regression class (the ADR-0029 risk, extends §19's Unresolvable-tenant class):** a `TestCase` created via the atomic route above — `test_condition_id IS NULL`, `RequirementTestCaseLink` present, no `TestSuiteTestCase` link — must resolve successfully (`200`) on an immediately-following `GET /test-cases/{id}`, not `404`. Tested as its own case, separate from the create call itself, precisely because the bug this catches (`resolve_test_case_org_id` missing the `RequirementTestCaseLink` branch) left the create call itself completely unaffected — the row inserts correctly either way; only the *subsequent read* exposes the gap. `TestStep`/`Attachment` inherit this same fix by delegation (§19's resolver-depth class) — no separate test needed for either, since neither has its own resolver logic to break independently.

**TestStep independent-editability class (TC-REQ-004):** add 3 `TestStep`s to one `TestCase` (`sequence` 1/2/3) → `GET /test-steps?test_case_id=<id>` returns all 3, ordered by `sequence`. `PATCH` one step's `action`/`expected_result` → re-fetching a *different* step in the same `TestCase` shows it unchanged — asserted by re-fetching the sibling, not just trusting the edited step's own `PATCH` response, since a route that accidentally updates every step sharing a `test_case_id` (a missing `WHERE id = ` clause, or an off-by-one on which row `PATCH` targets) would still return a correct-looking response for the intended step while silently clobbering others.

**TestStep reorder class (TC-REQ-004's own "reorder" clause, closed 2026-09-06):** a naive two-call adjacent swap (`PATCH` step A directly to step B's `sequence`) → `422` on the colliding call, `(test_case_id, sequence)`'s `UniqueConstraint` — tested explicitly as its own positive assertion (not just documented prose), proving the collision is real and surfaces the expected error code, not a 500 or a silent no-op. The actual reorder path — swap via a temporary out-of-range `sequence` (three `PATCH` calls: move A to a free temp value, move B into A's old slot, move A into B's old slot) — is tested end to end: final `GET`-list order reflects the swap, and a single-row re-fetch of the moved step confirms the new `sequence` persists, not just that the list view happens to look right. Atomic single-call reordering (a dedicated bulk-reorder endpoint) remains out of scope — no story asks for it — but "TestSteps can be reordered" as REQ-2's own AC3 claims is now a tested-and-passing guarantee via the temp-value workaround, not merely an assumption.

## 25. REQ-3 TestCondition rigor path — equivalence classes ([ADR-0028](../adr/0028-req3-test-condition-rigor-path-bespoke-routes.md))

REQ-3 does not introduce a new technique either — it reuses §6's traceability-path equivalence classes (Class 2, the TestCondition-mediated path) and §19's cross-org 404-boundary/resolver-depth classes. This section covers only what's specific to the two new atomic create+link routes, the generic-create removal, and the RBAC bundle extension.

**Atomic create+link classes (TC-REQ-005/006, the story's core verification burden):** `POST /requirements/{id}/test-conditions` with valid `description`/`priority` → `201`, **both** the `TestCondition` row and its `RequirementTestConditionLink` row exist afterward (asserted by querying the link table directly, not inferred from the `201` response body alone — a route that creates the entity but silently skips the link insert would still pass a response-shape-only test). **Transitive traceability class (TC-REQ-006's own AC wording):** from a `TestCase` created via the test-condition-mediated route, walking `TestConditionTestCaseLink` → `TestCondition` → `RequirementTestConditionLink` → `Requirement` reaches the exact originating `Requirement` — tested as an explicit multi-hop query assertion, not just "both link rows exist independently" (two correct link rows pointing at *inconsistent* parents would still each individually "exist").

**Both-paths-coexist class (TC-REQ-007):** in the same Project, one `TestCase` created via REQ-2's direct path (`test_condition_id IS NULL`, linked via `RequirementTestCaseLink`) and one via REQ-3's path (`test_condition_id` set, linked via `RequirementTestConditionLink`+`TestConditionTestCaseLink`) both resolve correctly and independently — `GET /test-cases/{id}` for each returns the expected `test_condition_id` (`null` vs. set), and each is reachable only via its own link table, not the other's. Verified at the API/DB layer per this story's own scope boundary (no traceability-view UI exists yet, FR-TRACE-1/2).

**Generic-create-removed class (TC-REQ-011, negative testing, same shape as §9's immutability classes):** `POST /test-conditions` (the factory's own path, pre-ADR-0028) no longer accepts `POST` — `GET`/`PATCH`/`DELETE /test-conditions/{id}` and `GET /test-conditions?requirement_id=` are unaffected, tested alongside the negative case to prove the restriction is `create`-only, not an accidental blanket removal.

**`test_manager` RBAC-bundle-extension class (TC-REQ-010, same shape as §16's PROJ-2 class):** a `test_manager`-only actor (no `org_admin`/`tester` anywhere) successfully calls both new routes — the only class that would catch the migration silently failing to apply, or the bundle silently reverting to pre-REQ-3 (`.read`-only) shape. Distinct from the routes' own `test_case.create`/`test_condition.create` positive classes above, which are satisfiable by `org_admin` alone and wouldn't catch a `test_manager`-bundle regression specifically.

## 26. REQ-4 TestSuite membership — equivalence classes ([ADR-0030](../adr/0030-req4-test-suite-membership-bespoke-routes.md))

`TestSuite`'s own name/purpose CRUD introduces no new technique — it's already covered generically by §19's ADMIN-2 classes (`TestSuite` is a direct-resolver-depth entity, same shape as `Requirement`). This section covers only the many-to-many membership routes this story adds.

**Many-to-many persistence class (TC-REQ-008, the story's own literal AC wording — "a TestCase can belong to more than one Suite"):** the same `TestCase` added to `TestSuite` A and `TestSuite` B (both in the same project) → both `TestSuiteTestCase` rows exist afterward, queried directly (not inferred from two `201` responses) — a route that silently overwrote a single "current suite" pointer instead of inserting a genuine second join row would still return two plausible-looking `201`s while failing this class specifically.

**Live-membership class (TC-REQ-009, AC2's core claim):** `TestSuite` with 2 member `TestCase`s → `GET /test-suites/{id}/test-cases` returns both. Remove one via `DELETE`, then call `GET` again *in the same test* → returns only the remaining one — tested as a sequenced pair (add-state, then post-remove-state), not two independent assertions that could each pass against a stale/cached read. **Zero-membership boundary:** a freshly created `TestSuite` with no adds yet → `GET` returns `200` with an empty list, not `404` (the suite itself exists; having no members yet is a valid, common state, not an error).

**Cross-project rejection class (TC-REQ-012, ADR-0030 decision #1):** a `TestCase` whose own resolved `project_id` (via any of the three ADR-0029 resolver branches — direct-link, TestCondition-mediated, or an existing `TestSuiteTestCase` link to a *different* suite) differs from the target `TestSuite`'s `project_id`, same org → `POST /test-suites/{id}/test-cases/{case_id}` → `422`, never `404` (the caller already proved org membership; this is a rejected relationship, not a hidden-existence case). Tested against more than one of the three resolver branches, not just the direct-link one, per the Master Test Plan's own risk note — a project-match check miscoded against only one branch's result would pass a single-branch fixture while leaking membership via the others.

**Duplicate-add class (TC-REQ-013, ADR-0030 decision #2):** a `TestCase` already a member of the target `TestSuite` → a second `POST` for the same pair → `409 already_in_suite`, distinct from `422` (this class exists specifically to catch an implementation that reuses REQ-3's generic `IntegrityError`→`422` handler by copy-paste instead of a dedicated `409` branch, per the Master Test Plan's own risk note) and distinct from a genuinely new pair's `201` (tested as a positive-then-negative pair in one test, not two independent tests).

**Remove-non-member class:** `DELETE /test-suites/{id}/test-cases/{case_id}` for a case that was never added (or already removed) → `404` — a `DELETE`'s "nothing to do" case reads as not-found, distinct from `POST`'s "already true" `409` above; the two verbs' idempotency postures are deliberately asymmetric (ADR-0030), tested as two separate classes so neither is assumed to mirror the other.

**Cross-org 404 boundary (reuses §4/§19's Class B/C verbatim, no new mechanism):** a `TestSuite` or `TestCase` belonging to a different org than the caller's own membership → `POST`/`DELETE`/`GET` on any of the three routes → `404`. Membership present but missing `test_suite.update`/`.read` → `403`. No new resolver logic to test here beyond confirming both routes reuse the existing `_TEST_SUITE_CONFIG`/`resolve_test_case_org_id` chains rather than a re-derived one.

## 32. EXEC-2 append-only TestLog — equivalence classes ([ADR-0038](../adr/0038-exec-2-append-only-test-log.md))

**Initial-recording log class (TC-EXEC-004's "from=null" half, Q2):** `POST /test-cycles/{id}/executions` → the immediately-following `GET /executions/{id}/logs` returns exactly one row, `event_type=status_change`, `payload.from=null`, `payload.to=<the recorded result>`. Not inferred from the create response alone — a route that inserted the `TestExecution` correctly but never appended the log would still `201` identically.

**Correction-appends-not-overwrites class (TC-EXEC-004's own literal wording, "correct to fail... appended, doesn't overwrite"):** an execution already `pass` → `PATCH .../executions/{id}` with `result=fail` → the timeline now has **two** rows (not one edited in place): the original `status_change` (`from=null, to=pass`) byte-for-byte unchanged, plus a new one (`from=pass, to=fail`). Asserting only "a new row with `to=fail` exists" cannot distinguish "appended" from "the first row was mutated and a second one added by coincidence" — the first row's own untouched content must be re-asserted after the `PATCH`, same "assert the untouched side too" discipline TC-REQ-004/TC-EXEC-003 already established for this codebase.

**No-op `PATCH` classes (Q6, two independent negative cases — neither is a weaker version of the other):** (a) a `PATCH` whose body has no `result` key at all (only `actual_result`/`executed_at`) → log count unchanged; (b) a `PATCH` whose body sets `result` to the value it already had → log count unchanged. **Comment/attachment class (TC-EXEC-004 extended, AC1's remaining two triggers):** `POST /executions/{id}/comments` with only `text` → `event_type=comment`, `payload.text` matches. **Agent-action override class (TC-EXEC-004 extended, Q3):** the same create/comment actions performed by an authenticated `AIAgent` (not a `User`) → `event_type=agent_action` regardless of which of the two actions it was, with `payload.kind` naming the real action and `payload.actor_type=ai_agent`. Distinguishes "agent overrides the type" from "agent is simply a different `actor_id` value" — a fixture using only a human actor cannot exercise this branch at all.

**Ordered-timeline class (TC-EXEC-006's own literal wording, AC3):** an execution with 3+ log entries created out of strict wall-clock order relative to test-assertion order (a create, then two corrections) → `GET /executions/{id}/logs` returns them `logged_at` ascending, oldest first — asserted by comparing the returned sequence's own timestamps pairwise (`items[i].logged_at <= items[i+1].logged_at`), not merely "all expected entries are present in the response" (which a shuffled-order bug would still satisfy).

**Immutability class (TC-EXEC-005, AC2 — reuses §9's "structural absence" shape):** `PATCH`/`DELETE` on any `TestLog` id → `405`, both before and after this story confirmed no code path ever registers those methods for the resource (§9's own correction above). No permission-driven `403` case exists for this class — the absence is structural, not authorization-gated, so a `403` result would itself indicate an accidental new route rather than confirm the intended behavior.

**RESTRICT-blocks-delete consequence class (not itself an AC, but the one behavior change this story's own append-on-create side effect causes — flagged per ADR-0038's Consequences):** a `TestExecution` with at least one log entry (true of every execution created through the app as of this story) → `DELETE /test-executions/{id}` → `409 restrict_blocked`, not `204`, and a follow-up `GET` on the same id still returns `200`. Existing tests asserting the pre-EXEC-2 `204`/gone behavior (TC-PLAN-017's own `DELETE` leg, `test_admin2_execution_trace.py`'s CRUD-happy-path test) were updated in place rather than left to regress silently.

**Cross-org 404 / permission-missing 403 boundary (reuses the established flat-route pattern, no new mechanism):** both new bespoke routes (`POST /executions/{id}/comments`, `GET /executions/{id}/logs`) — missing execution, or caller has no `OrgMembership` in its resolved org → `404`; membership present but missing `test_execution.update`/`.read` respectively → `403`, proven with an actor holding a real, unrelated permission (not a blanket no-roles-at-all rejection) per the standing `_create_custom_role_member` convention. Both routes additionally correct for an `AIAgent` caller specifically — `_actor_membership_exists`, not the org-membership check's `User`-only predecessor (a genuine pre-existing gap in `execution_authoring.py`'s create route too, found and fixed in the same change, not newly introduced by it).

## 35. EXEC-3 raise Defect — equivalence classes ([ADR-0044](../adr/0044-exec-3-raise-defect-from-execution.md))

**Atomic create+link class (TC-EXEC-007, the story's own literal "linked... and, via `TestCaseDefectLink`, traceable" wording, same shape REQ-3's TC-REQ-005/006 already established for their own atomic routes):** `POST /executions/{id}/defects` against a `fail`-result execution → `201`; the immediately-following pair of reads — `GET /defects/{id}` (the new `Defect` row, `test_execution_id`/`reported_by_actor_id` correct) **and** `GET /test-case-defect-links?test_case_id=<the execution's own test_case_id>` (a row linking that `test_case_id` to the new `defect_id`) — both confirmed in the same test, not inferred from the `201` response body alone. **Cross-org 404 / permission-missing 403 boundary (reuses the established flat-route pattern, no new TC row — same posture §32's EXEC-2 section already took for its own two bespoke routes):** both new bespoke routes — missing/cross-org `TestExecution` (for `POST .../defects`) or `TestCase` (for `GET .../defects`), or caller has no `OrgMembership` in the resolved org → `404`; membership present but missing `defect.create`/`.read` respectively → `403`, proven with an actor holding a real, unrelated permission (not a blanket no-roles-at-all rejection), per the standing `_create_custom_role_member` convention.

**Real-navigation class (TC-SHELL-038):** clicking an entity-group child (Test Design → Requirements) in a real browser lands on and renders the actual `/projects/:projectId/admin/requirements` screen (its own heading, its own breadcrumb trail) — not just an `href` string check, which would pass even if the target route were itself broken.

## 45. Tabler shell migration, Phase 2 — equivalence classes ([ADR-0054](../adr/0054-tabler-shell-migration-phase-2.md))

**Cascade-flip class (TC-DS-031, revised in place):** §44's own "no-visible-regression" claim inverts — this class now proves the OPPOSITE: Tabler's computed styles (`.card`'s `box-shadow`, `.btn-primary`'s `background-color`, `--tblr-primary`) win over AdminLTE's on both an unauthenticated screen and the authenticated shell, with a reversible control (moving Tabler's `<link>` back to the front of `<head>`, hand AdminLTE the cascade again) proving the win is genuinely caused by document position, not some other rule.
