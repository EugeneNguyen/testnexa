## 1. Purpose & scope

This document consolidates functional (FR) and non-functional (NFR) requirements for the scaffold: a full-stack ISTQB/IEEE829-aligned test management tool implementing the complete [07 ERD](../product-discovery/07-erd-draft.md) (28 entities), multi-tenant RBAC, JWT auth for human and AI-agent actors, and a first-party MCP server. Scope boundaries and the deliberate deviation from the validated MVP are recorded in [ADR-0001](../adr/0001-full-erd-scope-over-validated-mvp.md).

**Out of scope** (unchanged from the design spec): IEEE 829/29119-3 document-format export (RTM export is CSV only), SSO/OIDC/SAML/LDAP providers, AI test-case generation, billing/usage metering.

## 2. Functional requirements

Each FR ID maps 1:1 to the acceptance criteria already ratified in `docs/user-stories/`; this section is the canonical index, not a restatement — see the linked story for full Given/When/Then criteria. Priority: **Must** (blocks scaffold completion), **Should** (build now, lower polish priority), **Could** (exploratory, structural-only).

### 2.2 Multi-tenancy & RBAC — [rbac-tenancy-stories.md](../user-stories/2026-09-03-rbac-tenancy-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-RBAC-1 | Create an Organization; first-ever signup auto-creates org + org_admin; an existing org_admin can create further, fully isolated orgs | Must | Organization, OrgMembership, RoleAssignment |
| FR-RBAC-2 | Invite/suspend/reactivate org members | Must | OrgMembership |
| FR-RBAC-3 | Assign roles org-wide or project-scoped | Must | RoleAssignment |
| FR-RBAC-4 | Seeded system roles (org_admin, test_manager, tester, auditor, ai_agent_scoped) | Must | Role, Permission, RolePermission |
| FR-RBAC-5 | Structural human-only Approval enforcement (double-enforced) | Must | Permission, RoleAssignment |

FR-RBAC-1 ships as two routes, not one: `POST /auth/signup` (public, bootstrap-only — closes once any `Organization` exists deployment-wide) and `POST /orgs` (authenticated, for an existing org_admin minting a second org). Both assign the caller RBAC-4's already-seeded `org_admin` system `Role` in the org just created, rather than creating a per-org copy. `POST /orgs` needs a permission check with no target `org_id` to scope by (the org doesn't exist yet) — a bespoke any-org gate (`has_permission_in_any_org`), not FR-AUTH-4's path-scoped `require_permission` reused as-is. See [ADR-0016](../adr/0016-organization-bootstrap-creation-flow.md).

FR-RBAC-3 ships as `POST`/`GET /orgs/{org_id}/role-assignments` (bespoke, org-path-scoped, same `require_permission`/404-vs-403 boundary as every other org-scoped route). Creating a grant for a `User` actor requires that user already hold an `OrgMembership` (any status) in `org_id`; a `role_id`/`project_id` that doesn't resolve within the caller's own org → `422`, never `404` (no target-org existence to hide, since the caller already proved membership). This story also fixes a gap FR-AUTH-4/FR-PROJ-1 left open: `GET`/`PATCH /projects/{id}` (PROJ-1) now pass `project_id` into `has_permission`, so a project-scoped grant — including a project's own creator's auto-assigned `test_manager` role — actually works within that project, not just an org-wide grant. See [ADR-0021](../adr/0021-role-assignment-creation-flow.md). A follow-up addendum adds a UI slice — `GET /orgs/{org_id}/roles` (role dropdown data source) and a "Role Assignments" panel on `OrgHome` — not part of the original API-only scope, added on explicit CTO direction after the story's initial acceptance (ADR-0021's addendum).

FR-PROJ-1 ships as `POST /orgs/{org_id}/projects` (bespoke, org-path-scoped — reuses `require_permission`/the 404-vs-403 boundary as-is, same shape as FR-AUTH-4/FR-RBAC-1's own bespoke routes) plus `GET`/`PATCH /projects/{id}` (org resolved from the fetched row, anticipating the eventual generic CRUD factory's item-route contract). Closed by wiring `OrgHome` to `GET /projects?org_id=` — the generic-CRUD factory `list` route ADR-0022 already shipped and `getProjectsTotal` (FR-SHELL-3) already calls for its own dashboard widget. No new backend route, no new architecture decision: reuses an already-shipped, already-documented route. TC-PROJ-018 covers it.

FR-PROJ-2 ships as `POST`/`GET /projects/{project_id}/releases` (bespoke, project-path-scoped, same `has_permission`-called-directly + 404-vs-403 posture as `GET`/`PATCH /projects/{id}`) plus `GET /releases/{id}` and `GET /releases/{id}/test-cycles` (both row-resolved, no path `project_id`). `test_manager`'s seeded bundle is extended with `release.create`/`.read`/`.update` (it already held full `test_cycle` CRUD) via a new RBAC data migration — a considered fix, not a known-simplification deferral, since Marcus's persona needs to reach `release.create` without being `org_admin`. `TestCycle.release_id` is already a non-nullable FK (migrated); this story makes the relationship *queryable*, not creatable — `TestCycle` creation itself is FR-PLAN-3's scope. `GET /releases/{id}/test-cycles` returns every `TestCycle` targeting the release with its `TestExecution`s nested per cycle, gated on all three of `release.read`/`test_cycle.read`/`test_execution.read` (not `release.read` alone). Release listing sorts by `target_date` with `NULLS LAST` pinned explicitly in both directions. See [ADR-0019](../adr/0019-release-creation-flow.md).

**FR-PROJ-3 (2026-09-07) wires an already-shipped route to the UI for the first time — no new backend surface.** `DELETE /projects/{id}` has existed since ADR-0022's generic factory (`_PROJECT_FACTORY_CONFIG`, `methods={"list","delete"}`); no story had called it from any frontend screen until now. `project.delete` is already seeded (full-CRUD RBAC resource, `org_admin`'s bundle already grants it) — no RBAC migration needed. Edit replaces the old click-to-edit-in-place `standards_profile` field with a modal editing `name`+`standards_profile` together, reusing `PATCH /projects/{id}` (unchanged). Search/sort/pagination are all client-side over `listProjects()`'s already-fully-fetched result — no `?q=`/`sort=`/page-size query param added to the backend (the generic factory has zero `order_by` support today; adding one is out of this story's scope, see NFR-50). See [ADR-0039](../adr/0039-dash-2-org-home-dashboard-relabel-and-project-table.md).

**FR-PROJ-4 (2026-09-09) is a placement/navigation change only — the table it moves is byte-for-byte the code FR-PROJ-3 already shipped.** `ProjectsPage.tsx` is `OrgHome.tsx`'s Project-CRUD block extracted verbatim (same `data-testid`s, same Zod schemas, same API calls), mounted at a new route reached via a new sidebar nav item (`AppSidebar.tsx`'s single nav-item-list extension point, ADR-0018 AC5). `OrgHome`/"Dashboard" keeps only the two stat widgets and `RoleAssignmentsPanel`; its Project-count widget becomes a link to the new page. No backend route, permission, or schema change of any kind. See [ADR-0047](../adr/0047-proj-4-projects-page-sidebar-entry.md).

### 2.4 Requirement & test case authoring — [requirement-testcase-authoring-stories.md](../user-stories/2026-09-03-requirement-testcase-authoring-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-REQ-1 | Capture a Requirement (title, description, source, external_ref) | Must | Requirement |
| FR-REQ-2 | Author a TestCase directly from a Requirement (lightweight path) | Must | TestCase, RequirementTestCaseLink |
| FR-REQ-3 | Author a TestCase via optional TestCondition (rigor path) | Must | TestCondition, RequirementTestConditionLink, TestConditionTestCaseLink |
| FR-REQ-4 | Organize TestCases into TestSuites (many-to-many) | Must | TestSuite, TestSuiteTestCase |

FR-REQ-1 ships almost entirely via API-1/ADMIN-2's generic CRUD factory — `Requirement` was already one of the 20 factory-served entities before this story, so `POST`/`GET /requirements` (create, list/search, project-scoping, permission gating, 404-vs-403 boundary) required no new route code. The one real gap this story closes: `Requirement.title`, specified by this FR and by TC-REQ-001/002 since 2026-09-03, was never actually added to the schema — a plain oversight caught during this story's own planning, not a prior decision being revisited. See [ADR-0025](../adr/0025-requirement-title-field.md).

FR-REQ-2 is fully delivered: bespoke `POST`/`GET /requirements/{id}/test-cases` (atomic `TestCase` + `RequirementTestCaseLink` create, requirement-scoped list — `TestCase.create`/`list` were deliberately never registered via the generic factory, see [API Document §3](../api/2026-09-03-api-design.md#3-generic-crud-routes-router-factory-adr-0022)'s `TestCase` footnote), `TestStep` authoring via the existing generic-factory `TestStep` CRUD (already scoped by `test_case_id`, no new route needed). One real implementation gap was caught and closed during this story, not carried over from a prior decision: the shared `TestCase` org-resolver (ADR-0022) had no path at all for a direct-link `TestCase` (`test_condition_id IS NULL`, no `TestSuite` membership) — exactly REQ-2's own shape — so a freshly created one would `404` as "orphaned" on its very next `GET`/`PATCH`/`DELETE`. See [ADR-0029](../adr/0029-testcase-resolver-direct-link-fallback.md). UI: delivered as an expansion of the existing `ProjectDetail.tsx` screen (Requirement rows expand to a TestCase list + "New Test Case" modal, TestCase entries expand to a TestStep list + add/inline-edit), coexisting with FR-REQ-3's own TestCondition-section expansion of the same screen (below) rather than a dedicated `RequirementDetail` route (the Sitemap's stale reservation).

FR-REQ-3 ships as two new bespoke, atomic create+link routes — `POST /requirements/{id}/test-conditions` (creates `TestCondition` + `RequirementTestConditionLink`) and `POST /test-conditions/{id}/test-cases` (creates `TestCase` with `test_condition_id` set + `TestConditionTestCaseLink`) — plus a restriction: the generic factory's existing `POST /test-conditions` (ADR-0022) never wrote the link table, so it's removed in favor of the bespoke route (`TestCondition` now shares `TestCase`'s existing generic-create exclusion). `test_manager`'s seeded RBAC bundle is extended with `test_condition.create`/`.update`/`.delete` and `test_case.create`/`.update`/`.delete` (it already held `.read` on both) via a new data migration — Marcus's own persona needs to reach both new routes without also holding `tester`/`org_admin`, the same class of gap ADR-0019 closed once already for `test_manager`/`release.*`. See [ADR-0028](../adr/0028-req3-test-condition-rigor-path-bespoke-routes.md). FR-REQ-2's own direct-link route (`POST /requirements/{id}/test-cases`) is a separate, independently-delivered story (above) — both coexist per-TestCase within a project (ADR-0006).

FR-REQ-4's `TestSuite` entity itself (name, purpose, project-scoped) needed no new work — it was already one of ADR-0022's factory-served entities, full CRUD. The real gap this story closes is the many-to-many membership side: three new bespoke routes, `POST`/`DELETE /test-suites/{id}/test-cases/{case_id}` (join row add/remove, `test_suite.update`) and a new `GET /test-suites/{id}/test-cases` (live membership list, `test_suite.read` — not in the original API Document, added by this story since AC2's "reflects current membership" claim has nothing to call without it). Two decisions close the edge cases the schema alone doesn't resolve: adding a `TestCase` whose own resolved project differs from the `TestSuite`'s project (same org, different project) is rejected (`422`) rather than allowed, and adding a `TestCase` already a member of that suite is `409` (idempotency conflict, mirroring `org_memberships.py`'s `membership_already_exists` precedent), not `422`. No `test_manager`/`tester` RBAC bundle change needed — both already hold `test_suite.read`/`.update` from RBAC-4's original seed. See [ADR-0030](../adr/0030-req4-test-suite-membership-bespoke-routes.md).

### 2.5 Test planning — [test-planning-stories.md](../user-stories/2026-09-03-test-planning-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-PLAN-1 | Create a TestPlan (identifier/scope/approach/staffing/schedule) | Must | TestPlan |
| FR-PLAN-2 | Define entry/exit/suspension/resumption criteria | Must | EntryExitCriteria |
| FR-PLAN-3 | Run a TestCycle under a TestPlan, targeted at a Release, in an Environment | Must | TestCycle, Environment |

FR-PLAN-1's `TestPlan` entity itself (identifier/scope/approach/staffing_and_training/schedule, project-scoped, `status` defaulting to `draft`) needed no new work — it was already one of ADR-0022's factory-served entities, full CRUD, satisfying AC1 as-is. The real gaps this story closes: the many-to-many scope side, `TestPlanTestSuite`, had no route at all (three new bespoke routes, `POST`/`DELETE /test-plans/{id}/test-suites/{suite_id}` and a live-list `GET`, `test_plan.update`/`.read`), plus a new coverage query, `GET /test-plans/{id}/test-cases` (`test_plan.read`), answering AC2's literal "which TestCases does executing this plan cover" claim by resolving the two-hop `TestPlan`→`TestSuite`→`TestCase` chain and deduplicating. A third gap: the generic factory's `PATCH /test-plans/{id}` accepted any `status` value in any order with no legality check at all — a `status`-transition guard is added to that same route (`draft→approved`, `approved→superseded` only, else `409 invalid_status_transition`), closing AC3's "draft → approved → superseded" claim without waiting on GOV-1's own separate, human-only `/approve` route to exist. Two decisions close the edge cases the schema alone doesn't resolve, both mirroring FR-REQ-4's own precedent: including a `TestSuite` whose `project_id` differs from the `TestPlan`'s (same org, different project) is rejected (`422`), and including a `TestSuite` already in the plan is `409` (`already_included_in_plan`, distinct from `TestSuiteTestCase`'s own `already_in_suite`). No `test_manager` RBAC bundle change needed — it already holds `test_plan.*`/`test_suite.*` from RBAC-4's original seed. See [ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md).

FR-PLAN-2's `EntryExitCriteria` entity itself needed **zero new backend route code at all** — unlike FR-PLAN-1's `TestPlan`, it was already a fully factory-served entity (`POST`/`GET`/`PATCH`/`DELETE /entry-exit-criteria`, one-hop resolver, already correct) since ADMIN-2, with no gap of the resolver-completeness class ADR-0029/ADR-0030 found elsewhere. The two real gaps this story closes are both surface/visibility, not plumbing: (1) AC1's literal "listed against that plan" has nowhere to be exercised from a `TestPlan`'s own screen — `TestPlanDetail.tsx` (ADR-0031) explicitly reserved this as a non-goal, so a new full-CRUD "Entry/Exit Criteria" section (add/edit/delete, all 4 types) is added there, reusing the existing generic-CRUD config/routes verbatim, filtered by `?test_plan_id=`; (2) AC2's "visible alongside execution progress... one view" claim has no route to back it — `GET /releases/{id}/test-cycles` (PROJ-2/ADR-0019) already nests each `TestCycle`'s `TestExecution`s but nothing from `EntryExitCriteria`, so that response gains a new `exit_criteria` field per cycle (`type = exit` rows only, matching AC2's literal wording — entry/suspension/resumption stay scoped to `TestPlanDetail`'s own section), surfaced in `ProjectDetail.tsx`'s existing Release→TestCycle expand view (the one place execution progress is visible today; no dedicated `TestCycle` page exists yet, that's PLAN-3's scope). The route's existing triple-permission gate (NFR-26) extends to a quadruple, `entry_exit_criteria.read` added — no RBAC bundle migration needed, every role that can reach the route today (`test_manager`, `org_admin`, `auditor`) already holds it. See [ADR-0032](../adr/0032-plan2-entry-exit-criteria-visibility.md).

FR-PLAN-3 ships as two new bespoke routes, closing the last gap `_TEST_CYCLE_CONFIG`'s own module docstring had reserved since ADMIN-2: `POST /test-plans/{id}/test-cycles` (`test_cycle.create`, AC1 — creates `TestCycle` linked to the path `TestPlan`, a body-supplied `release_id`, and a body-supplied `environment_id`, rejecting `422` if either resolved `Release`/`Environment` belongs to a different project than the plan's, same cross-project posture ADR-0030/ADR-0031 established) and `POST /test-cycles/{id}/executions` (`test_execution.create`, AC3 — rejects `422` if the body's `test_case_id` isn't a member of any `TestSuite` included in the cycle's parent `TestPlan`, reusing PLAN-1's own two-hop coverage-query join as an `EXISTS` check rather than a new query shape). This second route is also FR-EXEC-1 AC1's own create path — FR-EXEC-1's acceptance criteria explicitly assumes PLAN-3's scope gate as a precondition ("a TestCase that's in scope for an active TestCycle, **per PLAN-3**"), and both the API Document and MCP tool table already fixed this as one shared route before either story was implemented, so this ADR builds the gated create in full rather than only a helper with no caller. `Environment`'s own entity CRUD needed no new backend work (already full generic CRUD via ADMIN-2, satisfying AC2's "admin screen" half); AC2's "create one inline while setting up a TestCycle" half is a frontend-only sequential-calls flow (`POST /environments` then the new `POST /test-plans/{id}/test-cycles` call), not a new atomic route — no link table is involved for a plain FK the way REQ-3's atomic create+link routes needed. The generic factory's existing `POST /test-executions` is restricted (`create` removed) in the same change, per the standing rule that a bespoke gated create must be the only reachable create path once one exists (same posture `TestCondition`/`TestCase` already have). `test_manager`'s seeded bundle is extended with `environment.create`/`.read`/`.update`/`.delete` (held none of the four before this story — AC2 names Priya's own `environment.create` permission directly) and `test_execution.create`/`.read` (minimum to reach both new routes as its own persona; `.update`/`.delete` deliberately withheld, left for EXEC-1/EXEC-3 to decide) via a new RBAC data migration, the fourth such extension for this role. See [ADR-0033](../adr/0033-plan3-test-cycle-creation-and-execution-scope-check.md).

### 2.6 Test execution & defects — [test-execution-defect-stories.md](../user-stories/2026-09-03-test-execution-defect-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-EXEC-1 | Record a TestExecution result (pass/fail/blocked/skipped) | Must | TestExecution |
| FR-EXEC-2 | Append-only TestLog for every status change/comment/agent action | Must | TestLog |
| FR-EXEC-3 | Raise a Defect from a failed TestExecution | Must | Defect, TestCaseDefectLink |

FR-EXEC-1 closes on top of a create path ADR-0033 (PLAN-3) already built ahead of this story being separately scoped — `POST /test-cycles/{id}/executions` already inserts a `TestExecution` with `executed_by_actor_id`/`executed_at` stamped server-side, gated `test_execution.create`, and (being a plain insert with no upsert) already satisfies AC3's "re-run creates a new row" literally. What this story adds: the bespoke `TestCycleDetail` frontend screen that's the first thing to actually call that route (no UI called it before this pass), AC2's live pass/fail/blocked/skipped dashboard — built by reusing the existing generic-CRUD list route's own `total` field across four `result`-filtered calls, the same "no new route, no manually maintained summary" posture FR-SHELL-3/NFR-27 already established, not a new aggregate endpoint — and the test-case picker on that screen scoped to PLAN-1's own `GET /test-plans/{id}/test-cases` coverage query so a QA lead is only ever offered `TestCase`s the backend's own scope-check would accept. No schema or RBAC change. FR-EXEC-3 (raise a `Defect`) was unbuilt as of this pass — see below, now closed by ADR-0044. See [ADR-0034](../adr/0034-exec-1-test-execution-recording-dashboard.md).

FR-EXEC-2 closes on top of `TestLog`'s own table/read-routes, built ahead of time by ADR-0027 — this story is what actually *writes* to it. A new generic `post_update_hook` on `CrudEntityConfig` appends a `status_change` `TestLog` row whenever a `PATCH /test-executions/{id}` actually changes `result` (AC1's "corrected from pass to fail" example), and the create route (`POST /test-cycles/{id}/executions`) now appends the same kind of row for the initial recording too, so the timeline has no gap before its first entry. Two new bespoke routes close the rest: `POST /executions/{id}/comments` (AC1's comment/attachment triggers — no new `Comment` entity, just another `TestLog` row; supplying an optional `attachment_url`/`file_name` logs it as `attachment` instead of `comment`, same "plain reference, no live integration" posture EXEC-3's `Defect.external_ref` already established) and `GET /executions/{id}/logs` (AC3's ordered timeline read, oldest first). An `AIAgent`-originated action of any of the above kinds logs as `event_type=agent_action` rather than the human-triggered type, satisfying AC1's third trigger with no new MCP surface (no MCP tool touches `TestExecution` yet). AC2 (immutability) was already structurally true since ADR-0025/ADR-0027 (no `create`/`update`/`delete` route ever registered for `TestLog`) and is now genuinely exercised — a real log exists to be immutable. No schema change (`TestLog`'s table/index already anticipated this); no RBAC change (both new routes reuse permission codes every relevant role already holds). One accepted, documented consequence: a `TestExecution` with any log entry can no longer be deleted through the still-existing generic `DELETE` route (`TestLog.test_execution_id` is `RESTRICT`) — the correct behavior for an audit-grade log, not a regression. See [ADR-0038](../adr/0038-exec-2-append-only-test-log.md).

FR-EXEC-3 closes on models/read-routes ADR-0027 already built ahead of time — `Defect` (full `GET`/`PATCH`/`DELETE`, `create` deliberately reserved from the start) and `TestCaseDefectLink` (`list`/`get` only, no row ever written to it). This story adds the reserved atomic create: `POST /executions/{id}/defects` (`defect.create`) inserts `Defect` (`reported_by_actor_id` stamped server-side) and `TestCaseDefectLink` (derived from the execution's own `test_case_id`) in one transaction, rejecting (`422`, business-rule, never `404`) a target `TestExecution` whose `result != fail` — AC1's own literal precondition. AC2 (`external_ref` plain text/URL, no live integration) needed no new mechanism — the column has been a nullable `varchar` since ADR-0027. AC3 ("all Defects ever raised... most recent first") is answered by a new bespoke `GET /test-cases/{id}/defects`, not the existing generic link-list (which has no ordering guarantee) — not in this story's original API Document scope, added here the same way ADR-0030/ADR-0031 each added a nested read mid-story once a real UI need surfaced. `test_manager`'s seeded bundle gains `defect.create` (held only `.read` before; `.update`/`.delete` deliberately withheld, same restraint ADR-0033 already took for `test_execution.*`), and both `test_manager` and `tester` gain `test_case_defect_link.read` (neither held it; needed to reach AC3's new view) via a new RBAC data migration — the fifth such ad hoc extension for `test_manager`. FR-ADMIN-2 ships as one router factory (`make_crud_router()`, called once per entity — composition, not a base-class hierarchy) applied to all 20 entities the API Document §3 lists, in one pass rather than accreted per-story ([ADR-0022](../adr/0022-generic-crud-router-factory.md), which PROJ-1/PROJ-2 both explicitly deferred building at 1–2-entity scale). Three problems past bespoke-route stories didn't have to solve generalize here: (1) tenant-resolution depth varies per entity — direct column, one FK hop, a branching two-nullable-FK case (`RiskItem`), a nullable-hop case (`TestCase`, ADR-0006), and no tenant at all for 4 global catalogs; (2) `require_permission`'s path-param read doesn't fit the factory's flat item-route shape (no `org_id`/`project_id` path segment), so item routes call `has_permission` directly instead, row-resolved, same posture `Project`'s/`Release`'s own bespoke item routes already established; (3) list/create routes require the immediate scope FK as an explicit query param/body field rather than inferring it, since there's no row yet to resolve from. List routes support both exact-match column filters and an opt-in `?q=` free-text search across a per-entity configured column set — this revises §1's original "no free-text operator" line in the API Document. `DELETE` distinguishes a RESTRICT-blocked FK (`409`) from a validation failure (`422`). `Project`'s/`Release`'s/`Organization`'s existing bespoke routes are untouched; the factory only registers whichever of the 5 methods aren't already bespoke-served for a given entity (e.g. only `DELETE` for `Project`).

**Completion pass ([ADR-0027](../adr/0027-generic-admin-crud-ui-and-backend-completion.md), 2026-09-05):** the above covers the backend factory only — the frontend half of FR-ADMIN-2's own ACs (config-driven list/form rendering, field-type-appropriate inputs, permission-aware hide/disable) was still unbuilt (`entityConfigs/`, `components/crud/`, `pages/admin/` were structural placeholders). This pass adds: (a) the frontend generic CRUD surface itself — entity registry + one field-config per entity, generic `EntityTable`/`EntityForm`/`FkAutocomplete` components, a scope-selector step for `RiskItem`/`Attachment`'s branching/deep-chain scope, and a `usePermissions` hook backed by a new `GET /orgs/{org_id}/permissions/mine` endpoint so action buttons hide/disable *before* an attempt (closing a real gap — no prior endpoint exposed the caller's own resolved permission codes); (b) backend completion for 3 entities that had zero routes at all — `TestExecution` (full CRUD, was simply unwired), `TestLog` (read-only, immutable), and the 4 traceability link tables (read-only) — using the same `make_crud_router()`/resolver-chain primitives ADR-0022 already built, no new backend architecture. Final scope: **28 admin-surface pages, every ERD entity except 4 structural exclusions** — every entity with a plain-field-CRUD-shaped route, including ones that already have a bespoke screen (`Organization`, `Project`, `OrgMembership`, `Release`, since their routes are already plain-CRUD-shaped). `Approval`, `User`, `AIAgent`, `AuthIdentity` are excluded structurally, not as a scope-trim: none of the four have a "set some fields and save" write path — `Approval`'s only write is the bespoke `test_plan.approve` action, `User` creation hashes a password and (for invites) sends email, `AIAgent` creation mints a one-time-displayed API key, and `AuthIdentity` is only ever created as a side effect of signup/invite-accept with an invariant (exactly one primary identity per user) a generic form can't preserve — forcing any of them through a generic form would require entity-specific logic, defeating AC1.
