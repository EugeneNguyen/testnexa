## 1. Purpose & scope

This document consolidates functional (FR) and non-functional (NFR) requirements for the scaffold: a full-stack ISTQB/IEEE829-aligned test management tool implementing the complete [07 ERD](../product-discovery/07-erd-draft.md) (28 entities), multi-tenant RBAC, JWT auth for human and AI-agent actors, and a first-party MCP server. Scope boundaries and the deliberate deviation from the validated MVP are recorded in [ADR-0001](../adr/0001-full-erd-scope-over-validated-mvp.md).

**Out of scope** (unchanged from the design spec): IEEE 829/29119-3 document-format export (RTM export is CSV only), SSO/OIDC/SAML/LDAP providers, AI test-case generation, billing/usage metering.

## 2. Functional requirements

Each FR ID maps 1:1 to the acceptance criteria already ratified in `docs/user-stories/`; this section is the canonical index, not a restatement — see the linked story for full Given/When/Then criteria. Priority: **Must** (blocks scaffold completion), **Should** (build now, lower polish priority), **Could** (exploratory, structural-only).

### 2.2 Multi-tenancy & RBAC — [rbac-tenancy-stories.md](../user-stories/2026-09-03-rbac-tenancy-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-RBAC-1 | Create an Organization; first-ever signup auto-creates org + org_admin; an existing org_admin can create further, fully isolated orgs | Must | Organization, OrgMembership, RoleAssignment |
| FR-RBAC-2 | Invite/suspend/reactivate org members | Must | OrgMembership |
| FR-RBAC-3 | Assign roles org-wide or project-scoped | Must | RoleAssignment |
| FR-RBAC-4 | Seeded system roles (org_admin, test_manager, tester, auditor, ai_agent_scoped) | Must | Role, Permission, RolePermission |
| FR-RBAC-5 | Structural human-only Approval enforcement (double-enforced) | Must | Permission, RoleAssignment |

FR-RBAC-1 ships as two routes, not one: `POST /auth/signup` (public, bootstrap-only — closes once any `Organization` exists deployment-wide) and `POST /orgs` (authenticated, for an existing org_admin minting a second org). Both assign the caller RBAC-4's already-seeded `org_admin` system `Role` in the org just created, rather than creating a per-org copy. `POST /orgs` needs a permission check with no target `org_id` to scope by (the org doesn't exist yet) — a bespoke any-org gate (`has_permission_in_any_org`), not FR-AUTH-4's path-scoped `require_permission` reused as-is. See [ADR-0016](../adr/0016-organization-bootstrap-creation-flow.md).

FR-RBAC-3 ships as `POST`/`GET /orgs/{org_id}/role-assignments` (bespoke, org-path-scoped, same `require_permission`/404-vs-403 boundary as every other org-scoped route). Creating a grant for a `User` actor requires that user already hold an `OrgMembership` (any status) in `org_id`; a `role_id`/`project_id` that doesn't resolve within the caller's own org → `422`, never `404` (no target-org existence to hide, since the caller already proved membership). This story also fixes a gap FR-AUTH-4/FR-PROJ-1 left open: `GET`/`PATCH /projects/{id}` (PROJ-1) now pass `project_id` into `has_permission`, so a project-scoped grant — including a project's own creator's auto-assigned `test_manager` role — actually works within that project, not just an org-wide grant. See [ADR-0021](../adr/0021-role-assignment-creation-flow.md). A follow-up addendum adds a UI slice — `GET /orgs/{org_id}/roles` (role dropdown data source) and a "Role Assignments" panel on `OrgHome` — not part of the original API-only scope, added on explicit CTO direction after the story's initial acceptance (ADR-0021's addendum).

### 2.4 Requirement & test case authoring — [requirement-testcase-authoring-stories.md](../user-stories/2026-09-03-requirement-testcase-authoring-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-REQ-1 | Capture a Requirement (title, description, source, external_ref) | Must | Requirement |
| FR-REQ-2 | Author a TestCase directly from a Requirement (lightweight path) | Must | TestCase, RequirementTestCaseLink |
| FR-REQ-3 | Author a TestCase via optional TestCondition (rigor path) | Must | TestCondition, RequirementTestConditionLink, TestConditionTestCaseLink |
| FR-REQ-4 | Organize TestCases into TestSuites (many-to-many) | Must | TestSuite, TestSuiteTestCase |
| FR-REQ-5 | Author a standalone TestCase with no Requirement or TestCondition, and optionally link it to a Requirement later | Should | TestCase, RequirementTestCaseLink |

FR-REQ-1 ships almost entirely via API-1/ADMIN-2's generic CRUD factory — `Requirement` was already one of the 20 factory-served entities before this story, so `POST`/`GET /requirements` (create, list/search, project-scoping, permission gating, 404-vs-403 boundary) required no new route code. The one real gap this story closes: `Requirement.title`, specified by this FR and by TC-REQ-001/002 since 2026-09-03, was never actually added to the schema — a plain oversight caught during this story's own planning, not a prior decision being revisited. See [ADR-0025](../adr/0025-requirement-title-field.md).

FR-REQ-2 is fully delivered: bespoke `POST`/`GET /requirements/{id}/test-cases` (atomic `TestCase` + `RequirementTestCaseLink` create, requirement-scoped list — `TestCase.create`/`list` were deliberately never registered via the generic factory, see [API Document §3](../api/2026-09-03-api-design.md#3-generic-crud-routes-router-factory-adr-0022)'s `TestCase` footnote), `TestStep` authoring via the existing generic-factory `TestStep` CRUD (already scoped by `test_case_id`, no new route needed). One real implementation gap was caught and closed during this story, not carried over from a prior decision: the shared `TestCase` org-resolver (ADR-0022) had no path at all for a direct-link `TestCase` (`test_condition_id IS NULL`, no `TestSuite` membership) — exactly REQ-2's own shape — so a freshly created one would `404` as "orphaned" on its very next `GET`/`PATCH`/`DELETE`. See [ADR-0029](../adr/0029-testcase-resolver-direct-link-fallback.md). UI: delivered as an expansion of the existing `ProjectDetail.tsx` screen (Requirement rows expand to a TestCase list + "New Test Case" modal, TestCase entries expand to a TestStep list + add/inline-edit), coexisting with FR-REQ-3's own TestCondition-section expansion of the same screen (below) rather than a dedicated `RequirementDetail` route (the Sitemap's stale reservation).

FR-REQ-3 ships as two new bespoke, atomic create+link routes — `POST /requirements/{id}/test-conditions` (creates `TestCondition` + `RequirementTestConditionLink`) and `POST /test-conditions/{id}/test-cases` (creates `TestCase` with `test_condition_id` set + `TestConditionTestCaseLink`) — plus a restriction: the generic factory's existing `POST /test-conditions` (ADR-0022) never wrote the link table, so it's removed in favor of the bespoke route (`TestCondition` now shares `TestCase`'s existing generic-create exclusion). `test_manager`'s seeded RBAC bundle is extended with `test_condition.create`/`.update`/`.delete` and `test_case.create`/`.update`/`.delete` (it already held `.read` on both) via a new data migration — Marcus's own persona needs to reach both new routes without also holding `tester`/`org_admin`, the same class of gap ADR-0019 closed once already for `test_manager`/`release.*`. See [ADR-0028](../adr/0028-req3-test-condition-rigor-path-bespoke-routes.md). FR-REQ-2's own direct-link route (`POST /requirements/{id}/test-cases`) is a separate, independently-delivered story (above) — both coexist per-TestCase within a project (ADR-0006).

FR-REQ-4's `TestSuite` entity itself (name, purpose, project-scoped) needed no new work — it was already one of ADR-0022's factory-served entities, full CRUD. The real gap this story closes is the many-to-many membership side: three new bespoke routes, `POST`/`DELETE /test-suites/{id}/test-cases/{case_id}` (join row add/remove, `test_suite.update`) and a new `GET /test-suites/{id}/test-cases` (live membership list, `test_suite.read` — not in the original API Document, added by this story since AC2's "reflects current membership" claim has nothing to call without it). Two decisions close the edge cases the schema alone doesn't resolve: adding a `TestCase` whose own resolved project differs from the `TestSuite`'s project (same org, different project) is rejected (`422`) rather than allowed, and adding a `TestCase` already a member of that suite is `409` (idempotency conflict, mirroring `org_memberships.py`'s `membership_already_exists` precedent), not `422`. No `test_manager`/`tester` RBAC bundle change needed — both already hold `test_suite.read`/`.update` from RBAC-4's original seed. See [ADR-0030](../adr/0030-req4-test-suite-membership-bespoke-routes.md).

FR-REQ-5 gives `TestCase` a fourth column, a nullable `project_id`, and unrestricts the generic CRUD factory (ADR-0022) for exactly that shape: `_TEST_CASE_CONFIG` gains `list`+`create`, scoped by `project_id` the same way `TestSuite` already is — a standalone case writes no link-table row, so there is nothing the factory's plain insert can get wrong the way `TestCondition`'s own briefly-broken generic `create` did (ADR-0028). The project-mode sidebar's pre-existing "Test cases" nav item (ADR-0051) was reachable but non-functional until this story — it starts working with no frontend route change. A new bespoke retrofit route, `POST /test-cases/{id}/link-requirement`, lets a standalone case gain a `RequirementTestCaseLink` after the fact (same table REQ-2's own create route writes, just decoupled from creation time) — rejecting a cross-project target (`422`), an already-linked case (`409`), or a caller with no membership in the resolved org (`404`). No unlink route, no retrofit-to-`TestCondition` — both explicitly out of this story's scope. See [ADR-0069](../adr/0069-req-5-standalone-test-case-with-optional-requirement-link.md).

### 2.5 Test planning — [test-planning-stories.md](../user-stories/2026-09-03-test-planning-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-PLAN-1 | Create a TestPlan (identifier/scope/approach/staffing/schedule) | Must | TestPlan |
| FR-PLAN-2 | Define entry/exit/suspension/resumption criteria | Must | EntryExitCriteria |
| FR-PLAN-3 | Run a TestCycle under a TestPlan, targeted at a Release, in an Environment | Must | TestCycle, Environment |

FR-PLAN-1's `TestPlan` entity itself (identifier/scope/approach/staffing_and_training/schedule, project-scoped, `status` defaulting to `draft`) needed no new work — it was already one of ADR-0022's factory-served entities, full CRUD, satisfying AC1 as-is. The real gaps this story closes: the many-to-many scope side, `TestPlanTestSuite`, had no route at all (three new bespoke routes, `POST`/`DELETE /test-plans/{id}/test-suites/{suite_id}` and a live-list `GET`, `test_plan.update`/`.read`), plus a new coverage query, `GET /test-plans/{id}/test-cases` (`test_plan.read`), answering AC2's literal "which TestCases does executing this plan cover" claim by resolving the two-hop `TestPlan`→`TestSuite`→`TestCase` chain and deduplicating. A third gap: the generic factory's `PATCH /test-plans/{id}` accepted any `status` value in any order with no legality check at all — a `status`-transition guard is added to that same route (`draft→approved`, `approved→superseded` only, else `409 invalid_status_transition`), closing AC3's "draft → approved → superseded" claim without waiting on GOV-1's own separate, human-only `/approve` route to exist. Two decisions close the edge cases the schema alone doesn't resolve, both mirroring FR-REQ-4's own precedent: including a `TestSuite` whose `project_id` differs from the `TestPlan`'s (same org, different project) is rejected (`422`), and including a `TestSuite` already in the plan is `409` (`already_included_in_plan`, distinct from `TestSuiteTestCase`'s own `already_in_suite`). No `test_manager` RBAC bundle change needed — it already holds `test_plan.*`/`test_suite.*` from RBAC-4's original seed. See [ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md).

FR-PLAN-2's `EntryExitCriteria` entity itself needed **zero new backend route code at all** — unlike FR-PLAN-1's `TestPlan`, it was already a fully factory-served entity (`POST`/`GET`/`PATCH`/`DELETE /entry-exit-criteria`, one-hop resolver, already correct) since ADMIN-2, with no gap of the resolver-completeness class ADR-0029/ADR-0030 found elsewhere. The two real gaps this story closes are both surface/visibility, not plumbing: (1) AC1's literal "listed against that plan" has nowhere to be exercised from a `TestPlan`'s own screen — `TestPlanDetail.tsx` (ADR-0031) explicitly reserved this as a non-goal, so a new full-CRUD "Entry/Exit Criteria" section (add/edit/delete, all 4 types) is added there, reusing the existing generic-CRUD config/routes verbatim, filtered by `?test_plan_id=`; (2) AC2's "visible alongside execution progress... one view" claim has no route to back it — `GET /releases/{id}/test-cycles` (PROJ-2/ADR-0019) already nests each `TestCycle`'s `TestExecution`s but nothing from `EntryExitCriteria`, so that response gains a new `exit_criteria` field per cycle (`type = exit` rows only, matching AC2's literal wording — entry/suspension/resumption stay scoped to `TestPlanDetail`'s own section), surfaced in `ProjectDetail.tsx`'s existing Release→TestCycle expand view (the one place execution progress is visible today; no dedicated `TestCycle` page exists yet, that's PLAN-3's scope). The route's existing triple-permission gate (NFR-26) extends to a quadruple, `entry_exit_criteria.read` added — no RBAC bundle migration needed, every role that can reach the route today (`test_manager`, `org_admin`, `auditor`) already holds it. See [ADR-0032](../adr/0032-plan2-entry-exit-criteria-visibility.md).

FR-PLAN-3 ships as two new bespoke routes, closing the last gap `_TEST_CYCLE_CONFIG`'s own module docstring had reserved since ADMIN-2: `POST /test-plans/{id}/test-cycles` (`test_cycle.create`, AC1 — creates `TestCycle` linked to the path `TestPlan`, a body-supplied `release_id`, and a body-supplied `environment_id`, rejecting `422` if either resolved `Release`/`Environment` belongs to a different project than the plan's, same cross-project posture ADR-0030/ADR-0031 established) and `POST /test-cycles/{id}/executions` (`test_execution.create`, AC3 — rejects `422` if the body's `test_case_id` isn't a member of any `TestSuite` included in the cycle's parent `TestPlan`, reusing PLAN-1's own two-hop coverage-query join as an `EXISTS` check rather than a new query shape). This second route is also FR-EXEC-1 AC1's own create path — FR-EXEC-1's acceptance criteria explicitly assumes PLAN-3's scope gate as a precondition ("a TestCase that's in scope for an active TestCycle, **per PLAN-3**"), and both the API Document and MCP tool table already fixed this as one shared route before either story was implemented, so this ADR builds the gated create in full rather than only a helper with no caller. `Environment`'s own entity CRUD needed no new backend work (already full generic CRUD via ADMIN-2, satisfying AC2's "admin screen" half); AC2's "create one inline while setting up a TestCycle" half is a frontend-only sequential-calls flow (`POST /environments` then the new `POST /test-plans/{id}/test-cycles` call), not a new atomic route — no link table is involved for a plain FK the way REQ-3's atomic create+link routes needed. The generic factory's existing `POST /test-executions` is restricted (`create` removed) in the same change, per the standing rule that a bespoke gated create must be the only reachable create path once one exists (same posture `TestCondition`/`TestCase` already have). `test_manager`'s seeded bundle is extended with `environment.create`/`.read`/`.update`/`.delete` (held none of the four before this story — AC2 names Priya's own `environment.create` permission directly) and `test_execution.create`/`.read` (minimum to reach both new routes as its own persona; `.update`/`.delete` deliberately withheld, left for EXEC-1/EXEC-3 to decide) via a new RBAC data migration, the fourth such extension for this role. See [ADR-0033](../adr/0033-plan3-test-cycle-creation-and-execution-scope-check.md).

### 2.6 Test execution & defects — [test-execution-defect-stories.md](../user-stories/2026-09-03-test-execution-defect-stories.md)

| ID | Title | Priority | Entities |
|---|---|---|---|
| FR-EXEC-1 | Record a TestExecution result (pass/fail/blocked/skipped) | Must | TestExecution |
| FR-EXEC-2 | Append-only TestLog for every status change/comment/agent action | Must | TestLog |
| FR-EXEC-3 | Raise a Defect from a failed TestExecution | Must | Defect, TestCaseDefectLink |

FR-EXEC-1 closes on top of a create path ADR-0033 (PLAN-3) already built ahead of this story being separately scoped — `POST /test-cycles/{id}/executions` already inserts a `TestExecution` with `executed_by_actor_id`/`executed_at` stamped server-side, gated `test_execution.create`, and (being a plain insert with no upsert) already satisfies AC3's "re-run creates a new row" literally. What this story adds: the bespoke `TestCycleDetail` frontend screen that's the first thing to actually call that route (no UI called it before this pass), AC2's live pass/fail/blocked/skipped dashboard — built by reusing the existing generic-CRUD list route's own `total` field across four `result`-filtered calls, the same "no new route, no manually maintained summary" posture FR-SHELL-3/NFR-27 already established, not a new aggregate endpoint — and the test-case picker on that screen scoped to PLAN-1's own `GET /test-plans/{id}/test-cases` coverage query so a QA lead is only ever offered `TestCase`s the backend's own scope-check would accept. No schema or RBAC change. FR-EXEC-3 (raise a `Defect`) was unbuilt as of this pass — see below, now closed by ADR-0044. See [ADR-0034](../adr/0034-exec-1-test-execution-recording-dashboard.md).

FR-EXEC-2 closes on top of `TestLog`'s own table/read-routes, built ahead of time by ADR-0027 — this story is what actually *writes* to it. A new generic `post_update_hook` on `CrudEntityConfig` appends a `status_change` `TestLog` row whenever a `PATCH /test-executions/{id}` actually changes `result` (AC1's "corrected from pass to fail" example), and the create route (`POST /test-cycles/{id}/executions`) now appends the same kind of row for the initial recording too, so the timeline has no gap before its first entry. Two new bespoke routes close the rest: `POST /executions/{id}/comments` (AC1's comment/attachment triggers — no new `Comment` entity, just another `TestLog` row; supplying an optional `attachment_url`/`file_name` logs it as `attachment` instead of `comment`, same "plain reference, no live integration" posture EXEC-3's `Defect.external_ref` already established) and `GET /executions/{id}/logs` (AC3's ordered timeline read, oldest first). An `AIAgent`-originated action of any of the above kinds logs as `event_type=agent_action` rather than the human-triggered type, satisfying AC1's third trigger with no new MCP surface (no MCP tool touches `TestExecution` yet). AC2 (immutability) was already structurally true since ADR-0025/ADR-0027 (no `create`/`update`/`delete` route ever registered for `TestLog`) and is now genuinely exercised — a real log exists to be immutable. No schema change (`TestLog`'s table/index already anticipated this); no RBAC change (both new routes reuse permission codes every relevant role already holds). One accepted, documented consequence: a `TestExecution` with any log entry can no longer be deleted through the still-existing generic `DELETE` route (`TestLog.test_execution_id` is `RESTRICT`) — the correct behavior for an audit-grade log, not a regression. FR-ADMIN-2 ships as one router factory (`make_crud_router()`, called once per entity — composition, not a base-class hierarchy) applied to all 20 entities the API Document §3 lists, in one pass rather than accreted per-story ([ADR-0022](../adr/0022-generic-crud-router-factory.md), which PROJ-1/PROJ-2 both explicitly deferred building at 1–2-entity scale). Three problems past bespoke-route stories didn't have to solve generalize here: (1) tenant-resolution depth varies per entity — direct column, one FK hop, a branching two-nullable-FK case (`RiskItem`), a nullable-hop case (`TestCase`, ADR-0006), and no tenant at all for 4 global catalogs; (2) `require_permission`'s path-param read doesn't fit the factory's flat item-route shape (no `org_id`/`project_id` path segment), so item routes call `has_permission` directly instead, row-resolved, same posture `Project`'s/`Release`'s own bespoke item routes already established; (3) list/create routes require the immediate scope FK as an explicit query param/body field rather than inferring it, since there's no row yet to resolve from. List routes support both exact-match column filters and an opt-in `?q=` free-text search across a per-entity configured column set — this revises §1's original "no free-text operator" line in the API Document. `DELETE` distinguishes a RESTRICT-blocked FK (`409`) from a validation failure (`422`). `Project`'s/`Release`'s/`Organization`'s existing bespoke routes are untouched; the factory only registers whichever of the 5 methods aren't already bespoke-served for a given entity (e.g. only `DELETE` for `Project`).

**Completion pass ([ADR-0027](../adr/0027-generic-admin-crud-ui-and-backend-completion.md), 2026-09-05):** the above covers the backend factory only — the frontend half of FR-ADMIN-2's own ACs (config-driven list/form rendering, field-type-appropriate inputs, permission-aware hide/disable) was still unbuilt (`entityConfigs/`, `components/crud/`, `pages/admin/` were structural placeholders). This pass adds: (a) the frontend generic CRUD surface itself — entity registry + one field-config per entity, generic `EntityTable`/`EntityForm`/`FkAutocomplete` components, a scope-selector step for `RiskItem`/`Attachment`'s branching/deep-chain scope, and a `usePermissions` hook backed by a new `GET /orgs/{org_id}/permissions/mine` endpoint so action buttons hide/disable *before* an attempt (closing a real gap — no prior endpoint exposed the caller's own resolved permission codes); (b) backend completion for 3 entities that had zero routes at all — `TestExecution` (full CRUD, was simply unwired), `TestLog` (read-only, immutable), and the 4 traceability link tables (read-only) — using the same `make_crud_router()`/resolver-chain primitives ADR-0022 already built, no new backend architecture. Final scope: **28 admin-surface pages, every ERD entity except 4 structural exclusions** — every entity with a plain-field-CRUD-shaped route, including ones that already have a bespoke screen (`Organization`, `Project`, `OrgMembership`, `Release`, since their routes are already plain-CRUD-shaped). `Approval`, `User`, `AIAgent`, `AuthIdentity` are excluded structurally, not as a scope-trim: none of the four have a "set some fields and save" write path — `Approval`'s only write is the bespoke `test_plan.approve` action, `User` creation hashes a password and (for invites) sends email, `AIAgent` creation mints a one-time-displayed API key, and `AuthIdentity` is only ever created as a side effect of signup/invite-accept with an invariant (exactly one primary identity per user) a generic form can't preserve — forcing any of them through a generic form would require entity-specific logic, defeating AC1.

**Backend-driven field shape ([ADR-0055](../adr/0055-admin-3-backend-driven-entity-schema.md), ADMIN-3, 2026-09-09 — partially supersedes the completion pass above):** the completion pass's own delivery mechanism for "config-driven list/form rendering" was a *hand-written frontend* config per entity (`frontend/src/entityConfigs/<entity>.ts`), independent of the backend's own `CrudEntityConfig` (ADR-0022) declaring the same entity's shape — two unlinked descriptions of one entity, which drifted for real: `Requirement.title` became a required backend create field under [ADR-0025](../adr/0025-requirement-title-field.md) (2026-09-05) and `entityConfigs/requirement.ts` was never updated, so every create from the generic admin form failed `422 validation_error: title Field required` with no `title` input in the UI to fix it from — found live 2026-09-09, four days later. **The backend becomes the single source of truth for field *shape*:** a new per-entity route `GET /entities/{resource}/schema` (API Document §3) serves `fields[]` (name/label/type/required/enum values/FK ref+label field/badge colors/`showInTable`) plus `methods`/`scopeField`/`scopeSelector`/`scopeResolution`/`searchFields`/`filterFields`, and every admin list/form page fetches it instead of importing a static file. Derivation is deliberately **hybrid, not full auto-inference**: type, required-ness and enum values come mechanically from the entity's own Pydantic `create_schema`/`update_schema`/`summary_schema`, while FK target+label field, enum badge colors, label overrides and `showInTable` are declared explicitly in a new backend-side `CrudEntityConfig.field_meta`/`FieldMeta` — a bare `uuid.UUID` annotation carries no signal that it is a foreign key, let alone which entity it targets, and this codebase already has irregular cases (`RiskItem`'s branching `requirement_id`/`test_plan_id`) a naming-convention guess would mis-map. **Navigation is explicitly *not* backend-driven** — route wiring, sidebar grouping, icons and nav order stay frontend-static (they are information architecture, and don't drift the way a field list does). FR-ADMIN-2's own ACs are unchanged in substance; only where the field description lives changes.

**Column sort ([ADR-0056](../adr/0056-admin-4-generic-admin-crud-column-sort.md), ADMIN-4, 2026-09-11):** confirmed via grep before starting — the generic `list` route had zero sort support anywhere (no `order_by`/`sort` reference in `crud_factory.py` at all), so every one of the 24 generic-admin-CRUD list screens rendered rows in undocumented DB-default order. `FieldMeta.sortable` (default `true`, same auto-derive-unless-overridden posture as `show_in_table`) is served as `sortable` on every field entry `GET /entities/{resource}/schema` already returns; `?sort=<field>`/`?sort=-<field>` on the `list` route (`apply_sort`, a pure query-builder) validates against that same schema's own allow-list at router-build time — not a second hand-kept set, closing the same class of drift ADR-0055 closed for field shape, applied to sortability specifically. Click a column header to toggle unsorted→ascending→descending→unsorted; a sort change resets to page 1, same posture as a filter/search change. `Release` (the one entity with no backend `CrudEntityConfig`, ADR-0055) is not sortable this pass — its list route is 100% bespoke, never routes through `apply_sort`.

**Column preferences (COLPREF-1, [ADR-0071](../adr/0071-entity-table-column-preferences.md), 2026-09-15):** FR-ADMIN-3 above gave the generic admin list control over *row* order; FR-ADMIN-4 gives the viewer control over which *columns* render and in what order. The gap it closes is a mismatch of lifetimes, not a missing feature: `showInTable` ([ADR-0055](../adr/0055-admin-3-backend-driven-entity-schema.md)) is the backend's single, global, deploy-lifetime answer to "is this field tabular at all," and is the right place for exactly that — it is the wrong place for one person's daily "I don't read `updated_at` on this list," which is what makes several of the ~28 admin pages (ADR-0027's final scope) unreadably wide at laptop width. FR-ADMIN-4's acceptance criteria:

- **AC1** — Given any entity's generic admin list, when the viewer opens the new "Columns" control in the table's own card header, then a modal lists every field the *served* schema exposes as a table column (the `showInTable !== false` set, read from `GET /entities/{resource}/schema`, never a second independently-derived list) — a field the backend says is not a table column is never offerable here; this control narrows the served set, it never widens it.
- **AC2** — Given that modal, when the viewer unchecks a field, then exactly that column disappears from the rendered table (both its header and its cells) and every other column is unaffected.
- **AC3** — Given that modal, when the viewer moves a field with its Up/Down control, then the rendered column order changes to match; the first field's Up and the last field's Down are disabled.
- **AC4** — Given a visibility or order change, when the viewer fully reloads the page, then the change is still in effect — the preference survives a reload, not just a re-render, without any server round trip (`localStorage`, per browser; NFR-71).
- **AC5** — Given a change made on entity A's list, when the viewer opens entity B's list, then B renders at its own defaults — preferences are keyed per entity (`testnexa.column-prefs.<resource>`), never shared across entities.
- **AC6** — Given a field the surface depends on structurally — the config's `detailLinkField` when `detailPath` is set ([ADR-0060](../adr/0060-projects-page-retired-generic-surface.md): it carries the only navigation into that entity's detail workspace), or whichever field is the last one still visible — then its checkbox is disabled and checked, and it renders regardless of what any stored preference claims. A viewer can never reduce the table to an actions-only column, and can never hide their own way into the detail screen.
- **AC7** — Given any state of the stored preference, a "Reset to defaults" action is available and clears it outright, returning the table to the served schema's own column set and order.

Deliberately **not** in FR-ADMIN-4: any backend surface (no route, no schema field, no migration, no permission code — this is entirely a client-side rendering preference); server-side or cross-device persistence (a per-user preference table/route is a separate decision with its own RBAC and tenant-scoping questions, ADR-0071's Alternatives); column resizing; drag-and-drop reordering.
**Filter modal, and `filter_fields` derived from the served schema (ENTITY-FILTER-1, [ADR-0072](../adr/0072-entity-table-filter-modal.md), 2026-09-15):** exact-match filtering is the fourth list-query capability (after pagination and `?q=` search, ADR-0022, and sort, ADR-0056) and the last one without a UI. Two gaps kept it that way, and this requirement closes both. **(a) The control was missing, not the pipeline.** `EntityTable`'s module docstring still claimed it rendered "a filter row for `filterFields`" and its props still declared `filters`/`onFilterChange`, but an earlier refactor had dropped that row and left the contract behind — neither prop was destructured or rendered anywhere, while `EntityListPage` continued the whole time to own real `filters` state, key its list query on it, and pass it to `listEntities`. **(b) `filter_fields` was a per-entity opt-in only 7 of 27 registered `CrudEntityConfig`s ever took** (`attachment`, `test_case`, `risk_item`, `defect`, `test_execution`, `test_log`, `org_membership`), most naming one or two columns — so a modal built over today's tuples would have been useful on 7 entities and empty on 20. `FieldMeta` gains `filterable` (default `true`), served as `"filterable"` on every `GET /entities/{resource}/schema` field entry alongside the existing `sortable`, and the list route derives its filterable set from that same `derive_entity_schema` — the identical mechanism, for the identical stated reason, ADR-0053/ADR-0056 already chose for sort. **The rule: every served field is filterable except those whose derived type is `text`** (an unbounded free-text column, which `?q=` covers properly and exact-matching misleads on); `CrudEntityConfig.filter_fields` survives only as an optional *narrowing* override, and the 7 existing declarations are deleted as strict subsets of what the derivation yields. This is deliberately a *derivation* where [ADR-0070](../adr/0070-search-fields-audit-and-numeric-cast.md) chose a hand audit for `search_fields`: equality is type-safe on every scalar column (an un-cast `ILIKE` against an `Integer` is not — that is the constraint that forced ADR-0070 to reason column-by-column), and "is this a useful filter" has a mechanical answer where "is this searchable" did not. No new route, no new query parameter (`?<field>=<value>` is ADR-0022's, unchanged in shape), no schema/RBAC change, and **no widening of what a caller can see** — the derived fields are exactly the entity's own `summary_schema` fields, which the list route already serializes in full into every response body, composed onto a query the org/scope gate has already constrained (NFR-1 untouched). UI: one icon-only "Filter" button in the `.card-header .card-tools` row next to ADR-0071's sibling "Columns" button, opening a `FilterModal` organism; conditions are **AND-only** (the backend supports exact equality and nothing else, and its chained `.where()` calls are `AND`ed unconditionally — so no operator control is rendered at all rather than a single-option select implying a choice nobody has), **at most one condition per field** (a second on the same field compiles to `field = a AND field = b`, always empty, which reads as "no results" rather than "contradictory query" — the field picker omits any field another row claims), and value controls reuse `EntityForm`'s own per-type branch so a field is filtered through the same control it is edited through. **Filters are deliberately NOT persisted** — a divergence from ADR-0071's `localStorage` column preferences, argued on an asymmetry: a hidden column announces itself (a header is visibly missing), while a silently-filtered list just shows *fewer rows*, which reads as missing data or someone else's deletions. Filter state stays in `EntityListPage` with the other four list-query parameters, all five already declared "component state only — deliberately not persisted" (TC-DS-018); the mitigation for the invisibility risk is a live active-condition **count badge** on the Filter button, plus `btn-outline-primary` while any filter is applied.
**Read-only record detail ([ADR-0073](../adr/0073-generic-entity-detail-page.md), 2026-09-15):** FR-ADMIN-6 is new, and it closes a gap two independent filters had opened. `EntityTable` renders only fields the served schema marks `showInTable`, and `EntityForm` renders only fields the API will accept in a write payload — so a field satisfying neither was visible **nowhere in the application**. Verified live against `GET /entities/{resource}/schema` for all 28 registered entities (2026-09-15): five entities carry `showInTable: false` fields — `TestPlan` (`scope`, `approach`, `staffing_and_training`, `schedule`, `created_by_actor_id`), `TestCase` (`preconditions`, `expected_result`, `created_by_actor_id`), `TestExecution` (`actual_result`, `executed_by_actor_id`), `Defect` (`reported_by_actor_id`) and `RiskItem` (`mitigation`). `TestPlan.scope`/`approach`/`schedule` and `TestCase.preconditions`/`expected_result` are exactly the long-form content a tester most wants to read, and the only way to see any of them was to open the *edit* form — entering a mutation surface in order to perform a read. A third page component, `EntityDetailPage`, renders `config.fields` **unfiltered** on two new routes (`/orgs/:orgId/admin/:entity/:id`, `/projects/:projectId/admin/:entity/:id`), reached by clicking a row. Genericity is preserved with **no per-entity branch**: the page is driven entirely by the same fetched schema (ADR-0055) plus one `GET {path}/{id}`, so a new backend field appears on it the moment the schema serves it. Read-only by design — Back plus a permission-gated Edit, and nothing else; inline editing, related-record panels and per-entity sections are explicitly out of scope, and `TestCase`'s own Defects/Requirement sections stay on `EntityFormPage` where ADR-0044/ADR-0069 put them. **No backend, API, database or RBAC change** — the route this page reads (`GET {path}/{id}`) has existed for every entity since ADR-0022/ADR-0027.

**Relationship tabs on the record detail view ([ADR-0074](../adr/0074-entity-detail-relationship-tabs.md), 2026-09-15):** FR-ADMIN-7 is new, and it partially supersedes FR-ADMIN-6's own "related-record panels are out of scope" framing (that clause's *read-only* half still holds in full — see ADR-0074 Decision §5/Consequences). A record's fields answer only half of "what is this record?"; its related records — a `Requirement`'s test conditions and risk items, a `TestCase`'s steps, attachments and linked defects, a `TestPlan`'s cycles and entry/exit criteria — previously required navigating to that *other* entity's list page and filtering it by hand. The relationships were already fully described in the backend, twice over and reachable from neither client: one-to-many is `FieldMeta.ref_entity` read backwards, many-to-many is [ADR-0005](../adr/0005-traceability-link-dedicated-join-tables.md)'s four dedicated link tables. `GET /entities/{resource}/schema` served an entity's *own* fields, so a client could see which parents a record points **at** and had no way to discover what points **back** short of fetching all 28 schemas. ADR-0074 adds a tenth key, `relations`, **derived** by walking `ALL_ENTITY_CONFIGS` rather than hand-authored — the completeness discipline `backend/CLAUDE.md` requires of any registry spanning many entities, since a missing relationship is silently invisible rather than loudly broken. A relation is emitted **only when the generic list route can actually serve it** (the FK must be the child's own `scope_field`, because `extract_scope_value` 422s a list request not carrying exactly one scope value); the 12 inbound FKs that fail this are explicitly enumerated and **flagged as a backend list-capability gap, not worked around** — each would need its own decision about widening a list route's contract. 22 relationships across 9 entities are live. *(Both counts are ADR-0074's own delivery figures and stay accurate as the record of what shipped that day; they moved twice afterwards — 12 exclusions → 14 under ADR-0075, then → **8** under its Amendment 1, with relationships reaching **30 across 10 entities**. See the Amendment 1 paragraph below.)* **No database or RBAC change**; the only API change is the additive `relations` key on an existing route, which the MCP `describe` tool picks up for free since it shares the same derivation.

**Junction-table registry completeness ([ADR-0075](../adr/0075-junction-table-registry-completeness.md), 2026-09-15):** no new FR — this completes FR-ADMIN-7 rather than adding to it, and corrects the exhaustiveness claim in ADR-0074's own Decision §4. ADR-0074 derived the relationship graph by walking `ALL_ENTITY_CONFIGS` specifically so it could not silently omit an entity; what it did not examine is that `entity_registry._ALL_CONFIGS` is itself a hand-typed tuple. Two junction tables populated in production by their own bespoke membership routes — `test_suite_test_case` (REQ-4/[ADR-0030](../adr/0030-req4-test-suite-membership-bespoke-routes.md)) and `test_plan_test_suite` (PLAN-1/[ADR-0031](../adr/0031-plan1-test-plan-membership-and-status-transition-routes.md)) — had no `CrudEntityConfig`, so `GET /entities/test-suites/schema` returned `"relations": []` and `TestSuite`'s detail page rendered **no tab strip at all**, indistinguishable from an entity that genuinely has no relationships. ADR-0074's own completeness test could not catch it: it partitions the FKs of the same registry the derivation walks, so an unregistered model contributes to neither bucket and the partition held vacuously. Both junctions are now registered as read-only entities (`list`/`get` only, shaped verbatim on the four ADR-0005 link tables), ~~scoped on their parent side so the reverse directions join the enumerated exclusion set rather than widening two of six link tables~~ (**superseded the same day by ADR-0075 Amendment 1** — all six junctions were widened together, see the paragraph below; the clause remains the accurate record of what Decision §3 chose and why); and completeness is now asserted at the **model layer** against SQLAlchemy's `Base.metadata` (NFR-76). A full audit of all 8 junction tables left 4 deliberately unregistered with stated reasons (`test_case_test_design_technique` — the relationship has no implementation at all, so a config would ship a permanently-empty tab; `role_permission` — the RBAC grant graph, a security decision; `approval`/`invite` — bespoke, and `invite` carries a `token_hash`), and the mirror case (a registered entity's FK field missing `ref_entity`) was audited against the database's live `pg_constraint` rows and found **clean**, all 7 omissions deliberate and documented in code. **API change:** two additive read-only routes (`GET /test-suite-test-cases`, `GET /test-plan-test-suites`, each plus `/{id}`). **RBAC change:** two new read-only resources (29 -> 31, catalog 100 -> 102), granted to `org_admin`/`auditor` by their existing definitions and to `test_manager`/`tester` explicitly, backfilled by migration `7d2c91af4e68` — the first RBAC extension in this repo that has to insert the `Permission` rows themselves rather than only `role_permission` grants. **No database schema change** — all three tables have existed since the initial migration.

**Bidirectional junction listing ([ADR-0075](../adr/0075-junction-table-registry-completeness.md) Amendment 1, 2026-09-15):** no new FR — this likewise completes FR-ADMIN-7, following the same precedent as ADR-0075's own paragraph above, and is an in-place `### Amendment` rather than a new ADR because Decision §3 did not reject this change on its merits: it explicitly parked it and named "widening all six later remains open" as the condition. Confirmed live before any code changed, `GET /entities/test-cases/schema` carried no `test_suite` or `test_plan` relation at all and `GET /entities/defects/schema` returned `"relations": []` — `TestCase` is the entity three separate junctions point at and its detail page could show none of them, while `Defect`'s page rendered no tab strip whatsoever, the exact symptom ADR-0075 was written to fix for `TestSuite` surviving in four other places. **All six** n-n junctions now carry a branching 2-tuple `scope_field` naming both of their FK columns — `requirement_test_case_link` `("requirement_id","test_case_id")`, `requirement_test_condition_link` `("requirement_id","test_condition_id")`, `test_condition_test_case_link` `("test_condition_id","test_case_id")`, `test_case_defect_link` `("test_case_id","defect_id")`, `test_suite_test_case` `("test_suite_id","test_case_id")`, `test_plan_test_suite` `("test_plan_id","test_suite_id")` — with the pre-amendment arm declared **first** in each pair, so `scope_validation_error` still keys its `422` on the same field name and every item route's tenant walk stays byte-identical. `derive_entity_relations` is **unchanged, not one line**: `_scope_candidates` already exploded a tuple, the same mechanism that has always made `RiskItem` a child of both `Requirement` and `TestPlan`, so a genuine capability widening across six entities cost zero changes to the derivation, the schema route, the MCP `describe` tool or the frontend. The one real risk — and the only new code — is that a widened `scope_field` needs a **branching resolver**: `_resolve_scope_for_write` hands `resolve_org_id` a `types.SimpleNamespace` carrying only the arm the caller supplied, so a config left with its single-arm walk would type-check, derive a good relation, render a tab, and 404 every request that tab fires; new `crud_factory.branching_resolver(branches)` generalizes the shape `resolve_risk_item_org_id` has always hand-written, each arm reusing the resolver that junction's own bespoke route already uses for that side so the two surfaces cannot drift (NFR-77). **Result:** `TestCase` gains three tabs at once (Requirements / Test conditions / Test suites, all `(linked)`, six total), `TestSuite` gains "Test plans (linked)", `TestCondition` gains "Requirements (linked)", and `Defect` gains a tab strip where it had none — **30 relationships across 10 entities**, was 22 across 9. ADR-0074 §4's exclusion table loses its entire link-table block: **8** enumerated exclusions remain, was 14, all of them genuine list-capability gaps of a different kind (filter-field-only FKs, and `RoleAssignment`'s missing `list` route). **No new permission codes and no migration** — permissions are per-resource, not per-direction, and all six junctions already hold their `.read` code. **Small, accepted API contract change:** an unscoped list on these six now returns `"exactly one of X or Y must be set"` instead of `"<X> is required."` (same `422`, same `validation_error` code, same keyed field name, and no client in this repo matches on the message text), and a request supplying **both** arms is newly reachable and rejected with `"...not both"` — `RiskItem`'s XOR narrowing, now applying here. **Found, not fixed:** two of the new `scope_selector` arms point at ref entities the shared `ScopeSelector` molecule cannot search today (`test-condition`, whose own list is scoped by `requirement_id`, and `defect`, scoped by `test_execution_id`) — a limitation `frontend/src/components/molecules/scope-selector/scope-selector.tsx` already documents by name for exactly these two, pre-existing rather than introduced here, and affecting only the generic admin list page's scope-gate picker, never the relationship tabs (which pass the parent id directly and render no picker).

**Write actions on the relationship tabs ([ADR-0076](../adr/0076-relationship-tab-write-actions.md), 2026-09-15):** FR-ADMIN-8 is new, and it is the first part of this surface that is not read-only. ADR-0074/0072 and Amendment 1 between them produced **30 relationship tabs across 10 entities, every one of them read-only** — and for four of [ADR-0005](../adr/0005-traceability-link-dedicated-join-tables.md)'s own traceability tables that was a real capability gap rather than a cosmetic one, because the tab is the only place in the app where the relationship is visible at all. A `RequirementTestCaseLink` row could only ever be written as a *side effect* of creating a brand-new `TestCase` through REQ-2's `POST /requirements/{id}/test-cases`; `RequirementTestConditionLink` and `TestConditionTestCaseLink` likewise through REQ-3's authoring routes; `TestCaseDefectLink` only while *raising* a new defect through EXEC-3's `POST /executions/{id}/defects`. Linking a record that already exists — "this failure is the defect we already have", "this existing test case covers that requirement" — had **no route anywhere**, so the traceability matrix the four tables exist to support could be grown by authoring new rows but never *assembled* from existing ones, which is what a requirements-traceability workflow actually looks like once a project is past its first week. The one-to-many tabs had the mirror-image gap with a much smaller cause: the child's generic `create` route already existed and was already used by `EntityListPage`; what the tab lacked was the affordance plus a way to fix the parent id. **Two facts no derivation can produce** stand between a generic tab and a create affordance — *which route writes a link row* (every link table is `list`/`get` only through the factory, and its rows come from a bespoke route whose URL shape is arbitrary) and *which permission that route gates on* (REQ-4's and PLAN-1's routes gate on the **parent's** `test_suite.update`/`test_plan.update`, not on anything named after the junction). Both are now **declared by the route itself**, in the module that defines it: a new optional `CrudEntityConfig.link_create` served as an eleventh, additive `linkCreate` key on `GET /entities/{resource}/schema` (`null` for the 23 non-link entities), riding the schema request the tab already makes. The obvious shortcut — a hand-authored frontend map from link entity to route — is exactly the per-entity map ADR-0074 Decision §1 exists to forbid, and would sit on the far side of the network boundary from the routes it describes, free to drift silently. **API change:** four new bespoke `POST` routes in `trace.py`, each the byte-identical boundary sequence [ADR-0030](../adr/0030-req4-test-suite-membership-bespoke-routes.md) fixed (`404` for an unresolvable parent or a far row in another org — never `403`, never `422`, per NFR-1; `403` for a missing permission; `422` for a same-org but cross-**project** far row; `409` on the pair's own unique constraint), plus the additive schema key. The generic surface is unchanged — `methods` stays `{"list","get"}` and `create_schema` stays `None`, so a link row still cannot be `PATCH`ed, `DELETE`d or factory-created; links remain immutable (ADR-0005). **RBAC change:** four new `.create` codes in a new `LINK_CREATE_RESOURCES` grouping (catalog **102 → 106**), granted to `org_admin` by definition, to `test_manager` together with the three link `.read` codes it lacked (granting the write alone would ship a button on a tab whose own list request `403`s before it renders), and to `tester` for `test_case_defect_link.create` **only** — the three requirement-level links are `test_manager`'s activity, and widening them would be a scope expansion no acceptance criterion asks for. Backfilled by migration `3e6b08c5da71`, whose `downgrade()` is deliberately asymmetric: it removes the four new codes and every grant of them, but for the three pre-existing `.read` codes it revokes only `test_manager`'s grants and never the catalog rows, which predate it and other roles hold. **No database schema change** — no new table, no new column, no new constraint. **Deliberately out of scope: unlinking.** Two of the six junctions have a `DELETE` half already and four have none; what removing a traceability link means for an already-exported RTM is a real decision belonging to its own story, so the tabs grow monotonically today.

**Both n-n actions, and a compound create-then-link ([ADR-0076](../adr/0076-relationship-tab-write-actions.md) **Amendment 1**, 2026-09-15):** no new FR — this corrects FR-ADMIN-8 in place (see the strikethrough on its own row) and adds **NFR-79**; it is an in-place `### Amendment` rather than a new ADR because it changes neither the `link_create` contract, nor any route, nor any permission code, nor the schema key — only which buttons the tab renders and one client-side sequence. ADR-0076's "one action per tab, never both" turned out to be right about *kind* and wrong about *count*: an n-n tab could only link a record that **already existed**, so the overwhelmingly common authoring case — "this requirement needs a test case, and that test case does not exist yet" — still meant leaving the record, finding the far entity's own list page, creating the row, navigating back, and only then linking. Found by a live click-through rather than by any failing test, the same class of post-hoc reversal [ADR-0063](../adr/0063-mcp-integration-screen.md)'s and [ADR-0048](../adr/0048-brand-identity-and-logo-system.md)'s own amendments record. **Every n-n tab now renders both** "Link existing &lt;far entity&gt;" and "Create new &lt;far entity&gt;", always both when permitted rather than conditioned on whether any linkable rows exist (which would hide the action exactly when it is least discoverable, and make the strip depend on a request the user has not made). 1-n tabs are **unchanged** — re-parenting an existing child to a different parent moves a row out from under whatever else references it, a different and riskier operation explicitly out of scope. "Create new" is **one** user-visible step: a single modal holding the **far** entity's own `EntityForm` — its schema, never the link entity's, whose two FK columns are the whole row and one of which is the record being viewed — whose submit runs the far entity's generic `create` and then the **same** declared `linkCreate` route "Link existing" already calls, with the id the create returned. The far entity's own scope field is prefilled and locked from the same derivation that scopes the picker (a scope field is a query param on `list` and a body field on `create`, so one rule serves both), left editable where no scope can be derived rather than locked to a guess. **No API change at all** — no new route, no new permission code, no new schema key, no migration; the sequence is exactly the two requests a user could already make by hand. **The two calls are not one transaction**, deliberately: making them atomic needs a new backend route combining two separately-gated operations, which is a larger decision than the residual risk warrants, so NFR-79 handles it from both ends instead — a fail-closed **both-permissions** gate up front (an actor holding only the far-create code sees **neither** button, which is worth stating because the intuitive expectation is that it sees "Create new" alone), and, if the link half fails anyway, a closed form plus a persistent error naming the created row's label **and** id, the API's own reason, and the recovery. **Found and fixed in the same change:** `Card.Body` silently dropped every `data-testid` — TypeScript does not excess-property-check a hyphenated JSX attribute, so the `entity-relation-actions` testid the UI Design Document §6.2 documents had never rendered; the atom now declares and forwards it. **Found, not fixed:** `EntityForm` sends `null` for every blank optional field, which a *defaulted-and-non-nullable* Pydantic field (`TestCase.status`) rejects with a `422` — pre-existing and reachable today from `EntityListPage`'s own create modal, so the real fix (omit a blank optional rather than sending `null`) belongs to its own story rather than a drive-by here.

**MCP-6 — one tool per entity per action ([ADR-0068](../adr/0068-mcp-6-per-entity-mcp-tools.md), 2026-09-13):** FR-MCP-5 delivered every capability, advertised through six reflective tools each taking a `resource: str` argument. FR-MCP-6 changes only the *advertisement*: the same registry, the same executors, the same REST route handlers, now surfaced as **146 individually-named tools** (`tn_organization_get`, `tn_project_create`, `tn_requirement_list`, `tn_test_case_update`, ...), generated at import time from `TOOL_REGISTRY` rather than hand-listed. Three consequences matter at the requirements level: (a) the entity is the tool's *identity*, so there is no `resource` string for a client to get wrong; (b) each tool's input schema carries only its own action's parameters; and (c) FR-MCP-5's "never more than REST grants" restriction is now enforced by **omission from `tools/list`** rather than by a `405` when called — an unsupported pair cannot be called because it was never offered (see NFR-68). Also retires FR-MCP-1's own two hand-wired tools by folding them into the scheme as `tn_test_case_create` (which gains REQ-3's rigor-path branch the hand-wired tool never had) and `tn_test_case_list`; one capability now has exactly one name.
